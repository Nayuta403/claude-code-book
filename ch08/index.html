用户看到什么¶

启动 claude，第一次模型看到的工具清单不到 20 个——BashTool、FileReadTool、FileEditTool 这些天天用的在里面，但像 mcp__slack__send_message、mcp__github__list_pulls 这些 MCP 工具、或者 NotebookEditTool、EnterWorktreeTool 这些低频工具，都不在初始清单里。模型知道它们存在（有一个 <system-reminder> 列出名字），但想真正调用得先 ToolSearch 一下。

接进 5 个 MCP server、总共 100+ 个工具之后，system prompt 的 tool definitions 段依然只长了一点点（多的是 ToolSearchTool 的一段说明 + deferred 工具的名字列表）。官方文档给的数字是传统 77K token 的工具定义缩到 8.7K（来源：https://www.anthropic.com/engineering/advanced-tool-use，访问于 2026-04-19）。

这章要讲两件事：

  1. 这 100+ 个异质工具（内置 / MCP / plugin / skill）是怎么沿着同一个 Tool 接口统一起来的；
  2. ToolSearch 这种"用一个工具发现其它工具"的懒加载模式在 Claude Code 里的具体实现——打分、回注、边界。

为什么挑这个设计出来讲¶

"大量可选工具 + 一个发现工具" 这个模式正在变成 agent 框架的标配做法。Claude Code 是这套模式的工业级落地样本之一——自己实现了一套 client-side 打分，没有依赖 Anthropic 服务端的 tool_search_tool_regex_20251119 / tool_search_tool_bm25_20251119 两个变体（这两个变体的官方说明见 https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool，访问于 2026-04-19）。代码量不大（ToolSearchTool.ts 约 470 行），但把 cache 稳定性、模型兼容性、第三方代理、MCP 动态连接 in-flight 几个角度都兜住了。读者读完能把这套搬到自己的 agent 栈上。

本章的外部引用只用三处 Anthropic 第一方来源（engineering 博客、platform.claude.com 的 tool-search-tool docs、claude-code 官方 GitHub issue）。关于 liteLLM、pydantic-ai 等第三方框架是否也用了类似两级暴露模式，留给读者自行对比——本章不把它们写进论据链。

关键流程 1：四个来源如何汇聚成一个 Tools 数组¶

Claude Code 的工具来自四处：内置 / MCP / plugin / skill。skill 和 plugin 走 SkillTool / 插件载入器封装成 Tool，本章不展开（ch.10 / ch.11）。值得一提的是 skill 作为一种 prompt 层的 deferred 机制和本章的 ToolSearch 是对称的：skill 在 system prompt 里只登记名字 + 触发描述，真正的 skill 正文 body 要在模型调 Skill 工具时按需加载进对话——两条路子、同一个"延迟暴露"思路。skill 侧的完整机制见 ch.10。

关键流程 2：ToolSearch 懒加载¶

这部分是本章重点。按 "为什么 → 哪些工具 defer → 怎么搜 → 怎么回注 → 边界" 讲。

为什么 defer¶

Anthropic 官方 tool search 文档给的经验数据（https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool，访问于 2026-04-19）：

A typical multi-server setup (GitHub, Slack, Sentry, Grafana, Splunk) can consume ~55k tokens in definitions before Claude does any actual work. Claude's ability to correctly pick the right tool degrades significantly once you exceed 30–50 available tools.

两个问题：token 成本和选错率。Claude Code 的自动阈值 @ src/utils/toolSearch.ts:44-49 设在 10% context window——超过就自动开启 defer：

选错率的数据侧注：Claude Code 没有跑独立的本地 evals 去证明 "客户端打分能把选错率压到和 server-side BM25 同一水平"——30–50 工具的拐点数字完全是援引官方 docs 的通用实验。线上侧，代码里埋了 tengu_tool_search_outcome（ToolSearchTool.ts:346-355）和 tengu_tool_search_mode_decision（toolSearch.ts:401-416）两个事件，收集召回数和 mode 决策分布——但这批数据在 Anthropic 内部，仓库里找不到公开结果。本章对选错率的论证到"引用 + 监控到位"为止，不做定量声明。

还有一条独立考虑：prompt cache 稳定性。MCP 工具是每用户动态发现的（每个用户连的 server 不一样），把它们塞进 system prompt 前缀会让跨用户 cache 共享失效。defer 让 MCP 工具不进 prompt 前缀，discovery 时作为 tool_reference 块追加在会话里——前缀不动，cache 保住（官方文档明说这点："Deferred tools are not included in the system-prompt prefix... The prefix is untouched, so prompt caching is preserved"）。

哪些工具会 defer¶

决策函数 isDeferredTool() @ src/tools/ToolSearchTool/prompt.ts:62-108 一个纯函数把 5 条规则编织起来：

几条规则的用意：

  • 规则 1 / 2：MCP 默认全部 defer，alwaysLoad 做个例外出口。MCP server 通过 _meta['anthropic/alwaysLoad'] 表达"我这个工具真的 turn 1 就要"。
  • 规则 3：ToolSearch 自己永不 defer——模型要能看到它才能发现别人。
  • 规则 4–5：AgentTool、BriefTool、SendUserFileTool 在特定 feature flag 下硬写死不 defer。共同点是它们的 prompt 里包含模型必须 turn 1 看到的契约文本——比如 Brief 的 text-visibility contract。如果 defer 了就要先 ToolSearch 一次才能读到契约，显然不行。
  • 规则 6：其它工具只要标了 shouldDefer: true 就 defer。

仓库里哪些工具主动 opt-in shouldDefer？Grep 查到 27 个（完整列表见 book/research/ch08/code-notes.md）。都是workflow 型或低频：

  • 模式切换类：EnterPlanMode、ExitPlanModeV2、EnterWorktree、ExitWorktree
  • Task v2：TaskCreate / Get / Update / List
  • 外部集成：WebFetch、WebSearch、LSPTool
  • 通信：SendMessage、AskUserQuestion、NotebookEdit
  • 时间轴：Cron 族、RemoteTrigger

Bash / FileRead / FileEdit / FileWrite 这些高频工具故意不 defer——符合官方建议的"Keep 3-5 most frequently used tools as non-deferred"。

怎么回注：tool_reference 块¶

ToolSearch 返回的不是 schema，是引用：

Anthropic API 拿到 tool_reference 块会自动展开成完整 tool schema 并追加进当前会话上下文——system prompt 前缀不动，cache 保住（官方文档第 "How deferral works internally" 一节：https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool，访问于 2026-04-19）。展开是 server-side 行为，客户端看不到。

下一轮请求前，Claude Code 还要扫历史找出"已经发现"的工具名：

extractDiscoveredToolNames() @ src/utils/toolSearch.ts:545-592 返回的 Set 决定了下一轮哪些 MCP 工具要直接加载（willDefer(t) = useToolSearch && !discovered.has(t.name) 语义），哪些仍然 defer。发现集合单调增长，discovered 一次就稳住。

compaction 边界问题：compact 会吃掉中间消息，tool_reference 一并消失。代码里 compact_boundary 系统消息携带 compactMetadata.preCompactDiscoveredTools——compaction 前把发现集合快照塞进去，下次 extractDiscoveredToolNames 再读回来（src/utils/toolSearch.ts:550-561）。没有这个兜底，每次 compact 之后模型都得重新 ToolSearch 一遍。

描述缓存¶

ToolSearch 每次打分要读每个候选的 description（await tool.prompt({...})）。这不便宜——prompt 函数可能读文件、跑 feature flag 查询。所以缓存：

失效策略 @ src/tools/ToolSearchTool/ToolSearchTool.ts:55-100：把当前 deferred 工具名排序 join 作为集合 key，每次搜索前比一下，变了就 cache.clear()。粒度粗——任何一个 MCP server 重连都打破全部描述 cache——但实现简单、正确性容易论证。

边界¶

几个具体限制：

  • 模型支持：Haiku 不支持 tool_reference block，ToolSearch 自动关（src/utils/toolSearch.ts:239-252 的 modelSupportsToolReference）。反向测试——名字匹配 DEFAULT_UNSUPPORTED_MODEL_PATTERNS = ['haiku'] 才判定不支持，其它模型默认支持。新模型不用改码。
  • 第三方代理：ANTHROPIC_BASE_URL 指向非 Anthropic 主机时默认关（src/utils/toolSearch.ts:299-311）。理由写在注释里："tool_reference is a beta content type that third-party API gateways typically don't support"。liteLLM 等部分代理能转，所以"非第一方 + ENABLE_TOOL_SEARCH 未设"才关——用户显式设了就信任。
  • Kill switch：CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS 一开，任何 beta 字段都剥（src/utils/toolSearch.ts:181-183 和 src/utils/api.ts:243-259），tool search 强制 standard mode。
  • MCP server 连接中：ToolSearch 搜不到结果时，如果还有 MCP server 在 pending 状态，会把 pending server 名字塞进返回结果里，让模型等一下再搜（src/tools/ToolSearchTool/ToolSearchTool.ts:334-339、:451-454）。
  • Bedrock / Vertex：client-side tool_reference 展开可能不支持。代码注释留了 warning（src/tools/ToolSearchTool/ToolSearchTool.ts:440-443），issue tracker 里也有反馈：https://github.com/anthropics/claude-code/issues/25212（访问于 2026-04-19）。

设计取舍¶

为什么 Tool 接口这么大¶

7 组职责在一个接口，不是按职责分层（像"ExecutableTool + RenderableTool + ClassifiableTool"）。好处：一个 tool 文件读完就知道这个工具的全部行为；工具作者不用跨 3 个文件查 interface。代价：MCP 工具得在 wrap 时填很多默认方法（src/services/mcp/client.ts 那一大段），以及 Tool 类型本身是一个超长的 type。

如果换成多接口组合，好处是每个接口职责纯；代价是每加一个工具都要写多个 class 或用 satisfies A & B & C，发生漏实现时是编译期 error 但报错位置不直观。buildTool + TOOL_DEFAULTS 是"单接口 + 默认值" 这条路线的折衷：保留单接口可读性，用默认值替代部分类型体操。

为什么 ToolSearch 用关键词打分而不是 server-side 或 embedding¶

三种备选：

方案成本准确度依赖
Anthropic server-side tool_search_tool_regex/bm25要模型学 regex 或自然语言查询官方提供依赖 API beta + 变体选择
客户端 embedding预热 + 索引 + 一次向量比较高依赖 embedding 模型或本地库
客户端关键词 + 权重打分（Claude Code 选这个）本地毫秒级中，靠 searchHint 质量无

Claude Code 选第三种的动机从代码上看是自主可控 + 零依赖。打分权重、select: 语法、+required 前缀、fast path（name 精确 / mcp__ 前缀 / full-pool fallback）都可以随需求调整，不用等服务端 API 变体。代价是 searchHint 写不好时召回差——这就是为什么代码里每个 shouldDefer: true 的工具都手写了 hint。

为什么 MCP 默认全部 defer¶

三层考虑叠加：

  1. Workflow-specific：每用户连不同 MCP server，github__* 可能一个人有一个人没有，不 defer 就意味着 system prompt 因人而异。
  2. Prompt cache：内置工具段要保持 "cross-user 共享的 contiguous prefix"（src/tools.ts:356-361 注释）。MCP 工具一进前缀就破坏共享 cache。
  3. Token 成本：一个 Notion / GitHub / Slack 的 MCP server 轻松 20–30 个工具，55K token 的量级。

alwaysLoad 是反向出口：某个 MCP 工具 workflow 特别重要，server 侧能通过 _meta['anthropic/alwaysLoad'] 让它回到非 defer 路径。

代码层隐藏细节¶

几个读一遍主流程不会注意到、但调试或改造时会被卡住的点。按"最容易踩"到"最容易忽略"排：

1. ToolSearch 的发现集合在 subagent 里不继承¶

主 agent 调 ToolSearch 发现一个 MCP 工具之后，这次 discovery 只存在于主 agent 的 message 历史里——tool_reference 块在 user 消息的 tool_result 里。spawn 一个 subagent 时，subagent 拿到的是 AgentTool 组装出来的新 message 序列（src/tools/AgentTool/runAgent.ts 附近），不是父会话的原始历史。也就是说：

  • subagent 要用同一个 MCP 工具，得自己再 ToolSearch 一次。
  • 主 agent 的 discovered Set 不会穿透给 subagent。

这不是 bug——subagent 的 context 本来就是刻意新建的（token 预算、角色隔离）。但会出现一种"我在主线程里用 Slack 发过消息，subagent 说它找不到 slack__send_message"的奇怪错觉。对症解法：subagent prompt 里提前写上 select:mcp__slack__send_message 让它 turn 1 就把 schema 加载进来；或者工具标 alwaysLoad 回到非 defer 路径。代码里 AgentTool 自身不在 subagent 的 ALL_AGENT_DISALLOWED_TOOLS 里（ant 用户 USER_TYPE 才例外允许递归），ToolSearch 也在 ASYNC_AGENT_ALLOWED_TOOLS 白名单里（src/constants/tools.ts:55-71），所以重新发现是随时能做的。

2. isReadOnly / isConcurrencySafe 谁在消费¶

代码里这两个字段的真实消费点只有三处（Grep isConcurrencySafe( 定位到 5 个源文件、3 个实际消费者）：

  • src/services/tools/toolOrchestration.ts:96-114：把同一个 assistant 消息里的多个 tool_use 块按 isConcurrencySafe 分批——连续若干个都 safe 就打成一个 concurrent batch，遇到不 safe 的就单独一 batch。
  • src/services/tools/StreamingToolExecutor.ts:84-148：流式执行时动态决策"能不能并发加塞"，规则是当前执行中所有工具都 concurrency-safe 时才允许再加一个 safe 的工具进去。
  • src/tools/BashTool/BashTool.tsx：isConcurrencySafe(input) = isReadOnly(input)——BashTool 把这两个绑在一起，用 checkReadOnlyConstraints 解析命令。

注意：isReadOnly 除了并发调度还有一个 UI 用法——collapseReadSearch.ts 把连续的 read / search 工具调用折叠成一块（"Read × 5"）。isDestructive 在主代码里目前只有一个消费点：permissions.ts 的 safety classifier。

Plan mode 下工具清单本身不缩——所有写工具仍然在 options.tools 里。plan mode 的实现方式是在 checkPermissions 里把非 isReadOnly 的工具拦在 ask 行为上，让用户在 ExitPlanMode 之前无法执行写操作（src/utils/permissions/permissions.ts 和 permissionSetup.ts 对 mode === 'plan' 的分支多处处理）。所以 ToolSearch 和 plan mode 之间没有相互影响——defer 的集合跟 permission mode 独立计算。

3. merged tools 的覆盖优先级¶

同一个 tool name 出现多次时谁胜出，按出现位置不同，规则不同：

合并阶段先者优先方代码位置
assembleToolPool：内置 vs MCP内置（spread 在前，uniqBy('name') 保留先出现的）src/tools.ts:362-366
mergeAndFilterTools：initialTools vs assembledinitialTools（同上机制）src/utils/toolPool.ts:65-70
MCP 内部：CLAUDE_AGENT_SDK_MCP_NO_PREFIX 下 MCP 用原名 vs 内置同名内置 仍然胜出（因为合并阶段内置 spread 在前）src/services/mcp/client.ts:1773
plugin MCP servers vs 用户 MCP serversplugin 侧通过"plugin-trusted"分类享有更宽松的权限门禁，但名字冲突时仍是先到先得（合并阶段决定）src/tools/AgentTool/runAgent.ts:112-127

一句话记法：先 spread 进去的名字胜出。不是按"plugin > 内置 > MCP > skill"的静态分层——而是按四个来源在合并函数里的 spread 顺序。这解释了一个非直觉现象：initialTools（REPL 启动时从 SDK props 传进来的工具）能覆盖内置 Bash——因为 uniqBy([...initialTools, ...assembled], 'name') 里 initialTools 在前。SDK 用户想替换内置工具实现，就是走这条路。

4. shared/ helper 的读写一致性假设¶

仓库里和工具相关的三个 "全局可变状态"：

  • getToolDescriptionMemoized 的 cache（ToolSearchTool.ts:66）—— 进程级单例，按 toolName 做 key。假设同名工具的 description 在当前 deferred 集合不变时是稳定的。失效策略是"当前 deferred 工具名集合变了就 clear"，粒度粗但正确。
  • getToolSchemaCache()（src/utils/api.ts:119 附近）——按 name 或 name + inputJSONSchema hash 做 key 缓存 toolToAPISchema 输出。假设同名同 schema 的 API 描述在进程生命周期内不变。
  • cachedDeferredToolNames: string | null 作为失效检测的 sentinel。

这些 cache 都是进程级单例，不按 session / agent 分片。意味着：两个并发的 subagent 如果同时访问同一个 tool name 的 memoized description，会共享同一个字符串。这在当前代码里没问题——描述不随 agent 身份变——但如果以后有人把工具描述写成"带 agent 信息的动态 prompt"，这层 cache 就得重写。买这笔简洁性的代价是"工具描述不依赖 ToolUseContext 的 agent 字段"这条隐式约束，文档里没明说，是从 memoize 的 key 推出来的。

5. toolMatchesName 的 aliases 双查¶

findToolByName / toolMatchesName 在 src/Tool.ts:348-360 查工具时会同时比 tool.name 和 tool.aliases[]——但合并阶段的 uniqBy('name') 只去重 name，不理 aliases。这意味着两个工具如果 name 不同但 aliases 重叠，都能进 pool，模型用 alias 调用时 findToolByName 返回的是数组里第一个匹配——分区排序之后就是字母序第一个。这个角落在代码里没显式处理，实际仓库里 aliases 重复的概率很低（每个工具 0-1 个 alias），所以不是问题；但如果有人给 MCP 工具加上 "和内置工具同名的 alias"，合并函数不会拦，findToolByName 返回谁取决于排序。写自己的 tool registry 时注意这条。

可迁移的点¶

这一章写完读者能拿走的四个点：

  1. Tool 接口里装变化率元数据。isReadOnly、isConcurrencySafe、isDestructive 不是给权限用，是给并发调度 + UI 折叠 + 安全分类器共用的。放进接口而不是外部 registry 的好处是作者写工具时就得面对这几个决策，不会漏。
  2. 两级工具暴露：一个 Search + 一堆 deferred。只要接口协议支持 tool_reference 块，这个模式不局限于 Anthropic。没有 server-side 支持时，客户端也可以自己基于"哪些工具这一轮要 defer"的集合为每个 tool schema 打上 defer_loading: true——Claude Code 的 willDefer(t) = useToolSearch && (deferredToolNames.has(t.name) || shouldDeferLspTool(t)) @ src/services/api/claude.ts:1208-1209 就是这个语义：deferredToolNames 是本轮判定为 defer 的集合（isDeferredTool 跑出来的），LSP 工具因为 server 初始化没完成也单独延后一次。真正决定"哪些 defer 工具在这一轮不再 defer"的是上游的 filteredTools 过滤 @ src/services/api/claude.ts:1160-1167——discoveredToolNames 进去就不再走 defer 路径。两件事分开看：willDefer 打标签，filter 决定是否发送。
  3. 决策规则写成单个纯函数。isDeferredTool() 把 5 条规则叠进一个 return 链，测试点明确。如果散在各个工具的 shouldDefer / alwaysLoad / isMcp 自己判断，跨版本迭代时规则变化一次改 N 处。
  4. cache key 用"当前 deferred 工具名排序 join"。粗粒度但正确——MCP 连接变动时一律失效。cache 的正确性比命中率好证明。
