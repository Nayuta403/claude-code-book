20.1 用户看到什么¶

Claude Code 的输入框表面上是一个普通的终端 prompt，但它背后有三套平行的"输入翻译层"：

  • 按 Ctrl+T 显示 todo，按 Ctrl+O 切换 transcript —— 走的是键位系统。在 ~/.claude/keybindings.json 改一行就能换键。
  • /vim 打开后，按 Esc 进入 NORMAL 模式，dw 删一个词，i 回到 INSERT —— 走的是 vim 状态机，完全在 text buffer 层内部。
  • /voice 打开后，按住 Space 说话，一小段波形在 footer 亮起，松开后文字插到光标处 —— 走的是 voice 通路：音频采集 → voice_stream WebSocket STT → 写回输入框。

这三件事挨着讲，是因为它们都在"物理输入（按键、音波）到应用接收一个语义动作"之间做翻译。要讲透的不是每件的全貌，而是它们共享什么（事件总线）、各自取什么舍什么（vim 故意不走键位系统，voice 故意借用键位系统），以及有什么可以搬走的抽象。

20.2 为什么挑这个设计出来讲¶

一句话：把"键盘"从组件里抽出来，抽成一张带作用域的动作表。

多数终端应用把 useInput 散在组件里 —— Ink 的官方例子也是。键位系统的做法正相反：业务组件不监听按键，只声明 useKeybinding('app:toggleTodos', handler)；键位本身（ctrl+t）由一个 JSON 文件或默认表决定，用户可改。键位表跟组件树并存，模态打开 → 推一个 context 上堆栈 → 相关 binding 优先。模态关闭 → 自动回退。

这个抽象跑通后，用户自定义键位几乎零成本，vim 可以选择性接入，voice 甚至可以"读键位表当配置源"自己写 hold 检测 —— 三种截然不同的输入需求共用一张表。本章把这三层拆开讲，每层讲到够用的深度，然后在 20.6 合流。

  • chord 的第二键 match：此时 ChordInterceptor 的 wasInChord 为 true，直接从 registry 调 handler。这是因为 useKeybinding 的 resolve 不共享 pending 状态，依赖它们协作完成 chord 会丢事件。
  • unbound（用户显式 null）：ChordInterceptor 吃掉事件，不让后面任何 useKeybinding 或 useTextInput 看到 —— "解绑"不是"没有 handler"，是"明确无效"。
  • chord_started：吃掉事件，避免单键匹配把第一步当普通字符输入写进 text buffer。

这套双层设计的代价是两次 resolve，收益是 pending 状态集中管理、unbound 能可靠吃键、chord 的第二键不会丢。

20.4 Vim 模式¶

20.4.1 为什么不嵌入真 vim¶

目标不是编辑文件，是编辑一行到多行的 prompt。字符集是 string，光标是一个 offset（useTextInput 暴露的接口，详见 ch.21 §21.8）。真 vim 的 buffer 模型、寄存器、ex 命令、插件生态在这里都是负担。Claude Code 选择实现一个 motion 子集 + operator 子集 + text object 子集，总计约 65 个可组合 token，不到 200 行状态转移代码。

Grep 证实：只有 INSERT 和 NORMAL，没有 Visual 模式。visualMode|Visual 在 src/vim/ 下零命中。Visual 模式在单行 prompt 场景里代价高收益低（选区 UI、shift+方向键已经能覆盖多数选择需求），砍掉是合理取舍。

20.4.5 与 useTextInput 的边界¶

useVimInput 是 useTextInput（Ink UI 的基座 TextInput hook，详见 ch.21 §21.8）的一层包裹：

关键路由在 handleVimInput（useVimInput.ts:175-295）：

最有信息量的是一条注释：

NOTE(keybindings): This escape handler is intentionally NOT migrated to the keybindings system. It's vim's standard INSERT->NORMAL mode switch - a vim-specific behavior that should not be configurable via keybindings. Vim users expect Esc to always exit INSERT mode.

—— src/hooks/useVimInput.ts:189-192

这是自觉的设计边界。Vim 的 Esc 不是一个"app-level 动作"，是 vim 的核心语义之一。放进键位系统 = 允许用户改掉它 = 破坏 vim。

相应地，Ctrl+... 组合全部透传给 textInput（顶层的 ChordInterceptor/useKeybinding 会抢），方向键在 idle 也透传（给 history 导航）。"归 vim 管的只有 vim 语义"，其它的都放走。

这里有一个容易踩到的语义冲突：NORMAL 模式下按 Ctrl+W 不是真 vim 的"删上一个词"，而是键位系统里绑的 action（默认 chat:clearLine 或类似）。vim 用户肌肉记忆里 Ctrl+W = 删词，这里按下去会直接清行。代码注释没提这条冲突，文档也没列 —— 这是"选择性透传"的代价。

启用路径很直：/vim 命令切 config.editorMode（src/commands/vim/vim.ts:17-22），src/components/PromptInput/utils.ts:12-15 的 isVimModeEnabled() 读 config，src/components/VimTextInput.tsx 条件渲染 useVimInput 而非 useTextInput。

隐藏细节（src/hooks/useVimInput.ts:34 / src/hooks/useVoice.ts:180+）：sub-agent（Task 工具调用的子会话）里 vim mode 和 voice 都不生效。useVimInput 和 useVoice 都挂在 PromptInput 子树里，sub-agent 是 headless run，不渲染 PromptInput —— 根本没有这两个 hook 的挂载点。直觉上会以为"vim 模式是全局 config 所以处处都生效"，实际 vim 是"文本输入层的模式"，没有文本输入层就没这回事（详见 ch.04 §4.6 的 sub-agent 上下文隔离）。

20.5.2 采集层：native + fallback¶

src/services/voice.ts:20-36 的核心是 lazy 加载原生模块：

audio-capture-napi 是 native 模块（macOS CoreAudio/AudioUnit，Linux/Windows 用 cpal）。dlopen 同步、~1s 热启动，最差 ~8s 冷启动。不能在应用启动时 preload（会卡住）；第一次 voice 键按下才加载，代价转嫁给第一次用 voice 的用户。

几个工程决策值得一说：

  • 为什么去 api.anthropic.com 而不是 claude.ai：voiceStreamSTT.ts:123-131 注释，claude.ai 的 Cloudflare zone 对非浏览器客户端做 TLS 指纹挑战（JA3），CLI 过不去。api.anthropic.com 同一个 private-api pod、同一个 OAuth，只是 CF zone 不拦。
  • OAuth 门槛：API key / Bedrock / Vertex / Foundry 用户的 tokens 都不通过 getClaudeAIOAuthTokens()，因此 voice 对它们不可用。官方文档[^4]说得更直白。
  • OS 级麦克风权限：voice 采集第一次调用会触发平台 TCC/PulseAudio 权限请求，这属于系统层授权，与 ch.09 讲的工具权限模型是正交的两套。拒授之后的 degrade 细节见 20.5.8 的 hidden detail。

另外，ASR 热词也值得一提：src/services/voiceKeyterms.ts 把当前项目名、git 分支名等作为 keyterms 送给 Deepgram（官方文档："Transcription is tuned for coding vocabulary..." 这句背后就是这张热词表），让"CamelCase 函数名 / git 分支名"不会被识成普通英文词。

[^4]: https://code.claude.com/docs/en/voice-dictation，访问于 2026-04-19。文档明确说"Audio is not processed locally."

坑都在时序上。用户按 Space 的一瞬间，还没收到第二次 auto-repeat，怎么知道是 tap 还是 hold？两条策略（useVoiceIntegration.tsx:36-54）：

  • bare char（默认 Space）：需要 HOLD_THRESHOLD = 5 次快速按键才激活。单次 tap 正常打一个空格。前 WARMUP_THRESHOLD = 2 次流入 input 让用户知道"在等"。
  • 修饰键组合（如 meta+k）：首键就激活。修饰键组合不可能被当正常输入，直接当 hold。

这两档策略在配置里就能选：用户把 voice:pushToTalk 绑到 meta+k 就没有 warmup。

20.5.8 几条容易被忽视的降级路径¶

隐藏细节（src/services/voice.ts + src/hooks/useVoice.ts:524-536）：原生采集失败 → Linux 上静默 fallback 到 arecord / rec；macOS/Windows 上则直接报"voice 不可用"。voice.ts 的 probeArecord（:75-100）和 rec spawn 只在 Linux 分支里；其它平台原生模块不可用就到此为止。用户看到的只是 "voice disabled"，不知道 fallback 链条只覆盖一个平台。

隐藏细节（src/hooks/useVoiceIntegration.tsx:323 + src/hooks/useVoice.ts:572-630）：useVoice 写了完整的 focus-driven 录音路径（终端获焦自动开录、失焦停录），但 useVoiceIntegration 调它时把 focusMode 常量传 false。这段代码完整但在 PromptInput 路径下未启用，属于典型的"代码里能看到、产品里摸不到"的功能切片。对照 ch.15 §15.4 讲的 Proactive terminalFocus —— 那边的 focus 检测是上了产品的，这边的 focus 触发录音是藏着的同型号机制。

隐藏细节（src/hooks/useVoice.ts:370-454，内部 issue anthropic#287008）：CE 后端偶尔会 session-sticky 到一个"接音但返空"的 pod，前端在 finalizeSource === 'no_data_timeout' + 确认有音频信号 + WebSocket 确实连上过时，用 fullAudioRef 缓存的整段音频在新 WebSocket 上重放一次。用户感知只是"按住说话偶尔要停顿一下才出文字"，代码层是明确的一次性重试。属于"前端掩盖后端间歇故障"的被动补偿。

OS 权限被拒后的体感：macOS 上首次 voice 按下会弹 TCC 对话框，用户拒绝后 audio-capture-napi 的后续 start 会在 init 阶段抛出；useVoice 把错误捕获并设 voiceState 为 idle + error，footer 上显示一个短提示，其他输入路径照常工作。不会把 voice 键当正常按键透传 —— 因为 voiceKeystroke 只要绑定存在就吃掉按键。这是"绑定存在但功能拒用"的边界情况，修法是用户回到系统设置给权限或 /voice 关掉功能。

20.6 三者怎么共存¶

20.6.1 事件分发的三层¶

一个按键事件从 Ink 出来，大致穿过三层：

  1. ChordInterceptor（KeybindingProviderSetup.tsx）：最先 subscribe 的 useInput，处理 chord pending 和 unbound 吞噬。
  2. 业务组件的 useKeybinding / useKeybindings：各自订阅 useInput，resolve 后调自己的 handler。
  3. useTextInput 或 useVimInput：最后看到没被 stopImmediatePropagation 的事件，处理文本输入。

stopImmediatePropagation 是各层彼此隔离的唯一机制。unbound 在第 1 层就吃掉；chord_started 在第 1 层吃掉；单键 match 在第 2 层由对应 useKeybinding 调 handler 并吃掉；没匹配任何 binding 的普通字符流到第 3 层。

20.6.2 Vim 和键位的边界¶

vim 开启时，useVimInput 替代了 useTextInput，坐在第 3 层。它主动把自己不关心的事件透传给 textInput（等价于放行到键位系统，因为 textInput 自己也只处理未被吞的事件）：

  • Ctrl+... 全部透传 → ctrl+t、ctrl+o 等键位照常工作
  • Esc：INSERT 下 vim 自己吞（切 NORMAL），NORMAL 下取消 pending command 也自己吞 —— 这是一条硬边界，不可配置
  • Enter：透传 → 键位系统里 chat:submit 接管（也可以在 NORMAL 下提交）
  • 方向键在 NORMAL idle 透传 → 让 textInput 做 history 导航
  • 其他 NORMAL 事件 → vim 状态机消化

官方文档[^2]在 "Vim mode interaction" 一节里把这个边界描述得很清楚："Vim mode handles input at the text input level; keybindings handle actions at the component level. The Escape key in vim mode switches INSERT to NORMAL mode; it does not trigger chat:cancel. Most Ctrl+key shortcuts pass through vim mode to the keybinding system."

20.6.3 Voice 和其他层的关系¶

voice 激活在 Chat context，vim 也跑在 Chat context。它们不直接冲突：

  • voice 只劫持 voice:pushToTalk 绑的那个具体键，通过读 bindings 知道是哪个
  • 其他键 voice 不动，由键位系统和 vim 各管各的
  • transcript 通过 insertTextRef.current.setInputWithCursor() 写 text buffer —— 和正常打字同一条管道，vim 的 insertedText 追踪也能收到这个变化（严格讲 setInputWithCursor 直接写 state，vim 的 insertedText 累积机制拿不到，但那是 dot-repeat 的已知简化，20.4.4 讲过）

还有两条与相邻章节共用的资源要记一下：

  • Buddy 的共享 tick 与 companionReservedColumns：footer 里 voice 的波形条、chord 提示、Buddy sprite 都挤在同一条右侧预留列（见 ch.19 §19.4 和 ch.21 §21.9）。三方共享的是 Ink 的 measureElement 帧调度 —— voice 在录音期间会 requestAnimationFrame 级别重绘波形，节奏上与 Buddy 的 sprite tick 互让，由 ch.19 的 Buddy soul 统一调度。
  • Proactive 的 terminalFocus：ch.15 §15.4 讲到的 terminal focus/blur 事件是复用的同一源（Ink 的 stdin.setRawMode + CSI 焦点序列）。voice 的 focus-mode 未启用并不影响 Proactive 对焦点的利用。

20.7 值得借鉴的一点¶

本章讲了三件事，其实只有一个核心设计值得单拎出来：

把"键盘"看成一个带作用域的动作表，而不是散落在组件里的 useInput。

这个设计在三个维度产生了复利：

1. 用户自定义的成本几乎为零。

action 是 string 枚举，binding 只是一张 key → action 的映射。用户改 JSON 文件不需要碰任何组件代码。新加一个 action 时，组件作者写 useKeybinding('namespace:action', handler, { context })，默认 binding 写一行 defaultBindings.ts，schema 加一行枚举 —— 三处。相比"去每个组件里加一个 prop 传入一个 key override"，这是 O(1) vs O(N)。

2. 作用域堆栈替代 useInput 的顺序依赖。

Ink 的 useInput 默认按 subscribe 顺序响应 —— "先挂的先看到"。模态窗口想抢 Escape 怎么办？靠它比其他 useInput 先 mount？这在重 render 下非常脆弱。

作用域堆栈把"谁优先"从"注册顺序"换成"生命周期中的 active contexts 集合"。模态打开 → 往堆栈推 Select → 解析时 Select 优先于 Global；模态关闭 → 自动 pop → 恢复。组件不需要知道其他组件的存在，不需要考虑渲染顺序。

一个意料之外的好处：unbound 成为一等公民。用户写 "space": null 明确表达"这个键我不想要它做任何事"，不同于"没绑过"。ChordInterceptor 看到 unbound 会 stopImmediatePropagation，阻止所有后续 useInput 看到 —— 这在"注册顺序决定响应"的模型里几乎不可能干净实现。

3. Voice 和 Vim 以截然相反的方式接入同一套系统。

  • Voice 借用键位系统作为配置源：读 voice:pushToTalk 的 binding 值，自己处理 hold 语义。键位系统不做分发，只回答"这个 action 目前绑到什么键"。
  • Vim 主动绕过键位系统：Esc 切模式、hjkl 移动光标都属于"text input 层的事"，放进键位系统就破坏 vim 语义。vim 的边界是源码注释里明说的（useVimInput.ts:189-192）。

两种用法都不是系统的 bug；它们验证了"键位系统是一个配置层+分发层，两层可以只用其一"。这种解耦让它能长期承载不同性质的输入需求。

想搬走这三个价值，最小实现大致是：

  1. 一个 { key, action, context } → handler 的 Map
  2. 一个 React Context 暴露 resolve(key, activeContexts) 和 registerActiveContext(ctx)
  3. 组件生命周期 push/pop activeContexts
  4. 一个根 effect（或 useInput）在 resolve 命中时调对应 handler 并停止事件传播

chord 支持、热重载、校验都是可选的加花。核心的"作用域动作表"在 300 行之内就能跑起来。
