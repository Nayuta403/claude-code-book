开章须知：两个"hook"¶

本书里 "hook" 有两层含义，读本章前先分开：

  • 本章讲的：用户在 settings.json 里配的 shell hook。Claude Code 在跑到特定生命周期节点时 spawn 一个子进程，把事件信息通过 stdin 的 JSON 交给用户脚本，再根据脚本的 exit code + stdout JSON 决定下一步。PreToolUse / PostToolUse / UserPromptSubmit / Stop / SessionStart / Notification 等 27 个事件都在此列。
  • 不讲的：src/hooks/use*.ts(x) 里的 React hook，终端 UI 层用的（useTextInput、useNotifyAfterTimeout、useCostSummary 等）。那部分属于 ch.21。

提到二者有交叉的地方会写 "React hook" 明示。无修饰的 "hook" 一律是 shell hook。

1. 用户看到什么¶

典型配置（~/.claude/settings.json）：

字段分三层：事件名 → {matcher, hooks[]} 数组 → 单个 handler 配置。上面这份 config 的语义是："模型要调 Bash 且命令以 rm 开头之前，先跑 block-rm.sh；模型改动过文件后跑 run-lint.sh"。

脚本里能做的事跟权限面板差不多：放行、阻断、改参数、注入上下文。但跟权限面板不一样的是：这是用户自己的 shell 代码，可以跑任何本地工具——接 git、接 CI API、接组织内部的合规系统。

2. 为什么挑这个设计出来讲¶

很多 agent 工具都提供事件回调，但 Claude Code 的版本有两个非平凡的选择值得拆：

  • JSON-over-stdio + exit code 的双通道协议。简单场景写一行 exit 2 就够阻塞；复杂场景返回 stdout JSON 控制得很细——permissionDecision: 'allow' / 'deny' / 'ask'、updatedInput（改 tool 参数）、additionalContext（注入 system-reminder）、continue: false（让 Agent Loop 停）。协议面大但读者不用一次吃完。
  • 把权限决策权下放给 hook，但不是绝对。PreToolUse hook 返回 allow 能跳过权限面板，但仍要过 checkRuleBasedPermissions——deny 规则能反否决 hook 的 allow。hook 的 deny 才是绝对 deny。这个"不对称"是 IT 部署的护栏：用户可以写 hook 放松权限，不能写 hook 绕过 managed 层的禁令。

3. 关键数据结构¶

3.1 事件枚举¶

27 个事件。官方 hooks 文档（https://code.claude.com/docs/en/hooks，访问于 2026-04-19）的表格列了 26 个，少一个 Setup——源码有实现（src/utils/hooks.ts:3902 的 executeSetupHooks），matcher 字段是 trigger: 'init' | 'maintenance'，对应 repo 初始化 / 维护场景。这里记一笔差异。

按作用分组看：

  • tool 生命周期：PreToolUse / PostToolUse / PostToolUseFailure / PermissionRequest / PermissionDenied
  • 一轮对话：UserPromptSubmit / Stop / StopFailure
  • session：SessionStart / SessionEnd / Setup
  • subagent：SubagentStart / SubagentStop
  • 上下文管理：PreCompact / PostCompact / InstructionsLoaded
  • teammate / task：TeammateIdle / TaskCreated / TaskCompleted（ant-only 的多人协作特性）
  • MCP：Elicitation / ElicitationResult
  • 环境变化：ConfigChange / CwdChanged / FileChanged / WorktreeCreate / WorktreeRemove
  • 通知：Notification

matcher 字段不同事件看不同的输入字段（src/utils/hooks.ts:1616-1669）——tool 类事件 match tool_name，SessionStart match source（startup/resume/clear/compact），Notification match notification_type，Elicitation match mcp_server_name，诸如此类。UserPromptSubmit / Stop / TeammateIdle 这几个没有 matcher，一配就全跑。

3.2 四种 handler¶

四种类型：

type触发成本场景
command一次 spawn90% 场景：跑个 shell 脚本
prompt一次 LLM 调用（默认 haiku）"让 LLM 判断一下这个 tool call 该不该过"
agent一次 subagent + 工具使用"让 subagent 去 grep / 读文件验证一下"
http一次 HTTP POST把决策托管给一个外部 service

prompt 和 agent 是 Claude Code 特有的——传统 hook 系统没这两种。它们把"让 LLM 自己审自己"做成了声明式配置。成本换 UX 的取舍很清晰：写一个 shell 脚本判断"这条 rm 是不是 dangerous" 很烦，写一句 prompt "Check if this rm is safe" 很省事。

所有 handler 共享的公共字段：

if 字段很有意思——它用 ch.09 的权限规则语法（Bash(git *)、Read(*.ts)）做预过滤。效果是"matcher 命中了，但 if 不匹配就不 spawn"。设计目的是避免给 "给 Bash 配了 hook 但 99% 的 Bash 调用跟 hook 无关" 的用户白白付 spawn 开销。

隐藏细节（src/services/tools/toolHooks.ts:372-391）：PreToolUse hook 是先跑、再进权限判定的——ch.09 讲的 checkRuleBasedPermissions 跑在 hook 之后。这条顺序决定了 hook allow 会被 deny 规则反否决，但 hook deny 是绝对 deny。设计意图、对 IT 部署的影响详见 §6.2。

4. 关键流程：一次 hook 调用的生命周期¶

用 PreToolUse 做主线，其它事件差异用脚注带过。

4.1 入口¶

tool 要执行之前，toolExecution 调 runPreToolUseHooks：

runPreToolUseHooks（src/services/tools/toolHooks.ts:435）转手交给 executePreToolHooks → executeHooks。入参集中在一个 struct 里：

createBaseHookInput（src/utils/hooks.ts:301-328）填公共字段：session_id / transcript_path / cwd / permission_mode / agent_id / agent_type。每个 hook 都能拿到这些。

4.2 匹配 + 去重¶

matcher 支持三种语法（官方文档）：

  • "*" / "" / 省略 → 全匹配
  • 只含 [a-zA-Z0-9_|] → 精确字符串或 | 分隔列表（"Edit|Write"）
  • 其它字符 → JavaScript regex（"mcp__.*"）

过完 matcher 再过 if（hooks.ts:1811-1848）。if 条件需要有 tool_name 和 tool_input 才能评估，所以非 tool 事件的 if 会被直接 drop（hooks.ts:1835-1840）。

去重按 handler 类型分别做（hooks.ts:1735-1806）：

  • command：key = shell + command + if 三元组
  • prompt / agent：key = prompt + if
  • http：key = url + if
  • callback / function：不去重

注意去重 key 比官方文档（"by command string"）更细：同一个 command 配了不同的 shell 或不同的 if，会被视为两个 hook。这是合理的——shell: 'powershell' 和 shell: 'bash' 的语义不一样。

4.3 信任门¶

所有 hook 在交互模式下必须等 trust dialog 通过才跑。这条源码注释写明了历史漏洞："SessionEnd hook 曾在用户拒绝 trust 时跑了 / SubagentStop hook 曾在早于 trust 时跑了"。集中在一个 gate 比每个事件各自判要稳。

4.4 并行 spawn¶

要点：

  • 每个 hook 独立 abort signal，父 signal（用户按 Ctrl-C）与 hook 自己的 timeout 合并
  • TOOL_HOOK_EXECUTION_TIMEOUT_MS = 10 * 60 * 1000（hooks.ts:166）是兜底，对应官方文档 command 类的"600 秒"。官方文档给 prompt / agent 类 handler 各自有更短的默认（30 秒 / 60 秒），如果你把 prompt hook 写得很重会先踩它们的默认
  • SessionEnd 专用 1.5 秒超时（SESSION_END_HOOK_TIMEOUT_MS_DEFAULT，hooks.ts:175）——shutdown 路径不能被 hook 吊住

隐藏细节（src/utils/hooks.ts:169-182）：SessionEnd 的 1.5 秒超时可以用 CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS 调。默认值跟其它事件的 10 分钟差了两个数量级——shutdown 钩子写得慢一点（IO 落盘、远程上报）就会被静默 kill，控制台看不到。

  • 纯 callback 走 fast path，直接顺序 await 不开 generator、不起 span（注释说微基准快 70%，hooks.ts:2036-2067）

Windows 下的 bash hook 走 Git Bash，所以所有路径都要从 C:\Users\foo 转成 /c/Users/foo（hooks.ts:808-811 的 windowsPathToPosixPath）。PowerShell 不转，保留原生路径。两条路径共享的 POSIX 化是 memoize 的纯函数（LRU-500），多次调用很便宜。

Stdin 一次性写入：

末尾 \n 不是美化——注释说 bash while read -r line 会卡在 EOF 判断，没换行读不到（源码引 gh-30509）。这是很实在的 shell 交互细节。

环境变量（hooks.ts:882-926）：

  • CLAUDE_PROJECT_DIR → 项目根（不是 cwd；进了 worktree 也不变）
  • CLAUDE_PLUGIN_ROOT / CLAUDE_PLUGIN_DATA → plugin hook 专用（plugin 怎么贡献 hook 见 ch.11）
  • CLAUDE_ENV_FILE → SessionStart / Setup / CwdChanged / FileChanged 事件专享，是一个 .sh 路径；hook 往里写 export FOO=bar，后续 Bash tool 会 source 这个文件。这是跨 hook / 跨 tool 持久化 env 的官方机制。

隐藏细节（src/utils/hooks.ts:917-926）：CLAUDE_ENV_FILE 只对上面列的 4 个事件生效。PreToolUse / UserPromptSubmit / Stop 之类事件的 hook 即使检测到 CLAUDE_ENV_FILE 并往里写 export，代码也不会加载那个文件——executeHooks 只在这 4 个事件后 source，其它事件的写入会被默默丢掉，不报错也不告警。误用时常见症状："我的 PreToolUse hook 改了 env 怎么没生效？"

隐藏细节（src/utils/subprocessEnv.ts:15-53）：subprocessEnv() 会在 CLAUDE_CODE_SUBPROCESS_ENV_SCRUB 开启时（GitHub Actions / claude-code-action 默认开）剥掉 ANTHROPIC_API_KEY / AWS_SECRET_ACCESS_KEY / ACTIONS_ID_TOKEN_REQUEST_TOKEN 等一组 secret。本地测试 hook 能拿到这些 env，放到 GHA 跑就拿不到——典型"产品层看不到但必踩"的陷阱，尤其是写上报脚本时容易以为 hook 进程继承了父 env。

隐藏细节（src/utils/hooks.ts:928-938）：spawn 子进程前会对 cwd 做探活——如果 getCwd() 返回的 worktree 已被删（AsyncLocalStorage 里的状态还没跟上 ExitWorktree），会自动回退到 getOriginalCwd()。不这样做 spawn 会直接 ENOENT 失败。这条回退在 /exit-worktree 之后紧跟一个 hook 触发事件时才会走到，隐藏度高。

4.6 Async hook 的握手¶

这个设计值得单独拎出来。Claude Code 支持把 hook "放到后台跑"，stdin/stdout 契约如下：

  1. hook 正常接 stdin JSON
  2. hook 在 stdout 的第一行输出 {"async": true}（或 {"async": true, "asyncTimeout": 30000}）
  3. 主进程看到这一行就 detach 子进程，立刻 resolve 父路径，不阻塞

注释特别提醒：只能 parse 第一行。如果 hook 很快写了多行，拼起来 parse 会失败，async hook 就退化成同步阻塞。这是 streaming 解析里容易踩的坑，写在代码里给维护者看。

隐藏细节（src/utils/hooks.ts:1112-1151）：async 握手要求第一次 data event 就必须是完整 JSON——不是"第一行里有 async: true 就行"。如果 hook 脚本分两次写 printf '{"async":'; sleep 0.01; printf 'true}\n'，第一波数据没包含 }，firstLineOf(stdout).includes('}') 返回 false，这次 data event 直接被跳过；等下一批到来时又带着前一批 stdout 累积，JSON parse 失败，async hook 退化成同步。单行 echo '{"async":true}' 是安全的。

进阶版 asyncRewake: true：后台跑 + 退出码 2 时 唤醒模型。实现是往 enqueuePendingNotification 扔一条 task-notification，由 proactive 机制在空闲时注入成下一轮的 system-reminder（详见 ch.15）。用场景是长检查脚本——跑着不阻塞，跑完发现问题再唤醒 Claude 修。

4.7 输出解析¶

stdout 以 { 开头的走 JSON 通道，其余当 plain text。plain text 对大多数事件是"展示给用户，不给模型"；PreToolUse / UserPromptSubmit / SessionStart 等事件的 plain text 会作为 additionalContext 注入给模型（具体由各事件 handler 决定）。

exit code 的三档语义：

退出码语义
0成功，stdout JSON 生效，放行
2阻塞错误，stderr 给模型看，事件被 block（PreToolUse 拦 tool / Stop 要求再跑一轮 / UserPromptSubmit 擦掉 prompt 等）
其它非阻塞错误，stderr 给用户看，放行

WorktreeCreate 例外：任何非零都阻塞（因为 worktree 没创建成功）。

6. 与权限系统的交界：谁说了算¶

这一节是最需要读者看清的地方——ch.09 讲了权限判定管线，本章讲 hook 怎么插进去。

6.1 执行顺序¶

PreToolUse hook 先跑完，再把 hook 的判定（如果有）喂给 resolveHookPermissionDecision。hook 在权限判定之前。

6.2 非对称的决策权¶

读这段代码能看出来三条规则：

  1. hook allow ≠ 绝对 allow：settings 里的 deny 规则 / ask 规则仍然起作用。只有在规则都没命中时，hook 的 allow 才跳过权限面板。
  2. hook deny = 绝对 deny：直接终止流程，规则不再评估。
  3. hook ask：走正常 canUseTool 链路，但 hook 的 message 当作 dialog 标题显示。

设计取舍：用户可以用 hook 放松权限，不能用 hook 绕过 managed 的 deny。IT 部署 managed 层写了 Bash(curl *) deny，用户写 PreToolUse hook 强行 allow 也无效。这是护栏。

7. Stop hook：Agent Loop 的 pivot¶

为什么 src/query/stopHooks.ts 单独抽一个文件——不是因为 Stop hook 特别复杂，而是因为它站在了 Agent Loop 的战略点上。

8. 配置合并：5 个来源¶

8.1 SOURCES 顺序¶

后面的覆盖前面的。官方文档（https://code.claude.com/docs/en/settings，访问于 2026-04-19）描述的优先级：managed（policy） > CLI flag > local > project > user。

但 hooks 字段特殊——不是覆盖，是合并 + 去重：

数组走 mergeArrays（concat + dedup），标量走 lodash mergeWith 覆盖。hooks 字段在 schema 里是 Partial<Record<HookEvent, HookMatcher[]>>——事件名是标量 key，matcher 数组会被 concat。

结果：user 层和 project 层给同一个 PreToolUse 配了不同 matcher，两边都跑，不是 project 盖 user。

8.2 Kill switch¶

四个开关，层层递进：

  1. policy 层 disableAllHooks: true → 所有 hook 全关，managed 也关
  2. policy 层 allowManagedHooksOnly: true → 只剩 managed
  3. isRestrictedToPluginOnly('hooks') → 只剩 plugin hook（plugin hook 来源见 ch.11）
  4. 非 policy 层 disableAllHooks: true → 保留 managed hook（用户关不掉 managed 的 deny 政策）

管理员的安全护栏：用户能关自己的 hook，但关不掉 IT 部署的 hook。

注意第 4 条的副作用：非 policy 层写 disableAllHooks: true 会让 shouldAllowManagedHooksOnly() 返回 true（hooksConfigSnapshot.ts:62-76），下游 analytics / telemetry 里这次会话的 allowManagedHooksOnly 字段也变 true。你在用户 settings 里关 hook，回头看管理面板数据，这个会话会被分到"仅 managed"桶里。

8.3 快照：防 ABA¶

启动时拍一次快照，/hooks UI 改了才 updateHooksConfigSnapshot() 重拍。原因：如果 hook 执行到一半用户在外部编辑器把 settings.json 改掉，下一次 getMatchingHooks 拿到的是新配置——同一次 PreToolUse 的前后 hook 看到不同的 config 是诡异的。快照锁死"一次会话内的 hook 集合"。

9. 内置事件源 vs 用户配置 hook¶

这里容易混，单独开一节厘清。

9.1 src/hooks/notifs/ 是 React hook 不是 Notification 消费者¶

src/hooks/notifs/ 下全是 use*.ts(x) React hook，import useEffect、useNotifications——管的是终端 UI 里的通知条（"update available" / "MCP disconnected" 等）。这些不消费 Notification shell hook 事件，是 UI 状态机的一部分。属于 ch.21。

9.2 src/costHook.ts 是 React hook¶

就一个 useCostSummary，process.on('exit', ...) 里打印成本。名字里的 "Hook" 指 React hook。跟本章主题无关，属于 ch.22。

10. 设计取舍¶

按"这样做的成本 vs 收益"列，不是夸。

  • JSON-over-stdio + exit code 双通道。成本：协议面大，syncHookResponseSchema 里有十几个事件各自的 hookSpecificOutput 形态，写完整 hook 要查文档。收益：简单场景 exit 2 一行搞定，复杂场景 JSON 给够粒度；跟 git hooks 的"只有 exit code"相比能表达更多。
  • 并行执行所有匹配 hook。成本：一个慢 hook 会拖慢整批；用户写了两个重复检查要手动去重（现在是按 identity 自动去）。收益：多个独立检查脚本不用手工编排顺序。
  • hook allow 不能覆盖 managed deny。成本：hook 的表达力打了折扣，用户可能困惑"我明明 return allow 了怎么还是被拦"。收益：IT 安全政策不会被用户本地配置绕过。
  • Stop hook 单独抽 stopHooks.ts。成本：多一个文件，调用路径多一跳。收益：Agent Loop 一轮结束的副作用（prompt suggestion、memory 提取、auto dream、jobs classifier）全挂这个 pivot，避免散落。
  • CLAUDE_ENV_FILE 持久化 env。成本：hook 脚本要 opt-in 判断 CLAUDE_ENV_FILE 是否存在，文档里不写就不会用。收益：SessionStart hook 可以 "export AWS_PROFILE=dev"，后续所有 Bash tool 都生效，不用用户重复配。
  • Async hook 的握手（第一行 {"async": true}）。成本：必须解析 stdout 的第一行，快速写多行的 hook 会退化成同步。收益：不用加配置字段就能声明 async，协议自描述。
  • 配置快照（captureHooksConfigSnapshot）。成本：/hooks UI 改配置要额外调 update 重拍。收益：防运行中 settings.json 被外部编辑器改掉导致同一轮前后看到不同 hook。
  • 信任门集中判。成本：每个 hook 入口都得调 shouldSkipHookDueToTrust。收益：注释里列的两个漏洞（SessionEnd / SubagentStop 早于 trust 跑）都堵在一个点，防回归。

11. 可迁移的点¶

读者可以带走：

  1. 用 stdin/stdout JSON + exit code 做"用户可编程事件回调"。比写 SDK 插件简单得多——用户只要能写 shell 脚本就能接。很多工具可以这么做而没做：lint runner 加一个 pre-lint hook、包管理器加一个 pre-install hook。
  2. 两段式协议：先 exit code 粗粒度、stdout JSON 细粒度。让"简单场景简单"——用户 90% 时间只需要 exit 2，剩下 10% 复杂场景才学 JSON schema。
  3. async 握手用第一行 JSON：不加配置字段、自描述、可以在脚本里动态决定同步还是异步。比"配置里写 async: true" 更灵活。
  4. 按 identity 去重 + 并行执行：多个来源（user/project/local/plugin）合并后可能有重复，用 {type, command, shell, if} 这种三元组做 key 比单纯按 command 字符串更鲁棒。
  5. 配置快照防 ABA：一次操作开始前拍一次配置快照，后续读快照不读文件。避免外部编辑器中途改配置导致同一次操作前后行为不一致。
  6. 信任 / 安全 gate 集中到入口一处：比在每个事件 handler 里各自判一次更抗回归。源码注释里列历史漏洞也是个好习惯——维护者知道为什么要这样防。
  7. pivot 式副作用收集：把"一轮结束"这种天然事件点做成一个函数，所有 "一轮结束要做但不在主路径上" 的任务都挂这里。比在 Agent Loop 各个分支里零散调用更容易维护。
