屏幕上看到的 "tool_use → tool_result → assistant → tool_use → ..." 这条流水线，就是本章要拆开讲的东西。它在 Anthropic 官方文档里是 5 行伪码；在 Claude Code 里是一个 1729 行的 async generator（src/query.ts）加上 1295 行的包装类（src/QueryEngine.ts），共同处理"5 行伪码没告诉你"的那些问题：流式工具执行、模型 fallback、上下文超限、输出被截断、stop hook 反复拦截、用户提前打断、read-only 工具并发、权限请求等待。

2. 为什么挑这个讲¶

官方文档 How tool use works 页面（来源：https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works，访问于 2026-04-19）把 client-tool agent loop 描述成：

  1. Send a request with your tools array and the user message.
  2. Claude responds with stop_reason: "tool_use" and one or more tool_use blocks.
  3. Execute each tool. Format the outputs as tool_result blocks.
  4. Send a new request containing the original messages, the assistant's response, and a user message with the tool_result blocks.
  5. Repeat from step 2 while stop_reason is "tool_use".

Claude Code 的主循环确实是 while + stop_reason 的结构，但它额外处理了 9 类事件：

事件循环内的表现
模型流中途拒绝，需要换 fallback 模型内层重试循环，丢弃已 yield 的 partial assistant
上下文超过模型窗口autoCompact / microcompact / snip / contextCollapse 四段式裁剪
输出被 max_output_tokens 截断先升 cap 再多轮 "resume directly" 指令
用户在工具执行中按 Ctrl+C给每个未配对的 tool_use 合成 is_error=true 的 tool_result
Bash 工具失败，连锁工具应该取消siblingAbortController 单独为 Bash 设置的死亡链
Stop hook 拦截 end_turn以 user 消息追加 hook 的错误后重新进入循环
用户指定 +500k token 预算90% 阈值前自动 continue，diminishing returns 时提前停
Sub-agent 嵌套的 depth/chainId 追踪queryTracking 字段每次迭代 depth++
权限被拒绝（详见 ch.09）合成 "User rejected" 的 tool_result，循环照常继续

这里没有单独"优美"的点，值得借鉴的是如何把这些横切关注点拼成一条可读的主干。本章要讲清：循环的每次迭代做什么、状态在哪里、出口有几个、每个错误恢复路径插在哪、取舍是什么。

3. 两层入口：QueryEngine 与 query()¶

Claude Code 把"一条 agent 会话"拆成两层：

  • 外层 QueryEngine（src/QueryEngine.ts:184）—— session 级对象，每 conversation 一个。持有跨 turn 不变的东西：mutableMessages、readFileState、abortController、totalUsage、permissionDenials、discoveredSkillNames。
  • 内层 query()（src/query.ts:219）—— 纯 async generator。只管"消息进、消息出"，不接 UI 状态、不管 session 存储。

这个分层的意义体现在 query() 的 reusability：它既被 QueryEngine.submitMessage 调用（主线程），也被 sub-agent 调用（src/services/tools/toolExecution.ts 的 AgentTool 起一个子 query，详见 ch.04），也被 compact 子任务调用（querySource='compact'，详见 ch.07）。分层因此不是可有可无。

QueryEngine 的职责¶

注释原话（src/QueryEngine.ts:175-183）明确了语义：

One QueryEngine per conversation. Each submitMessage() call starts a new turn within the same conversation. State (messages, file cache, usage, etc.) persists across turns.

submitMessage(prompt)（src/QueryEngine.ts:209-1156）是一条 prompt 从进入到 result 消息的全流程。它做三件事：

  1. 预处理（src/QueryEngine.ts:273-551）：构造 system prompt（fetchSystemPromptParts）、处理斜杠命令（slash command，processUserInput）、持久化 user 消息到 transcript、发 system_init 消息。
  2. 消费 query() generator（src/QueryEngine.ts:675-1049）：for-await 模型侧的消息流，按类型 switch（assistant / user / progress / attachment / stream_event / system / tool_use_summary），记录到 mutableMessages，并 normalize 成 SDK 格式 yield 给外部。
  3. 终止处理（src/QueryEngine.ts:842-1155）：内循环完成后检查 error_max_turns / error_max_budget_usd / error_max_structured_output_retries；异常路径走 error_during_execution；正常路径 yield result:success。

submitMessage 里有一段值得单拎出来，就是把错误预算拆成三个独立上限：

三者分别对应 "轮数上限"、"美元预算上限"、"结构化输出重试上限"。它们都走同一条 result 通道（带 is_error=true），但是 subtype 不同，让 SDK consumer 能分类处理。取舍：这三个 check 本可以塞进 query() 里，放在 QueryEngine 里的原因是 query() 不该知道"美元"或"JSON schema 重试"这种应用层概念。query() 只负责把消息往外 yield，QueryEngine 在外面决定何时喊停。

ask() 一次性包装¶

src/QueryEngine.ts:1186-1295 的 ask() 是无状态包装：给一条 prompt、构造 QueryEngine、走 submitMessage、出结果后把 readFileCache 写回。非交互式 / SDK 一次性调用用这条路径（Agent SDK 如何把 ask() 组合成面向外部消费者的 API 详见 ch.23）。

query() 的 wrapper¶

这层薄 wrapper 做一件事：正常返回时通知"这些 queued 命令完成了"。异常或 .return()（提前结束 generator）时跳过这一步。注释（src/query.ts:231-234）明确这是故意的 asymmetric signal：调用方能从"有 started 但无 completed"推断出 turn 失败。

真正的主循环是 queryLoop（src/query.ts:241-1728）。

4. 核心数据结构¶

QueryParams¶

这 13 个字段里有两个值得注意：

  • deps?: QueryDeps —— 依赖注入口子。默认 production 实现在 src/query/deps.ts:33-40，覆盖了 callModel / microcompact / autocompact / uuid。注释（src/query/deps.ts:7-20）交代了动机："Passing a deps override into QueryParams lets tests inject fakes directly instead of spyOn-per-module — the most common mocks (callModel, autocompact) are each spied in 6-8 test files today with module-import-and-spy boilerplate."
  • taskBudget?: { total: number } —— 注意这不是用户侧 +500k 预算。注释（src/query.ts:192-197）明确："API task_budget (output_config.task_budget, beta task-budgets-2026-03-13). Distinct from the tokenBudget +500k auto-continue feature. total is the budget for the whole agentic turn; remaining is computed per iteration from cumulative API usage."

State¶

10 个字段，每个都对应一条恢复路径或计数。最后一个 transition 字段的注释（src/query.ts:214-216）点明了一个常被忽略的测试技巧：

Why the previous iteration continued. Undefined on first iteration. Lets tests assert recovery paths fired without inspecting message contents.

把"怎么进到当前迭代的"写进 state，测试不用 parse messages 就能判断路径是否走过。这是可以直接抄的做法。

隐藏细节（src/query.ts:216, 1092）：state.transition 字段只被内部逻辑读过一次（1092 行 collapse_drain_retry 的防重入判断），既不进 logEvent，也不写进任何 yield 出去的消息。意味着从 telemetry 或外部 SDK 消费侧完全看不到"循环因为什么重试了"——要排查得靠进程内调试或 reactive compact / max_output_tokens 自己 logEvent 的那几条辅助事件。注释把这个字段定位成"for tests"，生产侧基本是黑盒。

5. 主循环的 8 个阶段¶

queryLoop 的 while(true) 每次迭代分 8 个阶段。不是所有阶段都 yield 消息，也不是所有阶段都会执行（有 feature gate 和早退出）。按执行顺序列：

阶段 1：迭代入口¶

三件事：destructure state（toolUseContext 是唯一会在迭代内被重赋值的，其他都是只读）、起动 skill discovery 的异步 prefetch、yield stream_request_start 让 UI 更新状态。

skill prefetch 的设计值得一看（src/query.ts:331-335）：它启动后不 await，而是让整次 API call 的时间（5-30s）掩盖 prefetch 的延迟。真正 await 是在阶段 8 的末尾，当 prefetch 已经 settled 时直接取结果，否则跳过（src/query.ts:1599-1614，pendingMemoryPrefetch.settledAt !== null）。这个 "start → hide under IO → consume when settled" 的模式在本章多处出现（memory prefetch、tool use summary）。

阶段 2：四段式裁剪¶

消息在进入模型之前要裁剪。Claude Code 用四个机制，顺序不能换：

顺序的理由（注释 src/query.ts:428-447 原话）：

Runs BEFORE autocompact so that if collapse gets us under the autocompact threshold, autocompact is a no-op and we keep granular context instead of a single summary.

每个步骤处理的问题不同：

  • applyToolResultBudget 处理"单条 tool_result 太大"（比如 cat 一个 10MB 的文件）
  • snip 处理"老消息过多"
  • microcompact 处理"单个 tool_result 在多轮后已经没意义"（例如最早那次 Read 文件，后面已经被 Edit 改过）
  • contextCollapse 处理"一段历史可以折叠成一句话"

四条流水线都跑完了还不够小才走阶段 3。

压缩的实际机制（分 summary、attachments、hookResults 三部分重建历史）在 ch.06 展开。本章只讲 queryLoop 看到的接口。

阶段 4：硬阻塞¶

只有在 autoCompact 关闭的情况下才会走这条短路，给用户留手动 /compact 的空间（注释 src/query.ts:593）。设计理由：自动压缩是可关的，但关了之后不能让循环无限尝试超大 prompt。

阶段 5：API 调用 + 流式消费¶

这是最长的一段，src/query.ts:650-954。结构：

三个值得讲的细节：

5.1 needsFollowUp 是循环不退出的唯一信号¶

官方伪码是 "while stop_reason == 'tool_use'"。Claude Code 不信任 stop_reason 字段（"it's not always set correctly"），只看 "assistant content 里有没有 tool_use block"。看到一个就置 true，流结束后 false 就退出循环。这个判定比 stop_reason 稳，代价是每条 assistant content 块都要过一次 filter。

5.2 Withhold + recover 模式¶

模式是：可恢复的 API 错误先不往外 yield，但留在 assistantMessages 里。流结束后外层分支检查"最后一条是不是 withheld 错误"，能恢复就继续，不能恢复才把错误发出去。

为什么这样做？注释（src/query.ts:788-798）解释：

Withhold recoverable errors (prompt-too-long, max-output-tokens) until we know whether recovery (collapse drain / reactive compact / truncation retry) can succeed. Still pushed to assistantMessages so the recovery checks below find them. Either subsystem's withhold is sufficient — they're independent so turning one off doesn't break the other's recovery path.

如果早早把错误 yield 出去，SDK consumer（比如 cowork / Claude Desktop）看到 is_error: true 就会提前终止 session。但循环其实还能恢复。所以做了 withhold。

隐藏细节（src/services/api/claude.ts:1874-1884）：流式调用有一个主动的 idle watchdog——如果连续 STREAM_IDLE_TIMEOUT_MS（默认 90_000ms，可由 CLAUDE_STREAM_IDLE_TIMEOUT_MS 覆盖）没收到新 chunk 就 abort 整条流。注释原话："Without this, a silently dropped connection can hang the session indefinitely since the SDK's request timeout only covers the initial fetch(), not the streaming body." 该 watchdog 默认关闭，需设 CLAUDE_ENABLE_STREAM_WATCHDOG 打开。另有一路轻量 stall 检测（同文件 1944-1958 行）即使 watchdog 关着也会记录 tengu_streaming_stall，但不会 abort——它只是被动"下一个 chunk 到了才发现刚才卡过"。此外若整条流结束都没收到 message_start 事件，触发 non-streaming fallback（claude.ts:2350-2364），所以"断流后重连"其实有两条路径：watchdog-abort 后走 fallback 循环；流自然结束但是空 → 直接非流式重试。

5.3 Fallback 的内层循环¶

Fallback 不算新的一轮。它在阶段 5 的内层 while 里处理，turnCount 不增。理由：用户提示没有变化，消息历史没有变化，只换了模型。把它当新轮记会误导 maxTurns 计数。

stripSignatureBlocks 只对 ant 用户生效。原因（注释 src/query.ts:923-926）：thinking block 的签名是模型绑定的，replaying 到非 protected 模型会 400。

阶段 6：Abort 清理¶

两个细节：

  1. yieldMissingToolResultBlocks（src/query.ts:123-149）给每个没配对的 tool_use 合成一个 is_error: true 的 tool_result。不补上的话下次 API 调用会 400（Anthropic API 要求每个 tool_use 必须有对应的 tool_result）。
  2. abort reason 为 'interrupt' 时不发中断消息。注释（src/query.ts:1044-1046）说："用户在工具执行中键入新消息" 这条路径里，后面那条 queued user 消息自带上下文，不需要再 yield interruption。

阶段 7：完成 / 恢复分支¶

!needsFollowUp 是说这一轮没有 tool_use。按理该出循环。但不急着 return —— 有五类情况需要"假装完成，其实要 retry"。

这里是状态机最复杂的地方，下一节专门拆。

阶段 8：工具执行 + 下一轮¶

如果进到阶段 8，说明 needsFollowUp === true，要执行工具。

然后：附件注入（文件变更、memory prefetch、skill discovery）、maxTurns 检查、构造 next State、continue 回循环开头。

附件注入阶段做的三件事（src/query.ts:1538-1614）：

  • 排队的 queued commands 转成 attachment 传给下一轮（cron 触发的定时任务也走这条队列，详见 ch.13）
  • pendingMemoryPrefetch 若已 settled，append 到 toolResults
  • skillPrefetch 若已 settled，append 到 toolResults

所有这些附件都作为 user 消息跟在 tool_results 后面，在下一次 API call 里一起送进去。

6. Tool call 的插入与并发切分¶

本节聚焦 queryLoop 和执行器之间的接口（batch 切分、并发上限、合成 tool_result）。Tool 接口定义本身、内置工具清单、ToolSearch 懒加载机制详见 ch.08。

6.3 并发 batch 的 context modifier 延后应用¶

runToolsConcurrently 里所有 context modifier 先进队列，整批执行完才统一 apply（src/services/tools/toolOrchestration.ts:42-62）：

理由：多个并发工具如果都调 modifier，最后一个胜出，顺序不可预测。延后到 batch 结束统一 apply 保证确定性。代价：并发 batch 里的单个工具不能立即看到其他并发工具的 context 修改 —— 这是刻意的约束。

6.4 StreamingToolExecutor 的状态机¶

每个 TrackedTool 走 queued → executing → completed → yielded 四态。canExecuteTool（src/services/tools/StreamingToolExecutor.ts:129-135）判定能否启动：

规则：要么现在没任何工具在跑，要么现在跑的全是 safe 且新来的也 safe。这和 partitionToolCalls 的切分语义一致，只是动态版。

6.5 Bash 特殊错误链¶

一个值得讲的细节。src/services/tools/StreamingToolExecutor.ts:356-364：

只有 Bash 工具出错才会触发 siblingAbortController.abort()，把同批并发的其他工具都杀掉。其他工具（Read / WebFetch / Grep）出错各自独立，不影响兄弟。

理由注释已说明：Bash 命令之间常有隐式依赖（mkdir foo && cd foo && touch bar.txt 这类），前一条失败后面就无意义。其他工具是独立的。

这个判断不动 parent abortController，所以不会终止整个 turn —— 只取消这一批里的兄弟工具，主循环继续处理它们产出的 "Cancelled: parallel tool call ... errored" 合成 tool_result。

6.6 三种合成 tool_result¶

src/services/tools/StreamingToolExecutor.ts:153-205 的 createSyntheticErrorMessage 按 reason 产出三种 is_error: true 的 tool_result：

  • user_interrupted —— 套 REJECT_MESSAGE，再用 withMemoryCorrectionHint 包一层，减少模型立刻重试同一操作的概率
  • streaming_fallback —— <tool_use_error>Error: Streaming fallback...</tool_use_error>，给下游 fallback 路径一个可识别的信号
  • sibling_error —— Cancelled: parallel tool call {desc} errored（有 erroredToolDescription 时带具体工具名，否则泛化）

三者都让模型在下一轮知道"这个工具没跑成，为什么跑不了"。

这一节讲两套完全不同的"预算"，读者容易混。先把边界划清。

7.1 预算 A：Context window（模型上下文窗口）¶

防止 prompt 超过模型能接受的 token 数。四段式裁剪（阶段 2）+ autoCompact（阶段 3）+ blocking limit（阶段 4）配合处理。阈值在 src/services/compact/autoCompact.ts:62-70：

留 20K tokens 给"万一触发 compact 时 summary 自身的输出空间"。这个保留量基于 p99.99 观测（注释 src/services/compact/autoCompact.ts:29）："Based on p99.99 of compact summary output being 17,387 tokens."

7.2 预算 B：Turn output token budget（用户 +500k 语法）¶

和上面完全不同。这是用户显式在 prompt 里写 +500k 表达"允许这轮花 50 万 output tokens 在反复思考上"的语法。目的：让 agent 在大任务里自动多轮 continue 而不需要用户反复敲回车。

语法解析在 src/utils/tokenBudget.ts:21-29：

决策函数 checkTokenBudget（src/query/tokenBudget.ts:45-93），关键常量 COMPLETION_THRESHOLD = 0.9 / DIMINISHING_THRESHOLD = 500。签名 (tracker, agentId, budget, globalTurnTokens) => { action: 'continue' | 'stop', ... }，三条决策规则：

  1. sub-agent 不吃此预算（agentId 存在）—— sub-agent 的 token 开销归到父 agent 的总预算里，不单独分配（sub-agent 调度的完整语义详见 ch.04）
  2. 未达 90% 且非 diminishing → continue，往 messages 塞一条 meta user 消息："Stopped at {pct}% of token target ({turnTokens} / {budget}). Keep working — do not summarize."（src/utils/tokenBudget.ts:66-73）
  3. Diminishing returns 判定：连续 3 次 continue 后、本次和上次增量都 < 500 tokens → 提前停止

为什么 diminishing 要连 3 次？注释没直接写，但从逻辑看是为了排除"一轮刚好做 1-2 次短 tool_use 就停"这种正常情况。3 次 + 双重小增量才认定是模型在"空转"。

循环里的触发点：

状态在进程级单例里：

sub-agent 不调 snapshotOutputTokensForTurn（src/screens/REPL.tsx:2927），所以读出来的 budget 是 parent 的。配合 checkTokenBudget 的 agentId 守卫，sub-agent 被明确隔离。

隐藏细节（src/screens/REPL.tsx:2167, 2927, 2999 vs src/QueryEngine.ts:1186-1295）：snapshotOutputTokensForTurn 的调用点只出现在 REPL.tsx 里。ask() / 非交互式入口 / Agent SDK（详见 ch.23）那条路径从不 snapshot，所以用户即使在 SDK 输入里写 +500k 也不会触发 continuation——那套预算是 CLI-only 特性。预算 A（context window）才是两条路径都走的。

7.3 两套预算混不得¶

三句话说清边界：

  • 预算 A 的单位是 input token 数（context window size）；预算 B 的单位是 output token 数（turn output）
  • 预算 A 的触发机制是 compact（把历史压成 summary 重新跑）；预算 B 的触发机制是 continuation（往消息末尾塞一条 "keep working" 继续跑）
  • 预算 A 全局生效；预算 B 仅对用户显式用 +500k 语法指定过的 turn 生效，且不含 sub-agent

8. 错误恢复的五条路径¶

都在阶段 7（!needsFollowUp）里。按源码出现顺序列。

8.1 Model fallback（阶段 5 内层，不是阶段 7）¶

严格说这是阶段 5 里的内层循环，不是阶段 7 的路径——代码已在 §5.3 贴过（src/query.ts:893-951），这里只列关键动作：

  • 补全孤儿 tool_use 的 tool_result（防止下次 API 400）
  • 清空本次的 assistantMessages / toolResults / toolUseBlocks
  • discard 旧 executor、建新的（避免 orphan tool_use_id 跨模型）
  • ant 用户 strip thinking 签名（签名是 model-bound 的）
  • 发 warning 告知切换

不走 turnCount++（maxTurns 语义详见 ch.04），不走 transition—— 因为这是同一轮的第二次尝试。

8.2 Prompt-too-long 413¶

两阶段恢复：

  1. Collapse drain（廉价）：把所有已 staged 但未 apply 的 context collapse 一次性 apply，不起新一轮 summary。判断是否有东西可 drain（committed > 0）。防止"刚 drain 过又 drain"用的是检查上一次 transition 是不是 collapse_drain_retry。
  2. Reactive compact（重）：起一个 forked agent 做 summary，完成后用 summary 替换历史。防止"compact 完还 too long → compact → ..."死循环用的是 hasAttemptedReactiveCompact 布尔，一轮只给一次机会。

注释里明确了死循环教训（src/query.ts:1291-1297）：

Preserve the reactive compact guard — if compact already ran and couldn't recover from prompt-too-long, retrying after a stop-hook blocking error will produce the same result. Resetting to false here caused an infinite loop: compact → still too long → error → stop hook blocking → compact → … burning thousands of API calls.

8.3 Max output tokens 截断¶

两级恢复：

级别 1 的条件非常严：必须 capEnabled（Growthbook gate）+ 未被用户覆盖 cap + 没设过 escalate override。满足了就把 override 到 64k 重跑一次同样的请求。

级别 2 是"已经是 64k 还被截断"的情况。这时不是加大 cap（模型本身不能超 64k），而是把截断的 assistant message 保留下来、后面追加一条 meta user 消息告诉模型 "别道歉别回顾，从断点继续；把剩余任务拆小一点"。最多 3 次。

prompt 文案值得注意："Resume directly — no apology, no recap of what you were doing. Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces." 每个字都有用：

  • "no apology" 阻止 "Sorry, let me continue..." 这种浪费 20+ tokens 的开场白
  • "no recap" 阻止模型重复上文，又浪费 token
  • "Pick up mid-thought" 暗示可以直接续写，不必另起一段
  • "Break remaining work into smaller pieces" 给下一次截断风险上个保险

8.4 Stop hook blocking¶

handleStopHooks（src/query/stopHooks.ts:65-473）在 end_turn 之前跑用户配置的 stop hook。返回 { blockingErrors, preventContinuation }：

  • preventContinuation: true → 直接终止（return stop_hook_prevented）
  • blockingErrors.length > 0 → 追加为 user 消息、置 stopHookActive = true 后重新进循环，让模型回应 hook 的错误
  • 都没有 → 继续后面的 token budget 检查，最后 return completed

stopHookActive 下次传入 handleStopHooks（src/query/stopHooks.ts:73, 184），hook 执行器知道"这是重试"，可选择不再拦截。

8.5 Streaming abort 补洞¶

不在阶段 7，散落在阶段 6（流中断）和阶段 8（工具执行中中断）。核心是保证每个已发出的 tool_use 都有配对的 tool_result，不然下次 API 400。yieldMissingToolResultBlocks（src/query.ts:123-149）遍历 assistantMessages 里的每个 tool_use block，按同样的 id 合成一条 is_error: true 的 tool_result 并带上 sourceToolAssistantUUID（用于 UI 关联）。Streaming 模式下 StreamingToolExecutor 在 getRemainingResults 里自行补洞，传统模式才用这个 helper。

9. transitions.ts —— 空 shim 的含义¶

这一节要讲清楚一个现象：

只有 3 行，而 src/query.ts:104 写：

Terminal 和 Continue 在 transitions.ts 里没有 export。import type 在编译后被 elide，所以运行时没影响，但 TypeScript 层面是有问题的 —— 实际上由 tsconfig 的 skipLibCheck 或 isolated modules 放行。

本章对此的解读：这是 source-map 还原期的 shim（参考 style-guide "还原仓库的处理"一节）。原始实现里这个文件应该有：

  • Terminal 类型 union（可能就是本章列的 12 种 reason 的字面量联合）
  • Continue 类型 union（7 种）
  • 一个真正在做事的 transitionQueryState 函数，可能是 (state, event, config) => State | Terminal 的 reducer

为什么这很重要：如果 transitions.ts 里有真实 reducer，那么 queryLoop 的业务逻辑就能和"状态转换"分离。单测能写成 expect(reduce(state, event)).toEqual({ transition: { reason: 'max_output_tokens_recovery', attempt: 1 } })，不需要 mock callModel / microcompact / stopHooks。

当前形态下：19 个 transition reason 散落在 return/continue 处，和 IO（yield 消息、调用模型）紧耦合。写单测必须搭一整套 fake（callModel fake / microcompact fake / autocompact fake / tool executor fake），看 deps.ts 的依赖注入设计（本章 4.1 小节）就能感觉到这种压力 —— 4 个最常 mock 的依赖被显式拎出来做注入点，正是为了缓解这一点。

可迁移的借鉴：如果你自己写 agent loop，把 state transition 做成 pure function 是值得的。测试成本一降，调试日志一条 transition line 就能复现问题。Claude Code 当前内联形态是可运行但难测试的一种折衷。

open-questions.md #1 里标记了"建议后续版本恢复 transitions.ts 原貌"。

10. 设计取舍¶

汇总本章提到的几个设计决定，按"取舍清晰度"排。

10.1 Generator-everywhere¶

从 query() 到 runTools() 到 runToolUse() 到 StreamingToolExecutor.getRemainingResults() 全是 async function*。

收益：

  • UI 能把每条 message 随拿随渲染，不等整轮结束
  • 工具的 progress 能实时流（例如 Bash 工具边跑边 yield 输出）
  • 传递取消信号靠共享 AbortController，层层监听 signal

成本：

  • 状态跨 yield 边界是 local 的，不能像 reducer 那样提取出来
  • Async stack trace 难读，打 log 时要自己带 queryChainId + queryDepth
  • 取消不能直接 generator.return()（会错过 clean-up），要走 abortController

对大多数 agent 系统，收益大于成本 —— UI 体验和实时性通常是 deal-breaker。但如果目标是离线批处理，更适合 non-generator 架构。

10.2 Withhold + recover 模式¶

API 错误不立即 yield，先缓存；外层判断能否恢复，能就丢弃错误，不能才 yield。

收益：SDK consumer 不会看到中间态错误后误判 session 结束 成本：多了一个"什么情况算 withhold-able" 的判定函数集合，每个新错误类型都要扩展

这个模式可迁移性最强。任何要从 LLM API 错误里 recover 的系统都值得抄。

10.3 两种工具执行模式并存¶

feature gate 切 StreamingToolExecutor vs runTools。

为什么不一步到位全用 streaming：

  • 两者语义不同：streaming 能在 assistant 还没说完的时候就启动工具；经典模式必须等整段 assistant 流完
  • 测试覆盖不对等：runTools 用了多年，StreamingToolExecutor 相对新
  • 回滚代价：发现 streaming 有 bug 时能 gate 一关

灰度策略本身不算设计亮点，值得记住的是新旧两条路径共用 isConcurrencySafe 接口。tool 一侧只需实现一次，执行器有多套。

10.4 Fallback 是内层循环¶

不增 turnCount，同一轮的第二次尝试。

对比 alternative：如果把 fallback 算新一轮，maxTurns 就会被模型 fallback 事件意外耗尽。用户并不知道 fallback 发生，他看到的 "maxTurns=10" 意味着"最多 10 次 agent 决策"，不是"最多 10 次 API 成功调用"。

小决定，但体现了"语义一致性优先"的风格。

10.5 transitions.ts 留空 shim¶

这不是"设计"，是 restoration artifact。但它揭示了一个原本存在的分层 —— reducer vs IO。本章第 9 节把它当设计信号讨论。

11. 可迁移的点¶

给自己做 agent 系统的读者，本章有 5 个能直接抄的做法：

  1. Session 态和 turn 态拆两层。Claude Code 的 QueryEngine 持跨-turn 状态（messages、file cache、usage、abort），query() 只是一个 async generator 处理单次推进。query() 能被主线程、sub-agent、compact 子任务共用。自己做时把它们分成 class + free function 的组合，不要混一起。
  2. State 里带 transition 诊断字段。transition?.reason 记"上次怎么进来的"。测试 assertion 看 transition 就行，不必解析 messages。调试日志也一行带过。成本近零，收益不小。
  3. Read-only 工具并发切分。isConcurrencySafe 在 Tool 接口上声明，partition 时把连续 safe 的工具聚成一个 batch 并发。比"一刀切全串行"快几倍，比"全并发"安全。上限用 env var（CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY=10）。
  4. Withhold + recover。可恢复 API 错误（上下文超限、输出截断、内容过大）先不往外 yield，外层判断能否 recover。恢复成功丢弃错误，失败才 yield。避免误杀上游 consumer。
  5. 两套预算分离。context window 预算（input side）和 output token 预算（output side）是正交的。Claude Code 用了两套不同机制：compact vs continuation。混到一起就难了。

还有一个不是"可迁移"、但值得记住的做法：注释里带 BQ 观测数据。Circuit breaker 为什么是 3 次、reserveTokensForSummary 为什么是 20K、为什么要防 "1,279 sessions 50+ 次失败"—— 这些在注释里都有具体数字和日期。写 agent 系统的人常要面对"选什么阈值"的问题，方法是：从生产数据看尾部分布，把选择的理由注释到代码旁。
