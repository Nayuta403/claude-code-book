22.1 用户看到的三层观测¶

Claude Code 是长跑进程。一次会话可能跨几小时、调上百次 tool、读写上千文件、烧几块钱 token，还可能把 Node 堆吃到 2 GB。工程师需要三件事：

  • 知道花了多少（cost）
  • 知道当前状态（observability）
  • 出事了能捞现场（debugging）

对应的用户触点是三层：

  1. 底部常驻一行 status line（下文统一作 statusline，专指那行 UI；/statusline 则是斜杠命令名）：实时显示 context %、cost、model、git 分支。
  2. 六个斜杠命令（slash command）：/cost、/usage、/stats、/doctor、/heapdump、/statusline。
  3. 会话退出时自动打印的总结（src/costHook.ts:6-22 在 process.on('exit') 里调 formatTotalCost）。

本章讲"数据从哪来、给谁看、为什么这样分"。几件事不在本章范围：Hooks 协议在 ch.14（本章的 costHook 只是其中一个内置消费者）；Agent Loop 在 ch.03（cost 的"源头归集"那条路径在那里画）；Ink 怎么把 statusline 画到屏幕上在 ch.21；SDK 如何消费这些 usage 数据在 ch.23；cost 怎么参与 compact 决策在 ch.07；跨机协作场景下 cost 归属到哪台机器，在 ch.17（remote session）。

22.2 为什么挑这个设计出来讲¶

本章有一个值得抄作业的设计点：把 statusline 的"模板语言"退化成"把 JSON 喂到 stdin、把 stdout 原样贴回屏幕"。官方不维护 DSL，也不提供变量语法，只约定一份 JSON schema。用户想怎么用 bash / python / node / jq / awk 都行。这个设计的代价是每次刷新 fork 一个子进程；收益是扩展面无穷、维护成本归零。见 §22.7。

其余还讲两件事：

  • Cost 累加器用单一真相源（modelUsage 按 model 分桶），所有总计都是派生。避免"总量对不上分项"的经典 bug（§22.3）。
  • /heapdump 的"先写 diagnostics、再写 snapshot"—— 失败域排序的小标本（§22.8）。

Prompt cache 的账单意义值得单独点一下。官方说明（来源：https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching，访问于 2026-04-19）：5 分钟 cache 的 read 是基准 input 的 0.1 倍、write 是 1.25 倍。Claude Code 的 Sonnet 价位 promptCacheReadTokens = 0.3、inputTokens = 3，比值刚好 0.1，能对上。所以 statusline / stats 里把 cache_read 暴露出来，不是炫耀，是对用户的经济提示：这一块 token 只花你 10% 的钱。

22.3.2 累加器：按 model 分桶，总计都是派生¶

Claude Code 会话里可以来回切 model（/model），还可能同时跑 advisor / classifier 这类 side query，每条都用不同的 model。要让 /cost 既能报总额，又能按 model 拆开，就得解决"总量对不上分项"的常见问题。

做法是只存一份：按 model 分桶的 modelUsage。

totalCostUSD 是单独累加的标量，但 token 维度全部是从 modelUsage 求和得到 —— getTotalInputTokens 就是 sumBy(modelUsage, 'inputTokens')。每个 model 的桶在 src/cost-tracker.ts:250-276 的 addToTotalModelUsage 里按字段累加，同时刷新 contextWindow 和 maxOutputTokens（便于后续读取）。addToTotalSessionCost 的调用点在 Agent Loop 的 stream 末尾（ch.03 讲 message_delta 收尾那一步），统计是 loop 驱动、不是 UI 驱动。

隐藏细节（src/cost-tracker.ts:266-275）：/model 中途切换到新的 model 时，cost 不会重算，也不会回补精度。modelUsage[model] 是按 model 分桶累加的，切换后新请求进新桶，旧桶原样保留。这意味着：如果价格表在切换前就"估错了"（未知 model 走 fallback），切换到新 model 后那一段不会自动纠正。totalCostUSD 是所有桶累加的标量，一旦写入就不再回滚。对"为什么总额和我心算的对不上"这类问题，先核 modelUsage 里每桶的 costUSD。

一个容易漏掉的分支：advisor 是递归的。addToTotalSessionCost 在统计完主 usage 之后，把 getAdvisorUsage(usage) 返回的子 usage 当新样本再跑一遍同样的分桶逻辑：

模型每隔几周就会发新版本。如果客户端没更新到最新价格表，账就算错了。Claude Code 的策略是 fallback + 可见警告：

22.4 /cost、/stats、/usage 的分工¶

三个命令名字都带"用量"，但数据源根本不同：

命令数据源回答
/cost会话内内存累加器（API usage 流）这次会话花了多少钱、调了多少 token、按 model 怎么分
/stats磁盘上的 session JSONL 记录历史活跃度、streak、每日 token 曲线、model 偏好
/usageclaude.ai 服务端 /api/oauth/usage订阅额度 5h / 7d 窗口剩多少

/stats 的类型定义能说明问题：

这些字段从 cost-tracker 根本拿不到 —— 它只活一个会话。/stats 调 aggregateClaudeCodeStatsForRange('all' | '7d' | '30d')（src/utils/stats.ts:718），去扫本地的 session 历史。有 persisted cache（src/utils/statsCache.ts）避免每次从零扫描。

/usage 则是走后端：

返回 five_hour / seven_day / seven_day_opus / seven_day_sonnet / extra_usage。这是订阅服务端的账本，和本地的 token 计数完全无关。在跨机场景下（ch.17），远端机器产生的 token 也记在服务端账本里、但本地 cost-tracker 看不见 —— 所以"跨机 cost 归属"这个问题 /usage 能答、/cost 答不了。

三个命令故意不合并。因为一旦合并，用户会误以为它们在回答同一个问题。

隐藏细节（src/utils/statsCache.ts:14-75）：/stats 的聚合结果有 stats-cache.json 持久化，但源 session JSONL 没有任何 rotation。全仓搜 pruneSessions / deleteOldSessions / rotateSession / maxSessionAge 均无匹配；PersistedStatsCache 类型注释里只承诺"bounded by days / sessions"（聚合层），源文件（~/.claude/projects/<slug>/ 下的 JSONL）不会被主动清理。长期跑同一个项目会让这个目录无界增长，要手动删。cache 是"聚合只算增量"的加速层，不是保留策略。

22.5 costHook：作为消费者¶

costHook.ts 很短，但承担了两件事：把总账打印到屏幕、保存到 config。它是 Hooks 协议（ch.14 讲协议本身：生命周期、触发点、用户可扩展面）的一个内置消费者 —— 用协议自身给的数据窗口做"会话退出时做点什么"。

它是 cost 数据的一个消费端点，不是 hook 协议本身（那部分协议 / 匹配 / 触发逻辑见 ch.14）。

注意 hasConsoleBillingAccess() 的守卫 —— 订阅用户在 exit 时也不会看到金额总结，和 /cost 的隐藏策略一致。但 saveCurrentSessionCosts 无条件执行：数据一直在盘上。

隐藏细节（src/utils/billing.ts:10-43）：hasConsoleBillingAccess() 比"是不是订阅用户"严得多。它依次检查：DISABLE_COST_WARNINGS 环境变量（任一 truthy 值直接关闭）、是不是 isClaudeAISubscriber（是就关）、有没有任何认证源（没有就关）、以及 org / workspace 角色必须是 admin | billing | workspace_admin | workspace_billing。所以企业 API 用户里"普通成员"角色 exit 时也看不到金额总结，常见的问题"为什么我没看到 cost 总结"通常是 DISABLE_COST_WARNINGS=1 或角色不在白名单里；grandfathered 用户（没重新走一次 re-auth 拿到 role 字段）也会被关掉。底层 saveCurrentSessionCosts 不走这个守卫，数据一直在 config 里。

22.6 Prompt cache 命中暴露在哪里¶

cache hit / miss 的统计对调优决策非常直接 —— cache read 便宜 10 倍，谁都想多命中。Claude Code 把这两个数暴露在三个地方：

  • /cost 输出的每行"按 model"统计里（src/cost-tracker.ts:213-223），显示 ... cache read, ... cache write。
  • statusline 的 context_window.current_usage 对象里，包含 cache_read_input_tokens 和 cache_creation_input_tokens（§22.7）。
  • OTel counter 的 type: 'cacheRead' | 'cacheCreation' 属性（§22.3.5）。

用户可以自己用这两个数算命中率。代码没做 "cache hit rate" 的一级字段，避免口径歧义 —— 你定义成 cacheRead / (cacheRead + input)？还是 cacheRead / (cacheRead + cacheCreation + input)？还是只看本轮 current_usage 不看历史累计？三个答案都合理，都各有场景。交给用户在 statusline 的 shell 脚本里自己 jq 算。

隐藏细节（src/utils/tokens.ts:138-157）：statusline JSON 里的 context_window.current_usage 不是"本会话累积"，而是 getCurrentUsage(messages) 从 messages 数组尾部向前找到的第一条带 usage 的 message 的 raw usage。换句话说，它是"最近一次 API 响应的原始数字"，每轮 API 响应都会整个换掉。如果你在 shell 脚本里把它当"累积用量"画进度条，compact 之后那一轮 cache_read_input_tokens 会突然暴涨，而下一轮又回落 —— 数字抖得很厉害。"累计"字段在同级的 total_input_tokens / total_output_tokens（从 modelUsage 求和）。这两个字段的区别是官方 Available Data 表里最容易被忽略的一对。

22.7 Statusline：shell + stdin 替代 DSL¶

这是本章最想让读者抄走的一个设计点。

22.7.1 它不是模板¶

首先澄清：/statusline 这个斜杠命令不是渲染命令。它是配置向导。

它做的事是：派一个 statusline-setup sub-agent，用户说"我想要 model + 分支 + context %"，sub-agent 去读用户 shell 的 PS1、生成一段 shell 命令、写到 ~/.claude/settings.json 的 statusLine 字段。真正 runtime 的逻辑在别处。

22.7.2 运行模型：JSON 到 stdin，stdout 到屏幕¶

用户在 settings.json 里配的是这样一段：

Claude Code 每次要刷新 statusline 时：

  1. 构造一个大 JSON 对象（下面会列）。
  2. fork 一个 shell 进程跑用户的命令，把 JSON 写进 stdin。
  3. 等命令退出；stdout 去掉空行、原样贴到屏幕；支持 ANSI 转义码。

实现在 src/utils/hooks.ts:4584-4666 的 executeStatusLineCommand：

5 秒超时、退出码非 0 丢弃 stdout、trust 未通过直接跳过。最终由 Ink 把 stdout 原样贴到屏幕（ch.21 讲 Ink 的渲染模型）。

隐藏细节（src/utils/hooks.ts:4587 + src/utils/settings/types.ts:550-556）：statusline 子进程硬超时 5 秒，且 settings.json -> statusLine schema 根本没有 timeout 字段（schema 只允许 type / command / padding 三项）。timeoutMs: number = 5000 是 executeStatusLineCommand 的默认形参，外部无配置点可覆盖它。超时时走 AbortSignal，result.aborted 为 true，函数直接 return undefined —— Ink 不刷新、屏幕上保留上一次的 statusline 文本，没有 "timeout" 视觉提示。想在 statusline 里跑 gh pr status / kubectl get pods / git fetch 这类偶尔超 5 秒的命令，这里必踩。解决办法是在命令里用更短超时的替代品（本地缓存 / 预跑后台任务写到临时文件）。

性能敏感的问题：每次都 fork 子进程很贵，不能每帧刷。Claude Code 的调度是 React 驱动的：

22.7.5 可迁移的点¶

做出"shell + stdin JSON"的判断，设计者多半考虑过 alternatives：

  • 自研 DSL（mustache-ish）：省 fork；代价是官方得维护 grammar、sandbox、错误诊断，扩展字段要同步文档，每个新 feature 要考虑"模板能不能打到"。
  • 嵌入 JS runtime（比如 deno / qjs）：比 DSL 强，但 sandbox 和内存成本都不低。
  • 当前方案：fork 一个子进程、喂 JSON、接 stdout。扩展 = 加字段，用户学成本 = jq 的 shell 用法。零 sandbox（反正跑的是用户的 shell、用户自己的权限）。零维护。

这个取舍可以迁移到很多"需要给用户一个'小窗口'展示实时数据"的场景：git hook、CI 状态行、IDE 左下角。只要你的数据本来就能 JSON 化、只要刷新不是每秒级，这个模式都可用。

22.8.3 先写 diagnostics、再写 snapshot¶

注释把这里的取舍讲清楚了：

这是失败域设计。想象一个 4 GB heap：v8.getHeapSnapshot() 自己就得分配大块内存做序列化，有概率崩。按经典做法（一次写完两个产物）一旦崩就什么都没有。Claude Code 先写那份 1 MB 的 JSON，再尝试 snapshot。即便第二步失败，工程师还有足够的症状（rss、detachedContexts、smaps_rollup）做第一轮分析。

产物都落在 ~/Desktop（Linux 没有 Desktop 目录时 fallback 到 $HOME，WSL 会尝试挂到 Windows 桌面 —— src/utils/file.ts:480-537）：

  • <sessionId><suffix>.heapsnapshot（给 Chrome DevTools → Memory → Load）
  • <sessionId><suffix>-diagnostics.json

文件权限 0o600，避免多用户机上其他账号看到你的 heap 内容。

隐藏细节（src/utils/heapDumpService.ts:243-245）：suffix = dumpNumber > 0 ? '-dump${dumpNumber}' : ''。手动触发（/heapdump）时 dumpNumber = 0，suffix 是空串 —— 也就是说同一 session 里连按两次 /heapdump，两次的文件名都是 <sessionId>.heapsnapshot，后一次直接覆盖前一次。自动 dump 路径才会传 dumpNumber > 0，生成 -dump1 / -dump2 后缀。想对比两次手动快照（例如 "跑一段长任务前后的 heap"），只能先手动把上一次重命名挪走，再跑第二次。

22.8.4 Bun vs Node 分支¶

Node 用流式 pipe（流起来内存峰值低）；Bun 的 generateHeapSnapshot 不是流式，强制同步写，写完立刻 Bun.gc(true) 尝试回收那份临时 ArrayBuffer。同步写的理由在 comment 里：避免跨 worker 线程克隆大字符串。

22.9 /debug-tool-call：在本仓库是 stub¶

它被列在 src/commands.ts:225-254 的 INTERNAL_ONLY_COMMANDS 里，external build 会完整剔除。恢复期的仓库里只看到壳。从命令名和 ant-only 的定位看，合理的猜测是"摊开最近一次 / 指定一次 tool 调用的完整 payload、response、耗时"的内部调试面板，对应 Agent Loop（ch.03）和 Tool system（ch.08）里本来不完全透明的内部状态 —— 但此章不按猜测写。如果你拿到 ant 构建的源码，请以真实实现为准。

公开可观测面上能用的等价数据：tengu_tool_use_success / error / cancelled 这组分析事件（OTel / analytics 侧）记录了每次 tool 调用的结果。

22.10 /doctor：诊断，不自愈¶

/doctor 要回答一个务实的问题：为什么我的 Claude Code 不正常。诊断项很杂，但设计模式只有一个 —— {issue, fix} 对：

每条 warning 必须带可以直接粘贴执行的 fix 字符串。例如 native 安装但 ~/.local/bin 不在 PATH 时：

/doctor 自己不改文件。它只把症状和修复命令列出来。用户可以按 f 键把修复请求递给 Claude，由 Claude 拿着 fix 字段去执行（来源：https://code.claude.com/docs/en/commands，访问于 2026-04-19）。

诊断项包括（src/utils/doctorDiagnostic.ts:514-625）：

  • 安装类型：npm-global / npm-local / native / package-manager / development / unknown
  • 同机上的多处安装（"Leftover npm global installation at /usr/local/bin/claude"）
  • managed-settings.json 里未知字段的 forwards-compat 检查
  • ripgrep 可用性 / 模式（system / builtin / embedded）
  • 自动更新是否开启、是否有权限
  • Linux sandbox 下 glob 规则的退化

src/screens/Doctor.tsx（574 行）里还追加：agent 解析失败、plugin 初始化错误、CLAUDE.md 过大警告、权限规则不可达、MCP 解析错误、sandbox 诊断、keybinding 冲突、版本锁。

这是一个长尾清单，几乎每加一个 feature 就得加一条 /doctor 检查。把 schema 卡死成 {issue, fix} 的好处就是：写新检查的人没得选，必须同时想好"怎么修"。

隐藏细节（src/utils/doctorDiagnostic.ts:573-586）：/doctor 不做运行时的 network 探测（没有 "能不能连上 api.anthropic.com"、"OAuth token 还有效吗" 这类主动 probe）。它只做静态检查：安装路径 / PATH / ripgrep 能不能找到 / npm-global 下 ~/.local/bin 的写权限（checkGlobalInstallPermissions 探测的是"能不能自动更新"，不是"API 能不能通"）/ managed-settings.json 的 forwards-compat / Linux sandbox 下 glob 规则的退化。想诊断"为什么连不上后端"，/doctor 不会告诉你；得看 tengu_api_error 分析事件或 REPL 里的 error toast。这是 /doctor 的设计边界：诊断本地安装，不诊断服务侧。

22.11 设计取舍¶

把前面讲的拧成几条可以带走的：

  1. 只信 API response 的 usage，不做本地估算 避免了"本地 tokenizer 和 Anthropic 不一致"的长期对账问题。代价是不能在请求发出前知道要花多少钱。Claude Code 判定这个代价可接受 —— 未知 model 走兜底 + warning。
  2. 三个"用量"命令故意不合并 数据源分别是内存累加器、磁盘 JSONL、服务端。合并会骗人。
  3. Cost 累加器单一真相源（modelUsage 按 model 桶），总计全部派生 读源码时一眼能看出"总量对分项的不变式"。无法写出不一致的状态。
  4. statusline = shell + stdin JSON 用"fork 子进程"的成本换"零 DSL、零 sandbox、零维护"。对需要给用户小窗口暴露实时数据的场景，这是值得抄的模式。
  5. /heapdump 先写 diagnostics、再写 snapshot 失败域排序。"一定不会崩的那份"先落盘。跟"先记日志再处理请求"是同一类思路。
  6. /doctor 的 {issue, fix} 契约 把"诊断"和"修复建议"绑成一个数据结构。写新检查的人被迫同时想好 fix。
  7. 高内存时只提示、不自动 dump 2 GB heap 的自动 dump 会把磁盘占满、把卡住的进程更卡。交给工程师按 /heapdump 决定。
  8. /cost 对订阅用户隐藏但数据仍累加 UI 和底层数据分离。底层不受上层策略影响，是正确的分层。

22.12 可迁移的点¶

  • 把"三种视角不同"的命令合并要慎重。先问"它们回答的问题是同一个吗"。
  • 给外部脚本 / hook 一个数据窗口时，首选喂 JSON 到 stdin，而不是自己发明模板语法。把 schema 文档化、版本化，比自研 DSL 容易维护。
  • 累加器配多个维度时，只存最细粒度的那一份（按 model / 按 type），总计是派生。避免"总 vs 分项不一致"的老 bug。
  • 长尾诊断项的数据结构里强制要求 fix 字段。把"诊断"和"怎么修"绑在一起。
  • 失败域设计：导出产物按"从便宜到昂贵 / 从稳到不稳"排序，先落便宜那份。
  • 给未知 / 新版本留 fallback 同时标出警告。让用户知道"这是估的"。
