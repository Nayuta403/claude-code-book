术语先对齐 —— Claude Code 里有两个"后台"¶

本章要写的"后台"在 Claude Code 里至少分两层。它们不是同一种抽象，只是共用了一部分基础设施和同一个按键。Owner 先把这两层分清楚，正文再逐层讲：

  1. 进程级后台（foreground ↔ background bash）：长跑的 bash 命令不再阻塞 agent 的 tool call；子进程脱钩继续跑，agent 得到一个 backgroundTaskId 后立刻回到主循环。
  2. 会话级后台（session backgrounding）：整个 REPL 的当前 query 脱离前景 UI，消息流进单独的任务槽；用户可以切走干别的事，query 跑完再把通知打捞回主对话。

关于另外几个不在本章的相关概念：

  • sub-agent 的"后台"属于 Async Task 系统（AppState.tasks 的 LocalAgentTaskState），见 ch.04 §2（sub-agent async / 任务调度）。本章进程级后台可被任何 agent 触发，但 sub-agent 的调度 / 协作不在这里讲。
  • Agent Loop 的等待策略（tool call 完成前如何让出主循环）见 ch.03 §3，本章只涉及"后台事件怎么回灌到上下文"。
  • BashTool 本身的接口设计（command / timeout / run_in_background 等字段）见 ch.08 §2，本章只讲 run_in_background 字段触发的后台流水线。
  • 定时任务 / cron trigger 把任务拉起后落到本章同一套后台基础设施上，见 ch.13 §4（cron 触发后的执行路径）。主动通知 UI（task-notification 怎么渲染到主对话）见 ch.15 §3。远程 / SSH session 下的后台行为见 ch.17 §2，IDE 里长跑任务的挂靠方式见 ch.18 §3。Ink 渲染见 ch.21。

值得借鉴的一点¶

把"后台进程"按下面这套组合来做：子进程 stdout/stderr 焊到磁盘文件 fd；共享的每秒 1 次 poller tail 文件尾驱动所有 UI 进度；size watchdog 每 5 秒检查文件大小；完成时把 XML <task-notification> 推进 agent 的消息队列。这个组合同时满足四个相互掐架的要求：

  • 长跑（小时级）不阻塞 agent 主循环；
  • 大输出（GB 级）不把 Node 堆撑爆；
  • 多任务并发（几十个任务同时跑）不炸 timer / fd 数；
  • 完成事件不污染 agent 的串行推理上下文。

后面用源码把这四条分别兑现。

进程级后台 —— 五个角色¶

角色 1：ShellCommand —— 子进程状态机¶

进程级后台的主类型在 src/utils/ShellCommand.ts:32-47：

四个状态 running → (backgrounded | completed | killed) 单向迁移。background() 返回 boolean —— 只有从 running 才能转后台；已经 completed / killed 的直接拒绝，避免竞态里重复登记。

两种执行模式并存（src/utils/ShellCommand.ts:60-113）：

  • file 模式：bash 命令走这条。子进程的 stdio[1] / stdio[2] 直接绑到磁盘文件 fd，childProcess.stdout / childProcess.stderr 是 null，JS 完全看不到输出数据。
  • pipe 模式：hooks 执行命令走这条。StreamWrapper 包裹 Readable 流，按 chunk 喂给 TaskOutput。

这个区分是后面所有设计的地基：JS 不参与数据搬运，长跑命令的吞吐不再受 Node event loop 调度影响，几 GB 的 stdout 不会撑爆 V8 堆。

角色 2：TaskOutput —— 唯一输出源¶

每个命令有一个 TaskOutput 实例，拥有 taskId、文件路径、内存 buffer、磁盘 spill、CircularBuffer（保存最近 1000 行）、onProgress 回调。

  • file 模式（stdoutToFile === true）：#stdoutBuffer / #stderrBuffer 永远不被写入；所有输出走磁盘 fd；进度靠 poller 读文件尾部。
  • pipe 模式：数据先进 #stdoutBuffer；超过 DEFAULT_MAX_MEMORY = 8MB 时 #spillToDisk() 把内存 flush 进磁盘然后切成磁盘直写模式。

两种模式对外暴露同一个 .getStdout() 接口，上层不需要分支判断。

容量边界：

  • 内存上限：src/utils/task/TaskOutput.ts:9 —— DEFAULT_MAX_MEMORY = 8 * 1024 * 1024
  • 磁盘上限：src/utils/task/diskOutput.ts:30 —— MAX_TASK_OUTPUT_BYTES = 5 * 1024 * 1024 * 1024 (5GB)
  • 文件路径：src/utils/task/diskOutput.ts:50-55 —— projectTempDir/<sessionId>/tasks/<taskId>.output

文件路径里嵌入了 sessionId 是有故事的 —— 注释里说明：并发 session 不嵌 session id 会互相删文件（src/utils/task/diskOutput.ts:38-47）。同理，sessionId 在第一次调用时 memoize，而不是每次现取，因为 /clear 会 regenerate session id，如果不锁一次后台任务的 fd 路径就失效了。

隐藏细节（src/utils/task/diskOutput.ts:49-55）：_taskOutputDir 是模块级变量，首次调用 memoize。即使之后 /clear 触发 regenerateSessionId()，已经注册过的 TaskOutput 仍然写入旧 session id 路径下的那个文件；新创建的任务才会进入新 session id 的目录。产品层面你只感到"/clear 之后旧会话的后台任务还在跑"，源码层面这行为的地基是"路径 memoize 在第一次调用"这一个赋值。这也是"后台 bash 穿越 /clear"语义的底层约束。

隐藏细节（src/utils/task/TaskOutput.ts:329-334）：file 模式下 getStderr() 无条件返回空串；子进程的 stderr 在 spawn 时就被重定向到和 stdout 同一个 fd（file 模式下两者合并写入 <taskId>.output）。产品层面看到的 ExecResult.stdout / ExecResult.stderr 看起来是两路，实际落盘时 stderr 不可单独分离 —— 只有 pipe 模式（hooks 执行命令）下 #stderrBuffer 才真正有值。影响场景：想从后台任务 tail 里 grep stderr 只看错误是做不到的。

隐藏细节（src/utils/ShellCommand.ts:269-272）：监听的是子进程 'exit' 事件而非 'close'。'close' 会等待所有继承 stdio fd 的 grandchild 也 exit —— 典型如 sleep 30 & 这种用户显式派生的后台子进程。用 'exit' 让 shell 自身退出就能立刻返回控制权，grandchild 留给系统自生自灭。用户层面你不感知，但这直接决定"后台命令'跑完'的瞬间"到底怎么算。

角色 3：共享 poller —— 进程级单例¶

这是最值得单独拎出来的设计。每个后台 bash 都要 tail 文件显示进度，但不给每个任务起一个 timer 的天然理由有：

  • timer 碎片化让 Node 的 timer wheel 抖动
  • 每个 task 一个 stat 调用会放大 IO 压力
  • React 组件卸载时收不到干净的退出信号

TaskOutput 用一个进程级共享的 interval处理所有活跃任务：

三点设计：

  • registry vs activePolling 分离：任务创建时就进 registry，但只有 React 渲染层显式调 startPolling 才进 activePolling。UI 卸载时 stopPolling，最后一个 active 退出时关 interval。资源跟着"谁在看"走。
  • .unref()：interval 不阻止进程退出。但"进程退出"和"后台命令存活"是两回事 —— 见下一节的 cleanup hook，退出时后台 bash 会被同步 kill，而不是变成 orphan 常驻。
  • 1 秒固定周期：不做 backoff。背景命令普遍高频输出，1s 够用；低频命令（如 git log -S）该 tick 读不到新字节时调 onProgress('', '', …) 唤醒上层检查"是否要自动后台化"—— 这是唯一不"按输出量收费"的例外（src/utils/task/TaskOutput.ts:121-124）。

行数外推：tail 只读 4KB，长输出的总行数靠比例外推：

Math.max(prev, extrapolated) 保证单调：tail 里恰好是一堆短行，下一 tick tail 里全是长行，比例外推值会下降 —— 这里用前值托底，避免 UI 计数抖动。

tail 窗口本身只有 4KB（PROGRESS_TAIL_BYTES = 4096，src/utils/task/TaskOutput.ts:11），也就是说 tick 里只读文件尾 4KB。超过这个窗口的历史输出不会被每秒扫一遍，只在任务完成或显式 Read 时才被取回。这是用"固定小尾巴 + 外推"换"无论文件多大都保持 tick 成本恒定"，让 1 小时跑出来 1GB 的任务在进度条上不会反映出"每 tick 更慢"。

隐藏细节（src/utils/task/diskOutput.ts:304-330）：BashOutput 增量读（getTaskOutputDelta）按字节偏移推进 —— newOffset = fromOffset + result.bytesRead。如果一次读取的 maxBytes 边界恰好切中一个 UTF-8 多字节字符或一行中段，返回的 content 会在中间被物理切断（半个字符、半行）。调用方（BashOutput 工具的实现）必须自己容忍这种"半行 / 半字符"的边界情况。产品层面你会偶发看到后台任务输出里中文字符变成问号或者一行被切两段，底层就是字节推进而不是行对齐。

角色 4：生命周期 —— LocalShellTask¶

task 层面有三个入口，对应"什么时候登记到 AppState"这个决策：

  • spawnShellTask()（src/tasks/LocalShellTask/LocalShellTask.tsx:180-252）：模型显式传 run_in_background: true 或 ShellCommand 超时触发 onTimeout。登记时 isBackgrounded: true，同时 shellCommand.background(taskId)。同一函数里还登记了进程退出的 cleanup hook（:200-202）—— 见下面的隐藏细节。

隐藏细节（src/tasks/LocalShellTask/LocalShellTask.tsx:200-202 + src/utils/gracefulShutdown.ts:447）：spawnShellTask 里每个后台任务都登记了 registerCleanup(async () => killTask(taskId, setAppState))。主 session 退出（Ctrl+C、/exit、SIGHUP）触发 gracefulShutdown，它 await runCleanupFunctions() —— 所有后台 bash 会被同步 kill（SIGKILL 级别），而不是 detach 成 orphan 进程。产品层面的直观印象是"我都按 Ctrl+C 退出 Claude 了，那个 npm run watch 也会停吧？"是的，会停，但原因不是 shell 的进程组传递，而是源码里这个 cleanup hook。想让长跑命令脱钩真正的一整夜，得 disown 或 nohup。

  • registerForeground()（src/tasks/LocalShellTask/LocalShellTask.tsx:259-287）：命令跑过 2 秒 progress threshold，UI 要显示但任务还没后台化。isBackgrounded: false，给 Ctrl+B 提供把手。
  • backgroundExistingForegroundTask()（src/tasks/LocalShellTask/LocalShellTask.tsx:420-474）：已登记的前台任务转后台。文件里注释说得很直白：

    > Used when the auto-background timer fires after registerForeground() has

    > already registered the task (avoiding duplicate task_started SDK events

三个入口长得像，但合并成一个会踩 SDK 事件重复发、cleanup 回调漏注销的坑 —— 把"登记"和"转换"分开是对的。

三个 watchdog / 自动化¶

Size watchdog —— 5GB 硬上限¶

后台 bash 把 stdout/stderr 焊到 fd 写磁盘，JS 既看不到数据也收不到字节计数。出事最快的 fail-safe 是：定期 stat 文件大小。

注释里提到 "768GB incident"（src/utils/ShellCommand.ts:52-54 的 SIZE_WATCHDOG_INTERVAL_MS 块注释 + :357 background() 方法里的重复提醒）：有过日志卡死死循环把磁盘写满 768GB 的真实事故。5GB cap + 5 秒检查周期是事故驱动的妥协：检查太频繁空耗 stat；阈值太低误杀正常大 build。

这个上限在官方 Interactive mode 文档里也明说：

Background tasks are automatically terminated if output exceeds 5GB, with a note in stderr explaining why —— https://code.claude.com/docs/en/interactive-mode，访问于 2026-04-19

对应源码会给 stderr 前缀加一行解释（src/utils/ShellCommand.ts:318-322），让模型下一轮读出来就知道是资源问题。

Stall watchdog —— 交互提示识别¶

后台命令长时间没有输出增长，大概率是"卡在 (y/n) 等输入"。startStallWatchdog（src/tasks/LocalShellTask/LocalShellTask.tsx:46-104）做这件事：

  1. 每 5 秒 stat 一次文件大小；
  2. 文件大小不增长超过 45 秒时，读文件尾部 1KB；
  3. 用一组正则（/(y\/n)/、/Press (any key|Enter)/、/Overwrite\?/ 等，PROMPT_PATTERNS 数组在 src/tasks/LocalShellTask/LocalShellTask.tsx:32-38，配套的 looksLikePrompt 函数到 :42）匹配最后一行；
  4. 匹配上就发一条 <task-notification> 告诉 agent 改用 echo y | command 或找 non-interactive flag。

关键在没匹配上的情况：不触发 kill、不发"还活着"的 ping，只是把 lastGrowth 重置让下一轮 45 秒后再看。这是正确的默默失败 —— 慢 build / git log -S 长时间无输出完全正常，不能骚扰 agent。

正则前的 cancelled latch（:72-73）也值得一提：并发 tick 可能同时命中，一次触发就关停；cancelled = true 在 async boundary 前置，保证后到的 tick callback 看到 cancelled === true 直接 bail。

自动后台化的三种触发¶

BashTool 对"后台"的触发不是一处，是三处互补：

  1. 超时自动后台（src/tools/BashTool/BashTool.tsx:967-971 + src/utils/ShellCommand.ts:135-141）：命令超过 timeout 且在允许自动后台的白名单里，选择后台化而不是 SIGTERM。白名单反向定义： ts // src/tools/BashTool/BashTool.tsx:220-221 const DISALLOWED_AUTO_BACKGROUND_COMMANDS = ['sleep'] sleep 被排除是因为它作为用户意图就是"阻塞 N 秒"；转后台没意义。
  2. assistant-mode 15 秒预算（Kairos 特性，src/tools/BashTool/BashTool.tsx:976-983）： ts const ASSISTANT_BLOCKING_BUDGET_MS = 15_000 在 Kairos 模式、主线程、未显式 run_in_background 的 bash 命令跑满 15 秒自动转后台。返回值上会带 assistantAutoBackgrounded: true，让 agent 看到：

    > Command exceeded the assistant-mode blocking budget (15s) and was moved to the background with ID: ... In assistant mode, delegate long-running work to a subagent or use run_in_background to keep this conversation responsive. 这个自动转后台的设计假设"用户不希望 agent 因为一个命令卡死主循环"，代价是 agent 后续看不到实时输出，得靠 Read 文件或等 task-notification。 语义澄清：setTimeout(..., 15_000).unref() 是从命令 spawn 那一刻起算的一次性判定 —— 不是累计 CPU 时间、不是每 tick 重新检查、更不是"多个命令共享 15 秒"。到点就触发一次 background 化；.unref() 保证这个 timer 不阻止进程退出。

  3. 显式 run_in_background: true：模型主动传的，直接转后台，立刻返回 backgroundTaskId（src/tools/BashTool/BashTool.tsx:989-1001）。

三者的关系：显式 > 超时自动 > assistant-mode 15 秒。显式的任何时候都优先生效；超时自动受白名单限制；assistant-mode 15 秒只在主线程 + 非显式后台的前提下兜底。

回灌与重同步¶

agent 侧读取：Read > TaskOutputTool¶

有两种方式读后台任务的输出：

  • TaskOutputTool（src/tools/TaskOutputTool/TaskOutputTool.tsx）：task_id + block + timeout，能轮询等完成。别名 BashOutput / AgentOutputTool 兼容旧 transcripts（:149-150，注意 API 层面 harness 给模型暴露的名字就是 BashOutput，不是 BashOutputTool）。
  • 直接 Read 文件路径：后台 bash 返回的 ExecResult 带 outputFilePath / outputFileSize，模型直接 Read 那个路径。

文档和 prompt 都劝 agent 用 Read：

理由是 Read 已经是 agent 主工具集里的核心工具，认知成本最低；多一个工具就多一个 schema 要塞进 system prompt。deprecation 后 TaskOutputTool 留下来只是为了兼容存量 transcript 回放（maxResultSizeChars: 100_000、shouldDefer: true、aliases: ['AgentOutputTool', 'BashOutputTool']）。停止后台任务的对应工具叫 TaskStopTool，对外 alias KillShell（src/tools/TaskStopTool/TaskStopTool.ts:39-44）—— BashOutput / KillShell 两个名字是 Claude Code harness 层的扩展，不在 API bash tool 标准参数里。

官方文档也是同样的表述：

Output is written to a file and Claude can retrieve it using the Read tool —— https://code.claude.com/docs/en/interactive-mode，访问于 2026-04-19

竞态处理 —— "我们刚 Ctrl+B 它就退出了"¶

BashTool 的进度 generator 和 shellCommand.result 之间会发生这种竞态：generator 正要把命令标记为"转后台"的时候，子进程自己退出了。handleExit 看到 #backgroundTaskId !== undefined 就按"后台命令完成"处理，但 generator 已经决定返回 "backgrounded" 给 agent，会留下"命令完成但通知会再发一次"的裂缝。

处理方式（src/tools/BashTool/BashTool.tsx:1047-1059）：

  • 从 result 里擦掉 backgroundTaskId —— agent 看到的是正常完成；
  • 重建 outputFilePath 给大输出用；
  • 调 markTaskNotified(taskId, setAppState) 让 .then() 回调里的 enqueueShellNotification 自动 bail（依赖前面说的 notified 原子 flag）。

这段不漂亮，但竞态窗口实际存在。原注释："race: backgrounding fired (15s timer / onTimeout / Ctrl+B) but the command completed before the next poll tick"。

会话级后台¶

这是和进程级后台并列的第二层"后台"。数据结构复用了 sub-agent 框架 —— LocalAgentTaskState 加个 agentType: 'main-session' —— 但触发条件和语义不同：进程级 Ctrl+B 是把 tool call 脱钩；会话级 Ctrl+B 是把整个 REPL query 脱钩。

useSessionBackgrounding 两分支¶

Hook 的核心行为在 src/hooks/useSessionBackgrounding.ts:41-74：

两分支判定的标尺是 foregroundedTaskId —— 谁正在被看？如果是某个 task，那这次按键是把它送回后台；否则把当前 query 背景化。

useEffect（:77-144）做的是把 foregrounded task 的 state 镜像到主视图：

  • task 的 messages 累积到 lastSyncedMessagesLengthRef 之后同步到主 messages；
  • task 的 status === 'running' 时 setIsLoading(true)，setAbortController(task.abortController)，让 Esc 能 abort 那个 task；
  • task 的 abortController 被触发时（例如用户 Esc），立刻 flip 回 isBackgrounded = true 让主视图恢复；
  • task 完成时自动拆回 background 状态。

这套单向数据流的代价是 foregrounded task 的 UI 交互全走 state 镜像，不能真的把 UI 组件重新 mount 到那个 task 上 —— 历史消息只能看不能重新滚到中间。但对"把当前 query 推到背后、切走做别的事、晚点回来"这个场景足够。

startBackgroundSession —— query 的 fork¶

src/tasks/LocalMainSessionTask.ts:338-425。把当前消息和 queryParams 打包交给一个独立的 query() async iterator 跑：

四个设计决策：

  • 独立 transcript 文件（src/tasks/LocalMainSessionTask.ts:104-111）：initTaskOutputAsSymlink 把 task 的 output 路径指向 getAgentTranscriptPath(asAgentId(taskId))，而不是主 session 的 transcript。这样 /clear 切换 session id 时后台 query 不会往新 session 的 transcript 里写。
  • 复用 LocalAgentTaskState：背景化 session 在任务列表里和 sub-agent 长得一样 —— 描述、messages、abort、result。UI 不用新建 task 类型。
  • AsyncLocalStorage 隔离：runWithAgentContext 用 Node 的 ALS 把 agentId 绑到这一条 async chain，skill 调用、permission 检查都能按 agentId 归属。前台和后台并发 query 不互相干扰。
  • abort('background') 的语义：REPL 层发起后台化时（src/screens/REPL.tsx:2558-2606）调的是 abortController?.abort('background') —— 这里的 abortController 是当前 query 的 controller（用来停掉主循环的 for await），不是 ShellCommand.#abortSignal。这两条 signal 链是分开的：bash 子进程的后台化完全走 shellCommand.background(taskId) 的状态迁移（running → backgrounded），子进程不接收任何 abort，继续照常跑。ShellCommand.#abortHandler（src/utils/ShellCommand.ts:186-193）只在它自己收到 abort 时起作用，而且只对 reason === 'interrupt' 放行不 kill（"用户提交了新消息"的场景，让 caller 有机会背景化以保留部分输出）；其他 reason 一律走 this.kill()。所以："'background' 走不 kill 路径"这个直觉描述的是最终效果（子进程确实继续跑），但具体机制不是通过 reason 分支，而是通过"abort 信号压根没传到 ShellCommand"。

设计取舍¶

  • 为什么 file 模式直接焊 fd，不在 JS 里缓存：JS 不是数据搬运的瓶颈点，但它成为瓶颈的概率高。后台命令可能跑一晚上、输出 10GB，JS 哪怕只做一次 .toString() 都是 heap 灾难。把 JS 从 hot path 彻底剥掉，换来 Node 进程可以稳定后台跑任意时长。代价：JS 看不到输出细节，得走文件 tail + 共享 poller 重建进度 —— 但 tail 4KB 的成本可以接受。
  • 为什么共享 poller 不做 per-task timer：per-task timer 在 20 个任务并发时就 20 个 stat + 20 个 timer tick，CPU wake-up 频率放大；共享 poller 一个 tick 串行处理所有 active task。代价：某个任务的 stat 慢会拖累其他任务的 tick 时机 —— 但 stat 是轻操作，且注释说"Non-async body (.then) to avoid stacking if I/O is slow"（src/utils/task/TaskOutput.ts:107-108），I/O 不阻塞 tick。
  • 为什么用文件路径 + Read 而不是 TaskOutputTool：减少 agent 需要认的工具数量。Read 对模型是熟悉的默认动作；TaskOutputTool 要在 prompt 里单独介绍。保留 TaskOutputTool 只为 transcript 回放兼容。
  • 为什么用 XML <task-notification> 包装而不是 structured JSON：XML 对 LLM 友好（tag-aware 训练语料丰富），对人读 transcript 也友好；同一份消息 print.ts 解析出 <status> 发 SDK 事件，模型和订阅者共享，不用维护两条路径。代价：XML 解析容错比 JSON 差，escapeXml 必须正确（src/tasks/LocalShellTask/LocalShellTask.tsx:164）。
  • 为什么 session 背景化复用 LocalAgentTaskState 而不是新建 type：UI 组件已经能渲染 agent task；复用减少新 code path。代价：语义被稍微拉扯 —— "main-session" agent 在任务列表里和真 sub-agent 并排看起来容易混，但通过 isMainSessionTask() 型别守卫能区分。

可迁移的点¶

  • "唯一输出源"类：给每个外部任务一个拥有 taskId / buffer / file path / progress 的 Output 对象，统一对外提供 getStdout()、spillToDisk()、clear()，让上层不操心数据在哪。对任何"跑子进程 + 可能很大 + 要 UI 展示"的系统都成立。
  • 共享 poller + UI 生命周期驱动：React 挂载 / 卸载触发 startPolling / stopPolling，interval 只在有人看时存在。这套模式能移植到任何"后台数据源 + 按需订阅"的场景。
  • 状态机四态 + status === 'running' gate：running → (backgrounded | completed | killed) 单向迁移，所有涉及后台化 / kill 的方法返回 boolean 表示是否成功 —— 多入口并发操作不用外面再套锁。
  • 完成事件走消息队列：agent 系统里异步结果不要直接 push 进 messages，会破坏推理串行假设。用队列 + 一次性 notified flag 保证每条完成事件恰好被消费一次。
  • 同一快捷键按状态分派：当用户意图随上下文变化（有前台任务 / 没有）时，键位层不必暴露两个键 —— 交给事件处理器按状态路由，UI 提示文案跟着变。
