1. 先说一段 MCP 是什么¶

MCP（Model Context Protocol）是 Anthropic 主推的一套 JSON-RPC 2.0 协议，把"给 LLM 接外部能力"这件事标准化。Host（LLM 应用）里跑 MCP client，client 连 MCP server。server 给 client 三类东西——tools（函数）、resources（数据）、prompts（模板）——client 也能给 server 回手：sampling、roots、elicitation。规范主页在 https://modelcontextprotocol.io/specification/2025-06-18（访问于 2026-04-19），方法列表简短：tools/list、tools/call、resources/list、resources/read、resources/subscribe、prompts/list 等，都是 JSON-RPC 名字空间里的普通请求。

本章不讲 MCP 本身的语义细节。本章要讲清三件事：

  1. Claude Code 在 MCP 协议里到底扮演几重身份。
  2. 外部 MCP server 的工具怎么变成 Claude Code 内部的 Tool——这是本章最值得借鉴的一点。
  3. src/upstreamproxy/ 和 src/bridge/ 这两个名字带"proxy/bridge"的目录和 MCP 没关系，本章顺手澄清。

3. 为什么挑"工具适配层"出来讲¶

MCP 协议本身简单——5 个方法能覆盖 90% 场景。真正工程上值得看的是：

  • 外部 MCP server 的 tools 形状是未知的。每个 server 自定义 name / description / inputSchema / annotations。
  • Claude Code 的内部 Tool 接口是固定的（见 ch.08 工具系统）：call / checkPermissions / renderToolUseMessage / isConcurrencySafe / isReadOnly 等一堆方法。
  • 两者的形状不同，数量不同，随时在变（MCP 支持 list_changed 通知），且最终要被 ch.08 的工具合并、ch.09 的权限、ch.10 的 Skills 无差别消费。

本章要讲的设计取舍就是：Claude Code 用 JS 对象的 spread-and-override 把未知形状的远端工具一次一个包成固定形状的本地 Tool，主干调用路径（tool.call(args, ctx, ...)）对 MCP 几乎无感——这里特意从"完全"改成"几乎"，因为 src/services/tools/toolExecution.ts 里确实有多处 isMcpTool(tool) / tool.isMcp 分支点（1377 / 1477 / 1495 / 1498 / 1540 / 1670 等行）。权限 / 遥测 / 特定展开路径会用这些分支做增量处理（工具合并逻辑见 ch.08，权限判定见 ch.09），但这些是 cross-cutting 关注点，不是主干分裂（见 5.2 末尾的措辞修正）。

三件事值得拎出来讲：

其一，spread-and-override 是适配层的骨架。外部 server 的 tools 彼此形状不同，但每个都能通过 { ...MCPTool, ...override } 成为一个合格的 Tool（工具合并逻辑详见 ch.08）。MCPTool 里预留的字段（UI renderer、结果大小上限、截断判断）继承；name / call / description / 注解映射这些每个工具独有的字段 override。Agent Loop 的调用主路径——tool.call(args, context, ...)——对"这是不是 MCP 工具" 几乎无感：它只面对统一的 Tool 接口。

需要措辞收敛的一点："完全无感"是夸大的。翻 src/services/tools/toolExecution.ts 能看到多处 isMcpTool(tool) / tool.isMcp 分支点（至少 1377 / 1477 / 1495 / 1498 / 1540 / 1670 等行），分别服务于：

  • 遥测：每个执行分支 emit metrics 时都打 isMcp: tool.isMcp ?? false 字段（420 / 526 / 627 / 645 / 698 / 1335 / 1646 多处）；
  • 权限：走 mcpInfoFromString(tool.name) 解析出 serverName 再进 ch.09 的 Permission 系统（详见 ch.09）；
  • UI 折叠：read / search 类 MCP 工具结果被 classifyMcpToolForCollapse 判一次，决定展开折叠行为。

这些是增量的 cross-cutting 关注点，不影响主干调用原语 tool.call(...) 的形状。所以更准确的说法是：主干调用路径对 MCP 几乎无感，横切关注点按需分支；设计点仍然是"把外部工具收敛到统一 Tool 接口"这个成果，而不是"一行 if 都没有"。

其二，annotations 到内部语义是 1:1 直接透传。MCP 规范 tools 章节（同 URL，访问于 2026-04-19）定义了 readOnlyHint / destructiveHint / openWorldHint 等 annotation。Claude Code 没有另起术语，直接把这些字段映射到自己的 isReadOnly / isDestructive / isOpenWorld。两个系统的接口稳定性锚点就是这几个规范字段名。值得注意：MCP 规范明文写 "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"——Claude Code 这里用了 ?? false 兜底，没有把 annotation 当成硬保证，它们只是"提示"。真正的权限决定在 ch.09 的 Permission 系统里做。

其三，inputSchema 不二次校验。外部 server 给的 tool.inputSchema 是 JSON Schema，这里直接当 inputJSONSchema 塞给模型。Claude Code 没有把它翻成 zod 再在本地做 runtime 校验——因为每个 MCP 工具的 schema 形状未知，运行时动态生成 zod validator 的成本不划算，直接让 server 自己 validate（MCP 规范也强制 server 必须验证）。

隐藏细节（src/services/mcp/client.ts:1779-1785）：MCP 规范的 tool._meta 是开放字段，Anthropic 在里头偷偷占了 anthropic/* 命名空间——anthropic/searchHint 和 anthropic/alwaysLoad——让自家 MCP server 能影响 Claude Code 的 ToolSearch 行为（searchHint 进来前还会被 replace(/\s+/g, ' ') 压成单空格，防止 \n 把 deferred 工具清单行切坏）。第三方 MCP server 不知道这个约定，也就享受不到 searchHint / alwaysLoad 的影响权——这是协议层"开放 _meta"被客户端默默解释成"私有命名空间"的典型现象。

5.4 in-process transport：避免 spawn 一个 300MB 的子进程¶

两个特殊 server 不走 stdio，而是直接塞在同一进程里。分支在 src/services/mcp/client.ts:905-943：

InProcessTransport（src/services/mcp/InProcessTransport.ts:1-63）是对 MCP SDK Transport 接口的一个 50 行实现：两个对象互为 peer，send 时通过 queueMicrotask 把消息投递到对方的 onmessage。

createLinkedTransportPair 返回两头互指的实例，一头给 client、一头给 server，两个对象在同一个 Node event loop 里跑。成本：省掉 spawn + IPC 的开销（Chrome MCP 子进程~325MB 内存、启动时间不小）；代价：server 崩了会把 client 一起带崩（同进程）。对"自家一定稳"的 MCP server 值得；对第三方 server 绝对不行。

这是值得借鉴的小模式：MCP SDK 的 Transport 接口抽象得够薄，用户可以按需自己写变种。stdio/http/ws 都是网络层，in-process 就是一组 microtask。

5.5 运行时调用链¶

模型生成一个工具调用 mcp__github__create_issue({...}) 后，链路是：

  1. Agent Loop 在合并工具池里按 name 查到刚才 fetchToolsForClient 包出来的 Tool 实例；
  2. 调这个 Tool.call(args, ctx, canUseTool, parentMessage, onProgress)——实际执行的是 client.ts:1833 那个 override；
  3. override 里 ensureConnectedClient(client) 保证连接活着（如果 session 过期，重建一次）；
  4. callMCPToolWithUrlElicitationRetry → callMCPTool（client.ts:3029）底层发 JSON-RPC tools/call；
  5. 回包的 content 被塞进 data；structuredContent 和 _meta 进 mcpMeta；
  6. 如果 SDK 抛 McpSessionExpiredError，清连接缓存，ensureConnectedClient 重建，重试一次（client.ts:1913-1921）。

进度事件 (mcp_progress) 在开始、完成、失败三个点 emit（client.ts:1846-1935），前端 UI 可以用来画 spinner 或显示 elapsedTimeMs。

隐藏细节（src/tools/AgentTool/runAgent.ts:648-686）：sub-agent 继承主 agent 的 MCP server 集合，不是隔离跑。initializeAgentMcpServers 把 agent 定义里声明的 MCP server 和父 toolUseContext.options.mcpClients 做 merge（mergedMcpClients），子 agent 的 toolUseContext 里 mcpClients: mergedMcpClients + mcpResources: toolUseContext.options.mcpResources 都指向父节点一份。含义：父 agent 连上了一堆 MCP server，子 agent 就能直接用父的这些连接 fire tools/call——不重新握手、不重登 OAuth。代价：父子 agent 的 MCP 能力耦合，无法用 sub-agent 去"隔离"不信任的 MCP server。（详见 ch.08 的 Agent 模型章。）

MCP 规范里 resources 和 tools 是两个不同的模型：

  • tools 是 model-controlled（模型自己决定什么时候调）。
  • resources 是 application-driven（host 应用决定怎么用，例如树形 picker 让用户选择要带入 context 的文件）。

规范原话（https://modelcontextprotocol.io/specification/2025-06-18/server/resources，访问于 2026-04-19）：

Resources in MCP are designed to be application-driven, with host applications determining how to incorporate context based on their needs.

Claude Code 是个 CLI，没有 resource picker UI。如果按规范建议"host 决定"硬塞——每次启动把所有 resource resources/list 完自动注入 system prompt——context 一眨眼就炸了。

源码里的做法是换一条路：不把 resources 自动注入，而是给模型两个元工具，让它自己按需列和读。

  • ListMcpResourcesTool（src/tools/ListMcpResourcesTool/ListMcpResourcesTool.ts:40-123）：可选 server 参数过滤，返回 {uri, name, mimeType?, description?, server}[]。背后 fetchResourcesForClient 带 size=20 的 LRU cache（src/services/mcp/client.ts:1724-1726），在 onclose 和 resources/list_changed 通知时失效。
  • ReadMcpResourceTool（src/tools/ReadMcpResourceTool/ReadMcpResourceTool.ts:49-158）：传 server + uri，发 resources/read。

隐藏细节（src/tools/ListMcpResourcesTool/ListMcpResourcesTool.ts:40-123 / src/services/mcp/client.ts:1724-1726）：MCP resources 不会 inject 到 system prompt，而是始终 on-demand——模型必须显式调 ListMcpResources/ReadMcpResource 才拿得到。好处是 context 不会被 resources 撑爆，代价是模型要自己判断"我现在需要列一下外部资源"。这个选择和 MCP 规范"application-driven"的建议方向相反（规范鼓励 host 主动管 resource 用法），因为 Claude Code 没有 picker UI，只有 Agent Loop 这一个消费方——把决策交给模型反而更简单。fetchResourcesForClient 的 LRU cache 在 resources/list_changed 通知时失效，所以 server 新增资源是能感知的，只是仍然要模型主动 re-list 才会拿到。

ReadMcpResourceTool 里有一段值得单独看——对 binary blob 的处理：

MCP 规范允许 resource 返回任意 mimeType 的二进制 blob（base64 编码）。塞进 agent context 没用——模型看不懂一堆 base64。这里的处理是拦截 blob 字段落盘：写成带 mime 扩展名的本地文件，返回路径给模型。模型拿到 blobSavedTo: /tmp/.../mcp-resource-...jpg 之后可以用 Read 或 Bash 工具处理。这是协议层 blob 到 agent context 的 narrow waist——tool call 结果里永远只传 text 或 file path。

7. MCP 认证：把 OAuth 包装成一个伪工具¶

remote MCP server 通常要 OAuth。如果是 IDE 插件或桌面客户端，OAuth 流无非就是开浏览器→跳 authorization URL→等回调。问题是 Claude Code 的 agent loop 里只有"工具调用"这一种和外部世界交互的原语——不存在"这里停一下等用户浏览器回来"这种事件。

src/tools/McpAuthTool/McpAuthTool.ts 的设计是：当 server 处于 needs-auth 状态时，给这个 server 插入一个伪工具 mcp__<server>__authenticate，工具的实现就是 OAuth 流。

用设计取舍的话来说：

  • 成本：Tool 的生命周期变复杂了。以前一个 Tool 从注册到卸载是静态的，现在有"伪 Tool 在运行时被真 Tool 批量替换"这一种过渡。需要前缀匹配批量 reject 再 concat 的逻辑（src/tools/McpAuthTool/McpAuthTool.ts:149-152，权限对 MCP 伪工具走 behavior: 'allow' 的短路也详见 ch.09）。
  • 收益：Agent Loop 完全不感知 OAuth。模型看到的永远是"工具调用，有返回值"。auth 失败就是普通的 tool error，模型可以走"工具报错了→告诉用户"的既有路径。整个 auth 子系统不需要自建事件总线。

OAuth 实现本身在 src/services/mcp/auth.ts（2465 行），重点：

  • ClaudeAuthProvider 实现 MCP SDK 的 OAuthClientProvider 接口。
  • performMCPOAuthFlow（src/services/mcp/auth.ts:847）跑 discovery → authorization URL → 本地 loopback 起一个一次性 HTTP server 等 callback → exchange code → 存 token（走 secureStorage，macOS keychain / Windows credential manager / Linux keyring）。
  • 支持 step-up auth：403 带 WWW-Authenticate insufficient_scope 时自动升级 scope 再走一次。
  • XAA（Cross-App Access，基于 SEP-990）是 Anthropic 内部的扩展，src/services/mcp/xaa.ts / xaaIdpLogin.ts 实现，允许共享 IdP token 跨 MCP server 使用。本章不展开（公开文档未找到）。

隐藏细节（src/services/mcp/auth.ts:467-576，ClaudeAuthProvider.saveTokens at :1704）：MCP OAuth token 的生命周期和 session 解耦——token 写进 OS 钥匙串（macOS Keychain / Windows Credential Manager / Linux keyring）后没有 TTL，没有"session 退出自动清理"这一步。清除路径只有一条：显式调 revokeServerTokens(serverName, ...)（例如 /mcp UI 里的 "Clear Auth"），它会先 RFC 7009 best-effort 服务端吊销，再 clearServerTokensFromLocalStorage 抹掉本地；除此之外 token 会一直留在钥匙串里，跨 CLI 多开共享。产品层面你感知不到，但如果你换了一台机器、改了账号、或者重装 CLI，旧 token 可能仍在钥匙串里，除非手动清。

两个设计点：

有意不再 re-expose MCP 工具。注释 // TODO: Also re-expose any MCP tools（62、103 行）是在占位，说明未来可能做但目前没做。不做的理由：Claude Code 的 MCP server 暴露的是自己的 built-in 工具盒子，如果把外部 MCP 再转出去，接入方（IDE 插件、Cursor 等）拿到的是一个"套娃工具清单"，里面的 mcp__foo__bar 是 Claude Code 连着的 foo server 的工具——接入方并不需要。它应该自己直接连 foo。

outputSchema 兼容性坑。MCP SDK 要求 outputSchema 根是 type: "object"。Claude Code 内部很多工具用了 z.union / z.discriminatedUnion，转 JSON Schema 后是 anyOf / oneOf，不合规。处理是直接 skip 这些工具的 outputSchema（70-81 行），附了 issue 链接 https://github.com/anthropics/claude-code/issues/8014（该 URL 由源码注释原样转载，Editor 核对当天 issue 页标题已变，无须据此做二次断言）。

隐藏细节（src/entrypoints/mcp.ts:119-120）：claude mcp serve 起的 server 在调用内建工具时，构造的 toolUseContext 里 mcpClients: [] / mcpResources: {} 是硬编码空的。即便父进程是一个 Claude Code session 自己连着一堆外部 MCP server，暴露给下游 host 的内建工具也拿不到这些 client 引用——配合 62 / 103 行的 // TODO: Also re-expose any MCP tools，构成一道双保险：外部 MCP 能力既不被 re-expose、也不被内建工具"间接透传"出去。

这一节讲到这里就够了。claude mcp serve 被谁消费（IDE 插件？Agent SDK？其他 host？）放到 Agent SDK 章（详见 ch.23）；Agent SDK 里还有个反向能力——createSdkMcpServer 让用户代码直接在内存里塞一个 MCP server 给同进程 Claude Code 用，也在 ch.23 讲。IDE / Chrome / Computer Use 这几个"自家 MCP consumer"的用户侧接入路径详见 ch.18；Skills 系统从 MCP 工具做包装的那一层详见 ch.10。

9. shims 下的两个 MCP：只讲怎么接入¶

shims/ant-computer-use-mcp/ 和 shims/ant-claude-for-chrome-mcp/ 是仓库的恢复期兼容层。package.json 里 "version": "0.0.0-restored" 已经标明。真实实现在 Anthropic 的私有仓（分别是 packages/desktop/computer-use-mcp 和 Chrome 扩展）。本章只讲这两个包作为 MCP server 怎么被连接起来、暴露什么工具目录。具体 Computer Use / Chrome 扩展能干什么、用户权限流程在 ch.18。

9.1 暴露的工具目录¶

脚注：上列工具目录是恢复仓 shim 里的声明。shim 的 createXxxMcpServer 函数只是打 warn 日志的 stub（shims/ant-computer-use-mcp/index.ts:120-144；shims/ant-claude-for-chrome-mcp/index.ts:89-113），真实工具实现在私有包里，数量可能有增减。

隐藏细节（shims/ant-computer-use-mcp/index.ts:120-144 / shims/ant-claude-for-chrome-mcp/index.ts:89-113）：shim 下的 createClaudeForChromeMcpServer / createComputerUseMcpServerForCli 是只写 warning 的空壳——它们返回的 server 对象实现了 MCP SDK 接口，但 tools/call 处理器永远 fallback 到"not implemented"分支。这意味着在恢复仓编译出来的 Claude Code 里，把 Chrome/Computer Use MCP "连上"是能成功的（in-process transport 不会失败），但真正跑工具会拿到空结果或错误。真实实现来自 Anthropic 私有包 @ant/claude-for-chrome-mcp / @ant/computer-use-mcp，本章贴的工具清单只是 shim 声明的形状约束，不是运行时行为（Chrome/Computer Use 的用户侧行为详见 ch.18）。

9.2 接入路径¶

对这两个 server，src/services/mcp/client.ts:905-943 走的是 5.4 节讲过的 in-process transport 分支：不 spawn 子进程、不走 stdio，createLinkedTransportPair 把 client 和 server 连在同一进程。Chrome MCP 的存在就是省掉 ~325MB 的子进程启动开销（注释直接写在 909 行）。

从本章视角讲清的点只有：它们是普通 MCP server，只不过 transport 用 in-process 代替了 stdio。工具调用链路跟任何外部 MCP server 完全一样（都走 JSON-RPC），只是 JSON-RPC 消息不过 pipe 过 microtask。

11. 可迁移的设计点¶

读完全章，有几个点值得带走用到自己的项目：

一、未知形状能力的适配：spread-and-override 模板。当你要接入 N 种外部能力、每种能力形状不同、但最终要被统一的内部接口消费——用一个基对象（MCPTool）定义共享字段（UI renderer、大小上限等），然后运行时 { ...base, ...perItemOverride } spread 出 N 个实例。主干代码只见内部接口，不感知适配层。

二、协议字段到内部语义 1:1 透传。MCP 规范 annotations（readOnlyHint / destructiveHint / openWorldHint）被 Claude Code 原样映射成 isReadOnly / isDestructive / isOpenWorld，没另起术语。两个系统的接口稳定性锚点就是规范字段名。你要接第三方协议时，尽量用规范里的字段名做内部方法名，换版本时兼容性最好。

三、副作用打包成一个 Tool。当主循环只有"工具调用"一种事件原语，所有需要异步完成的副作用（OAuth、安装依赖、跑 migration...）都可以包装成"一个会返回 URL 或其他 handoff 的 Tool"。上层完全不需要感知副作用的生命周期。Claude Code 的伪 authenticate 工具就是例子。

四、为 prompt cache 留稳定结构。内建工具作为连续前缀、外部工具独立排序后拼接的 assembleToolPool 策略，是"服务端 cache 设计向客户端传导约束"的典型。自己做 LLM app 时，工具列表、system prompt 各段的顺序一旦影响 cache breakpoint，就要把约束写在代码注释里（源码 354-361 行注释做了示范），避免被后人不知情重构掉。

五、薄 transport 抽象 + in-process 旁路。MCP SDK 的 Transport 接口抽象够薄（start/send/close/onmessage/onerror/onclose），Claude Code 用 50 行就实现了 InProcessTransport，省掉 spawn+IPC 开销。设计协议时把"传输层"抽象得薄一点，用户就能拿你的客户端做异地部署、进程内集成两种截然不同的集成方式。

六、伪 Tool 按名前缀批量替换。配合第三点，伪 Tool 和真 Tool 共享 mcp__<server>__ 前缀，重连成功后 reject(tools, t => t.name.startsWith(prefix)) 批量剔除伪的再 concat 真的。不需要额外事件或生命周期钩子——前缀就是替换 key。这种"约定好前缀 + 批量 reject-and-replace"的状态迁移在任何需要"占位→真实"切换的场景都能抄。
