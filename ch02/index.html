ch.01 把能力清点完了。这一章换视角：挑 5 个端到端的真实场景，看这些能力怎么配合。本章不展开任何模块的实现，触到的地方一律标"（详见 ch0X）"；重点是"胶水"——哪段代码把几件事串成一件事。

2.1 为什么单开一章讲场景¶

Claude Code 单个能力拿出来讲不稀奇：开一个 TUI、实现 tool use、装个 git worktree。稀奇在于，同一个二进制要把"用户选中 VS Code 里几行代码"、"在终端让 sub-agent 去 worktree 实现功能"、"下班把 session 推到云上接着跑"、"明早九点 cron 拉 CI 状态提醒"这些事塞进同一条 Agent Loop。

组装端的代码体量很小，但位置讲究。每个场景里真正值得抄的不是某个工具本身，而是某一条"跨模块的粘合路径"——例如"cron fire 把 prompt 扔进同一条命令队列，用 isMeta:true 把它藏起来"。这类粘合层在单章里最容易被忽略，所以把 showcase 单独拎一章。

挑选原则：

  1. 每个场景至少串三个模块，否则留给模块章讲。
  2. 每个场景有公开的真实使用佐证（官方文档 / Anthropic 博客 / 开发者分享）。
  3. 只讲粘合设计，不讲实现。

2.2 场景一：Review my PR¶

用户输入：

用户看到的节点：进度条显示 reviewing pull request；片刻后 Claude 跑一串 gh 命令（每条要点一次权限确认，除非已加白名单）；最后返回分段评论。如果用户当时在 plan mode，会先被问一次"Exit plan mode?"。

内部怎么拼起来：

  • /review 本身是 type: 'prompt' 命令，不渲染任何 UI；它只返回一段模板文本作为新一轮用户输入：

    模板指令让模型依次跑 gh pr list / gh pr view <n> / gh pr diff <n>（同文件 9-31 行），然后给结构化 review。

  • Agent Loop（详见 ch.03）接管后，模型的每次 gh 调用都走 Bash 工具，触发 permission 检查（详见 ch.09）。如果 gh 没在 allowlist，用户得按 y 放行一次。
  • 若当前在 plan mode，情况变得微妙。ExitPlanModeV2Tool 的 validateInput 会拒绝非 plan 模式下调用自身；但反过来，plan mode 对所有写操作和大部分 Bash 命令设 ask（详见 ch.05、ch.09）。也就是说：plan mode 下 /review 会先被 ExitPlanMode 的审批卡住，让用户确认"确定要从只读切到执行吗"，再才跑 gh pr diff。
  • Anthropic 把"多 agent 并行跑 review"放在云上 /ultrareview 与 GitHub App 里。官方博客描述的这条多 agent 链路，原话是 "The agents look for bugs in parallel, verify bugs to filter out false positives, and rank bugs by severity"（来源：https://claude.com/blog/code-review，访问于 2026-04-19）。仓库里的 /ultrareview 对应 src/commands/review.ts:48-53，是唯一进云端沙箱的入口。本节讲的是 local /review，两条路径共用命令名家族，但实现互不重叠。

这个场景跑通是因为：一条命令可以"什么都不做"，只往对话里贴一段内置 prompt。剩下的一切（git、Bash 权限、plan mode 门控、输出格式）都由 Agent Loop 自己决定。没有任何"review 专属"代码路径；也因此本地 /review 只有 50 行。

隐藏细节（src/commands/review.ts:33-42 + src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts:195-219）：在 plan mode 下输入 /review 1234，触发的不是 gh pr diff 被直接拦截，而是模型先尝试 ExitPlanMode、validateInput 检查 mode === 'plan' 通过后走 checkPermissions 返回 behavior:'ask'，弹出"Exit plan mode?"对话框。用户看到的感觉是"怎么问我退出 plan 了"，但其实是审批对象从 Bash 变成了 plan 退出。加了 Bash(gh *) allowlist 也救不了这条，因为它拦的是 plan mode 的 mode-change，不是 shell。

2.3 场景二：Overnight task with cron¶

用户输入（睡前）：

第二天早上打开终端，REPL 里多出几条"Running scheduled task" 的标记，每条后面是模型对 CI 的判断。

用户看到的节点：cron job 确认消息（带 ID 和 "Auto-expires after 7 days"）；之后每次 fire 时屏幕上出现一条 Running scheduled task (Apr 14 9:00am) 提示行，然后是模型的回复。若用户不在场，Notification hook（详见 ch.14 hooks）可把一条 desktop toast 推到系统。

内部怎么拼起来：

  • /loop 30m ... 会让模型调 CronCreate 工具（详见 ch.13 cron 的工具家族）：

    门控见 src/tools/ScheduleCronTool/prompt.ts:36-45：编译期 feature('AGENT_TRIGGERS') 与运行时 GrowthBook tengu_kairos_cron（默认 true）任一缺席都会让 cron 全家消失。

  • REPL 挂了一个轮询器 useScheduledTasks：scheduler tick 每秒检查一次到期任务，fire 时不直接发请求，而是把 prompt 塞进命令队列：

    priority:'later' 保证它排在用户刚敲的 prompt 后面（详见 ch.16 background tasks 里的命令队列）；isMeta:true 让它不污染可见历史；workload: WORKLOAD_CRON 被写进 API 请求的 billing header，用来在容量紧张时给 cron 请求降级。

  • cron 触发的回合会产生一条可见的 Running scheduled task (timestamp) 消息打头（useScheduledTasks.ts:110-113），后面才是模型的实际回复；这解决了"用户早上看屏幕分不清哪段是昨晚跑的、哪段是今天接着聊的"。
  • 若任务在后台 Bash 里触发副作用（例如 gh run view --log 比较长），结果会作为一种特殊的 queued command 以 mode: 'task-notification' 注入：

    collapse 逻辑（src/utils/collapseBackgroundBashNotifications.ts:28-70）会把连续的完成通知合成一条"N background commands completed"——否则早上打开终端会看到一屏的完成消息。

官方行为保证：

  • "The scheduler checks every second for due tasks and enqueues them at low priority. A scheduled prompt fires between your turns, not while Claude is mid-response"（https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）。
  • "No catch-up for missed fires. If a task's scheduled time passes while Claude is busy on a long-running request, it fires once when Claude becomes idle, not once per missed interval"（同页）。

社区印证：Rick Hightower 的文章 "Put Claude on Autopilot: Scheduled Tasks with /loop and /schedule built-in Skills"（https://medium.com/@richardhightower/put-claude-on-autopilot-scheduled-tasks-with-loop-and-schedule-built-in-skills-43f3be5ac1ec，访问于 2026-04-19）专门给出了 overnight polling 的配方。

跨章边界：本节讲的是 session-only 的 /loop——关掉终端就随 REPL 一起失效。官方页面把 /loop 与 durable /schedule（写 .claude/scheduled_tasks.json、跨会话存活）并列描述，二者实现路径不同：durable 侧的生命周期（持久化、7 天过期、teammate 禁用）留给 ch.13 cron 展开。

这个场景跑通是因为：cron 和"用户输入"走同一条 REPL 命令队列。cron 不是特权通道；它只是一个"模型自己输入自己"的特殊 enqueue，于是所有下游组件（permission、hooks、transcript）都自动兼容。

隐藏细节（src/hooks/useScheduledTasks.ts:71-82）：cron 触发的 prompt 进 API 时带 workload: WORKLOAD_CRON，服务端在流量紧张时会给这类请求排到更低 QoS。用户在 REPL 里完全看不到这条标记，但这是"半夜 cron 任务偶尔比预期慢"的根本原因之一——不是 cron 自己慢，是它被显式降级了。

隐藏细节（src/tools/ScheduleCronTool/CronCreateTool.ts:107-114）：durable:true（让任务写 .claude/scheduled_tasks.json，跨会话存活）对 teammate 一律禁用，返回 errorCode:4。原因是 teammate 不持久化，durable 会让 agentId 指向一个不存在的 teammate。产品 UI 里 /schedule 看不出这层限制，但若用 sub-agent 帮你排 cron 就会吃到。

隐藏细节（src/tools/ScheduleCronTool/CronCreateTool.ts:97-104）：每个 session 有硬上限 MAX_JOBS（官方文档给的数是 50），超过就返 errorCode:3，错误文案是 "Too many scheduled jobs (max ${MAX_JOBS}). Cancel one first."。REPL 用户只会看到这条报错，不会看到具体阈值——除非翻源码。对用 /loop 密集排各种轮询的用户，这条比 durable-teammate 限制更常撞到，cron 密度设计要预留冗余。

2.4 场景三：Plan → Worktree sub-agent 落地¶

用户输入：

用户看到的节点：底部指示器从 ⏸ plan mode on 切回 default；Ctrl+G 打开编辑器改 plan；确认对话 "Exit plan mode?"；主 agent 输出两个 AgentTool 调用，每个 agent 先跑一条 git worktree add；最后回到主 agent 汇总。

内部怎么拼起来：

  • /plan 或 Shift+Tab 进入 plan mode（详见 ch.05 plan mode），src/commands/plan/plan.tsx:73-91 把当前 mode 存到 prePlanMode，再切到 plan。这一步会剥离危险 permission 规则（通过 prepareContextForPlanMode）；ExitPlanMode 时若恢复到 default 再把它们塞回来。
  • 用户确认后，ExitPlanModeV2Tool 的 call()（src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts:243-418）把 plan 写盘、改 mode、视情况走 teammate 的 mailbox approval 分支；非 teammate 会走本地 setAppState 分支。
  • 主 agent 决定拆两个 sub-agent 时，AgentTool 的 input schema 支持 isolation: "worktree"（源码实际是 "external" === 'ant' ? … 三目，下面贴的是 external 分发在运行时命中的分支）：

    每个 sub-agent 实际调 createAgentWorktree（详见 ch.04 sub-agents、ch.06 worktree）；worktree 本体创建逻辑见 src/tools/EnterWorktreeTool/EnterWorktreeTool.ts:77-118，顺便清 claudemd / plansDirectory 缓存、process.chdir、持久化到 session storage。

  • Worktree 清理策略：sub-agent 完成时若没改动自动删；有改动保留。这是官方文档承诺的："No changes: the worktree and its branch are removed automatically. Changes or commits exist: Claude prompts you to keep or remove the worktree"（https://code.claude.com/docs/en/common-workflows，访问于 2026-04-19）。
  • 护栏层：用户可以再加一个 PreToolUse hook（详见 ch.14 hooks），拦掉 sub-agent 里的高危 Bash。官方给过脚本模板：

    HOOK 事件枚举见 src/entrypoints/sdk/coreTypes.ts:25-53。关键承诺："PreToolUse hooks fire before any permission-mode check. A hook that returns permissionDecision: 'deny' blocks the tool even in bypassPermissions mode or with --dangerously-skip-permissions"（https://code.claude.com/docs/en/hooks-guide，访问于 2026-04-19）。

这个场景跑通是因为：plan → code 的切换点是一次性的"mode transition + 剥离/恢复 permission rules"，之后 sub-agent 各跑各的不互相干涉。粘合点有两个：

  1. plan 写到磁盘（getPlanFilePath(context.agentId)），sub-agent 能 Read 到同一份。
  2. AgentTool.isolation 把 worktree 的复杂清理周期藏进 sub-agent 生命周期——主 agent 根本不管。

2.5 场景四：IDE → CLI → Remote Control → 手机 push¶

用户流程：

  1. 在 VS Code 里选中 src/auth/login.ts 的 30-45 行，按 Option+K 把 @src/auth/login.ts#30-45 塞进 Claude 扩展的输入框。
  2. 改完扩展觉得不过瘾，在集成终端里敲 /remote-control 把当前 session 暴露到 claude.ai。
  3. 上楼拿手机继续对话；Claude 跑一个长测试后需要确认，push 推到手机，用户点通知继续。

用户看到的节点：VS Code 里的 at-mention、Option+K 自动带行号；/remote-control 后底部出现 session URL / QR code；手机端出现推送。

内部怎么拼起来：

  • IDE 的选区事件是 MCP notification（详见 ch.12 MCP），useIdeSelection 订阅：

    @-mention 走类似通道：useIdeAtMentioned.ts:16-27 订阅 at_mentioned，在 58-60 把 VS Code 的 0-index 换成 1-index。

  • /remote-control 命令本身是薄壳：

    核心逻辑在 src/bridge/ 目录（详见 ch.17 remote sessions）。/session（别名 /remote）在 getIsRemoteMode() 为真时才显示 QR（src/commands/session/index.ts:1-14）。

  • 从手机推回来的输入会经过 isBridgeSafeCommand 过滤：

    local-jsx 全部被静默丢弃（理由：它们渲染 Ink UI，在手机上无意义）；local 型命令要显式加入 BRIDGE_SAFE_COMMANDS（src/commands.ts:651-660）——目前只有 /compact /clear /cost /summary /release-notes /files 六条；prompt（skill）默认通过。

  • Push 通道：当 feature('KAIROS') || feature('KAIROS_PUSH_NOTIFICATION') 时注册 PushNotificationTool（ch.01 §1.5.2）。官方承诺："Claude decides when to push. It typically sends one when a long-running task finishes or when it needs a decision from you to continue. You can also request a push in your prompt, for example notify me when the tests finish"（https://code.claude.com/docs/en/remote-control，访问于 2026-04-19）。

这个场景跑通是因为：三种 surface 不是 point-to-point 连接，而是"每种 surface 都把输入折叠成 REPL 的 prompt / tool_result"再入队。IDE 扩展其实只是自己跑了一个 MCP server（官方文档：the extension "runs a local MCP server that the CLI connects to automatically"，https://code.claude.com/docs/en/ide-integrations 访问 2026-04-19），CLI 用 MCP notification 订阅选区；Remote Control 本质是"claude.ai 的输入流转发给本地 CLI 的 stdin"。

隐藏细节（src/commands.ts:672-676）：手机上敲 /model 不会报错，也不会切换模型；它会被 isBridgeSafeCommand 静默吞掉（local-jsx 型命令不在任何白名单）。用户通常的反应是"没反应"。这条过滤规则在 PR #19134 是全量 block，后来才放宽到这个双层白名单。要从 mobile 添加一条安全命令，必须进 BRIDGE_SAFE_COMMANDS 显式加一行。

隐藏细节（src/hooks/useIdeSelection.ts:92-108）：在 VS Code 里选区停在行首（end.character === 0），行数会被 -1。这是把 VS Code 原生 Range 语义（"选择到下一行的开头算选了下一行"）调成用户直觉语义（"我光标还在上一行末尾，下一行没选"）。对 IDE 侧 UI 无影响，但影响 @file.ts#5-10 这种 #range 里的 10 到底是哪个值。

2.6 场景五：Web session → /teleport 回本地¶

用户流程：

  1. 下班前在终端：claude --remote "Run the migration rehearsal and report results"——云端 session 启动，clone repo、跑任务。
  2. 第二天早上终端打开，claude --teleport 或在会话里 /tp。picker 里选中那个 session，本地 git 自动 fetch + checkout 对应分支，transcript 被还原。
  3. 继续对话——Claude 没丢 context，但现在跑在本地机器上。

用户看到的节点：stash uncommitted changes 的提示（如有）；transcript 里出现 "Session resumed" 的 meta 消息；分支已切换。

内部怎么拼起来：

  • --remote 云端起 session（详见 ch.17 remote sessions）：官方承诺 "This creates a new cloud session on claude.ai. The session clones your current directory's GitHub remote at your current branch, so push first if you have local commits"（https://code.claude.com/docs/en/claude-code-on-the-web，访问于 2026-04-19）。这条路径在仓库里由 teleportToRemote（src/utils/teleport.tsx，供 AgentTool(isolation:'remote') 和 --remote 共用，见 src/tools/AgentTool/AgentTool.tsx:39 的导入）支撑。
  • --teleport 拉回：核心函数

    做三件事：fetch session logs（/v1/sessions/{id}/events）、拿 branch、本地 git fetch && git checkout。完成后注入一条 meta 用户消息给模型：

  • Teleport 的前置条件（官方）："Clean git state ... Correct repository ... Branch available ... Same account"（同 URL）。其中 "clean git state" 触发 stash 提示；"branch available" 要求云端推过分支，不然本地 fetch 不到。
  • 仓库里的 /teleport 命令目录是 stub（src/commands/teleport/index.js:1，export default { isEnabled: () => false, isHidden: true, name: 'stub' }）——真实行为走 CLI flag --teleport 与 src/utils/teleport.tsx 模块。这是 source-map 还原遗留的缺口（ch.01 §1.11）。

这个场景跑通是因为：云端 session 和本地 session 用同一个 SDK message 格式（src/entrypoints/sdk/），transcript 可以在两个进程之间二进制转发。分支切换是 git 的事；context 延续是 transcript deserialize 的事；两件事由一个 CLI flag 串起来。

隐藏细节（src/utils/teleport.tsx:1200-1222 与调用点审计）：archiveRemoteSession 是"拉回本地 → 归档云端 session"的闭环关键，但它只在 RemoteAgentTask 完成（src/tasks/RemoteAgentTask/RemoteAgentTask.tsx:841）和 ultraplan 本地执行分支（src/commands/ultraplan.tsx:157 与 395）里被调用。--teleport / /teleport 的 pull-down 路径不调它。结果是：用户把云 session teleport 回本地继续干了，云端那份 session 在 claude.ai 仍然显示为 idle，并不自动归档；要么在 web UI 里手动 archive，要么用 ultraplan/RemoteAgent 路径进行生命周期管理。对用户的直接影响：cloud rate limit 额度持续被占，直到用户记得回去点 archive。

2.7 横向看：这 5 个场景共同靠什么撑起来¶

归纳这 5 个场景的共同胶水，比逐个研究场景更有参考价值：

  1. 一条统一的命令队列是中枢。用户敲的 prompt、cron fire 的 prompt、task 完成通知、bridge 推下来的 /compact、teleport 拉回时注入的 meta 消息——全部统一成 queued command 排队进 REPL。模式字段区分用途（'prompt' / 'task-notification' / 'queued_command'，见 src/utils/attachments.ts:543-559、1044），priority 决定顺序（'later' vs. 默认）。任何新输入来源只要会自己 enqueue 一次，就自动享有 transcript、hooks、permission、token 计费的全部下游链路。
  2. permission 机制是跨场景的统一守门员。plan mode 的 ExitPlanMode 是 permission 事件、sub-agent worktree 里的 PreToolUse hook 是 permission 事件、bridge 白名单也是 permission 决策（只是在 command 层）。没有为任何场景开特例通道。
  3. feature flag 三层叠加决定"这台机器能看到什么"（ch.01 §1.3）。showcase 里每个场景都踩到至少一层 gate：AGENT_TRIGGERS（cron）、BRIDGE_MODE（remote control）、KAIROS 族（push、sleep）。这是 Anthropic 把"未 GA 功能"和"私有/公共账户差异"统一塞进一个二进制的成本，阅读源码时必须时刻意识到。
  4. 还原仓库的缺口不是致命的。/teleport 命令本体是 stub（src/commands/teleport/index.js:1），但背后的 teleport.tsx 是完整的；用户照样能通过 --teleport CLI flag 走完全流程。写本章时用"CLI flag + 真实模块"的组合来还原行为，而不是在 stub 上编故事。

如果只能带走一句：showcase 之所以能组合，是因为每个新入口都把自己降级成了"往队列里塞一个标了 priority 的输入"。没有任何 feature 自己开通道。
