17.1 用户看到什么¶

Claude Code 里"跨机器"有四个入口，用户感知不同：

  1. claude --remote "fix the auth bug"。本地 CLI 里按回车，终端里打一条 "Created remote session ... View: https://claude.ai/code/<id> ... Resume with: claude --teleport <id>"（src/main.tsx:3444-3446），然后如果 TUI 特性门是关的，claude 进程直接退出；如果打开的话则进入一个只做前端的本地 REPL，真正跑 agent 的是 Anthropic 云里的沙箱容器。你在本地按 Ctrl+C 发出去的是一个 interrupt 信号，本地不跑任何工具。本书把这条路径叫 CCR 云 session。
  2. Remote Control（源码里多叫 Bridge）。三个入口指向同一条路径：claude --remote-control（长 flag）、claude --rc（别名，src/main.tsx:3873-3874）、claude remote-control 子命令（src/main.tsx:4329、src/commands/bridge/index.ts:14）。终端停留在一个 server 界面，显示一个 URL 和 QR 码。你可以继续在终端里敲字，也可以用 claude.ai/code 或手机 App 往同一个 session 下消息。此时agent 跑在你这台机器上，手机只是 UI。斜杠命令 /remote-control 也进同一条路径。
  3. claude --teleport <id>（或 /teleport）。从云 session 拉取对话历史 + 切换到对应 git 分支，然后在本地开一个新的 CLI 进程继续。云端那个 session 没动。本章把它视为一个动作（见 §17.7），而不是第五种形态。
  4. createDirectConnectSession(...)（SDK / headless runner 用，下文称 DirectConnect）。连到一个自建的 HTTP + WebSocket 服务器，协议和云 session 不一样但数据结构一样。

官方 overview 表格把这几条概括为 "Continue a local session from my phone" / "Start a task locally, continue on mobile" 等用例（来源：https://code.claude.com/docs/en/overview，访问于 2026-04-19）。

仓库里还有一条路被恢复成了 shim：claude ssh / useSSHSession。接口齐全，实现留空（src/ssh/createSSHSession.ts:1-6、src/ssh/SSHSessionManager.ts:1）。本章会从 hook 端反推它的预期协议，但不把 shim 当真实实现讲。

17.2 为什么挑这个设计出来讲¶

本章 5 页篇幅留给一件事：

permission 反向回路。工具在 A 机器执行，permission UI 在 B 机器弹出，用户在 B 按下 allow，决定如何回流到 A，让那条调用真的在 A 上跑起来。

这条回路是四种形态共享的一层，也是决定"permission 模型能不能跨机器保真"的关键。Claude Code 的做法是让远端 agent 继续走自己的 can_use_tool 回调，不把它改造成 RPC——代价与收益见 §17.11。permission 模型本身（ask / allow / deny 的语义、mode 状态机）不在本章，见 ch.09。

其余形态差异只起辅助作用，作为 permission 回路的几种变体出现。control_request / control_response 这套控制面协议同源于 Agent SDK（见 ch.23）；本章描述的是它被 REPL 端复用的切面。

17.3 Remote session 的四种形态（先把概念对齐）¶

恢复后的仓库里，"远程"一词所指的几个路径必须先对齐名字再讨论。下表把代码位置、agent 位置、UI 位置三者拉清楚：

名字（本书用法）Agent 跑在哪UI 在哪主要代码
CCR 云 sessionAnthropic 云容器本地 REPL 或 claude.ai/codesrc/remote/、src/hooks/useRemoteSession.ts
Bridge（Remote Control）本地 CLIclaude.ai/code + 手机src/bridge/、src/hooks/useReplBridge.tsx
DirectConnect自建 HTTP+WS server本地 REPLsrc/server/、src/hooks/useDirectConnect.ts
SSH session（shim）远端 shell本地 REPLsrc/ssh/、src/hooks/useSSHSession.ts

Teleport 是一个动作，不是一种形态。 官方文档写得很清楚："--teleport is distinct from --resume. --resume reopens a conversation from this machine's local history and doesn't list cloud sessions; --teleport pulls a cloud session and its branch."（来源：https://code.claude.com/docs/en/claude-code-on-the-web，访问于 2026-04-19）。它是"从 CCR session 的 transcript 拉历史 → 本地新 CLI 进程做 resume"这一条动作，§17.7 单独处理。

另一个容易混的点：官方文档明示 --remote 和 --remote-control 是两码事：

--remote creates cloud sessions. --remote-control is unrelated: it exposes a local CLI session for monitoring from the web. —— https://code.claude.com/docs/en/claude-code-on-the-web

仓库里的证据：--remote 的 main.tsx 入口用的是 createRemoteSessionConfig + useRemoteSession（src/main.tsx:3473, 3506），走 src/remote/；--remote-control 走 useReplBridge → initReplBridge（src/hooks/useReplBridge.tsx:149-150），走 src/bridge/。两个完全不同的客户端代码路径，只在 sdkMessageAdapter.ts 这个翻译层共用。

17.4.3 createSyntheticAssistantMessage + createToolStub¶

REPL 的 ToolUseConfirm 结构要求一条 AssistantMessage 作为"上下文"。远端模式下本地没有真实的 assistantMessage（那条消息是在 CCR 容器里由模型生成的），但 UI 不关心，随便造一个能满足类型约束的就行。这是一个典型的"协议上的合成数据"用法——UI 复用度换来的代价是一行假的 uuid。

createToolStub（remotePermissionBridge.ts:53-78）解决另一个问题：远端挂了本地不认识的 MCP 工具时，用一个最小 Tool 对象让 UI 能渲染 confirm 框：

这个 stub 的 call 从不会触发（工具执行发生在远端容器），它只是为了通过本地类型系统。

17.4.4 convertSDKMessage —— SDK 形状到 REPL 形状的薄翻译¶

这个 switch 是 useRemoteSession、useDirectConnect、useSSHSession 三个 hook 的公共翻译器（sdkMessageAdapter.ts:22-27 注释直接点名）。这意味着无论消息来自 CCR、direct-connect server 还是 SSH 里的 stream-json，REPL 的 Message[] 侧看到的都是一样的形状。

17.4.5 BoundedUUIDSet —— echo 去重的环形 UUID 集¶

本地发 user message 给远端时，远端会把它回显到 WS 上（server 广播 + worker 写路径各回一次）。回显要过滤掉，否则用户会看到自己打的字两份。最朴素的"发的时候 add，收到 match 就 delete"写法有个坑：同一个 UUID 会被不同链路各回一次。

一个定长环形 buffer + 一个 Set。has 不改状态，所以同一 UUID 的多次 echo（server 广播路径 + worker 写路径各一次）都会被匹配；淘汰只发生在 ring 写满回卷时。useRemoteSession 用的是 new BoundedUUIDSet(50)（useRemoteSession.ts:137），最近 50 条本地发出的 user message 内的回显会被过滤，更早的由用户自己辨识。

17.5 关键流程之一：Remote session 的主干¶

以 claude --remote "..." 启动的 CCR 场景为例。

create session：main.tsx:3430 调用 teleportToRemoteWithErrorHandling，内部拨打 POST /v1/sessions，带上当前 git 仓库信息作为 session_context.sources（src/utils/teleport.tsx:867-879）。如果检测到本地 repo 没 GitHub 远端或 CCR 无权 clone，会切到 "git bundle" 模式——本地跑 git bundle --all，通过 Files API 上传，CCR 容器从 bundle clone（teleport.tsx:838-856）。

connect REPL：

launchRepl 把这个 config 交给 useRemoteSession hook。

订阅事件流：RemoteSessionManager.connect() → SessionsWebSocket.connect()（RemoteSessionManager.ts:108-141）。事件进 handleMessage（RemoteSessionManager.ts:146-184）：

  • control_request → handleControlRequest（见 17.6 节）
  • control_cancel_request → 从 pendingPermissionRequests 删除 + UI 消队
  • control_response → 只记日志（客户端不处理 server 的 ack）
  • 其他（SDKMessage 各 type）→ callbacks.onMessage

发用户消息：走 HTTP 而非 WS。manager.sendMessage → sendEventToRemoteSession → POST /v1/sessions/{id}/events（src/utils/teleport/api.ts:361-417）。请求体是一个 events: [userEvent] 数组，userEvent.uuid 由本地生成或由 caller 传入。

UUID 对齐：调用 sendMessage 时本地会先把 uuid add 进 sentUUIDsRef（useRemoteSession.ts:493），随后 onMessage 收到的任何 user 消息只要 uuid 命中就丢弃（useRemoteSession.ts:182-191）。

隐藏细节（src/hooks/useRemoteSession.ts:490-493）：sentUUIDsRef.current.add(opts.uuid) 必须在 await manager.sendMessage(...) 之前执行。WS echo 可以在 HTTP POST 的 promise resolve 之前就到达——这是一条 off-by-one 的 race condition，代码里用注释"Must record BEFORE the POST to close the race where the echo arrives before the POST promise resolves"锁死顺序。产品层只会看到"偶发的重复消息"，但根因就是这两行代码的先后。

渲染：convertSDKMessage → { type: 'message' | 'stream_event' | 'ignored' } → 针对 assistant 消息把里面的 tool_use 块 ID 加入 inProgressToolUseIDs（useRemoteSession.ts:289-305），让 UI 显示正确的 spinner 状态。注意这里和本地 session 的差别：本地是 toolOrchestration.ts 维护这组 ID，远端 session 因为没真的执行工具，要 hook 手动维护。

17.6 关键流程之二：permission 反向回路（本章核心）¶

17.6.1 问题¶

场景：agent 在 A 机器执行工具（CCR 容器里）。工具有 permission 需求（ch.09）。用户在 B 机器看（本地 REPL）。B 按 allow，怎么让 A 上那条工具调用真的跑？

直觉选项：

  1. RPC。A 暂停，远程调用 B 说"我要 Bash 'rm -rf foo' 行吗"，B 弹框、回复，A 继续。
  2. 事件流 + 对齐 ID。A 发一条 control_request，B 把它 render 成本地熟悉的 confirm UI，B 按键后发一条 control_response，A 按 request_id 找到挂起的那次 can_use_tool。

Claude Code 选的是 2。选择背后的理由是让 A 侧代码复用度最大化——无论是本地 session、CCR 容器、还是 Bridge（含 daemon 子场景），agent 侧都只需要一个 canUseTool(tool, input) → Promise<Decision> 回调。回调内部的差异（本地弹 Ink UI 还是发 control_request）被 transport 层吃掉。

17.6.2 远端 → 本地¶

远端 claude 进程发 control_request（格式见 src/bridge/sessionRunner.ts:32-43，这是 Bridge 场景下解析子进程 stdout 的类型定义，但两边 wire format 一致）：

两件重要的事：

  1. 把 request 存进 pendingPermissionRequests，用 request_id 做 key——这就是反向回路的"对齐 ID"。
  2. 不认识的 subtype 必须明确回 error，否则 server 会一直挂着（和下文 Bridge 的 initialize-or-die 同源）。

隐藏细节（src/remote/RemoteSessionManager.ts:198-213）：handleControlRequest 对不认识的 subtype 必须主动回 error，否则挂在 CCR 那侧等 response 的 can_use_tool（或未来任何 control_request 子协议）会超时——产品层看不到"协议超时"，只会看到"远端 agent 停住不动"。这是一条对所有 transport 都生效的契约：CCR、Bridge、DirectConnect 在收到未知 subtype 时都走"显式回 error"，SSH shim 没实现但在 hook 端预留了同一个回调签名。换句话说，control_request 协议是跨四种 transport 的共享语义层，谁接入谁就要承担"必须回话"的义务。

17.6.3 本地 → 远端¶

respondToPermissionRequest 做的事很直白：

响应走 WS 的 send()（SessionsWebSocket.ts:328-336），不走 HTTP。原因是响应要同步喂回挂起的 can_use_tool，HTTP 里再绕一次会拉长 tail latency。

17.6.4 Bridge 方向的对称¶

注意"Bridge"这个名字——它不是 MCP bridge，和 ch.12 里讲的 MCP server / MCP client 那个 RPC 面板没有继承关系。这里的 Bridge 是"把本地 CLI session 桥到远端 UI"的代号，在源码里是 src/bridge/ 目录名。

Bridge（本地跑 agent，远端 UI）做完全对称的事：本地 agent 的 can_use_tool 回调照常触发，回调里本地负责把请求发出去：

sendRequest 最终走 BridgeApiClient.sendPermissionResponseEvent（src/bridge/types.ts:153-158）的反向调用——客户端 POST 一条 event 到 session events API，服务器再推给所有订阅者（claude.ai/code 前端）；用户在浏览器点 allow，浏览器发 control_response 事件给 server，server 再通过 WS 回给本地 Bridge 进程，进程上查表、唤醒挂起的 can_use_tool，agent 继续。

两方向的回路结构一致：request_id 对齐，control_request/control_response 格式相同，只是推送方向相反。这让 Claude Code 的 permission 代码"两边都能当客户端"。弹窗弹在哪一侧取决于形态：CCR 里 agent 在云、弹窗在本地 REPL（或 claude.ai/code 前端，取决于哪端先订阅到事件）；Bridge 里 agent 在本地、弹窗在远端 UI（浏览器 / 手机 App）。同一份 can_use_tool 回调被两种形态共享，它不关心自己的 prompt 最终显示在哪块屏幕上，这也是 permission mode 能跨端（ch.09）保真的前提。

17.6.5 Cancel 路径¶

一个容易漏的 case：用户在 claude.ai/code 里关掉了 permission prompt 的浏览器标签页，或者 agent 因别的原因撤销了请求。服务端这时发 control_cancel_request：

hook 侧把对应 item 从 toolUseConfirmQueue 里剔除（useRemoteSession.ts:407-416）。这一层"取消"也走同一条反向回路，没有第二套协议。

17.6.6 设计取舍¶

这条回路的三个关键约束：

  1. 消息格式两向一致（request + response 都是 control_request / control_response，只是谁发谁收不同）
  2. 用 request_id 而不是队列位置或 tool_use_id 做对齐——tool_use_id 可能被重试、可能被同一 turn 内多次询问
  3. pendingPermissionRequests Map 生命周期与单条 request 严格绑定：存储在 handle 开始、删除在 response 结束或 cancel 时——不是"会话级"的表，这避免了跨 turn 的脏数据

换一种做法会怎么样？如果走 RPC——比如"agent 直接调用本地 HTTP 端口上的 prompt 服务"——会被一堆问题打穿：本地要开端口、断线后 RPC 挂起、移动端根本没端口、和 permission mode 的状态机耦合。事件流对齐 ID 的代价是：两侧都得维护 pendingRequests 表以及"request → response 绑定 + cancel 清理"的状态机（CCR 侧在 RemoteSessionManager，Bridge 侧在 bridgeMessaging），而且两份实现必须同步演化。Claude Code 选择承担这份维护成本，换来"同一段 agent 代码四种 transport 都能跑"。

17.7 Teleport 的确切语义¶

从仓库里看 teleport 的主入口：

返回类型是：

即 teleport = "拿 transcript + 可选 branch 名"。

main.tsx 里的处理（main.tsx:3510-3585）把这两件东西变成：

  1. checkOutTeleportedSessionBranch(branch) 切到对应分支（src/utils/teleport.tsx:315-343）
  2. processMessagesForTeleportResume(log, branchError) 把 transcript 当作 resume 的 initialMessages（teleport.tsx:301-308）

然后本地是一个新的 CLI 进程，从这些消息继续。云端的 CCR session 没有被 archive。

隐藏细节（src/utils/teleport.tsx:430-503 不调用 src/utils/teleport.tsx:1200-1223 的 archiveRemoteSession）：teleport 完成后，云端 CCR session 仍然"alive"。archiveRemoteSession 这个函数确实存在，但它只被 src/commands/ultraplan.tsx（orphan cleanup）和 src/bridge/bridgeMain.ts / replBridge.ts（Bridge teardown）调用，teleport resume 链路里没有任何一环触发它。产品层看到的结果：claude --teleport <id> 之后，去 claude.ai/code 那个 session 还在原位；如果用户同时在手机和桌面各跑一份续写，理论上可以分叉。动词 "pulls"（而不是 "migrates"）就是 API 契约这一侧的体现。

此外，transcript 本身是 snapshot + live 的拼接：teleportFromSessionsAPI 先通过 getTeleportEvents / getSessionLogsViaOAuth（teleport.tsx:573-588）取一份历史快照，随后 CCR session 的 WS 订阅继续推 live 事件。CCR 的 transcript 不是纯流式（每条消息都要 replay 到位）、也不是纯 snapshot（不能只看快照就完事），而是这两者的接力。断线重连时依赖 snapshot 重对齐游标，而不是从 seq 0 重放。

官方文档和这个描述完全一致：

--teleport is distinct from --resume. --resume reopens a conversation from this machine's local history and doesn't list cloud sessions; --teleport pulls a cloud session and its branch. —— https://code.claude.com/docs/en/claude-code-on-the-web（访问于 2026-04-19）

动词 "pulls" 在这里是关键：取回一份，不是搬迁，不是复制两边双向同步。云端还在那里，本地开了个 CLI 续写。

teleport 还有几条前提条件值得一提（源码用 validateGitState 和 validateSessionRepository 各做一部分）：

  • Clean git working tree（无 uncommitted changes，除非接受 stash 提示）
  • 当前目录是 session 绑定的 repo（不同 host / 不同 owner/name 会被拒）
  • Branch 已经 push 到 remote（否则本地 fetch 失败）
  • 同一 claude.ai 账户

官方文档的 requirements 表格与代码一一对应（来源：https://code.claude.com/docs/en/claude-code-on-the-web）。

把 Teleport 和 Bridge 放一起：

同一 session 多端同步新 session，把旧 transcript 拿过来
Agent 在云--remote 跑 CCR + useRemoteSessionclaude --teleport <id>
Agent 在本地claude remote-control（Bridge）不适用

Bridge 是"同一 session 多设备"；Teleport 是"跨设备换新 session，喂同一段历史"。两者底层共享 /v1/sessions API 和 CCR session 基础设施（官方文档 troubleshooting 节明示："--teleport connects through the same Remote Control session infrastructure that cloud sessions use"），但用户语义是反向的。跨机 cost 归属在这两种场景下也不同（CCR 用量计到云端账号名下，Bridge 的 token 开销仍计到本地执行 agent 那台机器的账号，见 ch.22）。

17.8 关键流程之三：断线重连与 transport 抽象¶

17.8.1 CCR 侧的简单策略¶

handleClose 三路决策（SessionsWebSocket.ts:232-288）：4003 永不重连；4001（session not found）允许 3 次重试——注释说这是为了兜住 compaction 期间 session 的短暂"失联"（SessionsWebSocket.ts:22-26）；其他前序是 connected 且重试没超限就 2s 定长重试。

隐藏细节（src/remote/SessionsWebSocket.ts:258-272 vs :247-253）：4001 和 4003 是一对刻意不对称的 close code。4003 = unauthorized = 永不重连；4001 = session not found = 视为 compaction 期间的瞬态失联，最多重试 3 次、每次退避时长按 RECONNECT_DELAY_MS * retries 递增。两个 code 在协议层都是"server 主动关连接"，但 client 对它们的态度完全不同。产品层只会看到"连上了"或"连不上"；这种"为什么 compaction 后能自动恢复、但被吊销授权后就永远红灯"的差别完全由这两个 close code 的语义定义。断线重连的保留时长由此决定：4001 最长 2s + 4s + 6s = 12s 的窗口，超过就彻底 onClose；其他正常断线 RECONNECT_DELAY_MS=2000 × MAX_RECONNECT_ATTEMPTS=5 = 约 10s 定长重试预算。

这是一条典型的"失序事件流"写法——宁愿欠计数也不过计数。断线期间丢的 task_notification 事件无法补发，如果不清零，UI 上的"N tasks running"会永远停在断线前的高水位。接受"span gap 的 task 少计"比"永远错报"更好。

隐藏细节（src/hooks/useRemoteSession.ts:421-431）：重连时 inProgressToolUseIDs 被整体清空。用户在 UI 上可能看到"某个工具原本在 spin，现在突然不转了"——这不是 bug，是代码层显式选择"宁欠不过"。消息补齐机制不存在：WS 里的事件是 fire-and-forget，断线窗口里的 task_notification / tool-use lifecycle 没有任何 replay，重连后 UI 状态就 reset。历史消息侧依赖 §17.7 讲的 snapshot + live 拼接；但运行时指示器（"N tasks running"、正在转的 spinner）是纯派生状态，重连即清零。这是设计选择：想得到完整回放就去 claude.ai/code 上重新 teleport。

17.8.2 Response timeout 的放宽¶

60s / 180s 两档。在 compaction 进行时 CLI worker 阻塞在一次 API call 上，正常消息流暂停，180s 窗口避免把 "busy" 误判为 "dead"。isCompactingRef 这个开关由 CCR 发来的 system.subtype === 'compact_boundary' 消息翻转（见 ch.07 的 compaction 侧，以及 sdkMessageAdapter.ts 对 system 子类型的分支）。

此外，viewerOnly 模式（RemoteSessionConfig.viewerOnly，主要用于 claude assistant 场景）会整个 skip 这套 timeout（useRemoteSession.ts:538-561 的 if (!config?.viewerOnly) 护栏）——观众端没有"发消息后等 reply"的语义，也不会因为 60s 无事件就主动重连，否则多人共享一个 CCR session 时会打架。同模式下还会跳过 updateSessionTitle（§17.4 末尾提过）和 interrupt 发送，把"只读观众"的语义落到协议层。

Bridge 因为要兼容 v1（Environments API + HybridTransport）和 v2（env-less + SSE），抽象了一层 transport 接口：

17.9 Bridge：本地跑 agent、远端 UI 的另一面¶

17.9.1 入口¶

/remote-control 斜杠命令只做一件事：flip AppState：

真正的连接发生在 useReplBridge（src/hooks/useReplBridge.tsx），它 watch replBridgeEnabled。打开时动态 import initReplBridge，关闭时 teardown。initReplBridge 里做一堆 gating 检查（OAuth、policy、feature gate、min version，见 src/bridge/initReplBridge.ts:131-200），然后选择进入 env-based 或 env-less 实现。

17.9.2 env-less 的 5 步（值得看的简化版）¶

v1（env-based）额外多了 Environments API 的 register / poll / ack / stop / heartbeat / deregister。那套是为多 worker 云调度而设计的，REPL 这种单进程场景下冗余。v2 的核心变化是"一次 OAuth 换 worker_jwt" 替代 "Environments API 分配 worker_jwt"——服务端 PR #293280 让 /bridge 这个 endpoint 每次调用都 bump worker epoch，自己就 IS 了 register。

17.9.3 server→client 控制协议¶

Bridge 连上之后，server 会主动发 control_request。handleServerControlRequest（src/bridge/bridgeMessaging.ts:243-391）列出了 6 种 subtype：

  • initialize：必须回 success，否则 server 10-14s 内杀 WS。回应里告诉 server 本地的 commands / models / account / pid（默认值）。
  • set_model / set_max_thinking_tokens / set_permission_mode / interrupt：调对应 callback，回 success。set_permission_mode 的 callback 返回 verdict（带 error 字符串），因为某些 mode 可能被组织 policy 禁用，这时要让 claude.ai 前端看到错误而不是"表面成功但什么都没发生"。
  • 未知 subtype：回 error。

这就是"server 必回"的契约——没有响应就等同于 WS 死亡。

17.9.4 outbound-only 模式¶

一个很有意思的开关：如果只想让远端 UI 看到本地 session 的对话（mirror），但不想让远端控制本地（改 model、interrupt、set mode 等），用 outbound-only：

关键点：initialize 仍然回 success，否则 server 会杀掉连接，远端连 session 都看不到。其他 mutating 请求一律回 OUTBOUND_ONLY_ERROR，这样 claude.ai 前端能显示一个具体的错误而不是"我按了但没反应"。

隐藏细节（src/bridge/bridgeMessaging.ts:260-283 vs :330-340）：outbound-only 模式不是一刀切的"全拒"，它区分存活请求（initialize——回 success 让 server 知道客户端活着）和修改请求（set_model / set_permission_mode / interrupt——回 error 让 UI 看到"这端拒绝控制"）。更隐蔽的是 set_permission_mode：即便不在 outbound-only 模式，若运行上下文没注册 onSetPermissionMode 回调（例如 daemon context），代码也会返回 error verdict 而不是假装 success，注释明写"would lie to the client"。产品层的表现是 claude.ai 前端会看到具体 error message；如果这里偷懒回 success，用户就会以为 mode 改了但其实没生效——典型的"沉默成功"反模式。

这条"必回 initialize，别的都拒"的技巧：控制面协议的"存活请求"和"修改请求"要分开，否则限制权限等于断连接。

17.10 DirectConnect 与 SSH：两个简化版本¶

DirectConnect 的本质是"对接一个 stdout 里吐 stream-json 的 claude 进程"。DirectConnectSessionManager.sendMessage 的注释直接点破：

也就是说协议就是 claude -p --output-format stream-json --input-format stream-json 的两端接上，中间套一个 WS。handleMessage 按 \n 切帧，每帧一条 JSON——因为 ndjson 是 stream-json 的默认输出格式。

隐藏细节（src/server/directConnectManager.ts:130-142）：DirectConnect 走 WS 但 payload 形状与 --input-format stream-json / --output-format stream-json 完全一致——注释原文 "Must match SDKUserMessage format expected by --input-format stream-json"。架构含义：DirectConnect server 本质上是"一个 subprocess 的 ndjson stdin/stdout 被 WS 代理了"。这意味着同一个 Agent SDK stream-json 契约（见 ch.23）在三个位置复用：本地子进程 stdio、CCR 云 session 的 WS 订阅、DirectConnect 的 WS 双向。谁能生产/消费这份 ndjson，谁就能接入。

SSH 从 hook 端推断（src/hooks/useSSHSession.ts:184-198）预期有 session.proc.exitCode、session.getStderrTail()、session.proxy.stop()。合理推测：SSH 子进程是远端跑的 claude，本地起一个 proxy 把 API 请求路由出去——也就是说SSH 模式更像"远端跑完整 claude 进程 + 本地做 API 反代与 REPL UI"，而不是把本地 session 序列化后经 SSH tunnel 传输。session.proc 和 session.proxy 并列出现是判断依据：proc 是远端 claude 子进程的 handle、proxy 是本地 API 反代的 handle，两件独立的事。该模块在仓库里为恢复期 shim，真实实现可能不同；但 hook 端的接口已经把语义钉死。它与 useDirectConnect / useRemoteSession 共享 convertSDKMessage 和 createSyntheticAssistantMessage / createToolStub——也就是说 SSH 路径上不重复写一套 permission 反向回路。

四条路径共享一个 adapter 是 §17.6 这条设计的最大红利。

17.11 设计取舍总结¶

取舍 1：control_request 事件流 vs RPC。

事件流赢在：

  • 不需要本地开端口
  • 断线重连时没有"挂起的 RPC"语义问题（下次连接时 server 会重新发 control_request 如果请求还 pending）
  • 移动端天然适配（只能走 outbound HTTPS）

事件流输在：

  • 两边都得做 pendingRequests 表和 echo 去重
  • 延迟多一跳

Claude Code 选事件流的工程理由是：它本来就 outbound HTTPS + WS，多出来的 Map 和 ring buffer 不是大开销。这个选择也直接决定了 ch.23 的 Agent SDK 控制面协议长什么样——两侧是同一套 control_request / control_response，REPL 不过是 SDK 的一种 front-end 消费方。

取舍 2：env-based 和 env-less 并存。

这是一个典型的"新老实现共存期"。两者走不同后端 endpoint，各自有 min version 要求（src/bridge/bridgeEnabled.ts:160-173 + src/bridge/envLessBridgeConfig.ts:checkEnvLessBridgeMinVersion），initReplBridge.ts 里靠 GrowthBook gate 在运行时挑。代价：两套代码都要维护、两套 transport 都要跑 QA。收益：可以先让 v2 在 REPL 场景 rollout（简单场景），daemon / print 留 v1（多 worker 云调度场景）。什么时候合并是后端团队的决定。

取舍 3：SDK message adapter 单向翻译。

convertSDKMessage 只做 "SDK → REPL" 的方向，反向没有（REPL 发给 server 的 user message 是直接构造 SDK 格式）。这是因为 REPL 内部 Message 类型耦合了大量 UI 状态（光标、FileHistorySnapshot、isMeta、toolUseResult 等），往回翻译意义不大。单向 adapter 的代码量比双向少一半。

取舍 4：UUID 去重用环形 buffer 而非 LRU。

LRU 的 delete-on-match 语义和"同一 UUID 可能回显多次"不兼容；O(capacity) 大小的环形 buffer 逻辑简单、成本定：一个 50 长度的 ring 加一个 50 元素的 Set 就是 hook 的全部 echo-dedup 成本。

17.12 可迁移的点¶

四条可以带走用：

  1. 跨机器 permission prompt 的事件流 + request_id 对齐。把"问用户"做成 control_request，UI 端造合成数据填本地类型系统的坑。远端 agent 继续用它自己的 canUseTool(tool, input) 回调，不知道 UI 跑在哪台机器上。
  2. Tool stub 模式。远端工具目录不用同步到本地——用一个能通过本地类型系统的最小 Tool 对象，call 永不触发。让"UI 能显示，执行发生在远端"和"UI 能显示，执行发生在本地"用同一条代码路径。
  3. Reconnect 时宁可欠计数也不过计数。断线期间丢的事件无法补，重置到零比停在旧高水位更不容易误导用户。
  4. Transport swap 时带断点（getLastSequenceNum + Last-Event-ID）。换底层协议时把"从哪里续"作为 transport 接口的一等公民，能让协议迁移不等同于数据丢失。

反面教材——协议契约里要分"存活请求"和"修改请求"。Bridge 的 initialize 即使在 outbound-only 模式下也必须回 success，因为它是"我还活着"的确认；其他 mutating 请求可以拒。把这两类混在一个开关下（"全都拒"）等同于断连接。
