15.1 用户看到什么¶

常规的 Claude Code 会话里，用户说一句、模型回一句。claude --proactive （或者设 CLAUDE_CODE_PROACTIVE=1）启动之后，模型不再等待用户输入 —— 它自己会不停"醒来"，检查有没有活干、没活就睡一会儿再试。REPL 的 footer 区在 proactive 启用时会多出一行 waiting 30s 的倒计时提示，告诉用户下一次 心跳什么时候到。用户按 Esc 中断，心跳就暂停；用户下一次提交输入，心跳 自动恢复。

和 proactive 相邻的两个机制在用户视角看起来也像"主动行为"：

  • Session recap（源码里叫 away_summary）。用户离开 terminal 五分钟， 窗口重新 focus 时，transcript 顶部会插入一张由小模型生成的 1-3 句卡片， 总结"你走开之前在做什么、下一步应该干啥"。Anthropic 官方文档把这个功能 叫 Session recap （访问于 2026-04-19）。
  • Teammate inbox。多人 agent swarm 里，别的 teammate 可以往当前 session 的邮箱写消息。session idle 时立即投递为新 turn，busy 时排队等主 loop 结束。 和权限请求一类的消息还会顺带弹一个桌面通知。

本章的主干是 src/proactive/ 的 Proactive mode，外加 useAwaySummary 作为"对称的独立机制"讲清边界。Inbox 协议细节属 ch.17（见 ch.17 §17.4 Teammate inbox 数据结构，含远端 inbox 与本地文件 inbox 的分裂）， 本章只从 Proactive 视角看它的 idle/busy 投递策略。Buddy 作为通知渲染端 / 消费者在 ch.19（见 ch.19 §19.7 通知集成 —— 渲染侧）；Hooks 里的 Notification 事件源见 ch.14（见 ch.14 §14.9 内置事件源 vs 用户配置 hook）； cron / 定时任务触发 proactive 见 ch.13（见 ch.13 §13.8 触发后：prompt 怎么被注入）。终端 focus 感知本身依赖 Ink 的事件层，见 ch.21 §21.5 一帧是怎么出来的。sub-agent 在 proactive 活跃时被强制后台化， 相关约束见 ch.04 §4.6 sub-agent 的生命周期。

15.2 为什么挑这个设计讲¶

副标题里的"不打扰"容易让人把 Proactive 误解成一个客户端节流器。读完源码 之后判断反过来：Claude Code 的 proactive 系统里，客户端代码几乎不做任何 节流，所有"不打扰"语义都写在 system prompt 里。

src/proactive/index.ts 全长 58 行，只暴露四个状态变量和一组 pub/sub 订阅点。真正的 tick 注入 —— 把 <tick> 塞进 command queue 让模型再跑 一轮 —— 是 src/cli/print.ts 里三十几行的 scheduleProactiveTick。然后 src/constants/prompts.ts:860-914 里 50 行的自然语言"做人哲学"告诉模型 心跳到了该怎么处理。

这个分工值得单独讲：

  • 客户端只负责门（feature flag、pause/resume、blocked/unblocked）。
  • 模型是节奏决策者。依据是 prompt 里给它的规则 + userContext 里塞的一条 "terminal 是否 focused"字符串。

比客户端写节流器便宜得多，更重要的是语义表达力强。"如果用户刚发了消息 就优先回复"这种条件，用代码写要定义"刚发"、"优先"两个阈值；用 prompt 一 句话就表达完了。

长时间 turn 结束后可能积压了好几个 tick（每轮 finally 都塞一个）。 queue 里这些是按 FIFO 排着的 priority:'later' + isMeta:true 命令。 drainCommandQueue 会贪心合并：

关键是 isMeta === head.isMeta 这一项。没有这个约束，一个 tick 可能会被 后到的用户真实输入合并进同一 turn —— tick 本是 hidden-in-transcript，用户 输入是可见的，混在一条 command 里会丢失"哪些是 tick"的信息。

batching 的效果在模型侧靠 prompt 兜底：

Multiple ticks may be batched into a single message. This is normal — just process the latest one. Never echo or repeat tick content in your response. —— src/constants/prompts.ts:868

多条 tick 到了模型那里就是一段连续的 <tick>...</tick>\n<tick>...</tick>， prompt 明确说"挑最新那条处理"。

隐藏细节（src/cli/print.ts:1958）：批量合并后留下的 uuid 来自 batch.findLast(c => c.uuid)?.uuid ?? command.uuid —— 只保留最后一个 带 uuid 的 command，而不是头元素。外部系统（clank / ccr footer 等跟踪 command lifecycle 的消费者）只能对账到批次末尾那个 tick，批次里早期 的 tick 没有 uuid 层面的 ack。用户视角看不出区别，但如果你在这基础上 自己写观测，采样会有偏：永远只看见"组内最后一次"。

15.4.6 System prompt 里的不打扰规则¶

src/constants/prompts.ts:860-914 的 getProactiveSection() 是 Proactive 活跃时注入 system prompt 的那段"做人哲学"。工程上它由七个小节组成 （Pacing / First wake-up / What to do on subsequent wake-ups / Staying responsive / Bias toward action / Be concise / Terminal focus），外加 顶部一段"ticks 是 check-in、多个 tick 会被 batch"的引子。七节每一节 对应一个具体的 anti-pattern。下面挑其中六节看它们分别在堵什么 （What to do on subsequent wake-ups 内容与 Pacing 有重合，这里并入 Pacing 一起讲）：

Pacing 专门挡住 "every tick → output 'still waiting'" 这个最容易发生 的失败模式。没有 Sleep 工具的话，模型每次醒来没别的动作可执行，只能吐一 段 text —— 既浪费 token 又刷屏。有了 Sleep + 强硬 prompt（"you MUST call Sleep"）之后这条变成确定性行为。Pacing 段本身一百来个词（~140 token 粗估），整段 "Autonomous work" 七节加顶部引子约 500 词（~700-800 token 粗估）—— 这是 proactive 活跃时每次 request 固定注入的"不打扰成本"，靠 prompt cache 命中摊销；冷缓存第一次必须全量走一遍。

First wake-up 挡住"启动就暴走"。不加这段，模型看到"你在 proactive mode，自己干"的指令后往往会立刻 grep / read 大量文件试图主动帮忙，用户 还没说要做什么就已经被扫了一遍 repo。

Staying responsive 挡住"用户发话了还埋头干上次的活"。

Bias toward action 是反方向的挡 —— 挡住"每走一步就问一下"。autonomous 模式下过度保守反而是打扰。

Be concise 挡住 narrate everything 的倾向。

Terminal focus 是所有规则的 modulator：focused 时偏向 Staying responsive，unfocused 时偏向 Bias toward action。

Prompt 的工程属性是很强的：每一段都在堵一类具体失败模式，不是笼统讲 "做个好 agent"。

隐藏细节（src/utils/systemPrompt.ts:99-107）：Proactive 活跃时， 自定义 agent 的 system prompt 从默认的"替换 default"切换成"追加到 default 之上"。也就是说，你在定义 agent 时写的 instructions 如果依赖 "我是唯一 prompt、上面没有别的内容" 的假设（比如"忽略前面所有指令"之类 的话术），在非 proactive 下成立、在 proactive 下就挂了 —— 默认 prompt、 Proactive 七节、Brief 段落会同时存在。这是跨两种模式复用 agent 定义时 最容易踩的坑。

隐藏细节（src/constants/prompts.ts:852-857, 913）：Brief 段落 （BRIEF_PROACTIVE_SECTION）在 proactive 活跃时由 getProactiveSection() 末尾的 ternary inline 追加，独立的 getBriefSection 在 proactive 活跃时 直接 return null 避免重复注入。改 Brief 段的开发者若只改了独立路径 忘了 proactive 这一条，会出现"非 proactive 下新内容生效、proactive 下 还是老内容"的诡异现象 —— Brief 与 Proactive 两个 feature flag 的互斥 路径藏在这里。

15.4.8 其他 proactive-aware 的消费点¶

Proactive 活跃状态在若干 UI 层被读来抑制会打扰用户的背景行为：

  • Terminal progress bar（OSC 9;4）禁用：

    用户离开 terminal 去别处做事时，不希望 dock / taskbar 上频繁闪动 —— 长 proactive session 会塞满一排 progress 变更。

  • Prompt suggestion 禁用（见 15.4.4 的注释）：proactive 下模型驱动 对话，onboarding 式的示例命令没意义。
  • sub-agent 默认后台化：

    proactive 下主 loop 自己在 tick 跑，不希望被 sub-agent 阻塞。

隐藏细节（src/tools/SkillTool/SkillTool.ts:162-164, 685-687, 1039-1041）：SkillTool 上报给 telemetry 的 invocation_trigger 在 queryDepth === 0 时一律写死为 'claude-proactive'（非 0 写 'nested-skill'）—— 不看 isProactiveActive()。也就是关掉 --proactive 跑技能也会在埋点里被标成 claude-proactive。这是 label 口径的遗留： 'claude-proactive' 实际意思是"最外层 Claude 自己发起的"，不是"Proactive mode 下发起的"。对线上数据分析的影响是：光数 invocation_trigger= claude-proactive 的事件无法得到"proactive session 跑了多少技能"，还要 另外对账 CLAUDE_CODE_PROACTIVE / --proactive 的 session 维度。

隐藏细节（src/tools/AgentTool/AgentTool.tsx:59, 567）：sub-agent 的 shouldRunAsync 读的是父进程的 proactiveModule?.isProactiveActive() —— proactive 是 process-wide 单例状态，sub-agent 并没有自己的一份。 结果是：sub-agent 本身不会收到 <tick>（它的 runAgent 走同步 turn 序列）， 也不会被注入 Proactive 七节 system prompt；但父进程的状态会沿着 "强制 后台化" 这条路径渗透进来。sub-agent 内部若想触发自己的 proactive 行为， 得走 Agent SDK 的 set_proactive 控制消息（见 §15.4.1），不能靠继承。 sub-agent 产出的 proactive 消息回到主 agent 的路径是标准的 <task-notification> + notifyOnCompletion，不会被当作新 tick 吞进来。

15.4.9 Away summary：同场景但独立的机制¶

Away summary 是 --proactive 没开也能用的功能（受 AWAY_SUMMARY feature flag 和 GrowthBook tengu_sedge_lantern gate 控制，3P 默认 false）。 它也读 terminal focus，但不走 tick、不唤醒主 loop，只做一件事：在用户 离开够久之后事后生成一张"你刚才在干啥"的 system message。

Hook 本体：

状态机：

  • focused / unknown → 不动。
  • blurred → 启 5 分钟定时器。官方文档写 3 分钟，源码这里是 5 分钟。[^3]
  • 5 分钟后还在 blur → generate()：如果正在 loading，先标 pendingRef 等 isLoading 变 false 再跑，避免 mid-turn 插一条 summary 打乱 transcript。
  • 用户焦点回来 → 清定时器 + abort 在途生成。

生成走独立通道：

几个设计选择：

  • 只取最近 30 条消息做 context，避免会话过长时 "prompt too long"。

  • 独立的 querySource: 'away_summary' 埋点，方便线上分析这部分开销。

输出塞回 transcript：

同 user turn 内只生成一次（hasSummarySinceLastUserTurn 的 guard）， 让连续离开再回来不会刷屏。

放在同一章讲的原因是它们共享两个输入信号 ——terminal focus 和 isLoading—— 但使用方向相反：Proactive 在 unfocused 时"更激进行动"，Away summary 只在 unfocused 够久且随后 focused 时"出一次摘要"。两者合起来覆盖了 "用户离开时 agent 该怎么 behave" 的两半：干活那一半在 Proactive，汇报 那一半在 Away summary。

15.4.10 Inbox poller：Proactive 视角下的投递策略¶

Teammate inbox 的实现细节见 ch.17（§17.4 关键数据结构 / §17.6 permission 反向回路）；本章关心两件事：这个消息流怎么在 Proactive session 里"不打扰"。

轮询频率固定 1 秒（useInterval 串起来，不做退避也不做 jitter）：

隐藏细节（src/hooks/useInboxPoller.ts:107, 954 + src/utils/teammateMailbox.ts:115-125）： 这 1 秒的轮询走的是本地文件 inbox（readUnreadMessages → readMailbox 走 fs）。它不 jittered、不退避、idle / busy 同频 —— 文件读 + filter(m => !m.read) 的开销低到可以忽略。与之对比的 远端 inbox（Remote inbox，由 src/bridge/ 侧订阅 WebSocket / 长连接推送，本章不展开，见 ch.17 §17.5 Remote inbox 投递链路）走 push 模型，没有固定 poll 周期；远端消息落到本地文件后再被这个 1 秒 poll 扫进 session。两条链路最终汇入同一个 AppState.inbox 队列，但 latency 特性不同 —— 本地 teammate 最坏等 ~1s 被看见， 远端消息的 latency 取决于 bridge 的 push 延迟。

投递策略按 session 状态分两路：

  • idle 且不在 dialog → 立即提交为新 turn。
  • busy 或者有 dialog → 落到 AppState.inbox.messages，状态 pending， 同时 UI 可见排队中的消息。
  • markRead() 放在最后 —— 保证只有确认投递或者确认入 pending queue 之后才标记为已读，崩溃恢复不丢消息。

session 变回 idle 时的 flush（useInboxPoller.ts:876-950）做两件事： 把 processed 状态的消息（mid-turn 已交付给模型，UI 还 pin 着的）清掉；把 pending 合并成一次 turn 提交。提交失败就保留 pending，等下一次 idle 再试。

桌面通知的抑制门独立一套：

只在 !isLoading && !focusedInputDialog 时弹通知 —— session 忙或用户正在 对话框里时都不弹。通知后端本身是一层独立抽象（详见 src/services/notifier.ts 以及 ch.14 §14.9 的 Notification hook 事件源；Buddy 作为渲染侧消费者见 ch.19 §19.7 通知集成 —— 渲染侧），这里只看调用时机。

隐藏细节（src/hooks/useInboxPoller.ts:354）：const firstParsed = isPermissionRequest(permissionRequests[0]?.text ?? '') —— 同一轮 poll 里即使有多条 permission 请求，也只对第一条发桌面通知。如果两个 sub-agent 同一秒内都排队等权限，第二个的通知会被吞（UI sticky dialog 仍会排队进 ToolUseConfirmQueue，不丢审批）。这是一条隐式去重策略， 把"同秒多个请求"当作一次打扰处理。

值得留意的是：Inbox 里"权限请求"类消息比"普通聊天"类消息更应该中断 用户，但抑制门两者一样 —— 都受 idle / dialog 的 gate。换句话说，没有 "权限请求永不抑制"的 override。权限请求的 urgency 在代码里由下面两点 替代：

  • 进 ToolUseConfirmQueue 后 UI 主动弹 sticky 对话框（focusedInputDialog='tool-permission'）， 中断当前 idle / streaming 视图。
  • 弹了桌面通知的消息就顺带进 confirm queue 永久等待用户决定（不会被新 tick 覆盖）。

15.5 设计取舍¶

15.5.1 状态模块只管四个寄存器¶

src/proactive/index.ts 没有"当前 tick 间隔"、没有"上次心跳时间"、没有 "用户注意力评分"。所有这类信息要么不存在（给模型读去判断），要么散在别 的文件里（REPL、print.ts、notifier）。

好处：

  • 整块 dead-code-eliminate：feature('PROACTIVE') || feature('KAIROS') 关闭时 REPL、Messages、PromptInput、tools、systemPrompt 里所有 require('../proactive/index.js') 都走 conditional require 分支，整 个子系统不进 bundle。
  • 状态少，测试面小。

成本：

  • 状态翻牌逻辑分散在 5-6 个文件。改"contextBlocked 何时置位"要同时改 REPL 的三个 compact 路径和 /clear。有漏改的风险。
  • nextTickAt 本应由 scheduleProactiveTick 写入但本仓库未见写入点，说明 这个"状态分散"的路径在恢复过程中容易断。

15.5.2 不打扰策略主力放在 prompt¶

几乎所有"不打扰"语义在 prompt 段落里实现（Pacing、Staying responsive、 Bias toward action、Be concise、Terminal focus），客户端只做少量硬抑制 （progress bar、prompt suggestion、sub-agent 后台化）。

好处：

  • 表达力：prompt 能说"如果用户刚发了消息就优先回复"、"focused 时少打扰" 这类条件，代码层面要写很多状态。
  • 可迭代：调"不打扰"的强度改一行 prompt 即可，不用改代码。
  • 少依赖：不用维护客户端的 attention model。

成本：

  • 依赖模型真的遵守。prompt 失败会表现为 spam 或者懒散，debug 路径不是 读代码而是读 transcript。
  • 非确定性。同一个 tick 在不同 session 可能被响应也可能被 Sleep。
  • token 成本：这段 prompt 每次 request 都在。Proactive session 是长时 运行的，cache 命中率高可以摊销，但仍然是每次都付。

15.5.3 Sleep tool 是必须的，不是可选¶

有了 Proactive 没有 Sleep 的话，模型对"没事干"只有一个表达方式 —— 输出一条空话然后等下一个 tick。Sleep 把这件事变成确定性动作：Sleep(60) → 60 秒后下一个 tick。Prompt 强制 "you MUST call Sleep"。

这个设计的可迁移价值在 ch.16（用户可能读到这里时叫不同的名字，但语义 是"给你的 LLM loop 一个 no-op 工具，强制 idle 去走工具而不是走文字输出"）。

15.5.4 Away summary 独立于 Proactive¶

它们场景都是"用户可能离开"，但分离得干净：

  • Proactive 主动地 "做事"；Away summary 被动地 "写摘要"。
  • Proactive 唤醒主 loop；Away summary 用 small-fast model 单独 query。
  • Proactive 活跃状态写 terminalFocus 到 userContext；Away summary 直接 订阅 terminal focus。
  • Proactive session 也能用 Away summary；非 proactive session 也能用。

合在一章讲是因为读者容易混淆 —— 都像 "用户离开后 agent 的主动行为"， 但工程上是两个系统。分清这点是把 "用户在不在看" 这类 attention signal 设计成可被多路订阅的单一事实源的前提。

15.5.5 可抑制 vs 不可抑制¶

按"永远不被抑制"的顺序往下排：

  1. 工具权限请求 —— 永远要用户决定。通过 ToolUseConfirmQueue 进 sticky dialog，idle / busy 都要阻塞 UI；不走 Proactive 的"不打扰"路径。
  2. 用户输入（stdin）—— 永远优先处理。setTimeout(0) + priority:'later' 专门让位。
  3. Tick —— 总是被上面两种抢占。
  4. 桌面通知 —— !isLoading && !focusedInputDialog 双 gate。
  5. Progress bar —— proactive 活跃时直接关。
  6. Prompt suggestion —— proactive 活跃时直接关。

1 和 2 是"无条件优先"；3 是"按需被抢占"；4/5/6 是"有 proactive 就禁用"。 没有中间的"延后合并"或"按优先级排序" —— 要么走权限队列要么走 command 队列，队列本身只有 now/next/later 三级。

15.6 可迁移的点¶

1. 最小状态机替代 scheduler。 给 CLI / bot agent 加 "autonomous loop" 时不要一上来就上 job scheduler。四个字段够了：

  • active：是不是 autonomous。
  • paused：用户有没有手动暂停。
  • blocked：有没有遇到需要等的错误。
  • nextTickAt：UI 倒计时。

三个布尔是否互锁决定能不能发下一次心跳。具体"多久一次"让配套工具 （Sleep）传参进来。

2. Attention 信号作为 prompt 输入。 把 terminal focus / 用户输入间隔 / 窗口活动这类信号翻译成一条自然语言字符串塞进 userContext，让模型自己 判断节奏，比写一套客户端节流中间件便宜且语义更强。注意：

  • 只在异常状态注入字段（这里只在 unfocused 注入）。省 token。
  • 字段名要稳定（terminalFocus），让 prompt 能显式引用。
  • 值是人话（"The terminal is unfocused — the user is not actively watching."），不是枚举值。模型读人话表现更好，调试也更清楚。

3. no-op 工具为 LLM 提供 idle 语义。 为 autonomous loop 定义一个显 式的 "waitDuration" 工具（本仓库的 Sleep）。prompt 强制"没事必须调用"。 好处是把"闲着"从概率行为改成确定性动作，同时给调用方一个可控的次醒 时间。

4. 心跳和用户输入的 queue 隔离。 用 isMeta / 优先级把二者区分开：

  • 同 workload / 同 meta 才允许 batching。
  • 用户输入比 tick 优先 dequeue。
  • setTimeout(0) 让位 stdin。

这样积压的 tick 可以合并省 turn，但不会把 tick 混进真实用户消息。

5. Blocked 状态独立于 Active。 遇高成本错误（context 满、API error） 时先挂起循环，在确定可以继续（compact 完成、用户清会话）再恢复。避免 "错误 → 重试 → 又错误"的 busyloop。清 blocked 的入口要覆盖所有可能的 "context 变小"路径 —— auto compact、manual compact、partial compact、 /clear —— 漏任何一条都会卡住。

6. Idle / busy 的双通道投递。 外部事件（本仓库的 teammate inbox） 在 session idle 时立即走主 turn，busy 时进暂存队列 + UI 显示。只有确认 投递后才 markRead，保证重启不丢消息。这个模式通用于任何"异步事件 → 同步主线"的系统。

7. skipCacheWrite 给次要任务用。 副业的 LLM 调用（本仓库的 away summary 用 small-fast model 生成一段摘要）明确指定 skipCacheWrite: true，避免污染主会话的 prompt cache。主副两条链的 cache 空间隔离是长 session 应用里常被忽略的优化点。

  • nextTickAt 在本仓库只被置为 null，没有被设置为具体时间戳的写入路 径。UI ProactiveCountdown 读它做倒计时，说明真实实现里该有写入。
