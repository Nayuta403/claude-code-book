6.1 用户看到什么¶

Claude Code 提供三条进入 worktree 的路径，底层共用同一套机制。

路径 A：CLI 启动标志。 在仓库根目录运行 claude --worktree feat-auth（或 -w feat-auth），Claude 启动时就把会话落进 <repo>/.claude/worktrees/feat-auth，分支名 worktree-feat-auth，以 origin/HEAD 为 base。没给名字就随机生成一个 bright-running-fox 形式的 slug。

路径 B：会话中的 EnterWorktree 工具。 用户对 Claude 说"帮我开个 worktree 做这个重构"，LLM 主动调 EnterWorktree，当前会话的 cwd 被切到新 worktree。工具 prompt 硬性限定：

Use this tool ONLY when the user explicitly asks to work in a worktree. … Never use this tool unless the user explicitly mentions "worktree". —— src/tools/EnterWorktreeTool/prompt.ts:2-12

所以这个工具不会被 LLM 自作主张触发，必须用户在输入里出现"worktree"一词。

路径 C：sub-agent 的 isolation: "worktree"。 主 agent 派 sub-agent 时（多 agent 调度的总图详见 ch.04），在 AgentTool 的 isolation 参数里选 "worktree"，sub-agent 会在独立的 worktree 里运行，结束后自动清理或保留（见 6.5）。内置 batch skill 直接把这条写成了硬约束：

三条路径的用户视角差异只有触发方式。退出时的 UX 也统一：无改动自动删、有改动弹 dialog 问 keep/remove，或者 LLM 主动调 ExitWorktree 工具（见 6.4）。

官方文档把路径 A 和 C 说得更详细：https://code.claude.com/docs/en/common-workflows（节 "Run parallel Claude Code sessions with Git worktrees"，访问于 2026-04-19）。

6.2 为什么挑这个设计出来讲¶

git worktree 作为 agent 沙箱，是"轻量 + 可回溯"的最大公约数。

比 Docker/VM 轻几个数量级 —— 不起容器、不起进程命名空间，纯 git 命令加几次文件 I/O。比 chroot 简单 —— 不碰权限。比纯临时目录 cp -r 强 —— 保留 git 历史，可以 commit、push、merge 回主 worktree。

取舍很明确：只隔离文件系统。 进程、环境变量、网络、凭据、shell history 全部继承主 session。这不是 bug。如果要求 agent 重新 auth、重新拉依赖、重新配 env，那就是另一个产品 —— 更像 Codespaces、不像 CLI 工具。隔离 fs 足够解决"两个 agent 同时改同一个文件"和"改坏了想回滚"这两个主要矛盾；其他矛盾不是 worktree 要管的。

这章讲透这套沙箱如何实现、清理如何兜底、并发如何处理，以及这个设计模式在哪些场景下能搬。

6.4 关键流程¶

6.4.1 Enter：路径选择与切换¶

EnterWorktreeTool.call 的正文只有 40 行：

几点值得注意。

单例守护。 Enter 第一行就拒绝已有 session，避免嵌套。Exit 的反向守护更细：工具显式设计成"没 session 就 no-op 而不是报错"（ExitWorktreeTool.ts:180-188），因为用户/LLM 可能误调。

路径解析到主仓。 如果 Enter 时 cwd 已经在某个 worktree 内部，先 chdir 回主仓再创建 —— 否则 git 会在嵌套 worktree 的子目录里尝试创建同级兄弟，语义错乱。

双 cwd 更新。 process.chdir 是 Node 进程的真 cwd，setCwd 是 bootstrap 里 state 层面的 cwd（src/utils/Shell.js）。两者必须同步，因为 Claude Code 内部不少代码不走 process.cwd()，走 getCwd()。BashTool 的 cd 只改后者，process.cwd() 保持不变 —— 这是已有的 split，worktree 逻辑只是遵守这个 split。

三个缓存清除。 clearSystemPromptSections 清的是 "env_info_simple" 一类系统段（含当前工作目录），clearMemoryFileCaches 清的是 CLAUDE.md 的加载缓存，getPlansDirectory 是计算 plans 目录的 memo。都依赖 cwd，cwd 变了必须重算。Plan slug 被 getPlanSlug() 用作 worktree 默认名，是 Plan Mode 的唯一耦合点（Plan Mode 本身详见 ch.05）。

隐藏细节（src/utils/claudemd.ts:858-897）：cwd 切进 worktree 后，memdir 加载器沿目录链上走时会同时经过 worktree 根和主仓根，两处都可能有 checked-in CLAUDE.md。加载器通过 isNestedWorktree + skipProject 去重，只保留 worktree 内的 Project-type CLAUDE.md，丢掉主仓那份；但 CLAUDE.local.md（gitignored）仍从主仓加载。产品层面你看不到这个分叉，但它决定了 sub-agent 在 worktree 里"能看见主仓的 local memory、看不见主仓的 project memory"——如果 sub-agent 依赖主仓 CLAUDE.md 里的指令，进 worktree 后就不再生效。

6.4.2 Path 与 branch 命名¶

路径常量固定在仓库内：

选 <repo>/.claude/worktrees/ 而不是 /tmp 的取舍：跟代码走、跟清理周期走、不占系统 tmpfs。代价是要加到 .gitignore（文档有提）—— 仓库本身并不预置这条规则，忘了加就会把 worktree 当 untracked 追进来。

隐藏细节（src/utils/permissions/filesystem.ts:456-468）：.claude/ 目录在权限系统里被整体标成 DANGEROUS_DIRECTORIES（敏感配置/密钥聚集地），但 .claude/worktrees/ 被显式特判放行——只要目录名叫 worktrees，权限系统就不再拦写入。这是 worktree 能在 .claude/ 下面正常工作的前提；反过来，如果将来有人把别的东西塞到 .claude/worktrees/ 下想绕过危险目录拦截，理论上也能绕过。权限系统的总体设计详见 ch.09。

slug 校验 防 path traversal：

segment 级校验允许嵌套（user/feature），但 ..、空段、drive spec、leading/trailing / 全部拒绝。值得抄：校验放在 path.join 之前，因为 path.join 会 normalize ..，校验放在后面就被绕过了。注释点明了这个顺序依赖。

flattenSlug 用 + 替换 /，因为分支名和目录路径都要展平。不展平会有两个问题：git 分支 worktree-user 作为文件和 worktree-user/feature 作为目录产生 D/F 冲突；目录 .claude/worktrees/user/feature/ 是 user worktree 的子目录，git worktree remove user 会把带未提交工作的子 worktree 也删了。

6.4.3 Base branch 的选择与 fetch 避让¶

getOrCreateWorktree 的核心 40 行值得细看：

两条优化都围绕"别 spawn git"：

  1. Fast-resume 走文件指针。 同名 slug 直接读 .git/worktrees/<slug>/HEAD 这个 pointer 文件。注释里写得明白：git rev-parse HEAD 即便目标只要 2ms 的工作，光 spawn 都要 15ms（worktree.ts:244-247）。对于 "我又跑了一次 claude -w feat-auth" 的高频场景，这是 resume-not-recreate 的关键。
  2. Skip fetch when ref exists locally. 大仓 git fetch 光扫 commit-graph 就 6-8 秒（worktree.ts:279-283）。优先读 refs/remotes/origin/<defaultBranch> 的本地 ref —— 值得稍微 stale 的代价。

创建命令：

用 -B 不用 -b 是故意的。-b 遇到同名分支会报"already exists"；-B reset 到指定 commit。场景：上次 worktree 目录被手删但分支还在。用 -B 省了一次 git branch -D 的 spawn。

Git 文档对两者的行为差异：https://git-scm.com/docs/git-worktree（访问于 2026-04-19）。

6.4.4 Post-creation setup¶

git worktree add 完事远不等于可用。Claude Code 补了四件事（src/utils/worktree.ts:510-624）：

1. 复制 settings.local.json（worktree.ts:514-534）。这个文件可能含 API key / 本地 override，要 propagate 到 worktree 的 .claude/settings.local.json，否则 worktree 会用默认值。

2. 链接 hook 目录（worktree.ts:537-578）。优先找 .husky，其次 .git/hooks，把 worktree 的 core.hooksPath 设到主仓的 hooks 目录。注释提到一个陷阱：git config core.hooksPath（不带 --worktree flag）写的是主仓 .git/config，所有 worktree 共享，所以这行本质是"所有 worktree 用主仓 hooks"。再设一次就 no-op，检查 existing 的逻辑是为了省那次 14ms spawn。

3. Symlink 大目录（worktree.ts:102-138、worktree.ts:580-585）。通过 settings 的 worktree.symlinkDirectories opt-in，典型是 node_modules。symlink("node_modules", destPath, "dir") 之后 worktree 共享主仓依赖，省几 GB。EEXIST / ENOENT 静默跳过。

4. 复制 .worktreeinclude（worktree.ts:391-504）。这是 gitignore 语法的白名单，列 .env / .env.local 这类"gitignored 但 worktree 需要"的文件。实现里有一个性能关键优化：

--directory 让 git 把 node_modules/ 一类完全 gitignored 的目录折叠成一条记录而不是列出里面每个文件。注释里给了数字：大仓能从 "500k entries / ~7s" 降到 "数百 entries / ~100ms"。只有 .worktreeinclude pattern 确实指向某个折叠目录内部时，才对那个目录做第二次 scoped ls-files 展开。

这段是值得借鉴的工程细节：不是"先列全、再过滤"，而是"先列折叠、按需展开"。同一套思路可以用在任何"在 gitignore 基础上二次白名单"的场景。

6.4.5 Exit：validateInput + call 的分工¶

三种拒绝：

errorCode 3 是 fail-closed 设计的核心：

函数的文档注释写得比代码还重要：

Returns null when state cannot be reliably determined — callers that use this as a safety gate must treat null as "unknown, assume unsafe" (fail-closed). A silent 0/0 would let cleanupWorktree destroy real work.

三态（ChangeSummary / null）而不是两态（is-dirty boolean）—— 因为用户对"误删"的容忍度远低于"没删干净"。这是整个 worktree 模块的一贯原则。

call 阶段（ExitWorktreeTool.ts:227-321）在 validateInput 放行后执行：

keepWorktree 只清 module 变量和 project config 里的 activeWorktreeSession，worktree 目录和分支不动（src/utils/worktree.ts:780-811）。

cleanupWorktree 的 git-based 分支（worktree.ts:813-894）做三件事：

  1. process.chdir(originalCwd) —— 先离开 worktree，不然自己占着删不掉。
  2. git worktree remove --force <worktreePath>。--force 是必须的：discard_changes: true 场景下 worktree 就是 dirty，git 默认拒绝删。
  3. await sleep(100) —— 等 git 释放锁（注释原文："Wait a bit to ensure git has released all locks"）。
  4. git branch -D <worktreeBranch> 删临时分支。

restoreSessionToOriginalCwd（ExitWorktreeTool.ts:122-146）是 EnterWorktreeTool.call 最后那段 mutation 的精确反向操作：setCwd + setOriginalCwd + 条件 setProjectRoot + saveWorktreeState(null) + 三个缓存 clear。

6.4.6 session 结束时的 Dialog¶

用户直接 /exit 或 ctrl+d 退 session 时，如果还在 worktree 里 —— WorktreeExitDialog 弹出来问（src/components/WorktreeExitDialog.tsx）。

关键设计：无改动不问。

在这里，"无改动"的判定比 ExitWorktreeTool 宽松一些 —— 只 git status --porcelain 加 rev-list --count，git 命令失败不会 fail-closed，走 catch 打印 "Worktree cleanup failed, exiting anyway"。这条路径假设用户主动退出，给出两个选择就够了；机器调用走 ExitWorktreeTool，fail-closed 才到位。两套 UX 对应两套容错策略。

6.5 两条并行路径：session 与 agent¶

Claude Code 里创建 worktree 的函数其实有两个，共用底层，顶层分叉：

共享底层：validateWorktreeSlug、getOrCreateWorktree、performPostCreationSetup、executeWorktreeCreateHook。

顶层分叉的差异：

  • createWorktreeForSession 写 module 单例 currentWorktreeSession、写 project config、不碰 process.chdir（留给调用方）。
  • createAgentWorktree 不写任何全局状态，纯返回 { worktreePath, worktreeBranch, headCommit, gitRoot }。

两条路径有一个关键差异：gitRoot 的解析。

"主 session 在 worktree A 里，然后派了个带 isolation: "worktree" 的 sub-agent" —— 用 findGitRoot 会返回 worktree A 自己，sub-agent worktree 会嵌到 worktreeA/.claude/worktrees/ 下。用 findCanonicalGitRoot 解析到主仓。结果是：所有 agent worktree 都平铺在主仓的 .claude/worktrees/，periodic stale sweep 才能统一扫到。

Resume 已存在的 agent worktree 会 utimes(worktreePath, now, now)（worktree.ts:944-948）：fast-resume 路径是只读的，worktree 目录的 mtime 维持创建时间，可能已过 30 天 cutoff，被 stale sweep 误删。主动 bump mtime 解决。

隐藏细节（src/utils/worktree.ts:942-948）：这个 utimes bump 是"长时间睡眠后唤起 agent 能不能恢复原 worktree"的唯一保障。产品层看不到——用户不会意识到"fast-resume 顺带刷新了 mtime"——但如果哪天 refactor 动了这行，30 天前创建、今天第一次重用的 agent worktree 会在本次启动的 cleanupStaleAgentWorktrees（worktree.ts:1094-1118）里被顺手清掉，看起来就是"长期任务的上下文无故丢失"。

6.5.1 并发¶

session worktree 单例：Enter 第一行就拒绝 currentWorktreeSession 非空（EnterWorktreeTool.ts:79-81）。一个 session 同时只能有一个 session worktree。

agent worktree 无上限：每次 AgentTool.call 生成新的 slug agent-<earlyAgentId.slice(0,8)>（AgentTool.tsx:591），createAgentWorktree 不碰全局状态 —— 主 agent 可以并发派任意多个 sub-agent，各占一个 worktree。

但 process.chdir 全进程只有一份，不能给每个 agent 用。解决方案：

runWithCwdOverride 通过 AsyncLocalStorage 把"cwd override"传给该 agent 栈内的所有 tool 调用，每个文件操作和 shell 命令都在 override 下工作 —— 不改进程 cwd。这是并发 worktree 跑起来的前置条件。

隐藏细节（src/utils/cwd.ts:12-14 + src/tools/AgentTool/AgentTool.tsx:640-641）：整个进程的 process.cwd() 始终是主仓，每个并发 sub-agent 的 worktree 路径只存在于 AsyncLocalStorage。若某个工具实现漏走 getCwd() / 绕过 override 直接读 process.cwd()，它会拿到主仓路径——结果是工具在 sub-agent 的 worktree 外"意外写文件"，且测试阶段很难复现（单 agent 情况下两者一致）。BashTool 的 cd 行为就是专门照这个 split 设计（改 getCwd() 不改 process.cwd()）。

隐藏细节（src/utils/worktree.ts:813-894 + 全仓库无 git worktree lock 调用）：Claude Code 没有使用 git 原生的 git worktree lock 机制；cleanupWorktree 里那句 sleep(100) 的注释"Wait a bit to ensure git has released all locks" 指的是 git 内部的 refs lock，不是 worktree lock。并发保护只靠两层：①currentWorktreeSession 单例守护 session worktree；②agent worktree slug 是 agent-<8hex> 随机、碰撞极小。剩下的唯一裸奔窗口是两个独立 claude --worktree <same-name> 进程撞在一起——fast-resume 的 readWorktreeHeadSha 到后续 git worktree add -B 之间没有锁，后到者会被 git 自己的 add lock 拒绝返回错误。产品层感知不到，但说明 worktree 模块默认假定单进程使用。

6.5.2 agent 结束后的清理¶

三分支：

  1. hook-based → 保留（hook 无法判断 VCS 有没有改动，保守）。
  2. git-based 无改动 → git worktree remove --force + git branch -D（worktree.ts:961-1020）。
  3. git-based 有改动 → 保留，把路径和分支名返回给主 agent，主 agent 在消息里看到 worktreePath 和 worktreeBranch 就可以告诉用户或决定下一步。

这是主 agent 能接收 sub-agent 结果"物质化"的关键：sub-agent 工作不丢失，以分支形式交付。

6.5.3 启动时的 stale sweep¶

cleanupStaleAgentWorktrees（src/utils/worktree.ts:1058-1136）在 cleanup.ts:595 的定期任务里调，cutoff 来自 cleanupPeriodDays 设置（默认 30 天）。

只扫 ephemeral 模式：

正则严格匹配"机器生成"的形状，用户命名的 feat-auth / bugfix-123 不会被扫。这是 docs 所说的"Worktrees you create with --worktree are never removed by this sweep"的实现。

三重 fail-closed 检查（worktree.ts:1094-1118）：

  • mtime 不过期 → 跳过。
  • git status --porcelain -uno 非零或有输出 → 跳过（-uno 忽略 untracked：30 天老的 agent worktree 的 untracked 多是 build 产物，扫一遍比较慢）。
  • rev-list --max-count=1 HEAD --not --remotes 非零或有输出 → 跳过（有未推送 commit 就不删）。

全过才删。扫完 git worktree prune 清 admin 文件。整个策略的口径就是"宁可留、不可误删"。

6.6 Hook 作为 VCS 抽象¶

worktree 不绑死 git。两个 hook WorktreeCreate / WorktreeRemove 在 settings.json 里配了以后，git 路径就被整体替换。

hook 合约很薄：输入 slug，输出 worktree 绝对路径写到 stdout（src/utils/hooks.ts:4928-4958）。remove hook 输入 worktree_path（hooks.ts:4967-5003）。这样 SVN / Perforce / jj / fossil 都能接进来，只要能提供 "给我一个 slug，给你一个隔离目录" 的语义。

副作用：hook-based worktree 没 originalHeadCommit（git 概念），countWorktreeChanges 进入 null 路径（ExitWorktreeTool.ts:94-98），Exit remove 必须 discard_changes: true。从"不绑 VCS"的角度看合理；从 SVN 用户角度看有点烦。文档没明说这个约束 —— 在源码注释里。

6.7 设计取舍¶

几种替代方案的对照：

方案隔离范围创建成本可回溯Claude Code 选择
Docker 容器fs + proc + net秒级起容器 + 卷挂载得 commit/export 才能带出重，不选
Linux namespace / chrootfs + proc需要 root / 特殊权限无原生用户态工具不适用
临时目录 + cp -r仅 fs拷贝时间与仓库大小线性相关丢 git 历史不能 merge 回
git worktree仅 fs（共享 object db）秒级git 原生选它

选择成本：

  • 不隔离 env/network/secrets。sub-agent 能读主仓的 .env、能发 HTTP、能调 ~/.ssh/id_rsa —— 这不是 worktree 要管的，由权限系统负责（详见 ch.09）。
  • 不能防止恶意行为。把"不信任的 agent 跑"当目标，worktree 不够，得上容器。
  • 主仓 object database 共享。一个 worktree 的 git gc 会影响所有 worktree；对长时运行的 agent 是考虑点。Claude Code 里 agent worktree 被设计成短期，问题不显著。

选择收益：

  • 秒级创建 / 删除。不 fetch 场景下 worktree add 通常 < 200ms，post-creation setup 多占 100-500ms（取决于 .worktreeinclude 大小）。
  • 共享依赖（symlink node_modules）。磁盘占用只和实际改动相关。
  • 和现有 git 工作流天然兼容。开发者手动 git worktree list / cd 过去继续干活。
  • 可以 merge 回主分支 —— 这是 vs 临时目录的根本差别。

6.8 可迁移的点¶

写完这章，几个可以直接搬到别处的模式：

1. 用 VCS 自带机制做沙箱。 不用自己发明 snapshot。hg 有 hg share、jj 有 jj workspace，Mercurial/Jujutsu 用户可以在 hook 里把 git worktree 的地方换成对应命令，Claude Code 架构不变。

2. Get-or-create 语义。 同名 slug = resume。fast-resume 路径读文件指针绕开 git spawn。这个模式在 cron retry、用户重跑同名任务、崩溃恢复都用得上。关键是：resume 必须幂等 + 必须快。

3. Fail-closed 三态删除门。 ChangeSummary | null 而不是 boolean。用户对"误删"的容忍远低于"删不干净"。这个模式也适用于权限撤销、资源回收、数据迁移的 dry-run 判断。

4. 分层复用。底层 getOrCreateWorktree / performPostCreationSetup 纯函数不碰全局状态。顶层 createWorktreeForSession（写单例）和 createAgentWorktree（不写）各自包装。比起"在底层加 isSession: boolean 参数"更清晰 —— 参数开关堆多了会变成 god function，分层之后每层只做一件事。

5. Hook 作为 VCS 抽象层。 两个 hook 就抽象了整个 VCS 后端。前提：把 worktree 的语义压缩到最小接口（slug in → path out）。这也适用于任何"核心逻辑用 git 但想兼容其他系统"的场景 —— 别试图在内部抽象出"VCS 接口"，让用户配置 hook 自己实现更简单。

6. 目录折叠 + 按需展开。 .worktreeinclude 处理 gitignored 文件时用 ls-files --directory 先折叠，再按 pattern 展开需要的。在任何"大量文件 + 白名单过滤"的场景都能搬（比如构建产物清理、大仓 CI）。

6.9 边界（交叉引用）¶

  • Agent Loop 本身不在本章范围（详见 ch.03）。worktree 是 agent 的运行地，不是 agent 的推理逻辑。
  • Sub-agent 调度（主 agent 何时派 sub-agent / async 还是 sync / 失败重试）详见 ch.04。本章只讲 worktree 侧 —— sub-agent 要不要隔离、在哪里隔离、如何清理。
  • Plan Mode 详见 ch.05。Plan 产出的 slug 会被 getPlanSlug() 用作 worktree 默认名（EnterWorktreeTool.ts:90），这是耦合点，但 plan 本身的机制不讲。
  • Tool 接口（buildTool 模板、shouldDefer、validateInput 在框架里的位置）详见 ch.08。
  • 权限（agent 能不能访问 worktree 外文件、能不能调 shell）详见 ch.09。worktree 提供文件系统隔离；访问控制由权限系统负责，两者互补不互替。
  • Agent SDK 的 isolation 参数（面向外部集成者、和本章 AgentTool 的 isolation 同义）详见 ch.23。
