9.2 为什么挑这个设计出来讲¶

Tool-based agent 的 UX 有个根本矛盾：安全感需要每次问，但每次问就没法用。要么像银行 app 一样每点一下敲一遍生物识别，要么像 rm -rf / 一样全权放手。Claude Code 的答案是把"决策权"切成八段，每一段都有机会在不打扰用户的前提下给出结论。真正走到面板那一步的，只有前面七段都不敢做主的那部分。

这一章讲两件事：八段决策管线，以及让前七段真的能处理掉 90% 场景的三条支撑机制。

9.3 关键数据结构¶

9.3.1 六种权限模式¶

外部用户五种，加上 auto 一种 ant-only。auto 的额外含义是：不是按规则做决定，而是让一个独立的分类器模型看当前对话和将要执行的动作，决定是否放行。

Shift+Tab 的循环只走 default → acceptEdits → plan（src/utils/permissions/getNextPermissionMode.ts:38-62）。bypassPermissions 必须用 --dangerously-skip-permissions 启动才进入循环，dontAsk 从不在循环里出现。这是刻意的：前者太危险，后者用于 CI。

隐藏细节（src/types/permissions.ts:28）：InternalPermissionMode 类型联合里还有一个 'bubble'，没有被放进 INTERNAL_PERMISSION_MODES 的运行时列表（src/utils/permissions/PermissionMode.ts:97-105 的 isExternalPermissionMode 也排除它）。用户通过 settings.json、CLI flag、Shift+Tab 任何入口都到不了这个值 —— 它只是类型收敛用的旗标，产品层看不到它存在。

9.3.3 规则值和规则来源¶

source 八种：userSettings | projectSettings | localSettings | flagSettings | policySettings | cliArg | command | session（src/types/permissions.ts:54-62）。前五种是持久化的，后三种只活在内存中。

磁盘层的加载顺序由 SETTING_SOURCES 常量（src/utils/settings/constants.ts:7-22）决定 —— 数组里靠后的 source 覆盖靠前的 —— 即 userSettings → projectSettings → localSettings → flagSettings → policySettings，policy 最高。getEnabledSettingSources（src/utils/settings/constants.ts:159-167）总是把 policySettings 和 flagSettings 强制包进来，因此 IT/CLI 层永远能压住 user 层。loadAllPermissionRulesFromDisk（src/utils/permissions/permissionsLoader.ts:120-133）在 allowManagedPermissionRulesOnly 开启时直接只读 policy、忽略其他所有 source。

9.3.4 运行时权限上下文¶

三种规则表（allow/deny/ask）各自按 source 分桶，{userSettings: string[], projectSettings: string[], ...}。判定时按 source 的优先级遍历。

9.3.5 变更是值¶

每次用户点一下"Always allow"，UI 不直接改 settings，而是构造一个 PermissionUpdate 数组交给权限层。destination 是 source 的子集，只有五档（src/types/permissions.ts:87-94）：userSettings | projectSettings | localSettings | session | cliArg —— flagSettings、policySettings、command 这三种 source 只读，不能被用户交互写回去。

这个数组同时被：

  • applyPermissionUpdates（src/utils/permissions/PermissionUpdate.ts:196-206）折叠进运行时 ToolPermissionContext
  • persistPermissionUpdates（src/utils/permissions/PermissionUpdate.ts:349-353）按 destination 落盘

两条路独立。放到 session 就只改内存；放到 localSettings 就同时改内存和磁盘；hook 返回一个 allow 带 updatedPermissions: []，就只授这一次权；hook 返回一个 allow 带 updatedPermissions 写明 destination，就既放行这次也替用户固化规则。supportsPersistence（src/utils/permissions/PermissionUpdate.ts:208-216）明确：只有 userSettings / projectSettings / localSettings 三档走磁盘路径，session 和 cliArg 走内存路径。

9.4.2 1d → 1e → 1f → 1g：bypass 免疫的四层兜底¶

bypassPermissions 一票通过太粗暴，真实系统需要在 bypass 之前就拦住一部分危险操作。这就是 1d 到 1g：

四种 bypass 免疫：

  • 1d 工具 deny：工具自己觉得危险，比如 Edit 里的 matchingRuleForInput(..., 'edit', 'deny') 命中
  • 1e requiresUserInteraction：AskUserQuestion、ExitPlanMode、ReviewArtifact 等"工具的意义就是要问人"的工具
  • 1f 内容特定 ask：用户显式写了 ask: ["Bash(npm publish:*)"]，那就不能被 bypass 盖过
  • 1g safetyCheck：.git/、.claude/、.vscode/、.idea/、.husky/、shell 配置文件（.bashrc、.zshrc、.profile 等）、.mcp.json、.claude.json 这一组"写了就毁仓"的路径，官方文档管它叫 protected paths（来源：https://code.claude.com/docs/en/permission-modes，访问于 2026-04-19）

这四层和官方文档的 "Protected paths"、"Bypass permissions mode skips permission prompts except for writes to protected directories" 是对应的。从设计上看，这是"bypass 是给环境用的，不是给人用的"—— 装 Docker 的容器内开 bypass，但 .git 里的 hook 文件仍要人来确认。

隐藏细节（src/utils/permissions/permissions.ts:1171-1181 + handleInteractivePermission 的 race 结构）：PreToolUse hook 返回 allow 也压不住 settings 里的 deny 规则。原因在决策的时间顺序：1a 的 tool-level deny 在 hasPermissionsToUseTool 里就直接返回，根本不会走到 handleInteractivePermission 那一层；hook 只在外层决策出了 ask 之后才以并发路径参与赛跑。官方文档同样写："Hook decisions do not bypass permission rules. Deny and ask rules are evaluated regardless of what a PreToolUse hook returns"（来源：https://code.claude.com/docs/en/permissions，访问于 2026-04-19）。反过来，hook 可以把一个 ask 改写成 allow，但不能把 deny 反否决。hook 的完整触发模型、exit code 2 的 "interrupt" 行为等见 ch.14。

9.4.3 2a → 2b → 3：模式闸门、全局放行、兜底问人¶

2a 是 bypass 模式唯一的出口。注意 plan 模式也可能在这里放行：如果用户曾经启用过 bypass 模式（isBypassPermissionsModeAvailable: true），那么即使切到 plan，也享受 bypass 的"全通"待遇。这条件之"奇怪"，是用户 launch 行为的记忆——--dangerously-skip-permissions 启动过的 session 里，plan 和 bypass 是同一条路。

2b 是全局放行规则。用户在 /permissions 里选 "Always allow Bash"，或在 settings.json 写了 "allow": ["Bash"]，就在这里命中。

3 是兜底。工具的 checkPermissions 返回 passthrough —— 意思是"我没看到我关心的情况"——那就统一升格为 ask，去问用户。

9.4.4 外层改写：dontAsk 与 auto¶

八步之后，外层 hasPermissionsToUseTool 再做一次模式改写：

dontAsk 的语义是"所有 ask 当 deny 处理"，这样 CI 脚本可以在 --permission-mode dontAsk 下跑：白名单里没写的一概拒绝，绝不 hang 住等人。注意这个改写放在最外层，而不是下放到每个工具。这么做的理由是：dontAsk 是跨工具的全局语义，每个工具自己判断反而会漏。这是对"分层"的一个反向选择—— acceptEdits 下放到工具，dontAsk 上提到顶层。

9.4.5 总结：八步的取舍¶

按 behavior 类型分组，这八步其实就是三张"优先级表"：

  • deny 的优先级：1a > 1d > 其他（最外层 deny 规则 > 工具自判 deny > 模式 deny）
  • ask 的优先级：1b > 1e > 1f > 1g > 3（工具级 ask > 交互类工具 > 内容特定 ask > 安全检查 > 兜底）
  • allow 的优先级：2a > 2b >（工具 checkPermissions 返回 allow 作为 toolPermissionResult 也在这条路径上）

deny 始终最高优先级，且绕不过；ask 仅在 bypass 之下几层豁免；allow 需要显式命中规则或模式。这和官方文档说的 "deny -> ask -> allow, first match wins" 一致（来源：https://code.claude.com/docs/en/permissions，访问于 2026-04-19）。

9.6 "每次都问却不烦"背后真正起作用的三条机制¶

到这里数据结构和决策管线都摆完了，看起来是个不错的复杂系统。但这章副标题问的是：为什么用起来真的不烦？

读完源码我挑出三条支撑机制，每一条单拎出来都能被其它 agent 项目直接借鉴。

9.6.1 工具自身有一等的 checkPermissions¶

权限判定不是中心化的"先查规则表、再匹配工具"，而是每个工具自己实现一个 checkPermissions(input, context): PermissionResult。中心调度只做：

  • 工具级粗粒度规则（1a / 1b / 2b）
  • 模式闸门（2a / 外层 dontAsk/auto）
  • passthrough → ask 的兜底

其他全部下放。后果是：

  • BashTool.isReadOnly(input) 可以识别 ls / cat / grep 这种 OS 里的只读命令；读操作工具自己就直接 allow 了，根本不升到决策管线（src/tools/BashTool/bashPermissions.ts:1154）
  • FileEditTool.checkPermissions 里对工作目录的写操作按 acceptEdits 自动放行（src/utils/permissions/pathValidation.ts:207）
  • FileReadTool 对工作目录的读直接 allow（src/utils/permissions/filesystem.ts:1136-1151）
  • MCP 工具的 ruleContent 用 mcp__<server>__<tool> 格式，让一条 mcp__puppeteer__* 规则涵盖整个 server 的所有 tool（来源：https://code.claude.com/docs/en/permissions，访问于 2026-04-19）

换句话说，最常见的场景（读工作目录的文件、跑 grep、跑 git log）根本就不走决策管线，工具自己就拍板 allow 了。用户感知里的"我做了很多事都没被问过"，底层的真相是"这些事到中心调度前就被工具级拍板了"。

这个架构的成本：每个工具都要知道权限怎么判。Tool 接口（src/Tool.ts:402-435）强制每个工具实现 checkPermissions / isReadOnly / isConcurrencySafe。TOOL_DEFAULTS（src/Tool.ts:757-769）里给的默认值有两层含义：

  • isReadOnly / isConcurrencySafe / isDestructive 默认都 false（假设不安全、要保守）
  • checkPermissions 默认返回 { behavior: 'allow', updatedInput: input } —— 源码注释写明 "defer to general permission system"

也就是说，工具不表态时不会被当成 ask，而是返回 allow 把判定权交还中心调度；由 2a/2b/3 决定最终结果 —— 没有命中 2b 的显式 allow 规则，才在第 3 步转为 ask。新工具 onboarding 必须显式思考"我是不是 read only"、"我的 input 里哪部分影响权限判定"，这是一个学习曲线。收益是每个工具都能给出最精确的答案，而不是在中心表里和别的工具共享一套方言。（Tool 接口的其他必实现字段、以及 requiresUserInteraction / isConcurrencySafe 的语义详见 ch.08。）

9.6.2 一次授权是一个值，五档 destination 任选¶

用户在面板上点 "Always allow Bash(rm)"，UI 层不是直接去改 settings，而是构造一个 PermissionUpdate：

destination 是用户在面板上二次选择的（"这个项目里"/"全局"/"只这次"/...）。这个对象流到 ctx.handleUserAllow：

persistPermissions（PermissionContext.ts:139-147）同时做两件事：落盘 + 更新运行时 ToolPermissionContext。纯函数 applyPermissionUpdate（src/utils/permissions/PermissionUpdate.ts:55-188）负责把 update 折叠进 context，persistPermissionUpdate（PermissionUpdate.ts:222-342）负责按 destination 写到对应的 settings 文件里。

这个抽象的延展性很强：

  • Hook 返回值也是 PermissionUpdate[]（src/hooks/toolPermission/PermissionContext.ts:232-237），一个 PreToolUse hook 可以说"放行这次，同时给我加一条规则"
  • Session destination 不落盘（PermissionUpdate.ts:208-216），用来实现 "Allow for this session only"
  • CLI --allowedTools 走 cliArg destination，也是纯内存
  • Sub-agent 把权限请求转给 leader（src/hooks/toolPermission/handlers/swarmWorkerHandler.ts:67-122），leader 应答的 permissionUpdates 同样以 PermissionUpdate[] 为货币

"变更是值"让权限系统和会话、hook、sub-agent、远程设备全都用同一个 currency 通信。对比那些把"授权"写成 hardcode boolean state 的系统，这里任何授权决定都能序列化、传递、延迟应用。Agent SDK 侧 canUseTool 回调返回的结构也与 PermissionUpdate[] 同构（详见 ch.23）。

隐藏细节（src/tools/AgentTool/runAgent.ts:297-300 + src/utils/forkedAgent.ts:146-167）：sub-agent 默认不继承主 agent 的 session "Always" 白名单。AgentTool 在启动 worker 时会构造一个新的 toolPermissionContext；如果 agent 定义里写了 allowedTools: [...]，runAgent 用 createGetAppStateWithAllowedTools 把这份列表写进 worker 的 alwaysAllowRules.command，且替换（不合并）原先的 command 桶 —— 源码注释写明"replaces ALL allow rules so the agent only has what's explicitly listed (parent approvals don't leak through)"。也就是说主 agent 刚刚点的 "Always allow Bash(rm)" 在 sub-agent 里不算数。这个隔离结合上面的 mailbox-claim 协议（见 9.6.3）：sub-agent 自己没有白名单命中就把权限请求回传给 leader，由 leader 重新决策。sub-agent 生命周期的完整视角见 ch.04。

这是最关键的一条，也是最容易忽略的一条。

当八段决策结果是 ask，useCanUseTool 把球传给 handleInteractivePermission（src/hooks/toolPermission/handlers/interactiveHandler.ts:57-）。它不是简单把面板弹出来然后 await 用户点击，而是：

核心抽象是 createResolveOnce，只有十几行：

claim() 是原子的 check-and-set：第一个叫到的路径赢，其他人调用都返回 false，默默退出。全仓用 createResolveOnce 做 claim 仲裁的消费者一共六路：

  1. 本地面板（interactiveHandler.ts:138 / 160 / 184）—— onAllow / onReject / onAbort
  2. Bridge（interactiveHandler.ts 内 bridgeCallbacks.onResponse）—— claude.ai 侧的远程应答（机制详见 ch.17）
  3. MCP channel（interactiveHandler.ts:363-398）—— Telegram / iMessage / Discord 等第三方通道的回调
  4. PreToolUse hook（interactiveHandler.ts:414-430）—— ctx.runHooks 的返回值（hook 的完整执行模型见 ch.14）
  5. Bash classifier（interactiveHandler.ts:454-521）—— executeAsyncClassifierCheck 的 onAllow
  6. Sub-agent worker → leader 的 mailbox（src/hooks/toolPermission/handlers/swarmWorkerHandler.ts:67-120）—— worker 把请求转给 leader，leader 这边的响应也走同一协议（sub-agent 的整体机制见 ch.04）

六路独立注册、独立竞争，共享同一个 12 行的原子抽象。

这套赛跑架构的实际意义：

  • 用户不需要盯着面板等。手机上的 Telegram channel、IDE 里的 claude.ai 标签页、本地终端——哪个先响应哪个就算数
  • PreToolUse hook 可以在用户看到面板的同时在后台读项目规则、查远程策略、决定是否替用户应答
  • Bash classifier（ant-only 的 "prompt rule" 机制）用一个独立模型判断 git status 这类命令是否"显然安全"，面板弹出来后几百毫秒内如果判断是 safe，自动以 "classifier 批准" 的身份 resolveOnce，面板打个勾消失（interactiveHandler.ts:454-521 里还有一段 "checkmark transition timer" 让用户看到"自动通过"的反馈，而不是面板无声消失）
  • Sub-agent 的权限转移——worker 把请求发给 leader，同时本地也可以有响应 —— 走的是同一个 claim 协议（swarmWorkerHandler.ts:81-119）

"不烦"最本质的来源是：大多数情况下用户根本看不到面板，因为 hook 或 classifier 在面板 render 完成之前就已经 claim 掉了。即使看到了，也可能几秒后自动消失（classifier 后到的批准会触发 checkmark 动画）。用户的实际体验是"偶尔问一下"，而不是 "一秒两个弹窗"。

赛跑架构的代价是每个路径都要幂等、每个回调都要检查 claim()、每个 pushToQueue 都要有配套的 removeFromQueue 兜底、abort signal 要挂满所有订阅。interactiveHandler.ts 长达 536 行，大半是这种管理并发状态的代码。但这正是"每次都问却不烦"的结构性来源——取消了"必须等用户"的同步依赖，异步响应者全部能贡献。

9.7.2 耦合点：沙箱给 Bash 开的豁免¶

两套机制的唯一耦合点在决策管线的 1b：

翻译成人话：即使用户配了 ask: ["Bash"]，只要沙箱开着且 autoAllowBashIfSandboxed 开着，Bash 的命令不走 ask 分支，而是交给 BashTool.checkPermissions 里更细的判断。沙箱给了 OS 级别的隔离（macOS 的 sandbox-exec、Linux 的 seccomp + bubblewrap），每条命令再弹一次面板就重复了。

checkSandboxAutoAllow（src/tools/BashTool/bashPermissions.ts:1270-）仍然会先跑显式 deny/ask 规则（包括 compound 命令的每一个子命令），所以这个豁免不是绕过用户的 deny: ["Bash(git push *)"]，只是取消"每次都问"。

官方文档原文：

"When sandboxing is enabled with autoAllowBashIfSandboxed: true, which is the default, sandboxed Bash commands run without prompting even if your permissions include ask: Bash(*). The sandbox boundary substitutes for the per-command prompt."

（来源：https://code.claude.com/docs/en/permissions，访问于 2026-04-19）

9.7.3 /sandbox exclude 的反向作用¶

/sandbox exclude "docker *" 把命令加到 sandbox.excludedCommands（src/utils/sandbox/sandbox-adapter.ts:865-875）。这些命令不会被沙箱包起来，所以 shouldUseSandbox(input) 返回 false，1b 的 canSandboxAutoAllow 条件不满足，流向常规的 ask 分支。

反直觉但合理："加到 excludedCommands" 和 "加到 allow" 意义相反。前者说"这个命令太复杂，不能塞进沙箱，反而要人工确认"；后者说"这个命令足够安全，沙箱里还是沙箱外都不用问"。

9.8 Plan Mode 在权限层做了什么¶

按副标题讲的逻辑，本章也要说清 Plan Mode 在 permission 判定里的角色。我找了半天源码，得出一个可能不符合直觉的结论：

Plan Mode 在 permission 层几乎什么也没做。

全仓扫 mode === 'plan'，对权限判定有实际影响的只有两处：

都是"继承前一种模式"的分支：plan + 曾开 bypass → bypass 规则继续；plan + auto 激活中 → classifier 规则继续。这俩都是放行的合并条件。

至于"plan 模式下写操作被拦下"这件事——在 FileEditTool.checkPermissions、FileWriteTool.checkPermissions、BashTool.bashPermissions.ts 里都没有 mode === 'plan' 的分支。也就是说 plan 模式的"禁写" 不是 permission 层硬拦截。

真实实现在两个地方：

  1. System prompt：plan 模式下，prompt 里附一段"you are in plan mode, do not use edit tools"的指令，让模型自己克制
  2. ExitPlanMode 工具作为唯一出口（src/tools/ExitPlanModeTool/prompt.ts:6）：模型要想写代码，必须先用 ExitPlanMode 向用户提交 plan，用户批准后才切到 acceptEdits 或其他写模式

所以 plan mode 在 permission 视角下就是个"不改变任何行为但记录了一个旗标"的模式。它靠的是对模型的劝说而不是对工具的拦截。这种设计选择背后是明确的 trade-off：如果要在 permission 层硬拦，每个写工具都要加一段 if (mode === 'plan') return deny，而且 deny 的错误消息得解释给模型看。现在的做法让 plan mode 的语义完全留在对话层，工具不用知道。

（Plan Mode 的完整机制、plan 文件的存储、ExitPlanMode 工具、5-phase plan workflow、以及 ExitPlanMode 被用户批准后如何切到 acceptEdits 等详见 ch.05。）

9.9 设计取舍¶

9.9.1 为什么不是中心化查表¶

最朴素的实现是做一张"工具 × 动作 × 资源"的查表，所有权限集中在一处匹配。Claude Code 没这么做。

代价：每个工具都要写自己的 checkPermissions，新工具 onboarding 要思考权限。 收益：

  • Bash 的 "read-only 命令放行" 逻辑、Edit 的 gitignore-style 路径匹配、WebFetch 的 domain 匹配、MCP 的 server__tool 匹配，全都用各自的代码写，不挤到同一张表里造方言
  • 工具 checkPermissions 返回 PermissionResult 而不是 boolean，可以携带 decisionReason、suggestions、updatedInput（让工具有机会"改写 input 再放行"）
  • 工具知道自己的 input schema，可以做结构化判断而不只是字符串匹配

中心调度只做通用的 5 段：tool-level 的 deny/ask/allow 规则、模式闸门、passthrough → ask 转换。

9.9.2 为什么 dontAsk 下放和 acceptEdits 上提的方向是反的¶

acceptEdits 下放到工具的 checkPermissions（具体是 pathValidation.ts:207），dontAsk 上提到最外层 hasPermissionsToUseTool（permissions.ts:505-517）。为什么？

acceptEdits 的语义是"在工作目录里的写操作放行"——而"什么叫工作目录"、"什么叫写操作"、"哪些路径是 protected" 是工具自己知道的知识。下放让每个写工具自己判断，Edit / Write / NotebookEdit 可以各自定义 acceptEdits 的覆盖范围。

dontAsk 的语义是"所有 ask 当 deny 处理"——这是跨工具的全局语义，每个工具自己抄一遍会漏。上提让一处代码兜底所有。

一个是"精细规则"，交给工具。一个是"粗粒度闸门"，交给顶层。这不是教条主义的"全下放"或"全集中"，而是按语义的宽窄决定位置。

9.9.3 赛跑架构的复杂度成本¶

handleInteractivePermission 536 行，大半是 claim 协议、abort 订阅清理、checkmark timer、queue 增删。对比一个朴素实现"弹出面板 → await 用户点击"可能 50 行就够了。

这个复杂度值不值？

把这 10× 的代码翻译成用户体验：每次 ask 都同时在本地、远程设备、hook、classifier 几条路径上等应答。如果 PreToolUse hook 在 10ms 内返回了 allow，用户甚至看不到面板。如果 classifier 在 300ms 内判断安全，面板弹出来立刻打钩消失。如果用户正在手机上，面板在手机的 iMessage 里先被点了。

减少用户看到面板的概率 = 减少用户的干预次数 = "不烦"。这个指标不线性反映在代码行数上，但会线性反映在"一个 30 分钟的会话里被问几次"上。

9.10 可迁移的点¶

做 agent、做 CLI 工具、做需要用户确认动作的系统，可以直接借走的三个做法：

  1. 决策管线分段。硬 deny 最先（没有例外）→ 工具自判 → 模式闸门 → 硬 allow → 问用户 → 外层模式改写。每一段都是一次"能不能在这里短路"的机会。不要把所有判定挤在一个函数里。
  2. 把授权建模成值（PermissionUpdate）。不要直接 mutate 权限 state。{type, target, behavior, destination} 这种四元组可以同时被 UI、hook、远程、CLI flag 用同一份代码处理。destination 的"session / local / project / user"分级让临时授权和永久授权走同一条路。
  3. claim() 做赛跑仲裁。十几行的 createResolveOnce 换来几路异步路径的原子竞争。任何"要等用户点击"的场景都可以套这个抽象：加一路 hook 预检、加一路远程审批、加一路 AI 自动判断，每一路独立实现，加一路代码行数几乎不增加。

这三条合在一起就是本章的副标题：每次都问——每个动作都走决策管线，不跳过任何判定；却不烦——前面七段在用户看到面板之前就解决了绝大多数场景，剩下那少数真到面板的，还有三路异步响应者和用户赛跑。
