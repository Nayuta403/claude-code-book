7.1 本章要讲的核心设计¶

Claude Code 的记忆系统真正值得拆开讲的是一个点：memdir —— 把"跨会话记忆"从对话缓冲里搬到普通的文件系统，用 MEMORY.md 当索引、用 YAML frontmatter 做类型约束，让模型自己维护它。

围绕这个核心，有三层周边设计：

  • CLAUDE.md —— 用户写、每次 session 启动全量加载、不做截断。
  • Compact —— context 快满时把历史压成一段摘要、保留 boundary marker 作时间分割线。
  • Token 估算 —— API 真值 + 本地 rough 估算，让 compact / /context 的数字和实际 API 请求对得上。

本章把这四块按"用户实际看到什么 → 怎么实现 → 设计取舍"的顺序讲一遍。读完你应该能回答：Claude Code 的三层记忆边界是什么？memdir 为什么用文件系统？compact 怎么保证不把关键信息丢光？src/query/tokenBudget.ts 和 context 预算的关系到底是什么？

7.2 三层记忆的边界¶

官方文档把记忆系统分两层（CLAUDE.md + auto memory，来源：https://code.claude.com/docs/en/memory，访问于 2026-04-19）。从工程实现看应该分三层，把会话内 messages[] 也算上：

层谁写何时加载何时清文件位置
会话 messages[]（详见 ch.03）Agent Loop不加载，本来就在/compact 把它压成 summary内存 + ~/.claude/projects/<p>/sessions/
CLAUDE.md 系用户每次 session 启动 + compact 后重读不清项目 / 用户 / 管理员
memdir（auto memory）模型自己启动时注入 MEMORY.md 索引；运行时 findRelevantMemories 选 top-5不清~/.claude/projects/<p>/memory/

注意：仓库里的 src/history.ts 管的不是对话历史，是斜杠输入框的 Up-arrow / ctrl+r 历史（详见第 20 章输入层）。它和 context 管理基本没关系，本章不展开。如果你在 src/history.ts:19 看到 MAX_HISTORY_ITEMS = 100，这是输入框的条目数上限；文件落在 getClaudeConfigHomeDir() 下的 history.jsonl，和会话落在 ~/.claude/projects/<p>/sessions/ 的 jsonl 是两套文件。

7.2.1 会话内 messages¶

Message[] 由 Agent Loop 持有，结构和 API 的消息协议几乎对齐（user / assistant / system / attachment / hookResult / systemCompactBoundary）。本章只关心两个事实：

  1. 它是 compact 的输入。
  2. compact 后 messages[] 被替换成 [boundaryMarker, ...summary, ...preservedTail, ...attachments, ...hookResults]。

Agent Loop 怎么在每一轮检查 token 预算、什么时候调 autoCompactIfNeeded（详见第 3 章 Agent Loop）。

7.3 memdir：文件系统作为 memory¶

7.3.1 用户看到什么¶

第一次用 Claude Code 工作一段时间后，~/.claude/projects/<sanitized-repo>/memory/ 下会出现一个目录：

MEMORY.md 长这样：

每条一行，指向一个话题文件，附带 one-line hook（做决策用）。话题文件本身带 frontmatter：

运行 /memory 斜杠命令会弹一个列表，让你选任一 memory 文件用 $EDITOR 打开（src/commands/memory/memory.tsx:21-63）。

7.3.2 为什么挑这个设计出来讲¶

大多数 agent 的"跨会话记忆"是个向量库、一张 KV 表，或者直接写进 system prompt 加固。这三种办法的共同问题：用户看不见、改不了、diff 不出来。

memdir 的选择有三个可迁移的点：

  1. 普通的 markdown 文件。 用户可以 cat / grep / vim / git diff。模型也可以用它已经熟练的 Write / FileRead / Grep 工具直接操作 —— 不需要一套专用的"memory API"。
  2. 索引文件 + 话题文件的分离。 每次 session 启动只把索引（≤ 200 行 / 25 KB）注入 context，详细信息按需读取。这把"维护 memory"和"消耗 context"解耦了。
  3. frontmatter 做闭集类型约束。 不是开放标签，而是 user / feedback / project / reference 四个枚举值，外加一份"什么不存"的反面列表。这比"随便分类"能约束得住模型得多。

下面按这三个点展开。

7.3.3 关键数据结构¶

memdir 根路径（src/memdir/paths.ts:223-235）：

getAutoMemBase 用 findCanonicalGitRoot（src/memdir/paths.ts:203-205），因此一个 git 仓库的所有 worktree 共享一份 memory —— 切分支切 worktree 时记忆不会失联。

索引截断（src/memdir/memdir.ts:34-38）：

两条截断规则：先按 200 行截，再按 25 KB 截（切在最后一个 \n）。第二条是防"单行索引太长"的病理情况 —— 有用户把一整页 markdown 塞进 200 行内但 byte 数爆了（注释里记录了 p100 观测到 197 KB）。截断后末尾追加 WARNING（src/memdir/memdir.ts:95-98）告诉模型哪根 cap 触发了、让它缩索引。

隐藏细节（src/memdir/memdir.ts:87-98）：两道 cap 谁触发 WARNING 里会点名（"197 KB (limit: 25 KB) — index entries are too long" 还是 "234 lines (limit: 200)"），不是一条通用的"已截断"。这是 prompt 工程上一个很细的闭环：模型读到自己写的索引被截、被告诉具体原因，下一轮才会对症缩行或并条。通用 WARNING 只会让它缩一半凑合。

类型枚举（src/memdir/memoryTypes.ts:14-19）：

四种的语义边界写在 TYPES_SECTION_INDIVIDUAL 里（src/memdir/memoryTypes.ts:113-178），每种都有 <description> / <when_to_save> / <how_to_use> 三段，外加 <examples>。简化成一张表：

type存什么不存什么
user用户角色、目标、知识背景、偏好当前任务细节
feedback工作方式纠正 / 确认（附 Why: / How to apply:）一次性的修复步骤
project决策背景、正在发生的事、deadline（日期转绝对）git blame 能查的
reference外部系统指针（Linear / Slack / Grafana URL）本仓库的文件路径

隐藏细节（src/memdir/memoryTypes.ts:28-31 parseMemoryType）：这个"闭集"只是 prompt 层的约定，运行时没有写入校验。写话题文件的是 Write 工具，不走任何 memory 专用 API；parseMemoryType 在 读取（memoryScan.ts:61）时对未知或缺省的 type 字段返回 undefined 并静默继续，manifest 里 [type] 前缀就不带标签。换句话说，模型随手写个 type: workflow 的 frontmatter 不会报错，只会在下次被 selector 看到时"没分类"。闭集靠 prompt 自律 + selector 对带标签的更敏感来维持，不是靠强校验。与 skills 的 frontmatter 约定同构（详见第 10 章 Skills）。

7.3.4 反面列表¶

WHAT_NOT_TO_SAVE_SECTION（src/memdir/memoryTypes.ts:183-195）是这个设计里最容易被忽略、但最关键的部分：

这是对 memdir 的信息论约束：凡是能从当前项目状态（代码、git、CLAUDE.md）重新得到的，就不要存。存进 memory 的应该是派生不出来的事实 —— 用户偏好、决策背景、外部指针。

最后一句（"even when the user explicitly asks you to save"）关掉了模型最容易犯的错：用户随口说"记一下今天的 PR 列表"，如果照做，下周 memory 就变成活动日志垃圾堆。反面列表强制模型把"存"这个动作升格为"在反面列表允许范围内"的问题。

7.3.5 写入约定¶

模型写 memory 的规矩是"两步写"（src/memdir/memdir.ts:223-234）：

  1. 新建话题文件（带 frontmatter），内容写进去。
  2. 去 MEMORY.md 加一行 - [Title](file.md) — one-line hook。

MEMORY.md 本身没有 frontmatter，它是纯索引，每行 ≤ ~150 字符（src/memdir/memdir.ts:227 明确提示）。

这个两步写有个容易忽略的工程细节（src/memdir/memdir.ts:116-119）：

注释解释：

Shipped because Claude was burning turns on ls/mkdir -p before writing. Harness guarantees the directory exists via ensureMemoryDirExists().

Harness 先 ensureMemoryDirExists（src/memdir/memdir.ts:129-147 递归 mkdir，静默吞 EEXIST），在 prompt 里明确告诉模型"目录已存在，直接 Write"。这种"把副作用前置到 harness、用 prompt 断言既成事实"的做法在本仓库里出现很多次 —— 主动消除模型的防御性动作。

7.3.6 读取：启动 + 运行时¶

启动注入走 getUserContext（src/context.ts:155-189）：把 memdir 的 MEMORY.md 和 CLAUDE.md 系一起拼成 user context。模型一进会话就看到"现在我记得这些东西"的索引。

运行时召回由 findRelevantMemories（src/memdir/findRelevantMemories.ts）做：

流水线：

  1. scanMemoryFiles 读目录下所有 .md（排除 MEMORY.md），只读前 30 行解析 frontmatter，按 mtime 排序取前 200（src/memdir/memoryScan.ts:21-22）。
  2. 格式化成 manifest 列表（src/memdir/memoryScan.ts:84-94）： ```
    • [feedback] feedback_testing.md (2026-02-14T10:20:00Z): Integration tests must hit real DB

    ```

  3. 用 Sonnet 跑一个 sideQuery，system prompt 是 SELECT_MEMORIES_SYSTEM_PROMPT（src/memdir/findRelevantMemories.ts:18-24），JSON schema 限定返回 {selected_memories: string[]}，max_tokens: 256。
  4. 过一遍 validFilenames 过滤幻觉。

两个 prompt 工程细节值得留意：

  • recentTools 参数（src/memdir/findRelevantMemories.ts:88-96）：模型正在用 mcp__X__spawn 时，把该工具的 reference 文档塞进 context 是噪声 —— 对话里已经有实际用法了。selector 会在 prompt 里收到 "Recently used tools: ..." 提示，避开 keyword 重合的 false positive。
  • alreadySurfaced 参数：之前 turn 已经 surface 过的不再选，省 5 slot 给新候选。

隐藏细节（src/memdir/findRelevantMemories.ts:98-122）：selector 走 sideQuery 用 getDefaultSonnetModel()，max_tokens: 256，output_format 强制 JSON schema {selected_memories: string[]}。这三个参数各有讲究：用 Sonnet 不用主模型（不污染主会话 prompt cache、独立计费）；256 tokens 是"5 个文件名 + 少量 JSON 括号"的紧上限，不给 selector 留写解释的空间（返回里只能有名字）；JSON schema 保证下游不需要 parse 自然语言。返回后还要过一道 validFilenames.has(f) 筛幻觉（:130）—— Sonnet 偶尔会返回根本不在 manifest 里的文件名。

7.3.8 安全边界¶

记忆目录是可写的，可写目录要防越界：

src/memdir/paths.ts:109-150 validateMemoryPath 拒绝：

  • 非绝对路径（../foo 会被 CWD 错误解释）
  • 长度 < 3（/a 这种近根）
  • Windows drive root（C:\）
  • UNC 路径（\\server\share）
  • null byte（syscall 截断）

裸 ~ / ~/ / ~/./~/.. 也拒绝 —— 否则 isAutoMemPath 会匹配整个 $HOME。

src/memdir/teamMemPaths.ts:109-171 realpathDeepestExisting + isRealPathWithinTeamDir 用 realpath 防 symlink 逃逸 —— 有人往 memory/ 里塞一个 symlink 指向 ~/.ssh/authorized_keys，字符串层 containment check 通过、真实路径检查拒绝。代码里明确写这是 PSR M22186 的处置（src/memdir/teamMemPaths.ts:103-107）。

另一处（src/memdir/paths.ts:176-186 getAutoMemPathSetting）：autoMemoryDirectory 设置不接受 projectSettings，只接受 policy / local / user settings：

a malicious repo could otherwise set autoMemoryDirectory: "~/.ssh" and gain silent write access to sensitive directories via the filesystem.ts write carve-out

这个威胁模型很具体：memory/ 目录在文件系统层有写权限特例，如果允许仓库内 .claude/settings.json 改它的路径，克隆恶意仓库就能写任意位置。排除 projectSettings 是跟 hasSkipDangerousModePermissionPrompt 同类的安全模式。

7.3.9 和 CLAUDE.md 的分工¶

官方文档：

Use CLAUDE.md files when you want to guide Claude's behavior. Auto memory lets Claude learn from your corrections without manual effort.

代码里对应的差别：

用一句话概括：CLAUDE.md 是"用户约定"，memdir 是"模型笔记"。两层都过 getMemoryFiles 同一条管道（src/utils/claudemd.ts:980-1007），在最终拼接层才通过 description 和 type 区分语义。

隐藏细节（src/tools/AgentTool/agentMemory.ts:52-65, 109-114）：sub-agent 不默认共享主 agent 的 memdir。当一个 agent 定义里显式声明 memory: 'user' | 'project' | 'local'（src/tools/AgentTool/loadAgentsDir.ts:92）时，它会拿到自己独立的 agent-memory 目录（<memoryBase>/agent-memory/<agentType>/ 或 .claude/agent-memory/<agentType>/），里面有自己的 MEMORY.md + 话题文件。没声明 memory: 字段的 sub-agent 则完全不挂载任何 memdir（连主的都不共享，避免污染主 agent 笔记）。CLAUDE.md 的加载逻辑走的是另一条路（文件系统向上搜），sub-agent 仍能看到项目的 CLAUDE.md —— 所以 CLAUDE.md 共享，memdir 隔离。详见第 4 章 sub-agent 执行边界。

7.4 Compact：上下文快满时的拯救¶

7.4.1 为什么必须主动 compact¶

官方文档：

Newer Claude models (starting with Claude Sonnet 3.7) return a validation error when prompt and output tokens exceed the context window, rather than silently truncating. （来源：https://platform.claude.com/docs/en/build-with-claude/context-windows，访问于 2026-04-19）

硬上限撞墙即报错（prompt_too_long）。所以 Claude Code 必须在撞墙前主动清出空间。加上另一条：

As token count grows, accuracy and recall degrade, a phenomenon known as context rot.

就算没撞墙，context 过满模型也会变蠢。所以还有一个"提前 compact"的动机。

7.4.2 阈值¶

所有阈值都从"有效 context window"（context window - 输出预留）倒推：

阈值设计的两个点：

  • summary 本身要占 17-20K（经验值 p99.99 = 17387 tokens）。所以 effective window 先减 20K，相当于"留一个压缩请求的位置"。
  • autocompact 和 blocking 之间留 3 KB 余量。这 3 KB 是为手动 /compact 保留的最后一次机会 —— auto compact 已经试过失败时，用户还能手动触发。

shouldAutoCompact 里真正触发的断言（src/services/compact/autoCompact.ts:225-238）是 tokenCountWithEstimation(messages) - snipTokensFreed >= getAutoCompactThreshold(model)。snipTokensFreed 是上一次 snip 已经省出来、但最近一条 assistant 的 usage 还没反映的量 —— 不减会导致连续误触发。

7.4.3 熔断器¶

注释：

BQ 2026-03-10: 1,279 sessions had 50+ consecutive failures (up to 3,272) in a single session, wasting ~250K API calls/day globally.

autocompact 可能 irrecoverable —— 上下文已经超过模型能摘要的规模，summary 请求本身就 prompt_too_long，每轮都重试的话就是死循环。熔断器：连续 3 次失败后放弃，本 session 剩下的轮次不再试。用户看到的表现是 UI 警告停止刷新、/compact 手动命令仍然可用。

隐藏细节（src/services/compact/autoCompact.ts:171-183）：shouldAutoCompact 还有一组递归抑制，和熔断器正交。当 querySource 是 'session_memory' 或 'compact' 时直接返回 false —— 这是为 fork agent 本身兜底的：compact 派出的 summary agent 如果自己的 context 涨了（比如拿到的 messages 堆已经巨大），它不能自己再触发一次 autocompact，否则两个 fork 互相生成会死锁。同样 'marble_origami'（ant-only ctx-agent）也被显式拒掉，因为它的 runPostCompactCleanup 会调 resetContextCollapse() 清主线程 committed log。这些 querySource gate 在代码里看着像"拍脑袋加的防御"，其实每一条都对应一次真实出过问题的 recursion。

7.4.4 主流程¶

几个细节值得拎出来：

Summary 派 fork agent 生成（src/services/compact/compact.ts:451）。fork agent 用独立的 prompt 跑，不污染主会话状态。注意 fork 时用 cacheSafeParams（src/services/compact/compact.ts:435-438）—— feature flag tengu_compact_cache_prefix 控制是否让 fork agent 复用主会话的 prompt cache 前缀。2026 年 1 月的实验数据：关掉这个 flag 的路径 98% cache miss，占 fleet cache_creation 的 0.76%（每天约 380 亿 tokens）。这条评论（src/services/compact/compact.ts:431-434）是典型的"数据驱动的默认值选择"。

PTL 重试（src/services/compact/compact.ts:243-291 truncateHeadForPTLRetry）：summary 请求本身 prompt_too_long 时，按 API round 分组丢最旧的组，直到够塞下。API 给出 getPromptTooLongTokenGap(ptlResponse) 指示差多少，就按这个差额累积丢。Vertex/Bedrock 的错误格式解析不了时回退到"丢 20%"。注意丢完后要补一条合成 user message（src/services/compact/compact.ts:284-288）—— API 要求第一条必须是 role=user，直接丢掉 group 0 会留下 assistant-first 序列。

messagesToKeep（src/services/compact/compact.ts:349-367 annotateBoundaryWithPreservedSegment）：compact 可以保留尾巴最近 N 条消息。boundaryMarker 的 preservedSegment 字段记录 {headUuid, anchorUuid, tailUuid}，用来在 session 回放时把被保留段接回 boundary 后面。这比"全部压成摘要"更耐用：最近的工具调用、正在进行的编辑上下文不会丢。

7.4.5 pre vs post compact token count：一个命名坑¶

历史上这俩都叫过 postCompactTokenCount，后来为了 event field 兼容保留了老名字，实际含义必须看变量名：

  • compactionCallTotalTokens：调 compact API 这次请求+响应的 token 总数。输入是 pre-compact 全量，输出是摘要文本。这是成本。
  • truePostCompactTokenCount：压缩后 context 实际大小 = boundary + summary + 重建的 attachments + hook 消息。这是下轮 shouldAutoCompact 会看到的数。

tengu_compact 事件里还有个 willRetriggerNextTurn（src/services/compact/compact.ts:656-658）基于后者判断：如果 compact 完还在阈值之上，下轮会立即再 compact 一次。这是健康度指标。

7.4.6 compact 后 CLAUDE.md 和 memory 的重载¶

src/commands/compact/compact.ts:63:

getUserContext 是 memoized 的（src/context.ts:155 memoize），清缓存后下次读会重新走 getMemoryFiles → 重新读磁盘上的 CLAUDE.md 和 MEMORY.md。官方文档对应的描述：

Project-root CLAUDE.md survives compaction: after /compact, Claude re-reads it from disk and re-injects it into the session. （来源：https://code.claude.com/docs/en/memory，访问于 2026-04-19）

子目录里的嵌套 CLAUDE.md 不自动重读 —— 它们靠"Claude 读那目录下的文件时"按需加载，compact 清了这个状态，下次读才触发。

隐藏细节（src/commands/compact/compact.ts:63, 117, 203）：getUserContext.cache.clear?.() 在 三条 compact 路径上都调一次（session memory / 传统 / reactive），而且用的是 ?.() 带可选链 —— 说明 cache 可能未挂（shim 或某种 memoize 实现）。被清的不是 MEMORY.md 文件本身，是 getUserContext 这个函数的 memoize 结果：CLAUDE.md、MEMORY.md 索引、以及拼接后的整段 user context 全部下次调用再重读。因此 /compact 之后 CLAUDE.md 的 任何文件系统变更（你在另一个窗口改了 ~/.claude/CLAUDE.md）会立刻生效 —— 这是一个没写在官方文档里的副作用。话题文件本来就不在 getUserContext 缓存里（按需召回），所以不受影响。

7.4.7 microcompact：只清 tool result，保留缓存¶

完整 compact 成本很高（要跑一次 summary API 调用）。src/services/compact/microCompact.ts 提供一条轻量路径：只删老的 tool result，不改对话结构。

COMPACTABLE_TOOLS（src/services/compact/microCompact.ts:41-50）限定在 FileRead / Shell / Grep / Glob / WebSearch / WebFetch / FileEdit / FileWrite —— 这些工具的结果可以重新执行得到，删了不会丢信息（模型可以重读）。

两条触发路径：

  1. Time-based（evaluateTimeBasedTrigger）：距上一次 assistant 消息超过阈值（几分钟），prompt cache 已经冷了，反正要重写整个前缀，那就顺便把老 tool result 清了 —— 减小重写量。
  2. Cached microcompact（ant-only，cachedMicrocompactPath）：用 cache editing API 从 prompt 中删 tool result，不改本地 messages。服务器端的缓存前缀保持不变，只是告诉它"这几个 tool_use_id 对应的 result 在下次请求里不要算"。

第二种更有意思：它把 compact 的副作用放到了 API 层而不是客户端。trade-off 是依赖服务端的 cache editing 支持（beta feature）。

7.7 设计取舍 & 可迁移的点¶

7.7.1 为什么 memory 用文件而不是向量库¶

Trade-off 很清楚：

文件 + 索引向量库
用户能读能改是否（opaque embedding）
Git 可 diff是否
召回准确度依赖 Sonnet 选 top-5更高
增量存储成本每 memory ~几百字节索引 + embedding ~几 KB
模型操作难度复用现有 Write / Read 工具需要专用 memory API

Claude Code 选了前者。关键理由：memory 系统的 success metric 是"模型能正确维护"，而不是"召回召回率高"。召回错了下次会改；维护不动直接废掉。模型熟练的是文件 I/O 不是 vector query，所以前者更稳。

这个 trade-off 不是普适的 —— 如果你的 agent 面对的是海量非结构化文本（法律文档、代码库全文），vector store 仍是对的。但对"agent 自己工作时生成的笔记"，文件路径赢。

7.7.2 为什么 MEMORY.md 和话题文件分离¶

"索引常驻 + 详细按需"是这个设计最值得借鉴的一点。它把两个相反的需求解耦：

  • 模型每次启动都需要知道"我记得什么"。这是全量 scan。
  • 模型大多数时候不需要读详细内容。只有特定查询相关时才要。

把索引单独放一个文件、截断到 200 行，既保证每次 session 都有 orientation，又避免把几十个话题文件的内容全灌进 context。一个 memory 系统长到几百条，index 仍然是 200 行可控的，详细内容按需 read。

配合 findRelevantMemories 的 Sonnet selector，形成一个两阶段召回：索引给粗粒度线索 + 按 query 精选 top-5。

7.7.3 为什么 frontmatter 用闭集 type 而不是开放 tag¶

开放 tag 的问题：模型会逐渐发明新 tag（workflow、tip、note、important），语义漂移。存 memory 和读 memory 的模型对同一个 tag 可能理解不同。

闭集有两个好处：

  1. 语义稳定。4 个值都在 prompt 里写了明确的 <when_to_save> / <how_to_use>，没有歧义空间。
  2. 反面列表有抓手。WHAT_NOT_TO_SAVE_SECTION 能写"这不属于以上四种任何一种，所以不存" —— 强反面约束。

代价：有些东西放不进任何一类就只能丢掉。这是设计者认可的代价 —— memory 要的是少而准，不是全。

顺便一提：memdir 的 frontmatter 契约（name / description / type + 反面列表）和 skills 的 frontmatter 同构（详见第 10 章 Skills）。这不是巧合 —— 同一套"文件 + frontmatter + MEMORY.md / SKILLS.md 索引 + 模型自己维护"的模板在仓库里复用了至少两次。

7.7.4 可迁移到自己项目的东西¶

如果你在做一个类似的 agent 系统，下面这些几乎可以直接搬：

  1. 文件式 memory + 索引。 目录 + MEMORY.md（≤ 200 行 / 25 KB）+ 话题文件 + frontmatter。
  2. 闭集类型 + 反面列表。 不要开放 tag。把"什么不存"写进 prompt，而且加一句"用户明确要求也不存这些"。
  3. 索引截断时附 WARNING 说明哪根 cap 触发。 模型看到 WARNING 会主动缩短。
  4. dir exists 断言前置。 ensureMemoryDirExists + prompt 断言"目录已存在，直接 Write" —— 省掉模型 ls/mkdir 的回合。
  5. 老化 disclaimer 用 <system-reminder> 标签。 超过 N 天的记忆自带"这是快照"提示。
  6. 召回用独立的小模型 selector。 不要把全量 memory manifest 塞进主会话；用 Sonnet / Haiku 跑一次独立的 selection 调用，max_tokens 256 够。
  7. compact 要有熔断器。 autocompact 失败 3 次就停，不要对着 prompt_too_long 死磕。
  8. "我看到的 context 大小" 必须复用"要发给 API 的预处理管道"。 否则 UI 和实际永远飘。
