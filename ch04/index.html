4.1　用户看到什么¶

在 Claude Code 的交互里，sub-agent 有两种观感。

同步 sub-agent。主 agent 在一轮回答里调一次 Agent 工具，终端上那条 tool 调用会挂十几秒到几分钟，显示一个转圈加"Running task"的进度行，超过 2 秒后多出一条"可以 Ctrl+B 移到后台"的提示。等它结束，主 agent 立刻拿到一条 tool_result，看起来就像一次普通的工具调用返回——只不过这条返回内容是"一段文字"，里面是 sub-agent 的最后一段陈述。

异步 sub-agent。主 agent 调 Agent 时带了 run_in_background: true，或者在 coordinator 模式下（下面会讲），调用立刻返回：

主 agent 拿到这条确认，本轮就结束。过若干分钟，一条 "user 角色的消息" 被塞回对话：

它看起来像用户说话，其实是系统塞进来的通知。主 agent 的系统提示里教过它识别 <task-notification> 开头，当成 sub-agent 的"回流信号"处理（coordinator 模式下这条规则在 src/coordinator/coordinatorMode.ts:144-160 有完整模板）。

终端底部还有一个背景任务 pill（ant 构建下走 Coordinator Panel，external 构建下走 pill）。键入 /tasks 可以展开：每条任务显示状态、描述、耗时。

4.2　为什么挑这个设计出来讲¶

可以用一句话概括：主 agent 的一次 tool call 被替换成 sub-agent 的完整 run。

这句话的工程含义是：主 agent 的 Agent Loop 代码并不需要区分"本地工具"和"sub-agent"，它看到的都是 tool_use / tool_result 对；是 Agent 工具的实现把"一整段 agent 生命周期"压进了一个 tool_result 里（Agent Loop 的完整结构见 ch.03）。这个抽象的副作用很好：

  • sub-agent 想怎么折腾 context 都行，它的 tool noise 停在它自己的 sidechain transcript 里。
  • 主 agent 的 prompt cache 不会因为 sub-agent 里调了一个工具就 bust 掉——它根本看不见那些 tool_use。
  • sync 和 async 两条路径共用同一个 tool 名字、同一个 schema，切换只是输出 union 的哪个分支。

官方博客对这个模式的描述是："they help manage context: subagents use their own isolated context windows, and only send relevant information back to the orchestrator."（来源：https://claude.com/blog/building-agents-with-the-claude-agent-sdk，访问于 2026-04-19）。

本章把源码里"这一条 tool call 到底做了什么"拆开。重点是三件事：上下文边界怎么画、state 机怎么对 sync 和 async 保持一致、权限请求怎么回流。

边界先说清楚：单 agent 的 Agent Loop 本身（query()、turn、stream event）不在本章，见 ch.03。Tool 接口与 buildTool 不在本章，见 ch.08。权限决策（allow/deny 规则、bash 规则） 不在本章，见 ch.09。worktree 文件系统隔离见 ch.06。cron 触发 Task 见 ch.13。Plan Mode 下的只读 sub-agent（Explore / Plan 的职责边界）见 ch.05。Remote permission bridge（异步 sub-agent 的远端权限回传通道）见 ch.17。Agent SDK 的 canUseTool hook 见 ch.23。

同步 sub-agent（sync）¶

  • 触发：run_in_background 为假、background: true 没在 agent 定义里设、非 coordinator、非 fork、非 kairos/proactive（判断在 src/tools/AgentTool/AgentTool.tsx:567）。
  • 生命周期：主 agent 当前 turn 被挂起直到 sub-agent 完成；期间主 agent 的 abortController 被 sub-agent 共享（src/tools/AgentTool/runAgent.ts:526-528），按 ESC 一起死。
  • 返回：一条 tool_result，data.status === 'completed'。
  • 结果内容：sub-agent 最后一条 assistant message 的 text 块，加一条 agentId: ... <usage> 尾巴（AgentTool.tsx:1363-1373）。

异步 sub-agent（async）¶

  • 触发：run_in_background: true、或 selectedAgent.background === true、或 coordinator/fork/kairos/proactive 任一为真。
  • 生命周期：AgentTool 登记一个 LocalAgentTaskState，void runAsyncAgentLifecycle(...) fire-and-forget 地跑（AgentTool.tsx:733-752）；tool 立刻返回 async_launched。
  • abortController 是全新、独立的（runAgent.ts:526），与主线程脱钩——ESC 不影响背景 agent。
  • 结果回流：完成时 enqueueAgentNotification 往消息队列里塞 <task-notification> XML，Agent Loop 下一轮作为 user role 注入（4.5 节展开；投递路径见 ch.03）。

两个特殊变种同样走 async 路径但外层处理不一样：

  • fork（forkSubagent.ts，gate FORK_SUBAGENT）：不传 subagent_type，子 agent 继承父的完整对话 + 父的系统提示，目的是最大化命中 prompt cache（4.8 节讲）。
  • remote（isolation: 'remote'，gate ant-only）：走 CCR 远端环境，返回 remote_launched，sessionUrl 里是远端 session URL。Remote 路径的权限回传通道（远端 session 与本地 lead 之间的桥）详见 ch.17。
  • worktree 隔离（isolation: 'worktree'）：sub-agent 运行在独立的 git worktree 里，父子共享一份 repo 但各写各的文件（详见 ch.06）。

两种形态的区别可以概括成一句：sync 用调用栈保留 sub-agent 的生死，async 把生死挪到 AppState.tasks 的 state 里，用一条 XML-in-user-message 把结果"外部送达"。

4.5　关键流程：一次 sub-agent 跑完一生¶

以一次 async sub-agent 为主线，sync 在必要处对比。

1. 选 agent + 组工具¶

AgentTool.call() 的入口在 src/tools/AgentTool/AgentTool.tsx:239-260。前几十行做的事按顺序：

  1. Swarm 分支（:262-316）：team_name && name 齐备走 spawnTeammate()（tmux 分屏或 in-process 新进程），直接返回 teammate_spawned。不进入后续路径。
  2. Fork 分支（:318-357）：实验开关 + 省略 subagent_type → 选 FORK_AGENT；否则按 subagent_type 查 agent 定义。如果找不到或被权限规则否定，抛 Agent type 'X' not found/denied。
  3. MCP 依赖等待（:370-410）：agent 定义的 requiredMcpServers 里有当前还没连接的，最多阻塞 30 秒等 MCP 握手完成。
  4. Remote 隔离（:435-482，ant-only）：teleportToRemote 建远端 session，立返 remote_launched。
  5. 系统提示组装（:492-541）：fork 路径从 toolUseContext.renderedSystemPrompt 取父的渲染产物、再 buildForkedMessages 克隆父的最后一条 assistant；普通路径调 selectedAgent.getSystemPrompt({ toolUseContext }) + enhanceSystemPromptWithEnvDetails。
  6. worker 的工具池独立于父（:573-577）： ts // src/tools/AgentTool/AgentTool.tsx:573-577 const workerPermissionContext = { ...appState.toolPermissionContext, mode: selectedAgent.permissionMode ?? 'acceptEdits' } const workerTools = assembleToolPool(workerPermissionContext, appState.mcp.tools) 父可能在 plan 模式（只读），sub-agent 照样按自己的 permissionMode 能写就能写。

到这里 runAgentParams 组装完成，进入 async/sync 分叉（AgentTool.tsx:686）。

隐藏细节（src/tools/AgentTool/runAgent.ts:577-646）：sub-agent 不继承主 agent 在交互中临时加载的 skills。runAgent 里只走一条 "从 agent 定义的 frontmatter 读 skills: [...]、用 getSkillToolCommands(getProjectRoot()) 查表并 preload 为 isMeta user message" 的路径，没有任何"把父的已加载 skills 注入子"的逻辑。—— 产品层面你感觉 sub-agent "应该和主 agent 一样什么都能用"，但实际上：你在主会话里通过 /skill foo 拉过的 skill，sub-agent 看不到；只有在 sub-agent 的 agent 定义 .claude/agents/xxx.md 的 frontmatter 里显式声明 skills: [foo] 才会被它 preload。要让一个 skill 在 sub-agent 里也能用，要么改 agent 定义，要么在 prompt 里把 skill 的实质内容直接写进去。

隐藏细节（src/tools/AgentTool/runAgent.ts:95-110, 647-664）：MCP server 的继承规则是additive：如果 agent 定义没声明 mcpServers，initializeAgentMcpServers 直接返回 parentClients 原样（:104-109）——父会话里连上的所有 MCP server sub-agent 都能用，不需要子自己重连。只有当 agent 定义里显式列了 mcpServers: [...] 时才追加新的（或引用已有配置），追加后 uniqBy([...resolvedTools, ...agentMcpTools], 'name') 按工具名去重。新连上的 inline MCP 在 sub-agent 退出时走 mcpCleanup() 断开；从父继承的连接不断。—— 产品层面你感觉 "sub-agent 的 MCP 工具要单独配"，实际上父的 MCP 池默认穿透过来，子只在需要额外 server 时声明，握手等待在 AgentTool.tsx:370-410 有最多 30 秒的兜底。

6. async 完成：enqueueAgentNotification¶

背景 agent 完成时走 runAsyncAgentLifecycle 的正常路径：completeAgentTask(agentResult, rootSetAppState) 改 state 为 completed，然后 enqueueAgentNotification 把 <task-notification> 塞队列。Agent Loop 下一轮把这条 XML 当 user message 注入（详见 ch.03），主 agent 在下一个 turn 里"读到 sub-agent 的完成消息"。

错误和终止走对应分支：catch AbortError → killAsyncAgent + status='killed' 通知；其他 error → failAsyncAgent + status='failed'。每一条通知都走同一条 enqueueAgentNotification，只是 status 不同。

4.6　上下文隔离的落地¶

隔离这件事的实现核心在两个函数：createSubagentContext 和 runAgent 里的 override 逻辑。

createSubagentContext¶

src/utils/forkedAgent.ts:345-462。按字段分类如何对待父 context：

克隆（isolation）：

  • readFileState：新 Map，sub-agent 读过的文件不污染父的 cache（:379-381）。
  • contentReplacementState：有则克隆，cache-sharing fork 需要和父做同样的替换决策来保持 prefix 字节一致（:399-403）。

共享（保持一致）：

  • abortController：显式 override > shareAbortController 时共享父 > 否则建 child controller。
  • updateAttributionState：调度用，函数式 setter prev => next，并发安全（:435）。
  • setAppStateForTasks：永远走父或爷爷的（:416-417）。这是一条"永远通往 root store"的后门。

stub 成 no-op：

  • setAppState：除非 shareSetAppState，否则空函数（:410-412）。意图：子 agent 不能污染父的 UI state。
  • setInProgressToolUseIDs / updateFileHistoryState（:425, 432）。
  • UI 回调：addNotification / setToolJSX / setStreamMode / setSDKStatus / openMessageSelector 全置 undefined（:437-442）。子 agent 不能控制父终端。

新建：

  • queryTracking：新的 chainId + depth +1（:452-455）。允许统计嵌套深度。
  • agentId：默认新建（:448）。

"setAppState 是 no-op 但 setAppStateForTasks 通往 root store" 这组看起来冗余，其实是被 bug 喂出来的设计。forkedAgent.ts:413-415 的注释说得清楚：嵌套 async agent（父本身就是 async）的 setAppState 已经是 no-op 了，但子 agent 起的 bash 子进程必须登记到 root store 才能在会话结束时被统一 kill；否则这些进程变成 PPID=1 僵尸。单一通道无法区分"我要改 UI"和"我要登记任务"，所以拆成两条。

官方对隔离的说法¶

"Each subagent runs in its own fresh conversation. Intermediate tool calls and results stay inside the subagent; only its final message returns to the parent." （https://code.claude.com/docs/en/agent-sdk/subagents，访问于 2026-04-19）

源码对应的是两个选择：

  1. runAgent 不把父的 messages 传给子（除 fork 路径的 forkContextMessages 外），子的 initialMessages 只有 [...contextMessages, ...promptMessages]，其中 contextMessages 是 fork 才有、promptMessages 是一条装了 prompt 字符串的 user message。
  2. finalizeAgentTool 只抽最后一条 assistant text，前面所有 tool_use/tool_result 都丢给 sidechain。

这两步一内一外合起来实现了文档的"only its final message returns to the parent"。

readonly sub-agent 的瘦身¶

runAgent.ts:390-410 两段对 Explore / Plan 的特殊处理：

  • 去掉 claudeMd（:390-398）：read-only agent 不需要看 commit/PR/lint 规则，父会自己解读产物。注释写 "Dropping claudeMd here saves ~5-15 Gtok/week across 34M+ Explore spawns."
  • 去掉 gitStatus（:400-410）：Explore/Plan 需要时自己 git status。注释写 "Saves ~1-3 Gtok/week fleet-wide."

这是"上下文隔离"的进阶版：连父的"当前仓库状态"都不往下传，让 sub-agent 按需自取。成本是 sub-agent 偶尔多跑一条 git 命令，收益是规模化后的 token 节省。

隐藏细节（src/context.ts:155-189 + src/tools/AgentTool/runAgent.ts:380-398）：sub-agent 的 memdir / CLAUDE.md 不独立——它从进程全局的 getUserContext() 里直接拿，而这个函数用 memoize(...) 缓存整个会话，意思是 父和子读到的是同一份 memory files 快照，子不会再次扫盘，也不会看到 sub-agent 启动后才新增的内存笔记（它们要等下一个会话才生效）。Explore / Plan 之所以能"瘦身"，是因为 omitClaudeMd flag 显式把 claudeMd 字段解构掉（runAgent.ts:394-398），而不是因为它们有独立的 memdir。—— 产品层面你以为 sub-agent "在新环境里重新起"，实际上只是看了同一份字典里更短的片段；如果你在主会话里 /memory edit 改了 CLAUDE.md，当前 turn 的 sub-agent 读到的仍是旧内容。

4.7　Task 家族的 6 个工具¶

来把那 6 个 Task*Tool 一次性说完。它们按作用分两组。

操作背景任务的两个¶

TaskStopTool（src/tools/TaskStopTool/TaskStopTool.ts:39-131，wire 名 TaskStop，别名 KillShell）。核心逻辑完全委派给 stopTask()：

getTaskByType 在 src/tasks.ts（本章未展开）按 task.type 找注册好的 Task 实现，每个 Task 类型提供自己的 kill()。LocalAgentTask.kill 就是 killAsyncAgent（src/tasks/LocalAgentTask/LocalAgentTask.tsx:273-275）。

对 bash task 有个 subtle 的区别（stopTask.ts:70-95）：bash 被 kill 后，正常通知会是 "exit code 137"，被标为噪声；stopTask 抓住这种情况，先把 notified=true 写回 state 再发一条 SDK 事件。agent task 则不做 suppress——killAsyncAgent 会正常走 enqueueAgentNotification，payload 带 extractPartialResult(agentMessages)，这是 sub-agent 在被终止瞬间攒下的 partial 输出，有用不是噪声。

TaskOutputTool（src/tools/TaskOutputTool/TaskOutputTool.tsx:144-308）。开头的 description 是：

这个工具在 ant 构建下甚至不加载（:163-165 isEnabled() { return "external" !== 'ant' }）。保留下来兼容旧代码。功能上：block=true 阻塞等完成；block=false 立刻返回当前状态；对 agent task 会优先从内存中的 agentTask.result.content 抽干净的 final answer（:96-105）而不是回放整个 transcript。

推荐路径是 AgentTool 的 async_launched 返回结果里的 outputFile 字段 + Read 工具——这也是为什么 async_launched 的 tool_result 文本里直接给了这个路径（AgentTool.tsx:1329）。

TodoV2 的四个（和 sub-agent 调度没有直接耦合）¶

这四个操作的不是 sub-agent，是模型给用户看的待办清单。

  • TaskCreateTool（src/tools/TaskCreateTool/TaskCreateTool.ts:48-138）：建 todo，写磁盘（getTasksDir(getTaskListId())）；触发 TaskCreated hooks，可阻塞。
  • TaskListTool（TaskListTool/TaskListTool.ts:33-115）：读 todo 列表。
  • TaskGetTool（TaskGetTool/TaskGetTool.ts:38-128）：读单条 todo。
  • TaskUpdateTool（TaskUpdateTool/TaskUpdateTool.ts:88-406）：改 subject/description/status/owner/blocks；status: 'completed' 时触发 TaskCompleted hooks；status: 'deleted' 时删文件。

它们在 swarm 模式下被额外做成了 teammate 间的协作信道：owner 变化时 writeToMailbox 把 task_assignment 消息投给新 owner（TaskUpdateTool.ts:276-298）。所以你会看到 UI 上"A teammate 被分配到一个 task"——本质上是 lead 用 TaskUpdate 写了一条 owner 字段。本章不深入 mailbox 机制（见 ch.13）。

UI 同步逻辑在 src/hooks/useTasksV2.ts:29-229：一个 singleton store + fs.watch + 5 秒兜底轮询 + React useSyncExternalStore。所有消费者（REPL、Spinner、footer）共享一个 watcher。设计重点：不要为每个 UI 位置建 fs.watch——Spinner 每轮 mount/unmount，watcher 频繁起停会打中 Bun 的 PathWatcherManager 死锁（useTaskListWatcher.ts:46-50 的同样注释）。

容易混的一条规则¶

主 agent 的 Agent 工具（同步 sub-agent 路径）和 TaskOutputTool 之间没有耦合。同步 sub-agent 完成后直接把 text 放到 tool_result 里返回，不需要 TaskOutputTool；异步 sub-agent 推荐通过 outputFile + Read；TaskOutputTool 只是历史兼容和 bash 背景任务的通用读取口。

4.8　Fork：最大化 prompt cache 共享的 sub-agent 变体¶

fork 是 sub-agent 的一个特殊路径，默认关闭，在 gate FORK_SUBAGENT 打开时生效。核心结构在 src/tools/AgentTool/forkSubagent.ts。

语义¶

  • 调 Agent 时省略 subagent_type，落到 FORK_AGENT（forkSubagent.ts:60-71）。
  • 子 agent继承父的完整对话历史（toolUseContext.messages） + 父的已渲染系统提示（toolUseContext.renderedSystemPrompt）。
  • 所有 fork spawn 强制 async。
  • 子 agent 的工具池字节级等同父（useExactTools=true，runAgent.ts:500-502 + runAgent.ts:667-695）。

为什么非要字节级对齐¶

LLM API 的 prompt cache 以 request prefix 为单位命中。只要子 agent 的系统提示、工具定义、消息前缀都和父的历史请求一致（前 N 个 token 字节完全等同），后端就能复用父的 KV cache，省下重新 prefill 的开销。forkSubagent.ts:98-106 的注释：

"For prompt cache sharing, all fork children must produce byte-identical API request prefixes."

于是有这两个细节：

  1. 子 agent 的系统提示从父的"已渲染产物"取，不是重新 render。因为 GrowthBook 的 feature flag 可能在"父 render 时" vs "子 spawn 时"已经飘了一位（cold vs warm），重新 render 会产生 1 字节差异，cache 全没。
  2. tool_result 占位符所有子 agent 相同：

每个 fork 子的 tool_result 块都是这句话，这样多个 fork 并行时 request prefix 继续对齐，只有最后一块 user text（per-child directive）不同。

buildForkedMessages¶

得到的 wire 形状：[...父历史, 父最后一条 assistant (包含所有 tool_use), user (所有占位 tool_result + 本子 directive)]。

fork 的 system prompt 教学¶

fork 子 agent 的 system prompt 是在 buildChildMessage()（forkSubagent.ts:171-198）拼出来的——其实是塞在 user message 里的规则，因为父的 system prompt 被保留了（为了 cache）。关键条款：

  • "You are NOT the main agent."
  • "Do NOT spawn sub-agents; execute directly." —— 配合 isInForkChild 递归 fork 守卫（:78-89），扫消息找 <fork-boilerplate> tag 检测。
  • "Your response MUST begin with 'Scope:'." —— 结构化输出。
  • 报告格式硬性约束：Scope / Result / Key files / Files changed / Issues。

fork 是 sub-agent 一个特殊化的设计点：当继承上下文比省 token 更值得时，用继承；当子 agent 应该完全独立推理时，用 subagent_type。

4.9　Coordinator 与 Swarm：sub-agent 之上再加一层¶

到这里 AgentTool 和 Task state 都讲清楚了。Coordinator 和 Swarm 是在这之上加壳。

Coordinator¶

入口是环境变量：

开启后主 agent 拿到的系统提示是 getCoordinatorSystemPrompt()（src/coordinator/coordinatorMode.ts:111-369，260 行的硬编码 prompt），把自己定位成 orchestrator：

"You are a coordinator. Your job is to: help the user achieve their goal · direct workers to research, implement and verify code changes · synthesize results and communicate with the user · answer questions directly when possible — don't delegate work that you can handle without tools."

工具被收窄：只有 Agent（spawn worker）、SendMessage（继续 worker）、TaskStop（停 worker）、加几个 GitHub 订阅工具。Worker 类型固定：

几个硬约束：

  • 所有 sub-agent 强制 async（AgentTool.tsx:567 的 isCoordinator 短路）。
  • <task-notification> 作为 worker→coordinator 的唯一回传契约——在系统提示里作为规则讲给模型（coordinatorMode.ts:144-160）。
  • INTERNAL_WORKER_TOOLS（coordinatorMode.ts:29-34）—— TeamCreate / TeamDelete / SendMessage / SyntheticOutput，这些 worker 自己用不到。

Coordinator 本质上就是 "用 prompt 把主 agent 变成一个调度器"，底层还是 AgentTool + <task-notification>。没有新发明的调度引擎——prompt 是最低摩擦的架构。

Swarm¶

比 Coordinator 更重：每个 teammate 是一个独立 Claude Code 进程（tmux 分屏或 in-process），通过磁盘 mailbox 和共享任务板通信。官方定义：

"Agent teams let you coordinate multiple Claude Code instances working together. One session acts as the team lead, coordinating work, assigning tasks, and synthesizing results. Teammates work independently, each in its own context window, and communicate directly with each other." （https://code.claude.com/docs/en/agent-teams，访问于 2026-04-19）

它由 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS 开启。本章只涉及和 sub-agent 调度有直接关系的两个 hook：

useSwarmInitialization（src/hooks/useSwarmInitialization.ts:30-81）：在 teammate 启动时恢复 team 上下文（从 transcript 第一条消息读 teamName / agentName，或从 env 取 team config），装 teammate hooks。这是把"独立进程"挂回"团队协作网"的桥。

useSwarmPermissionPoller（src/hooks/useSwarmPermissionPoller.ts:268-330）：teammate（worker 侧）每 500ms 扫自己的 resolved/<requestId>.json——看 lead 有没有回应它的权限请求。本章只讲路由，决策见 4.10 和 ch.09。

Team 架构的完整清单文档原话：

"Team lead: The main Claude Code session ... · Teammates: Separate Claude Code instances ... · Task list: Shared list of work items that teammates claim and complete · Mailbox: Messaging system for communication between agents." （https://code.claude.com/docs/en/agent-teams，访问于 2026-04-19）

Task list 就是 TodoV2（4.7 讲的那四个工具），Mailbox 是 src/utils/teammateMailbox.ts（本章未展开）。多进程协调、tmux 细节、团队命名等见 ch.13。

4.10　权限回传：sub-agent 怎么问父/用户¶

Sub-agent 做敏感操作（写文件、跑不在白名单里的 bash 命令）需要许可。权限决策的规则匹配、allow/deny 格式、auto 分类器逻辑详见 ch.09——本节只讲"跨 agent"这一层：请求如何从 sub-agent 路由回父 / lead / 用户。场景按主体分三层。

本地同步 sub-agent¶

默认共享父的 abortController 和 toolUseContext（4.6），toolUseContext.canShowPermissionPrompts 为 true 时继续用父终端的权限弹窗。

隐藏细节（src/tools/AgentTool/runAgent.ts:465-479）：sub-agent 默认继承父的 alwaysAllowRules——你在主会话里按过 "Always allow" 的那些规则，sub-agent 里也照样生效。只有当 AgentTool 的 caller 显式传入 allowedTools 参数时，agentGetAppState 才会把 alwaysAllowRules.session 字段替换为 [...allowedTools]；注意此时 cliArg 字段（来自 SDK --allowedTools）被有意保留，代码里的原话是 "Preserve SDK-level permissions from --allowedTools"。—— 产品层面你不会注意到主/子 agent 的权限字典差别，但这条规则决定了：跨 agent 的 "Always" 是默认传染的，想要彻底隔离得在 AgentTool 调用处传 allowedTools 显式重置。跨 agent 权限规则的语义、匹配优先级见 ch.09。

本地异步 sub-agent¶

shouldAvoidPermissionPrompts 在 runAgent.ts:436-452 默认被设为 true：

"避免弹窗"不等于"无脑拒绝"——awaitAutomatedChecksBeforeDialog（:458-463）让 async agent 先等自动分类器（auto mode classifier）和 hooks 给答案，只有在自动链路都无法决定时才求助于"能弹窗的权限 channel"。

bubble 模式¶

permissionMode: 'bubble' 的 agent（目前主要是 FORK_AGENT，forkSubagent.ts:67）反过来：强制冒泡到父终端。因为 fork 继承父上下文、行动范围也和父类似，让用户在父终端直接决定是自然的。

Swarm worker¶

进程隔离，不能共享 abortController，也不能弹父的终端。流程：

  1. worker 侧构造 SwarmPermissionRequest： ts // src/utils/swarm/permissionSync.ts:167-207（节选） export function createPermissionRequest(params): SwarmPermissionRequest { return { id: generateRequestId(), workerId, workerName, workerColor, teamName, toolName: params.toolName, toolUseId: params.toolUseId, description: params.description, input: params.input, permissionSuggestions: params.permissionSuggestions || [], status: 'pending', createdAt: Date.now() } }
  2. worker 调 writePermissionRequest，带 lockfile 写到 ~/.claude/teams/<team>/permissions/pending/<id>.json。
  3. Lead 侧读 pending 目录，弹自己的终端问用户或按规则自动判。结果写到 resolved/<id>.json。
  4. worker 侧 useSwarmPermissionPoller 每 500ms 查 pollForResponse（permissionSync.ts:544-564）： ts const resolved = await readResolvedPermission(requestId, teamName) if (!resolved) return null return { requestId: resolved.id, decision: resolved.status === 'approved' ? 'approved' : 'denied', feedback: resolved.feedback, updatedInput: resolved.updatedInput, permissionUpdates: resolved.permissionUpdates }
  5. Poller 命中后调注册好的回调（onAllow 或 onReject，useSwarmPermissionPoller.ts:231-257）。

这套机制还有一条并行的 mailbox 推送路径：processMailboxPermissionResponse（useSwarmPermissionPoller.ts:124-156），让 lead 直接通过 mailbox 投递回应而不是写磁盘等 poller 扫到。两条路径各自独立，都走同一个回调 registry——典型的"推拉两用"设计，磁盘做兜底、mailbox 做快路径。

500ms 的轮询节奏是硬编码（useSwarmPermissionPoller.ts:28）。读文件的 fs.read 次数与 pending 请求数成正比。真实负载下这个节奏够用，不是本章要讨论的性能课题。

官方文档对这件事的描述：

"Teammate permission requests bubble up to the lead, which can create friction. Pre-approve common operations in your permission settings before spawning teammates to reduce interruptions." （https://code.claude.com/docs/en/agent-teams，访问于 2026-04-19）

（前文已点明 ch.09 是权限决策规则本身的归宿。）

4.11　设计取舍¶

把"为什么选 A 不选 B"的几对关键决定列出来。

把 sub-agent 的整段 run 压成一条 text-only tool_result¶

  • A（选中）：finalizeAgentTool 只保留最后一条 assistant 的 text 块。
  • B（替代方案）：把 sub-agent 的完整 transcript 塞回主 agent。

A 的成本：主 agent 如果想看"sub-agent 具体怎么找到答案的"，必须再跑一次或读 sidechain transcript 文件（outputFile）。B 的成本：sub-agent 可能调 50 个工具，这 50 条记录进入主 agent 的 context window，tool noise 会把主 agent 推向 prompt cache bust 和注意力分散。Claude Code 的选择是 A，以"可观察性"换"上下文整洁度"。

<task-notification> 用 XML-in-user-message，不发明新 message type¶

  • A（选中）：异步结果作为 user 消息塞回队列，系统提示教会模型识别 <task-notification> tag。
  • B（替代方案）：在 Message 类型里加一个 'task-notification' 子类型，改 schema，改所有下游（SDK、UI、transcript writer）。

A 的成本：模型必须学会这个 tag 的含义——在 coordinator 模式下 system prompt 专门讲了（coordinatorMode.ts:144-160）。B 的成本：schema 改动传染整个生态，SDK 消费者要兼容新字段，transcript 回放兼容要加版本号，prompt cache 会对旧历史 bust。A 的胜出理由：transport 层零改动、向后兼容一阶免费。

主 agent 的 abortController 和 async sub-agent 解耦¶

runAgent.ts:526 用了一段显式注释：

"Don't link to parent's abort controller -- background agents should survive when the user presses ESC to cancel the main thread. They are killed explicitly via chat:killAgents."

  • A（选中）：async sub-agent 新建独立 AbortController。
  • B（替代方案）：child controller 继承父。

B 看起来更"家族一致"但会让 ESC 取消主线程 = 杀所有背景任务。async 的语义是"我现在不等它"，这和"用户想结束当前 turn"应该是两件事。A 的代价是需要一个额外 kill 通道（chat:killAgents、killAllRunningAgentTasks）。

sync 到 async 的切换用 Promise race 而不是信号¶

  • A（选中）：AgentTool.tsx:886-892 的 Promise.race([agentIterator.next(), backgroundPromise])。
  • B（替代方案）：捕获用户键入并通过信号把同步循环"打断"。

A 的胜出理由：无需额外同步原语。每一轮工具调用返回都是一个自然的 yield 点，Promise race 天然对齐；切到 async 之后当前迭代器 return()（触发 finally 清理），下一段在 void 里重新起一个 async 的 runAgent，前半段已经积累的 agentMessages 被带过去用作 progress 初值。

setAppStateForTasks 和 setAppState 拆成两条通道¶

表面上冗余，实际解耦了"UI 更新"和"任务注册"两个语义。嵌套 async 场景下只有后者需要永远送达 root store，前者有意 no-op。

4.12　可迁移的点¶

读者想把哪些东西借走，放到自己项目里？

  1. 一次 tool call = 一个完整 agent run。这个抽象让主 agent 的推理代码不需要区分"本地工具"和"agent"，两者共用一个 schema 和生命周期契约。自己写 agent 框架时可以先定一条规则：任何子 agent 的产出都必须能被压缩成父 agent 的一条 tool_result。能压就让它进系统，不能压的东西（比如长 log）要么流式写盘（outputFile 模式），要么事后 Read。
  2. sub-agent 结果只保留最后一条 text。这是 context isolation 的底线实现。哪怕你不想做 fork / worktree / remote 这些重功能，只要做到"子 agent 的 transcript 不回流主 agent"，就能防住绝大多数 context bleed。
  3. XML-in-user-message 作为异步结果通道。<task-notification> 是设计成"看起来像用户说的话"的 system 通知，让主 agent 复用已有的 user role 处理路径。你自己系统里如果也有"异步事件要喂给 LLM"的需求（webhook 回来了、cron 跑完了），这个模式直接能抄：一个命名 tag + 一个 prompt 教程说明，比设计新 message type 成本低。
  4. Promise race 做生命周期状态切换。不用额外的信号/锁，也不用跨线程通信原语——把"能随时发生的外部事件"做成一个 Promise，在事件循环的每个自然 yield 点 race 一下，命中就换分支。AgentTool.tsx:886 的 background 切换、Ctrl+B 都走这一条。
  5. 双通道 state 回写：UI 通道（可以被 stub 成 no-op）和任务通道（必须通达）分开。只要你的系统里存在"某些状态不能让子任务影响，但某些状态必须记到根上"的需求，这种拆分就有价值。
  6. singleton store + fs.watch + 兜底轮询 + React useSyncExternalStore（useTasksV2.ts 的模式）。任何要把磁盘目录当"共享状态"的系统都能抄：watcher 起一次、多个消费者订阅、fallback poll 防止 watcher 漏事件。
  7. 字节级对齐来命中 prompt cache。fork 的全部设计目标。普通工程里也能用：如果你给 LLM 做多变体 prompt（A/B 测试、多路查询），能对齐的公共前缀尽量字节对齐——哪怕重构一点代码也值。
  8. 用系统提示教模型识别内部协议（coordinator 的 <task-notification> 教程、fork 的 <fork-boilerplate> 条款）。当你的系统需要 LLM 识别一类特殊消息时，把规则写进 system prompt 比在代码里加特判更省——模型一次学会，下游所有路径自动兼容。
  9. 状态机拆迁移函数、用纯函数改 state（LocalAgentTask.tsx 的 register* / complete / fail / kill / background / unregister）。每个迁移一个函数，幂等（比如 notified flag），测起来很好测。

本章到此。把 sub-agent 调度的 "边界在哪里、state 怎么迁、结果怎么回" 三件事讲清楚了。配套细节——Tool 接口和 buildTool 怎么把 AgentTool 这种大家伙装进统一框架，见 ch.08；权限决策的具体规则和分类器，见 ch.09；swarm 的多进程 tmux / mailbox，见 ch.13。
