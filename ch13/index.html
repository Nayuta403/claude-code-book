1. 用户看到什么¶

Claude Code 里有一层"定时"能力可以让一个长时间运行的 REPL 自己给自己派活。用户可以这么用：

  • 直接跟 Claude 说"每 5 分钟检查一下部署"。Claude 会调 CronCreate 工具，落下一条 cron。
  • 打斜杠命令 /loop 5m check the deploy。/loop skill 把 5m 翻译成 */5 * * * *，再调 CronCreate，并立刻先执行一次。
  • 打 /schedule 让 Claude 帮你配一个远端 trigger——那是 Anthropic 云上跑的 isolated 会话，不受你机器关机影响。远端执行的 session 启动细节详见 ch.17。

无论哪种入口，本地触发时用户会看到一条 dimmed 的系统消息 Running scheduled task (Apr 19 3:07pm)，紧跟着 Claude 开始处理那条 prompt。这条 prompt 不是用户敲的，来自前面某个 CronCreate 调用里存下来的文本。官方文档把这类功能的落地版本定为 Claude Code v2.1.71（来源：https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md，访问于 2026-04-19——"Added /loop command … Added cron scheduling tools for recurring prompts within a session"）。

2. 为什么挑这个设计出来讲¶

Cron 本身是 1975 年就存在的老技术。这里值得挑出来讲的不是"cron 本身"，而是把 cron 塞进一个 interactive REPL 的工程选择。

独立的 cron 守护进程有自己的进程空间、自己的用户、自己的生命周期。Claude Code 的 cron 活在 REPL 进程里：

  • 不能打断用户正在跟模型对话的 turn
  • 不能让同一个 cwd 的两个 Claude 进程双发同一个任务
  • 全球用户写 0 9 * * * 的都瞬时击中 API 会让 Anthropic 的容量炸掉
  • REPL 关了要不要保留任务？保留多久？没跑成的任务要不要补？

后面几节把这四件事对应的代码拎出来看。最后一节讲可迁移的点。

3. 三层定时能力的划分¶

在开始看代码之前，先把"定时"这事在 Claude Code 里分成三层。这是后面所有讨论的坐标系。

层触发存储生命周期入口工具
本地 session-onlyREPL 进程自己STATE.sessionCronTasks（内存）REPL 退出即丢CronCreate({durable:false})
本地 durableREPL 进程自己.claude/scheduled_tasks.json跨 session，7 天过期CronCreate({durable:true})
远端 triggerAnthropic 云（scheduled agent）服务端独立于本地会话RemoteTrigger({action:'create'})（详见 ch.17）

两个斜杠命令 /loop 和 /schedule 是这三层之上的 skill 壳：

  • /loop → CronCreate（本地，默认 session-only）
  • /schedule → RemoteTrigger（远端 scheduled agent）

官方文档用的三分法一致（来源：https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）：Cloud / Desktop / /loop——其中 Desktop 是 Claude Desktop 应用的独立 scheduler，不走 Claude Code CLI 这条代码路径，本章不展开。

本章后面 70% 的内容都在讲第一层和第二层（它们共享一个 CronScheduler）。第三层（远端 scheduled agent）只讲本地如何把任务发给远端这一边界，云端执行在 ch.17 远端 session 一章。/loop 与 proactive 模式的触发协同见 ch.15；cron fire 触发的 prompt 走完一轮 turn 后如果形成新的 sub-agent 任务回流，走的是 ch.16 background tasks 通道。

上游注记：本章以仓库里恢复出来的 shim 为基线。官方文档承诺的 /loop dynamic 模式（无 interval、模型自选周期、Esc 取消 pending wakeup）在仓库源码里搜不到完整实现，§9.1 单独拎出来讨论。正文每处给出的行号都对应仓库里的真实代码；跨章节交叉引用同样按章节号而非页码给出。

5. Cron 表达式：自研 5-field 解析器¶

仓库用的是标准 5 字段，没有 6 字段秒级 cron。

解析器是自己写的，不依赖任何第三方 cron 库。支持四种原语：wildcard、单值、step（*/N）、range（N-M 带可选 /S）、list（, 分隔）。不支持 L / W / ? / MON/JAN 这类名字别名（src/utils/cron.ts:5-8）。

官方文档和这完全一致（来源：https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）：

CronCreate accepts standard 5-field cron expressions … Extended syntax like L, W, ?, and name aliases such as MON or JAN is not supported. When both day-of-month and day-of-week are constrained, a date matches if either field matches. This follows standard vixie-cron semantics.

对应 src/utils/cron.ts:150-158 的 OR 语义：

自研这个解析器的代价是表达能力窄。收益有三点：

  1. 包更小——不拉整个第三方库。
  2. DST 语义自己掌控：fixed-hour cron 落在 spring-forward gap 那一天自然被 hourSet.has(t.getHours()) 过滤跳过（src/utils/cron.ts:113-117 明确注释），fall-back 重复小时只触发一次。
  3. 计算下次运行时间的算法就逐分钟 walk（src/utils/cron.ts:138，最多 366 * 24 * 60 = 527040 次迭代）。简单到不会有微妙 bug。

代价小，收益实在。这是"写比引"合理的场景。

人类可读翻译 cronToHuman（src/utils/cron.ts:218-308）故意写得保守：只覆盖 "Every N minutes" / "Every hour" / "Daily at H:MM" / "Every Monday at H:MM" / "Weekdays at H:MM" 这几个常见模式，其他直接 fall through 返原字符串。带一个 utc?: boolean 选项——远端 trigger 的 cron 在 UTC 执行，展示时要翻译成用户本地时区，要多走一点 midnight-crossing 的补偿逻辑。

6. 调度器主循环¶

整个调度器被抽成一个与 REPL 解耦的 createCronScheduler(options)，放在 src/utils/cronScheduler.ts。REPL 用它（通过 useScheduledTasks hook），-p / SDK 模式也用它（src/cli/print.ts:2702-2734）。差异只在 options 里的几个回调。

6.1 start() 的两条启动路径¶

两条路径的用意：

  • Daemon path（dir 显式传入）：SDK 或外部 agent 调用，没有 bootstrap state，直接进 enable。
  • REPL path：先看磁盘有没有任务——有就直接启。没有就 setInterval 1 秒探一次那个"enable"标志位，等 CronCreate.call() 在运行中翻标志（CronCreateTool.ts:133 会 setScheduledTasksEnabled(true)）。

为什么要探 flag 而不是直接永远启动？因为 chokidar file watcher 有启动成本，大多数 session 从不创建任务。标志位让冷启动成本只在需要时付。

6.2 enable() 抢锁¶

enable() 的第一件事是抢 .claude/scheduled_tasks.lock（路径由 LOCK_FILE_REL = join('.claude', 'scheduled_tasks.lock') 给出，src/utils/cronTasksLock.ts:23；跟 JSON 任务文件同目录，便于一起 .gitignore）：

tryAcquireSchedulerLock（src/utils/cronTasksLock.ts:111-173）的核心是一行 POSIX O_EXCL：

wx 是"write + fail-if-exists"，是文件系统级别的原子 test-and-set。锁文件内容是一个 Zod 校验的三元组 { sessionId, pid, acquiredAt }（src/utils/cronTasksLock.ts:25-32）——不是一个空文件，后面的 passive probe 要从里面读出 PID。做不到就回读现有 lock：

  • 同 sessionId 但不同 PID（--resume 恢复后 PID 变了）→ 刷新 PID，idempotent（src/utils/cronTasksLock.ts:139-145）
  • 不同 sessionId 且 PID 还活着 → 返回 false（:149-157）
  • PID 死了 → 这是 stale lock，unlink 一次再 retry O_EXCL（:160-171）

Callout / 锁文件路径与格式：.claude/scheduled_tasks.lock（相对 project root）。内容 JSON { sessionId, pid, acquiredAt }，由 schedulerLockSchema Zod 校验。O_EXCL 原子创建失败后的仲裁全靠读这三字段——PID liveness probe 判死活、sessionId 匹配 --resume 换 PID。这个格式是跨进程协调的最小必要状态。

不抢到锁的 passive session 每 5 秒 LOCK_PROBE_INTERVAL_MS 探一次（src/utils/cronScheduler.ts:44, :418-434），等 owner 死了无缝接管。注意 passive session 仍然处理自己的 sessionCronTasks——那是进程私有的，另一个 session 看不到，无双发风险；锁只挡磁盘任务。

这把锁的模式来自 computerUseLock.ts，是仓库的一个复用设计（src/utils/cronTasksLock.ts:8 注释标了）。跨进程协调不开独立进程、不用 inotify 锁文件描述符、不用 sqlite 事务——就一个 O_EXCL + PID liveness probe，简单到几乎不会出错。

6.3 check() 每秒一次¶

unref() 让这个 timer 不再阻止进程退出——-p 模式跑完一轮就该退，不能因为 cron 挂着。

check() 的逻辑精简到流水线：

  1. isKilled?() 返 true → 立刻 bail，已运行的 scheduler 原地死（src/utils/cronScheduler.ts:231）。这就是 CLAUDE_CODE_DISABLE_CRON 怎么实时生效的——每 tick 查一次 feature flag。官方文档明确承诺这条路径（https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19："Set CLAUDE_CODE_DISABLE_CRON=1 … any already-scheduled tasks stop firing"）。
  2. isLoading() && !assistantMode → 本 tick 不触发（:232）。这是"prompt 只在 REPL 空闲时触发"的落地。
  3. 合并两个 store 的 tasks：isOwner 的话加磁盘，dir === undefined（REPL 路径）加 session。
  4. 对每个 task 调 process(t, isSession)。

Callout / mid-query 时 fire 怎么处理：第 2 步 isLoading() 返 true 的那一 tick 整个 check() 直接 return，不入队、不记录"这次被跳过了"。nextFireAt 依然停在原值，下一秒 tick 再来一遍。等到 REPL 空闲（比如用户 turn 结束、模型 response 完成），第一个满足 now >= next 的 tick 就把该 fire 的任务全部入队一次——注意是一次，不是按错过的 tick 数补发。这就是官方文档承诺的 "No catch-up for missed fires"（https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）在代码里的落地：不是显式的去重表，而是因为 check() 跳过一整 tick 时根本没把任何 fire 记进 firedFileRecurring。用户体感就是"卡住一阵后，cron 只提醒一次而不是攒了十几条砸过来"。

process() 里第一次见到某个 task 时建 nextFireAt 记录：

lastFiredAt ?? createdAt 是个关键细节。重启后第一次见这个 task，从 lastFiredAt 起算能让刚 fire 过的 task 不马上再 fire。永远没 fire 过的 recurring task 从 createdAt 起算——如果它有个 pinned date（30 14 27 2 *），从 now 起算会算到明年，从 createdAt 起算会被 check() 立即 fire。

时间到了之后：

注意 newNext 是从 now 算，不是从旧的 next 算。如果 REPL 被卡了 20 分钟，一个每分钟的任务不会上来 catch-up 20 次——它只会在空闲时 fire 一次，然后重排到下一个整分钟。官方文档原话（https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）：

No catch-up for missed fires. If a task's scheduled time passes while Claude is busy on a long-running request, it fires once when Claude becomes idle, not once per missed interval.

6.4 isRecurringTaskAged¶

7 天过期这条规则被抽出来单测：

注释给的理由直白（src/utils/cronTasks.ts:339-345）：cron 是 session p99 时长从 61 分钟涨到 53 小时的主要驱动，unbounded recurrence 会让 tier-1 内存泄漏不断累积。7 天覆盖"这周每小时看一下我的 PR"这种典型工作流，同时把最坏 session 寿命卡住。permanent: true 是 assistant mode 几个内置任务（catch-up / morning-checkin / dream）的 escape hatch，只有 src/assistant/install.ts 能直接写 JSON 设置。

Callout / 7 天过期由谁执行：不是 CronCreate 写盘时打时间戳、也不是单独的 cleanup job，而是 scheduler 每次 fire 时就地判定。process() 在 fire 完后跑一次 isRecurringTaskAged(t, now, maxAgeMs)（src/utils/cronScheduler.ts:302）：如果判 aged，这次 fire 就当"最后一次"——prompt 照样入队，但 fire 完不再排下一次，走跟 one-shot 同一条 cleanup 路径（src/utils/cronScheduler.ts:315-344，isSession ? removeSessionCronTasks : inFlight + removeCronTasks），同时打一条 tengu_scheduled_task_expired analytics。也就是说：一个 10 天没打开过的任务，下次 Claude 启动时 check() 第一个 tick 就发现它 aged，最后 fire 一次再删。过期窗口 recurringMaxAgeMs（默认 7 天）由 CronJitterConfig 控制，GrowthBook 能下发覆盖——"7 天"这个数字运维可以在事故里临时改，不是 hard-code。

7. Jitter：一行哈希的错峰¶

task id 是 8 个十六进制字符（randomUUID().slice(0, 8)，src/utils/cronTasks.ts:203）。当 u32 解析除 0x1_0000_0000 得 [0, 1) 区间的均匀分布。跨进程可重现（不像 Math.random()），不需要外部状态。

两种 jitter：

Recurring 推迟（src/utils/cronTasks.ts:381-398）：

延迟是"下次间隔长度"的一个比例（默认 recurringFrac = 0.1，即 10%）。把几个常见 cron 代入得到具体窗口：

cron间隔jitter 上限（=间隔 × 10%）实际落点
* * * * *（每分钟）60s6s[:00s, :06s)
*/5 * * * *（每 5 分钟）300s30s[:00s, :30s) 紧跟每 5 分钟的整点
0 * * * *（每小时）3600s360s[:00, :06)——官方文档原话
0 0 * * *（每天）86400s8640s，但被 15min cap 截到 900s[00:00, 00:15)

最后一行是 recurringCapMs = 15 * 60 * 1000 的作用：daily 任务按 10% 算会推迟到 2:24，对用户来说不合理，硬封顶在 15 分钟。每分钟的任务只推迟 [0, 6s)，不会失去实时性——官方文档对此有对应原话（https://code.claude.com/docs/en/scheduled-tasks，访问于 2026-04-19）。

隐藏细节（src/utils/cronTasks.ts:381-398）：recurring jitter 的实际窗口是 min(周期 × recurringFrac, recurringCapMs) 取小，不是简单"10% 或 15 分钟"。对 */5 * * * * 来说是 30s（远没到 cap），对 0 * * * * 是 6 分钟（依然没到 cap），只有周期 ≥ 150 分钟的任务才真正撞到 15min cap。官方文档 "up to 10% late, capped at 15 minutes" 描述的是两个独立上限，运维场景下这对"每 5 分钟"类任务意味着 window 其实只有 30 秒——这个细粒度产品层面看不到，但在事故复盘里解释为什么 cap 调大没用很重要。

One-shot 提前（src/utils/cronTasks.ts:421-445）：

只在 fire 分钟落在 % 30 == 0（默认，即 :00 和 :30）时生效，因为"人类挑整点"是触发全球同步 fire 的主要原因。其他分钟数（比如 3 9 * * * 里的 :03）本来就不是 hotspot，别给人加莫名的提前。CronCreate.prompt() 里专门用一大段教模型避开 :00 和 :30（src/tools/ScheduleCronTool/prompt.ts:104-110）：

"every morning around 9" → "57 8 \ \ \" or "3 9 \ \ \" (not "0 9 \ \ \") "hourly" → "7 \ \ \ \" (not "0 \ \ \ \*")

这是 prompt 工程替代服务端限流：让模型一开始就别把所有请求打到同一秒，胜过事后抖动。事后抖动是防御深度。

GrowthBook push 下发 tengu_kairos_cron_config 可以在事故中临时把窗口拉大（详见注释 src/utils/cronTasks.ts:410-414）：

{oneShotMinuteMod: 15, oneShotMaxMs: 300000, oneShotFloorMs: 30000} 会把 :00/:15/:30/:45 触发散到 [t-5min, t-30s] 的窗口，每个任务至少提前 30 秒，没人精确落在整点。

8. 触发后：prompt 怎么被注入¶

先立个结论：cron 触发不开新会话。新 prompt 塞进当前 REPL 的命令队列，和用户手敲的 prompt 走一样的 drain 路径。

useScheduledTasks hook（src/hooks/useScheduledTasks.ts）是 REPL 侧的 thin wrapper。核心就是构造一个 scheduler 并把 fire 回调接到队列：

三个字段值得单独讲：

priority: 'later'。队列的优先级顺序是 now > next > later（src/utils/messageQueueManager.ts:151-155），用户输入默认 'next'（:129）。cron 用 'later' 保证永远不会饿死用户输入：即使积压 50 条 cron prompt，用户现在敲一行，也在队首。

isMeta: true。这个字段控制消息是否在 transcript UI 里可见。系统生成的 prompt 加这个标记就不会污染"用户说了什么"的视图。注意 src/hooks/useScheduledTasks.ts:67-71 的注释说：斜杠命令（如 /loop fire 出的 /some-command）目前不 forward 这个 flag，所以斜杠命令类的 cron prompt 在正常模式下仍然会显示——是个已知的小缺口。

workload: WORKLOAD_CRON。这是 'cron' 字符串（src/utils/workloadContext.ts:26），通过 AsyncLocalStorage 传到 API 请求的 attribution header 里作为 cc_workload=cron。服务端可以据此给 cron 请求 lower QoS——没人在等这个响应。ALS 用 .run(...) 建 boundary 防止 context 在上一 turn 留下后被下一轮 turn 的 scheduling chain 捕获（src/utils/workloadContext.ts:36-50 大段注释写了为什么直接 return fn() 会 leak）。

对 team lead（没有 teammate 上下文），fire 时除了入队 prompt 还打一条 scheduled_task_fire 系统消息（src/hooks/useScheduledTasks.ts:110-113）——这是 ## 2.1.85 版本加的"timestamp markers in transcripts"（来源：https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md，访问于 2026-04-19）。

这条 fire 后的 SessionStart hook 触发路径与 ch.14 Hooks 一章交叉：cron 触发不开新 session，所以 SessionStart hook 不会因 cron fire 再跑一次——只有 --resume 或首次启动走 hook 路径。

"wakeup" 这个词暗示有一个对应的唤醒事件机制。

  1. 模型每轮结束自己调 CronCreate(recurring: false) 埋一次性下一轮（最小实现，无需新工具）。
  2. 一个未恢复的 ScheduleWakeup 工具配合 scheduler 的 onFireTask，模型显式承诺下一唤醒时间。
  3. 模型直接用 Monitor 工具（仓库里已存在，见章尾 cross-ref）做事件驱动的等待，不走 cron。

本章下文只讨论 fixed-interval 路径，因为它有源码支撑。

保守结论：本章只讲 fixed-interval 路径。dynamic 模式的完整落地可能存在于 shim 未含的更新版 skill prompt 里，详见 book/research/ch13/open-questions.md。Agent SDK 对应的 watchScheduledTasks 入口在 ch.23 讲，那里会再把三种 store 和 scheduled agent 的观测路径串一遍。

10. Missed task：重启后怎么追补¶

用户在 0 9 * * * 上创建了一个 one-shot 提醒 "remind me at 9am to push release"。8:59 关掉 Claude，10:00 才回来——这个任务的 fire 时间已经过了。怎么处理？

调度器只在 load(initial=true) 时处理这类 missed task（src/utils/cronScheduler.ts:179-228）：

只处理 !recurring——recurring 留给 check() 自然追上（第一个 tick 就 fire，因为 nextFireAt 被 anchor 到 createdAt 所以立刻到期）。

一旦判定 missed，调度器做三件事：

  1. nextFireAt.set(t.id, Infinity) 锁住这个任务不让 check() 后续 tick 再触发（:202-203）。
  2. 从磁盘上删掉这些任务（:218-223）。
  3. 把所有 missed task 拼成一条 notification，入队（:216）。

这条 notification 的文本精心反注入：

三个防御点：

  • 显式指令：先问再执行，让模型走 AskUserQuestion 工具。
  • 原 prompt 包 code fence：fence 长度自适应，是原 prompt 里最长反引号串加 1。这样原 prompt 里包含 ``` 也不会提前 close fence，让后续的 header 文本被解读成可执行指令。这是 CommonMark fence-matching 的一条规则。
  • 任务已经从磁盘删除：即使模型或用户后来决定不执行，下次启动也不会再被当 missed 出来。

Recurring task 不走这条路的理由写在 :187-191：chokidar-triggered reload 不重新 surface 老的 overdue——只有 initial load 会。这避免了"missed while Claude was not running"对中途刚产生 overdue 的任务变成误导性提示。

14. 两层 feature gate¶

调度器入口有两层 gate，一编译时一运行时：

feature('AGENT_TRIGGERS') 是 bun:bundle 的编译时常量，false 的话整个 hook 代码会被 dead code elimination 剔掉，不进 bundle。

运行时 gate：

  • CLAUDE_CODE_DISABLE_CRON 是 local override，短路左侧。不走任何服务。
  • tengu_kairos_cron GrowthBook flag，5 分钟刷。默认 true——Bedrock / Vertex / Foundry 和 telemetry 关了的客户根本连不上 GrowthBook，默认 false 会让他们的 /loop 失效（:28-32 注释说这对应 GH #31759）。

这个 flag 不是 effect 依赖。useScheduledTasks 只依赖 assistantMode（src/hooks/useScheduledTasks.ts:126），不会因为 flag 翻转 re-mount。scheduler 怎么响应 flag 变化？每 tick 查一次 isKilled()（src/utils/cronScheduler.ts:231）。flag 从 true 翻 false，运行中的 scheduler 下一秒自己退。这比"react 到 flag 变化重新挂载"简单，代价可忽略（一次 feature cache read）。

类似的 isDurableCronEnabled()（src/tools/ScheduleCronTool/prompt.ts:56-62）是 durable 的独立 kill switch，关了之后 CronCreate.call() 会强制 effectiveDurable = false（src/tools/ScheduleCronTool/CronCreateTool.ts:120），但 schema 保持稳定不让模型拿到 validation error。细粒度 kill 的好处是可以在事故中只砍磁盘路径（有 I/O 问题），保留内存 cron（健康）。

15. 设计取舍¶

把前面看到的几个选择列出来做对照。

自研 cron 解析 vs 引库。只支持 5-field 常见子集，代价是表达力窄。收益：包小、DST 行为自己掌控、cronToHuman 和翻译逻辑跟解析共享 field 约定。在 agent 场景下这层抽象够用——用户不会写 L 或 MON。

每秒轮询 vs 精确 setTimeout。精确 timer 在 chokidar 触发 reload 时要全部清掉重建，还要在 jitter 变化时重算；1 秒轮询则是"算一下 now >= next"。代价是每秒一次空转，收益是状态机简单——任何 flag 或配置变更都在下一秒生效。

单文件 + per-project 锁 vs 独立守护进程。锁用 O_EXCL，进程退出时 cleanup registry 释放。没有跨进程 IPC，没有额外服务。代价：passive 进程每 5 秒探一次能否接管；同一 cwd 下打开多个 Claude 时只有一个在真正 tick。对 agent 场景完全够用。

Deterministic jitter vs 随机 jitter。parseInt(taskId.slice(0, 8), 16) / 0x1_0000_0000 让同一个任务跨进程、跨 tick 产生同样的抖动值。好处：

  • check() 每 tick 重算 nextFireAt，如果是随机 jitter 每次结果都不一样，getNextFireTime() 会给远端 SDK daemon 不稳定答案。
  • 重启后基于 lastFiredAt + jitter 计算的 newNext 跟在线时算出来的完全一致，idempotent。

代价：同一个 task id 永远落在同一个相对偏移上——但在 fleet 级别看，task id 本身就是 UUID 均匀分布，全局无 hotspot。

7 天硬过期 vs 用户显式取消。源码注释说得直接（src/utils/cronTasks.ts:339-345）：cron 把 p99 session 时长从 61 分钟拉到 53 小时，内存泄漏压力跟着放大。7 天覆盖最常见的"这周帮我"工作流，同时给长跑任务一个兜底。想持续用就每周 recreate，或者切 durable routine / Desktop tasks。

16. 可迁移的点¶

  1. 把"定时任务"建模成一个存储层差异。{cron, prompt, durable} 三元组，durable 只控制存到内存还是磁盘；调度层对两种 store 走一样的流程，仅在 fire 之后的清理路径（isSession 分支）区分。让新加"第三种存储后端"只动一个 process(t, isX) 分支。
  2. 跨进程文件锁：O_EXCL 原子创建 + PID liveness probe + --resume 时刷 PID 保留所有权。这组模式处理绝大多数跨进程协调不需要引 redis / sqlite / zmq。仓库里 computerUseLock.ts 和 cronTasksLock.ts 共享这个模式。
  3. Deterministic 哈希 jitter 一行写完。parseInt(id.slice(0, 8), 16) / 0x1_0000_0000 就是一个 task-stable 的均匀分布。比随机 jitter 更适合调度场景（idempotent、可预测）。
  4. Feature flag 放在 check() 轮询里。不在 effect 依赖里，不需要 unmount/remount 整个 scheduler。flag 翻转时运行中的调度器自己 bail。简单到不会错。
  5. 双字段标记系统注入：isMeta: true（UI 不可见）+ priority: 'later'（不饿死用户）+ workload: 'cron'（API 降级）。三个字段值正交。第三个通过 AsyncLocalStorage 透传到 HTTP header，是整本仓库的统一模式（src/utils/workloadContext.ts）。
  6. Reinjection 防注入：当系统拼一段"用户原始文本"重新喂给模型时，用 CommonMark fence 包起来，fence 长度自适应是"原文最长反引号串 + 1"——这是一行就能实现的可靠防御。src/utils/cronScheduler.ts:556-560 的 buildMissedTaskNotification 是可直接搬的例子。
  7. 调度层与驱动层解耦：createCronScheduler 接 onFire(prompt) 回调，不关心是 React hook 还是 -p 流式 loop。加一个新运行模式就加一个 factory 调用，不改 scheduler 内部。
