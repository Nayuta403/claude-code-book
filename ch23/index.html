23.1 用户看到什么¶

Claude Code 有两个日常入口。一个是终端 REPL：

另一个是 npm 库：

两个入口跑起来行为几乎一致：同一套工具（Read / Edit / Bash / Grep / ...），同一套权限 mode，同一套 MCP / hooks / skills 体系。官方原话——"The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code."（来源：https://code.claude.com/docs/en/agent-sdk/overview，访问于 2026-04-19）。共享的 Agent Loop 主干见 ch.03。

区别只在终点：REPL 把 SDKMessage 交给 Ink 渲染，SDK 把 SDKMessage 交给调用方的 async-for 循环。

23.2 本章关注点¶

读者真正要学的一件事：一份 Agent Loop + 工具 + 权限 + MCP + Hooks 引擎，怎样以零代码分叉的方式同时当终端工具和第三方库？

Claude Code 的答案是——不给 SDK 写第二份引擎，而是让 SDK spawn CLI 子进程，用 NDJSON 流复用 CLI 的 stdio 当控制面 + 数据面。扩展点全部降级成消息协议：自定义 Tool、canUseTool、hook、动态改 model、改权限模式、查 MCP 状态——每一个都是一条带 type / subtype 的 JSON。

这带来两个效果：

  1. CLI 功能更新自动同步给 SDK，不用两套实现对齐。
  2. 跨进程 / 跨网络 transport 可以用同一份协议——终端 stdio、Remote Session WebSocket（见 ch.17 §17）、daemon bridge 都走这份 union 类型。

23.3 SDK 的表面积¶

SDK 类型真身在 src/entrypoints/agentSdkTypes.ts —— 重新导出 core 类型、runtime 类型、声明对外函数签名。本仓库里这些函数的函数体都是 throw new Error('not implemented')（src/entrypoints/agentSdkTypes.ts:120-122 等）。

真正的运行时实现在 npm 包 @anthropic-ai/claude-agent-sdk（见 package.json:29），它把 Claude Code 二进制作为 optionalDependency 打包并 spawn 为子进程[^1]。

[^1]: 官方明文："The TypeScript SDK bundles a native Claude Code binary for your platform as an optional dependency"（来源：https://code.claude.com/docs/en/agent-sdk/overview）。本仓库内 src/entrypoints/sdk/runtimeTypes.ts:1-22 把 Options / Query / SDKSession 等都定成 Record<string, unknown> ——这是 source-map 还原的 shim，协议级真相以 Zod schema（coreSchemas.ts / controlSchemas.ts）为准。

23.3.2 Options 的扩展点¶

官方 TS SDK 文档（https://code.claude.com/docs/en/agent-sdk/typescript，访问于 2026-04-19）列出 Options 的字段群，按职责分组：

  • 核心：model / cwd / maxTurns / continue / resume
  • 权限：permissionMode（default / acceptEdits / bypassPermissions / plan / dontAsk / auto）、allowedTools / disallowedTools、canUseTool、allowDangerouslySkipPermissions
  • 工具 & MCP：tools（string[] 或 { type: 'preset', preset: 'claude_code' }）、mcpServers
  • Agent & System：agent / agents、systemPrompt（字符串或 { type: 'preset', preset: 'claude_code' }）、appendSystemPrompt
  • 思考：thinking / effort
  • 输出：outputFormat: { type: 'json_schema', schema }、includePartialMessages
  • Hooks：hooks: Partial<Record<HookEvent, HookCallbackMatcher[]>>
  • 进阶：abortController / sandbox / plugins / settingSources

每一项都有仓库对应：它们被 SDK 翻成 initialize control_request 的字段（见下节）和 runHeadless 的 options（src/cli/print.ts:455-492）。Options 里没有"必传"字段——一个空 Options 跑的就是 CLI 默认行为。这一条很关键，决定了迁移成本为零。

隐藏细节（src/utils/claudemd.ts:939）：SDK 的 settingSources 默认值是 []——即默认不加载 CLAUDE.md / .claude/ 目录 / skills / commands / plugins。这与 CLI 默认全加载正好相反（注释原文："the SDK defaults settingSources to [] when not specified"）。官方 overview 文档措辞"With default options the SDK loads these from .claude/..."与源码直接冲突，以源码为准。SDK 首次跑起来发现"claude 不吃我的 CLAUDE.md"基本都是这一条。

隐藏细节（src/entrypoints/agentSdkTypes.ts:101）：createSdkMcpServer 注册的进程内 MCP tool 走 60s 默认 close timeout，注释原文："If your SDK MCP calls will run longer than 60s, override CLAUDE_CODE_STREAM_CLOSE_TIMEOUT"。用户写长任务 SDK tool 时到 60s 会被 kill，这是标准踩坑点，文档只埋在 docstring 里。

23.4 控制协议：把回调变成消息¶

SDK 用户传的 canUseTool 回调、hooks 回调跑在宿主进程，Agent Loop 跑在 CLI 子进程——跨进程怎么把结果接回去？

23.4.1 control_request / control_response 信封¶

信封只有一层：

request_id 是 UUID，用来在两侧的 pending map 里配对 response。额外还有 control_cancel_request（controlSchemas.ts:612-619）—— 单字段 request_id，让一侧通知对端取消某个 pending 请求。远端 WebSocket transport 复用的正是同一份信封（ch.17 §17 有独立视角）。

23.4.3 initialize 握手¶

SDK 和 CLI 的第一件事是一次 initialize：

CLI 回一份能力表（controlSchemas.ts:77-95）：commands / agents / available_output_styles / models / account / pid。之后 SDK 宿主就能对着表做 UI 选择。

Hook 回调的注册方式值得看一下。用户传的函数在 SDK 进程，CLI 拿不到；握手时 SDK 把每个 hook 分配一个 hookCallbackIds: string[]（SDKHookCallbackMatcherSchema，controlSchemas.ts:43-51），CLI 要触发时发一条 hook_callback request 带 callback_id（controlSchemas.ts:363-372），SDK 侧 dispatch 到对应 JS 函数。整条链路和 MCP server 的做法同构——hooks 的其他注入路径（shell / HTTP / prompt / agent）见 ch.14 §14。

23.5 CLI 侧的运行时：NDJSON StructuredIO + runHeadless¶

23.5.1 启动条件¶

src/main.tsx:2831-2835 决定走 SDK 模式：-p/--print 标志加上 --output-format=stream-json。

自动设置的真正触发条件是 --sdk-url：提供后，input/output format 都会被自动置为 stream-json（main.tsx:1242-1258），同时顺带把 verbose 和 print 打开。若没有 --sdk-url，--input-format=stream-json 并不会自动升格 output——反而是 input === stream-json && output !== stream-json 时直接报错退出（main.tsx:1829-1832）。

之后动态 import('src/cli/print.js') 跑 runHeadless()，Ink UI 永不加载。

runHeadless 的 options（src/cli/print.ts:455-493）就是 Options 的 CLI 侧接收端。里面几个 SDK 独有的字段：

  • includePartialMessages：开 stream_event 发射。
  • replayUserMessages：把 stdin 的 user message 再 echo 回 stdout，供宿主做 ack。
  • enableAuthStatus：允许 auth_status 消息，供 IDE 感知登录态。
  • workload：进程级别的 billing-header tag，SDK daemon callers that spawn subprocesses for cron work（main.tsx 选项注释）用。

23.5.2 NDJSON StructuredIO：协议多路复用器¶

src/cli/structuredIO.ts:135 起。职责清晰：

  • 按行读 stdin，jsonParse → normalize → 按 type dispatch（processLine，structuredIO.ts:333-463）。
  • 维护 pendingRequests: Map<string, PendingRequest>（structuredIO.ts:137），每条 control_request 挂一个 {resolve, reject, schema, request}。
  • 所有对端 response 按 request_id 查表、Zod schema 校验、resolve pending promise（structuredIO.ts:362-429）。
  • 取消路径：AbortSignal fire 就 enqueue 一条 control_cancel_request 并 reject 本地 promise（structuredIO.ts:490-509）。

值得留意的抗重入保护：

有了它，WebSocket 重连 / 消息重放造成的"同一个 tool_use_id 的 control_response 到两次"不会把重复 assistant message 推进 history（会导致 API 400 tool_use ids must be unique）。第二次直接忽略（structuredIO.ts:378-394）。这是跨进程 + 不稳定网络场景必须做的事。

隐藏细节（src/cli/structuredIO.ts:133 + 176-186）：resolvedToolUseIds 上限是 MAX_RESOLVED_TOOL_USE_IDS = 1000，满后 FIFO 驱逐最旧条目。也就是说，去重窗口有上限——极长 session 里超过 1000 条 tool_use 之后，若最早那批的重复 response 姗姗来迟，会再次被当成"新"的处理掉。正常场景碰不到，边界上需要留意。

23.5.3 canUseTool 的双源 race¶

Claude Code 的权限系统让 SDK 宿主的 canUseTool 回调与 PermissionRequest hook 并行竞速（src/cli/structuredIO.ts:576-659）。权限系统的本地 rules / allowedTools / disallowedTools 判决细节见 ch.09 §9。

前置：本地 permission 系统先跑一次——只要 behavior === 'allow' 或 'deny' 就直接返回，不发任何 control_request（structuredIO.ts:544-559）；只有 behavior === 'ask' 时才进 race。整段 race 的逻辑：

为什么并行而不是串行等 hook？——hook 可能是 shell 进程或 HTTP 服务，无上限慢；SDK 宿主（比如 VS Code 的权限弹窗）该立即出现就立即出现，不被后台 hook 卡住。输的一方 abort。这是值得偷的模式：并发扩展点之间别串行等。

23.5.4 NDJSON 清洁¶

SDK 模式下任何意外 console.log 都会毒化宿主的行分片 parser。runHeadless 一开始就装 stdout guard（print.ts:594-596），把非 JSON 行改道到 stderr。上线 NDJSON 协议要记得做这件事。

23.6 SDK 与 CLI 的代码复用面¶

共享（同一份代码）：

  • Agent Loop（见 ch.03 §3）：入口一致，本章不展开。
  • 工具系统（见 ch.08 §8）：Tool 接口、getTools()、ToolSearch 的动态注入都是共用代码；SDK 自定义 Tool 走 createSdkMcpServer 封装进来，详见 ch.12 §12。
  • 权限（见 ch.09 §9）：hasPermissionsToUseTool 先判本地规则（structuredIO.ts:546-552），再决定是否发 can_use_tool。
  • MCP（见 ch.12 §12）：MCP 客户端 / server 配置 / elicitation 管道全共享。createSdkMcpServer 产出的进程内 server 走同一份 client codepath。
  • Hooks（见 ch.14 §14）：SDK 的 createHookCallback（structuredIO.ts:661-689）是 hook 执行者的第五种（另外四种：shell / HTTP / prompt / agent）。
  • Skills / Plugins / Memory（见 ch.10 / ch.11 / ch.07）：SDK 的 settingSources 决定是否加载——默认值 []（见 §23.3.2 callout）与 CLI 默认全加载相反，这是"共享引擎 + 不同默认"的一个典型分叉，迁移到 SDK 时需要显式传 ['user', 'project', 'local'] 才能恢复 CLI 行为。
  • Sandbox / Session 存储。

CLI 独占：Ink UI（ch.21）、keybindings / voice（ch.20）、statusline / Buddy（ch.19）、交互式 trust dialog、OAuth 登录向导。

SDK 独占：NDJSON StructuredIO 读写、runHeadless 的 options 展开路径、initialize 握手、ControlErrorResponseSchema.pending_permission_requests 断连恢复（controlSchemas.ts:599-602）。

隐藏细节（src/cli/structuredIO.ts:682-686）：SDK hook 回调里 throw 不会让 agent 退出——createHookCallback 用 try/catch 捕获异常，console.error 一行后返回 {}（pass-through）。与 shell hook 的"exit code 2 = block"行为完全不同：在 SDK 里写 assert(...) 会被静默吞掉，hook 实现里的防御判断必须显式返回 decision 字段，不能靠抛错阻止工具执行。

隐藏细节（src/cli/print.ts:5348-5352）：Query.setMcpServers() 运行时注入 MCP 仍然跑企业 allowedMcpServers / deniedMcpServers 策略过滤（与 --mcp-config 同一条 filter）。注释原文："SDK V2 Query.setMcpServers() was a second policy bypass vector"——没有这层检查的话，运行时热插拔 MCP 就能绕过 enterprise 策略。被 block 的 server 在 response.errors 里报出，SDK 宿主据此展示。

粗略估计共享率：高。分叉点几乎都在"渲染终点"和"用户输入源"上。Agent Loop、Tool、MCP、Permission、Hooks、Skills、Plugins、Memory、Sandbox、Telemetry、Session 存储——这些是本书大部分章节讲的核心——两端一份代码。

23.7 Session 生命周期与错误恢复¶

23.7.1 一次性 query vs 持久 session¶

官方文档演示的主流用法是每次调用新起 session，复用靠 session_id：

第二次 query 传 options.resume: sessionId 就续接。本仓库 unstable_v2_createSession / unstable_v2_resumeSession（agentSdkTypes.ts:129-144）提供了持有 session 对象的 v2 风格 API，但标 @alpha 未稳定——生产建议走 session_id 路线。

23.7.2 错误暴露给 SDK 用户¶

错误从三个通道走：

  1. SDKAPIRetryMessage（coreSchemas.ts:1572-1588）：API 5xx / 超时等可重试错误，CLI 自动重试前发一条通知，带 attempt / max_retries / retry_delay_ms。SDK 用户只读不响应。
  2. SDKRateLimitEvent（coreSchemas.ts:1358-1367）：带 resetsAt / rateLimitType（five_hour / seven_day / 等）。
  3. SDKResultErrorSchema（coreSchemas.ts:1428-1451）：终态错误。subtype 枚举：error_during_execution / error_max_turns / error_max_budget_usd / error_max_structured_output_retries。errors: string[] 累积具体原因，permission_denials 含本 session 里被拒绝的工具调用。

中断：SDK 用户发 control_request{ subtype: 'interrupt' }（或直接 abortController.abort()）。本地产生 AbortError（agentSdkTypes.ts:109）。

断连恢复的专门设计：ControlErrorResponseSchema.pending_permission_requests（controlSchemas.ts:594-603）——宿主重连后可以从 error response 里拿回未完成的权限请求列表，继续处理。这条在本地 NDJSON StructuredIO 路径看不到，是留给跨网络 transport（Remote Session，见 ch.17 §17）用的。

隐藏细节（src/utils/sessionRestore.ts:452-462）：forkSession 不止"拷贝 JSONL 换 UUID"——必须显式 recordContentReplacement 把原 session 的 content replacement 搬到新 session。否则后续 claude -r {newId} 的 tool_use_id 会被判为 FROZEN，全文重传走 cache miss 路径，注释原文称此为 "permanent overage"。SDK 用户调 forkSession 时不需要感知这层，但若跳过 SDK 自己复制 JSONL 拼凑 fork 会直接踩坑。

23.8 src/entrypoints/mcp.ts：SDK 的另一种入口¶

Claude Code 还把自己暴露为一个 MCP server。src/entrypoints/mcp.ts:35-196 的 startMCPServer() 通过 stdio transport 把所有内置 Tool 注册为 MCP tool，供其他 MCP client（比如另一个 Claude Code 实例，或任何 MCP 宿主）调用：

这是 SDK 之外的另一条调用路径：不经 query() + canUseTool 协议，而是走 MCP 的标准 tools/list + tools/call。两端最终都落到同一个 getTools()（src/entrypoints/mcp.ts:64）。MCP server 侧的 Tool 注入和 ToolSearch 行为见 ch.08 §8、ch.12 §12。

23.9 设计取舍¶

23.9.1 子进程 vs 嵌入式库¶

SDK 为什么不直接把 Agent Loop 做成纯 JS 函数 export 出来？三条理由从源码能看出来：

  1. CLI 启动有大量全局 state 依赖顺序：src/entrypoints/init.ts:57-238 的 memoize + 串行 checkpoint（init_configs_enabled / init_mtls_configured / init_proxy_configured / ...）假设一个进程只 init 一次。SDK 宿主自己已经有一份完整 Node 进程 state，两套合并会踩 env 变量 / TLS 证书 cache / TZ 这些全局。
  2. 可热升级：子进程二进制由 SDK 按需下载 / 更新（官方文档："bundles native Claude Code binary ... as an optional dependency"）。宿主进程不用重启就能换 Claude Code 版本。
  3. 故障隔离：Claude Code 有文件 watcher / LSP / plugin 生命周期，崩一条线不影响 SDK 宿主。

代价：每次 query() 冷启子进程。官方 SDK 提供 startup() 预热函数（文档提及，本仓库未暴露 stub）缓解。NDJSON 序列化 / 反序列化相比函数调用有开销，但 Agent 的瓶颈是 API 延迟，这点开销占比小。

23.9.2 把扩展点变成消息类型¶

这是本章最值得借鉴的点。

常规写法是"接口接受一堆 optional callback"：

Claude Code 的写法是：所有可扩展的双向交互都通过 control_request 子类型。加一个扩展点 = 在 SDKControlRequestInner 里加一个 z.literal(...) 成员（controlSchemas.ts:552-576，当前 21 种），SDK 宿主按 subtype switch。

相比 callback 集合：

  • 接口稳定：query({ prompt, options }) 签名不改。
  • 多 transport 通用：同一份协议既走 stdio，又走 WebSocket（见 ch.17 §17 远端），又走 daemon bridge。加 transport 不动 schema。
  • 可持久化 / 可回放：断连恢复用 pending_permission_requests 让对端回放未完成请求——这在 callback 模型下做不到。
  • 协议版本化：Zod schema 可以加 discriminator，旧 SDK 不认得的 subtype 可以 fallback。

代价：SDK 侧需要自己维护 pending request 表（structuredIO.ts:137），callback 风格要简单得多。

隐藏细节（src/cli/print.ts:3709-3718）：apply_flag_settings 用 null 作为"清除这一键"的哨兵值——因为 JSON.stringify 会把 undefined 的属性直接 drop 掉，双方无从约定"擦除"语义。CLI 在 merge 前统一把值为 null 的 key delete 掉，再送进 Zod optional 校验。JSON-native 协议做 PATCH 语义都得想好这件事，不是语法糖。

23.9.3 Zod schema 作为单一真理源¶

coreSchemas.ts 文件开头注释（coreSchemas.ts:1-8）：

These schemas are the single source of truth for SDK data types. TypeScript types are generated from these schemas and committed for IDE support. @see scripts/generate-sdk-types.ts for type generation

TS SDK 的类型、Python SDK 的类型（官方 Python 包）、CLI 侧的运行时校验——都从这一份 schema 生成或手动对齐。改字段只改一处，三端一起更新。

Zod schema 天然包含两项：类型 + runtime validator。CLI 侧 StructuredIO.processLine 对 stdin 的 control_response 用 request.schema.parse(result)（structuredIO.ts:416-423）做校验，schema 直接当防御第一层。比手写 TS interface 再写 if (typeof x === 'string' && ...) 的防御省事一大截。

23.9.4 并发扩展点不串行¶

canUseTool × PermissionRequest hook 的 race（structuredIO.ts:576-659）是一个小但重要的模式：同一个决定有多个可能 resolver 的时候，并行启动所有 resolver，先到先赢，其他 abort，不要做"hook 决定了就不问 SDK"这种看似简单的串行逻辑——因为 hook 可能无限慢。

这个模式在 agent 系统里有通用价值：用户输入来源多元（UI 弹窗 / 快捷键 / hook / 外部 API），任何一个"第一候选人"都不能独占等待时间。

23.10 可迁移的点¶

给做 agent 库 / agent 产品的读者：

  1. NDJSON over stdio 做控制面 + 数据面。进程间传 agent 流就够了，比 gRPC 轻，比 JSON-RPC 自由（JSON-RPC 没法在同一条流里随意插 partial event）。每行一个 type / subtype 字段就能走很远。
  2. request_id + Map<string, PendingRequest> 统一异步回调模式。取消、去重、超时、跨网络恢复都用同一套。参见 structuredIO.ts:469-531 的完整实现。
  3. 扩展点 → 消息类型。接受 callback 的方案，扩展面积大了接口会爆炸。把扩展点变成 discriminated union 的子类型，主入口签名永远是 query({ prompt, options })。代价是 pending 表管理，但这玩意儿只写一次。
  4. Zod schema 作协议源。特别是跨语言 / 跨进程场景，先写 schema、生成类型、运行时 parse 一条龙。手写 interface + 手写 validator 的 drift 是长期维护的大坑。
  5. stdout guard。要发 NDJSON 就别让依赖库污染 stdout——安装一层 redirect（参考 print.ts:594-596）把非 JSON 行送到 stderr。
  6. 断连恢复要在协议里留口子。像 pending_permission_requests 这种字段，只在"对端重连"时才用得上，但协议里留着，比日后加不兼容升级容易得多。
  7. 并发扩展点 race 而不是 sequence。同一个决定多个可能的 resolver，让他们并行，先赢者取，输者 abort。
  8. JSON PATCH 语义要选 null 而非 undefined。JSON.stringify 会 drop undefined，两侧无法约定"擦除这一键"。用 null 当哨兵，接收端在校验前统一转成 delete。

脚注：本章涉及的所有 CLI → SDK 协议字段均以 src/entrypoints/sdk/coreSchemas.ts 与 src/entrypoints/sdk/controlSchemas.ts 的 Zod schema 为准。agentSdkTypes.ts 导出的函数在本仓库里全部是 throw new Error('not implemented') 的 shim——真正的运行时在 npm 包 @anthropic-ai/claude-agent-sdk（package.json:29）内，它作为 SDK 宿主 spawn 本仓库 CLI 二进制。
