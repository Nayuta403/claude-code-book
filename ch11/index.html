11.2 为什么挑这个设计出来讲¶

Plugin 不是一个功能，是一个打包器。本仓库源码里能被 plugin 贡献的子系统十种（以 PluginManifestSchema 实际合并的 partial shape 为准，见 src/utils/plugins/schemas.ts:884-898）：commands（详见 ch.01 §1.2）、skills（详见 ch.10 §10.3）、agents（详见 ch.04 §4.3）、hooks（详见 ch.14 §3）、MCP servers（详见 ch.12 §2）、LSP servers、output styles、channels（MCP 通道集成）、plugin-scoped settings.json（仅 agent 白名单，scope 级联见 ch.09 §9.3）、userConfig。每一种都先能独立存在（skills 在 ~/.claude/skills/、hooks 直接写 settings.json、MCP server 写 ~/.claude/.mcp.json），plugin 只是在这些机制之上再加一层统一的：

  • 声明式 manifest（.claude-plugin/plugin.json）
  • 可被版本化的分发（marketplace）
  • 统一的 enable / disable / uninstall 开关
  • 统一的热重载入口（/reload-plugins）

隐藏细节（src/utils/plugins/schemas.ts:884-898）：官方 docs（https://code.claude.com/docs/en/plugins-reference，访问于 2026-04-19）另外列举了 monitors 和 bin/ 两种贡献点（前者"Plugin monitors require Claude Code v2.1.105 or later"，后者"Executables added to the Bash tool's PATH"）。但本仓库的 PluginManifestSchema 里没有对应的 PluginManifest*Schema partial——schemas.ts:884-898 合并的 partial 只有 metadata / hooks / commands / agents / skills / outputStyles / channels / mcpServers / lspServers / settings / userConfig 十一个。配合 schemas.ts:875-883 的"顶层 unknown key silently stripped"策略，这意味着：用户按 docs 在 plugin.json 里写 monitors / bin 字段，当前版本 zod 静默剥离，无任何错误提示、无效果、无日志——这是"顶层宽容"策略的具体代价。本章后续不把 monitors / bin 算作贡献点，只按本仓库实际实现的十项讨论。

真正值得讲的是第三和第四点。一个现代 IDE 的 plugin 系统通常要求重启进程，或者只热更其中一部分子系统。Claude Code 的热重载在一条 /reload-plugins 里同时换掉了命令、agent、hook、MCP 连接、LSP 配置、plugin 提供的 settings 叠加层——实现做法是把三层（intent / materialized / active）拆清楚，每层给一把 cache invalidation 钥匙。这章主要讲这个。

Commands / Skills / Agents / MCP / Hooks 本身不在本章（分别详见 ch.01 / ch.10 / ch.04 / ch.12 / ch.14）。本章只讲 plugin 怎么包住它们。

11.3 Plugin 的形态¶

一个 plugin 就是一个目录。npm / git / github / 本地路径只是"把这个目录弄到本地"的多种方式，不是 plugin 的本质。目录根下长这样（允许部分缺失，字段对应 PluginManifestSchema 合并的 partial shape）：

隐藏细节（src/utils/plugins/pluginLoader.ts:1776-1782）：PluginSettingsSchema 用 SettingsSchema().pick({ agent: true }).strip()——仅 agent 一个 key 进白名单，其余静默剥离。官方 docs（https://code.claude.com/docs/en/plugins-reference）描述允许 agent 和 subagentStatusLine 两个，但本仓库代码只收 agent。配合 .strip()，作者在 plugin 的 settings.json 里写 env、permissions、subagentStatusLine 都不会报错——加载后默默无效。这对想按 docs 测试的 plugin 作者是个隐蔽坑（settings scope 的完整级联见 ch.09 §9.3）。

manifest 可以完全省略——省略时从目录名取 plugin name，自动扫 skills/ commands/ agents/ 等默认路径。写 manifest 是为了：声明元数据（版本、作者）、改路径、内联 hooks/MCP 配置、声明 userConfig（用户侧变量）、声明 dependencies（版本化依赖其他 plugin）。完整 schema 见 src/utils/plugins/schemas.ts:884-898：

这个 schema 有一个取舍值得讲：顶层 unknown key 静默剥离，嵌套 unknown key fail-fast。作者在 schemas.ts:875-883 的注释里解释：

Unknown top-level fields are silently stripped (zod default) rather than rejected. This keeps plugin loading resilient to custom/future top-level fields that plugin authors may add. Nested config objects (userConfig options, channels, lspServers) remain strict — unknown keys inside those still fail, since a typo there is more likely to be an author mistake than a vendor extension.

顶层留扩展余地（未来加字段、作者可加供应商特定字段），嵌套内部严格（打错字早发现）。这个策略比单一地"一律严格"或"一律宽松"更细——取决于该字段位置的"可能是未来扩展 vs 可能是打字错误"的先验概率。同样的取舍可以用在任何长寿命的 JSON schema 上。

channels：MCP server 作为消息通道¶

十种贡献点里最特别的是 channels（schemas.ts:655-703）。它不是一个独立的代码装载器，而是在 mcpServers 之上加一层语义标记——把某个 MCP server 声明成"能往会话里注入消息的通道"，典型场景是 Telegram / Slack / Discord 集成：

声明 channel 的价值来自它和 userConfig 的联动：plugin 启用时 UI 会弹出 PluginOptionsFlow 要求用户填入这个 channel 专属的 bot token / owner id 之类的敏感变量，存到 settings 后在 MCP env 里替换 ${user_config.KEY}——用户不用手改 settings.json。server 字段和 mcpServers 的 key 跨字段对齐，但 schema 解析时不做交叉校验：

The server field must match a key in the plugin's mcpServers — this is not cross-validated at schema parse time (the mcpServers field can be a path to a JSON file we haven't read yet), so the check happens at load time in mcpPluginIntegration.ts instead.（schemas.ts:665-668）

消费侧在 src/utils/plugins/mcpPluginIntegration.ts:290-318 的 getUnconfiguredChannels()：plugin 启用后 ManagePlugins.tsx 调它过一遍所有 channel，凡 validateUserConfig 不通过（必填项没存）就塞进返回列表，触发配置 dialog。这是"让用户在正确时间填对值"的一种温和强制——绕过它就只是看到 server 起不来。

11.5 Marketplace 与官方市场¶

官方市场 claude-plugins-official 启动即装，默认 auto-update。但"官方"并不等于"一定自动更新"：

隐藏细节（src/utils/plugins/schemas.ts:30-35）：NO_AUTO_UPDATE_OFFICIAL_MARKETPLACES = new Set(['knowledge-work-plugins'])——保留名单 8 个里有 1 个被显式从 "官方默认 auto-update" 里剔除。其余 7 个官方 marketplace 默认 auto-update（isAutoUpdateEnabledForMarketplace 在 schemas.ts:37-67），knowledge-work-plugins 走"和非官方 marketplace 一样要显式开"的路径。这个差异在 UI 上没有任何提示：用户会默认"官方的都 auto-update"，但装 knowledge-work-plugins 里的 plugin 后新版本静默停滞。原因是这类内容型 marketplace 更新意味着行为变化，不宜无声替换。

Marketplace source 有九种（schemas.ts:906-1044）：

  • settings——内联 marketplace 清单，直接写在 settings.json 里；reconciler 会合成一份 marketplace.json 放到 cache

11.6 三层加载模型¶

这是本章的核心概念。refresh.ts:2-8 的注释一句话说清：

  • Layer 1 意图：用户写 enabledPlugins 和 extraKnownMarketplaces 到 settings 文件。
  • Layer 2 物化：~/.claude/plugins/ 下的 known_marketplaces.json、installed_plugins.json、版本化 cache 目录。
  • Layer 3 激活：当前 session 的 AppState.plugins、STATE.registeredHooks、MCP 连接管理器状态。

三层分开的价值在于：每层的写路径独立、读路径有 invalidation 钥匙。改了 Layer 1，Layer 2 不自动跟；Layer 2 变了，Layer 3 只在 /reload-plugins 时跟。这种松耦合意味着：

  • 用户手动编辑 settings.json（Layer 1 改），不会在键入瞬间触发磁盘 clone
  • 后台 auto-update 改了 Layer 2，不会吃掉正在跑的 session 状态
  • /reload-plugins 只负责 Layer 3，它能假设 Layer 2 已经物化好

11.7 安装的完整链路¶

一次 /plugin install foo@bar 下去会发生什么：

  1. Parse：parsePluginArgs("install foo@bar") 解析出 { type: 'install', plugin: 'foo', marketplace: 'bar' }（src/commands/plugin/parseArgs.ts）。
  2. UI 分发：PluginSettings → ManagePlugins 或 BrowseMarketplace 组件。
  3. 操作层：src/services/plugins/pluginOperations.ts 写 enabledPlugins[<scope>]、调 cachePlugin()。
  4. 下载：cachePlugin() 走六条路径之一——字符串本地路径 + 五种对象 source（pluginLoader.ts:937-963）： ts // src/utils/plugins/pluginLoader.ts:937-963 if (typeof source === 'string') { await installFromLocal(source, tempPath) } else { switch (source.source) { case 'npm': await installFromNpm(...) case 'github': await installFromGitHub(source.repo, tempPath, source.ref, source.sha) case 'url': await installFromGit(...) case 'git-subdir': gitCommitSha = await installFromGitSubdir(...) case 'pip': throw new Error('Python package plugins are not yet supported') } }
  5. 物化：拷贝到 ~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/，版本化目录结构在 pluginLoader.ts:139-162。写入 installed_plugins.json。
  6. Layer 3 标记 dirty：AppState.plugins.needsRefresh = true。
  7. 通知，不自动刷新： ts // src/hooks/useManagePlugins.ts:293-303 useEffect(() => { if (!enabled || !needsRefresh) return addNotification({ key: 'plugin-reload-pending', text: 'Plugins changed. Run /reload-plugins to activate.', color: 'suggestion', priority: 'low', }) // Do NOT auto-refresh. Do NOT reset needsRefresh — /reload-plugins // consumes it via refreshActivePlugins(). }, [enabled, needsRefresh, addNotification])
  8. 用户跑 /reload-plugins：refreshActivePlugins() 完成 Layer 3 swap。

为什么不自动刷新？refresh.ts:14-18 的注释给了答案：之前试过，有个 stale-cache bug。只清了 loadAllPlugins 的 memoize，下游 getPluginCommands、loadPluginAgents、loadPluginMcpServers 各自还有独立 memoize，读了老数据；而且 MCP 连接、agentDefinitions 这些散落状态也没被同步考虑。

与其小心翼翼维护"自动刷新能清掉的所有东西"的清单，不如把 refresh 整理成一个原子重入点，让用户显式触发。

UX 上显式触发看似倒退，工程上它把一个分散的 invalidation 问题收敛成了单点——少写一段自动化代码，换来一套可预测的状态机。

11.8 refreshActivePlugins 做到了什么¶

来看 Layer 3 的完整 swap：

五个不同子系统的 swap，用五种不同方式：

  1. Commands & agents：直接清 memoize cache，再跑一遍。
  2. Plugin settings 层：cachePluginSettings() 把 enabled plugin 的 settings.json（只有 agent key 被白名单 pick）合并进 settings cascade，作为最底层的 default（pluginLoader.ts:3281-3295）。
  3. Hooks：loadPluginHooks() 里的 clear-then-register 原子对——下节细讲。
  4. MCP：不直接重连，只 bump mcp.pluginReconnectKey。真正的重连逻辑在 useManageMCPConnections effect 里，依赖 pluginReconnectKey 变化自己重入。refresh 不跨模块越权。
  5. LSP：reinitializeLspServerManager() 重读配置。因为 LSP server 是 lazy-start 的，重读配置等价于"准备好，等第一次需求再起"。

这五种方式的共通点：refresh 本身不知道每个子系统内部怎么重建，它只负责 invalidate 正确的 key。每个子系统自己在合适的时点重建。这是"谁拥有状态，谁负责重建"的常规做法，但在一个有九种贡献点的 plugin 系统里能坚持做，是本章最值得借鉴的一点。

clear-then-register 原子对¶

Hook 的 swap 有个专门的细节值得单独贴：

原来 "清 cache" 和 "重注册" 是两个分开的函数——clearPluginHookCache() 和 loadPluginHooks()。结果任何调 clearAllCaches() 的地方都会先清 hook，下次 loadPluginHooks() 被触发之前 hook 是死的。SessionStart 因为显式 await，幸运地总能重注册；但 Stop hook 没有这个保证，悄悄死掉了（GitHub issue #29767）。

修复方式是把 clear 挪到 loadPluginHooks() 内部，作为"先清再注册"的原子对。调用者不再有"先清再等另一个 function 重注册"的窗口期。

这个教训可迁移：任何"cache + rebuild"的双步操作，把步骤放进同一函数比把它们作为独立 API 暴露更安全。库的用户永远会找到奇怪的顺序。

11.9 memoize 分层：cache-only vs full¶

loadAllPlugins 有两个 memoize 入口：

两个 memoize cache 是独立的，关系单向：

  • loadAllPlugins 会触网（git clone、npm install），结果能满足任何 caller
  • loadAllPluginsCacheOnly 只读已物化的 plugin，结果不能满足要 fresh source 的 caller
  • 但 full load 完成后会主动 warm cache-only 的 memoize（pluginLoader.ts:3106）

起点是 startup 性能：启动时一大堆模块（命令、agents、MCP config）都想 loadAllPlugins()。如果它们全去跑完整 load，git clone 会串起来。改用 cache-only 后，interactive 启动永远不阻塞在 clone 上；显式刷新路径才跑 full。

环境变量 CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 让 cache-only 降级为 full load——给 headless 首次运行用（还没 installed_plugins.json，cache-only 会全部 miss）。

这个设计可迁移的点是：同一个数据源两个 memoize key 代表两个语义等级，让不同调用方按自己的 SLA 选择。比"一个 cache + 一堆参数"清晰。

隐藏细节（src/utils/plugins/pluginLoader.ts:3100-3106）：loadAllPlugins 完成后主动写进 loadAllPluginsCacheOnly.cache——"既然刚 full load 过，cache-only 的调用拿这份结果天然成立"。这让 refreshActivePlugins 里后续看似独立的 getPluginCommands() / getAgentDefinitionsWithOverrides()（两者现在调 cache-only 变体）读到的是刚 clone 完的那份，不会穿透去读还没被 flush 的 installed_plugins.json。两个 memoize 之间的单向 warming 少见，文档不会提——但删掉它 refresh 路径会偶发读到 stale cache。

11.10 Plugin vs Skills vs MCP 的边界¶

本章一开始就说过 plugin 是个壳。以依赖方向图示：

（官方 docs 还列了 monitors / bin/ 两项，本仓库源码未实现；见 11.2 的隐藏细节 callout。）

读取方（消费点）也是双入口。以 MCP 为例：

MCP 连接管理器既读 settings 里的 mcpServers（用户直配），也读 LoadedPlugin.mcpServers（plugin 贡献）。两路输入最终汇到同一个连接池（连接池细节见 ch.12 §5）。Plugin 不是 MCP 的前提，只是 MCP 配置的一种来源。

这个边界上的限制是：plugin 里的 agent 不支持 hooks、mcpServers、permissionMode（来源：https://code.claude.com/docs/en/plugins-reference，访问于 2026-04-19）。plugin 之外的自定义 agent 可以用这些字段。理由是 plugin 作为可分发单位信任级别更复杂——plugin 安装时用户同意了 "这个 plugin 能装 MCP server"，但如果 plugin 里的 agent 又能塞自己的 MCP，信任模型就套了一层没打招呼的嵌套。把这几个字段在 plugin agent 里禁掉，避免授权扩散。

隐藏细节（src/utils/plugins/loadPluginAgents.ts:153-168）：被禁的这三字段（permissionMode / hooks / mcpServers）在 plugin agent frontmatter 里写了不会报错——for (const field of ['permissionMode', 'hooks', 'mcpServers']) { if (frontmatter[field] !== undefined) logForDebugging(..., { level: 'warn' }) }。只走 logForDebugging 的 warn 级别落日志，文件照常被载入、其他字段正常生效。配合日志默认不开，plugin 作者容易以为自己声明的 hook 生效了（agent 确实跑起来了）却查不出为什么 hook 没 fire。要看到这条 warning，得显式开 debug 模式或过滤 *.log。

隐藏细节（src/utils/plugins/pluginOptionsStorage.ts:385-399）：plugin 里 skill / agent 的 markdown 内容可以插 ${user_config.KEY} 占位符引用 userConfig——但如果 KEY 在 schema 里被标了 sensitive: true，substitute 返回的不是变量值也不是空串、不抛错，而是字面字符串 [sensitive option 'KEY' not available in skill content]。设计意图是让 plugin 作者一眼看到"你把敏感值放错了位置"——敏感值走 hook env / MCP env，不该出现在模型能看到的 prompt 文本里。这个做法比静默落空更有反馈，比直接 throw 更宽容。

11.11 错误处理：二十多种类型，用 2 种¶

作者在 types/plugin.ts:86-99 注释里承认：

IMPLEMENTATION STATUS: Currently used in production (2 types):

  • generic-error: Used for various plugin loading failures
  • plugin-not-found: Used when plugin not found in marketplace

Planned for future use (10 types - see TODOs in pluginLoader.ts): ... These unused types support UI formatting and provide a clear roadmap for improving error specificity. They can be incrementally implemented as error creation sites are refactored.

这是把 TODO 表固化进类型系统的用法。好处是每个未用类型都在 getPluginErrorMessage()（types/plugin.ts:295-363）里有对应的 formatter，UI 层一旦升级，上游只要切换 error 构造点就能直接用。坏处是 discriminated union 的 exhaustiveness check 对调用方是误导：TypeScript 告诉你"要处理所有 20+ 种"，但运行时只会看到两种。

可迁移性：作为路线图载体，这个做法适合一次规划、渐进实现的场景；但如果团队更在意 API 对消费者的可预期性，把未用类型先注释掉 / 放在分开的"roadmap type"里更好。

11.12 路径版本化与 7 天墓碑¶

Plugin cache 路径是版本化的：

安装新版本时，老版本目录不立刻删——写一个 .orphaned_at 时间戳文件，7 天后 GC（src/utils/plugins/cacheUtils.ts:23-24, 74-116）。

为什么 7 天？正在运行的 session 可能已经把老版本的代码加载进内存——删掉它的文件会让 require/import 解析失败（比如 lazy 导入的模块）、让 Glob/Grep 工具在老版本目录里乱翻（后者用 clearPluginCacheExclusions，orphanedPluginFilter.ts 专门拦）。7 天是 "合理的长 session 寿命 + 安全余量"。

跨版本持久数据走另一个目录 ~/.claude/plugins/data/<id>/——plugin manifest 里变量替换 ${CLAUDE_PLUGIN_DATA} 指到这里，不随版本切换丢失。典型用法是把 node_modules 装在这里，每次更新用 diff 比对 package.json 决定要不要 reinstall（来源：https://code.claude.com/docs/en/plugins-reference，访问于 2026-04-19）。

11.13 设计取舍汇总¶

选择放弃的换到的
显式 /reload-plugins，不自动刷新"配置改了立刻生效"的便利可预测的状态机 + 免维护"什么变化该刷新什么"的表
顶层 unknown key 静默剥离、嵌套严格统一的严格策略顶层可扩展、嵌套错字可察
卸载热更 + 安装慢更的非对称行为一致性破坏性操作走快路径、安全兜底
LoadedPlugin.mcpServers 懒填简单数据结构启动时不必解析所有 plugin 的 MCP
loadAllPlugins + loadAllPluginsCacheOnly 双 memoize单一 cache APIstartup 路径不阻塞 git clone
session > marketplace > builtin，managed 例外纯粹优先级开发便利 + 企业策略两全
把二十多种 PluginError 当路线图Union exhaustiveness 的诚实类型即文档即迁移清单
MCP 重连靠 bump pluginReconnectKey 而不是 refresh 直接调直接性模块边界清晰，不越权

11.14 可迁移的点¶

工程上值得搬走用的：

  1. manifest 驱动的 plugin 系统 + 宽/严双策略 zod：顶层宽容、嵌套严格是长寿命配置 schema 的好默认。
  2. 三层分离（intent / materialized / active）+ 每层独立 invalidation key：有多层异步状态的系统通用；写 / 读 / 刷新分流。
  3. clear-then-register 作为原子对：任何 "先清 cache、再重注册" 的 API 都应合成一个 function，不暴露中间状态。
  4. cache-only vs full load 双 memoize：同一数据源两个 SLA，调用方选择。
  5. 破坏性操作走快路径，构建性操作走慢路径：安全相关的 invalidation 不应等用户显式触发。
  6. ${id}@{source} 命名空间：用来源作 ID 后缀，一眼看出 plugin 从哪来，方便日志、UI、策略匹配。
  7. discriminated union 作路线图：当"目标错误类型 >> 当前实现"时，可以把剩下的写进类型，但要在注释里说清楚哪几个实际在用。
