19.1 用户看到的是什么¶

Buddy 是 Claude Code 在 2026-04-01 释出的一个小玩意儿：终端输入框右下角蹲着一只 5 行高、12 列宽的 ASCII 小动物，缓慢扭动，偶尔眨眼。主 agent 回了一轮话后，动物上方会浮出一个 round-border 的气泡，它讲一句跟这轮对话有关的俏皮话，10 秒后自动退去；用户滚屏一下，气泡立刻消失。

终端窄于 100 列时，整只动物折叠成一行——一张小脸加上自己的名字。首次启动 Claude Code v2.1.89+ 的那一周（2026-04-01 到 04-07 本地日），还没孵化 Buddy 的用户会在右下角看到一条彩虹色 /buddy 字样飘 15 秒——过了那一周永远不再提示。孵化之后，没有付费订阅的用户会被服务端拦下（Pro 要求，来源 https://claudefa.st/blog/guide/mechanics/claude-buddy，访问于 2026-04-19）；本仓库的客户端代码没有 Pro 门禁，只看 feature('BUDDY') 编译时常量。

随手记一句背景，好让技术细节不突兀：Buddy 的客户端源码比官方预告早了一步——@anthropic-ai/claude-code@2.1.88 的 npm 包误打了 59.8 MB 的 source map，社区几天内就拿到了实现（来源：https://claudefa.st/blog/guide/mechanics/claude-buddy，访问于 2026-04-19）。本章讨论的还原仓库就来自那次泄漏。

19.2 为什么挑这个功能出来讲¶

严肃 CLI 工具里做情感化设计不是常见选择。把一个会扭动、会冒话的 widget 塞到一个工程师每天盯几小时的终端里，最大的风险是打扰：屏幕带宽被挤占、注意力被不相关的动画偷走、输入 wrap 因为它错位。Buddy 的代码里有一套足够小的"克制预算"可以抄——怎么用列预算换屏幕面积、怎么用默认关闭换入侵性、怎么用 prompt 注入避免主 agent 抢戏。本章要讲透的是这套预算，不是 Buddy 本身的观赏价值。

19.3 关键数据结构：bones / soul 分层¶

Buddy 的状态拆成两层。一层可派生、不落盘；一层用户可编辑（首次由模型生成）、进 config。类型定义在 src/buddy/types.ts:101-124：

CompanionBones 从用户 ID 派生（src/buddy/companion.ts:107-113），每次读配置时重算；CompanionSoul（名字 + 人设）由服务端模型生成，存在 config.companion（src/utils/config.ts:269-271）。设计意图作者自己写在 types.ts:121-124 注释里：species 重构不破坏老存档，用户改 config 也刷不到 legendary。

合成路径见 src/buddy/companion.ts:127-133：

bones 在后覆写 stored——老格式 config 里残留的 bones 字段会被清掉。这比"读 config 时做 migration"简单，相当于每次读都做无代价 migration。

这套 bones/soul 分层的可迁移性不小。任何"用户 ID 决定某些属性、用户自己又能改某些属性"的场景（个性化头像、工作区偏好、只读身份 metadata）都能照搬：派生的不存，存的不派生，合并时派生的后覆盖。

PRNG 的种子在 src/buddy/companion.ts:84 固定为 const SALT = 'friend-2026-401'，roll(userId) 对 userId + SALT 做 mulberry32(hashString(...))（companion.ts:107-113）。没有时间、session、启动次数这些维度——同一个 account UUID 跨机器、跨时间、跨重装，hatch 出的 bones（物种、眼、帽、稀有度、shiny 位、stats 底数）完全一致。rollFrom 最后还掷一次 Math.floor(rng() * 1e9) 塞进 inspirationSeed（companion.ts:101），留给服务端 soul-gen 的 LLM 做确定性种子——同一个用户每次请求 soul 生成也是同一颗种子。

隐藏细节（src/buddy/companion.ts:84, 98, 107-113）：bones 的随机性只绑在 userId + SALT，不含时间或 session 维度。shiny 的 rng() < 0.01 说的是"1% 的 account UUID 能出 shiny"，不是每次抽卡 1%——单个用户要么永远 shiny 要么永远不 shiny，换机器/重装/删 config 都改不了。用户想触发 shiny 的唯一办法是换 account UUID（比如 any-buddy 这种第三方工具靠改 config 绕过，但服务端 soul-gen 仍按真 UUID 走）。

19.3.1 一个 bundle-hygiene 旁注¶

types.ts:10-52 把 18 种 species 字面量全都用 String.fromCharCode 拼出来。注释原文（types.ts:10-13）：

18 种里有一个和内部模型 codename 撞词（具体哪个没说）。因为 build-output grep 是正则，需要保持字符串从 bundle 里消失；但又不能特例处理一个——特例处理就失去了对齐的风格，下次加新物种容易漏。全部走 fromCharCode 的代价是一行变多行，收益是扫描规则对代码无感。这种"整列统一写法换规则独立性"的 trick 值得留意。

19.4.2 渲染器¶

两点值得拆开看。

第一，帽子只占空行。frame 2（"fidget"）有时会用 line 0 放装饰元素——dragon frame 2 的 ~ ~ （sprites.ts:135）、octopus frame 2 的 o （sprites.ts:157）、robot frame 2 的 * （sprites.ts:364）。这种帧里帽子让位。配戴 legendary 水晶王冠的 dragon fidget 瞬间短一下王冠，换来烟气效果。

所以 penguin 永远不 shift。这就是注释里 frames.every(...) 判断的存在理由——任何一帧用了 line 0，高度就要保留，否则物种会在 4 行和 5 行之间抖动。

19.4.3 动画节拍¶

src/buddy/CompanionSprite.tsx:16-23：

15 槽循环，每槽 500ms，一个周期 7.5 秒。frame 0 占 12 槽（rest），frame 1 和 2 各占 1 槽（fidget），-1 占 1 槽（blink：frame 0 + eye 全替换成 -）。这个分布是刻意的低频——大多数时间 sprite 纹丝不动；工程师读 transcript 时，视线不会被右下角的动物偷走。

"被触发后加速"的策略见 CompanionSprite.tsx:244-258：

气泡出现或用户刚 pet 时，绕开 IDLE_SEQUENCE 让 sprite 用 tick % frameCount 轮播全部帧——每 500ms 换一帧。相当于"我要说话了"/"你在撸我"的时候动得更多。之后自动回到 idle 节拍。

19.4.4 Pet 爱心¶

src/buddy/CompanionSprite.tsx:27 定义了 5 帧爱心序列：

H = figures.heart（来自 figures 库的心形字符）。5 帧 × 500ms 正好 2.5 秒，和 PET_BURST_MS 对齐。最后一帧是 · · · ——爱心散成小点，暗示"淡出"而不是突然消失。

触发流：/buddy pet 命令写 AppState.companionPetAt = Date.now()（src/state/AppStateStore.ts:170-171），组件在 render 里比较 tick - petStartTick 算 petting 状态。sync-during-render 的 trick 值得一提（CompanionSprite.tsx:186-200）：

用 if (...) setState(...) 在 render 里同步新 petStartTick——React 会丢掉当前 render 再重跑，保证第一次 petting render 看到的是 frame 0 而不是差 500ms 的 frame 1。用 useEffect 会慢一个 tick，第一帧被吞掉。

隐藏细节（src/buddy/CompanionSprite.tsx:186-200）：这是 React 官方允许但文档里几乎不推荐的 "derived state during render" 模式——违反 "render 必须是纯函数"的直觉。常规做法是 useEffect(() => setPetStart(...), [petAt])，但 effect 在 render 提交后才跑，500ms 定时器的第一帧就会错过 petStartTick=tick，爱心动画第一帧被吞。这里用 render-phase setState 强制让新值立即可见，是 Ink 场景下用 500ms 格子做动画同步的一个局部正确解。

两个计时器其实共享同一个 tick：bubbleAge = tick - lastSpokeTick 和 petAge = tick - petStartTick 都用同一个 500ms setInterval（CompanionSprite.tsx:201-214）。相当于用 UI 层的共享 clock 做同步，不会出现两个独立 setInterval 漂移导致"爱心散完了气泡才开始淡"这种错位。

隐藏细节（src/buddy/CompanionSprite.tsx:201-214, 220-223）：爱心动画和气泡淡出共用一个 500ms setInterval，差值法（tick - lastSpokeTick / tick - petStartTick）在同一个单调计数器上做差。如果用两个独立 setInterval——哪怕都是 500ms——clock drift 几分钟就能让两者相差半帧，视觉上表现为"爱心刚散，气泡还完整"或反过来。产品层看不到这种 drift，但一旦出现抖动，定位起来非常痛苦。"一个共享 tick + 差值法"是 Ink 场景下做多路时间动画同步的最低成本方案。

19.5 状态机（弱）¶

Buddy 没有一个统一的 FSM。它的状态由两维正交量组合：

视觉节拍：

  • idle —— 默认走 IDLE_SEQUENCE。
  • excited —— 被 reaction 或 petting 激活时 cycle all frames。
  • petting —— 2.5 秒内叠加 heart 帧。
  • blink —— idle 序列里的 -1 槽。

对话气泡：

  • 无气泡（默认）。
  • speaking —— companionReaction !== undefined。
  • fading —— bubbleAge >= BUBBLE_SHOW - FADE_WINDOW（最后 3 秒 dim 化，边框换成 'inactive'，提示即将消失）。
  • 立即清 —— 用户滚屏触发。

两个维度独立演进。气泡淡出时 sprite 可以照常 excited（因为被 pet 的 burst 可能还没结束）；没气泡时照样能 fidget。

companionReaction 的生产侧只有一个：fireCompanionObserver，在每轮 agent query 结束后被调用（src/screens/REPL.tsx:2836-2841）：

AppStateStore.ts:168 注释写这个 observer 来自 src/buddy/observer.ts，但该文件在当前还原仓库中缺失——REPL 里 fireCompanionObserver 甚至没有 import 语句。本章不能展开 observer 的具体实现（比如用什么模型、选词策略），只能确认它存在且每 agent turn 触发一次，异步产出 reaction 文本写回 AppState（本段落结论基于 REPL.tsx:2836-2841 调用点和 AppStateStore.ts:168-169 字段注释）。

消费侧是 CompanionSprite 的 useEffect（CompanionSprite.tsx:205-214）：

收到 reaction 设 10 秒 timer，到点自动清；effect 的 cleanup clearTimeout 保证 reaction 期间再有新 reaction 来会重置 timer 而不是叠加。

19.6 Prompt 注入：不让主 agent 串戏¶

Buddy 要在用户对话里"旁白一句"，但不能让主 agent 把自己误认成 Buddy。方案是一段 system-reminder，在 Buddy 激活时注入一次。

19.6.1 Intro 文本¶

src/buddy/prompt.ts:7-13：

三件事：

  1. 主 agent 不是 Buddy，Buddy 是另一个 watcher。
  2. 用户叫 Buddy 名字时，主 agent 压到一行以内（或只回答和自己相关的部分）。
  3. 不要解释、不要替 Buddy 说话——气泡自己会处理。

19.6.2 注入路径¶

src/buddy/prompt.ts:15-36 返回一个 attachment：

只注入一次：扫历史消息，如果已经有同名的 companion_intro attachment 就返回空。改名重 hatch 会自动重注。

收集器在 src/utils/attachments.ts:864-870：

最终在 src/utils/messages.ts:4232-4239 被翻译成 user message：

isMeta: true + wrapMessagesInSystemReminder 等于一段 <system-reminder> 包裹的 user message——主 agent 看得到，但用户看不到。具体地，companion_intro 进了 NULL_RENDERING_TYPES 列表（src/components/messages/nullRenderingAttachments.ts:35），UI 渲染直接跳过，也不算进 200-message 渲染预算。

19.6.3 为什么用 user-side system-reminder 而不是 system prompt¶

没有直接的源码注释解释这个选择，但可以从 API 设计推：system prompt 在一段会话里稳定不变；system-reminder 是插在对话流里的 user 消息，能随上下文漂移。Buddy 的 soul 可以改（改名、重 hatch），muted 开关可以翻，这些都比"一次设定、永不再变"的 system prompt 更适合走 reminder。另一个好处是 compaction 之后 reminder 也会被 strip 掉，下次需要时再注入一份新鲜的——getCompanionIntroAttachment 扫历史消息那一步天然就做了这件事。

19.7 通知集成：三条触发路径¶

Buddy 在不同场景用不同通道，每条都有明确的时限。

19.7.1 启动彩虹 teaser（时间窗口 + 本地日）¶

src/buddy/useBuddyNotification.tsx:12-21：

"external" === 'ant' 是 bun 打包时字符串替换的 target 判断——Anthropic 内部构建这一条恒为 true，外部构建走日期判断。这套技巧在仓库里不止一处，本章不展开，只说内部构建相当于永久开启。

注释里解释的是为什么不用 UTC 做日期判断：用本地日是"24 小时滚动曝光"——亚洲先早上进窗，美国晚几小时才进，Twitter 热度拉长，服务端 soul-gen 负载也被摊平。相当于不靠后端 rollout 排队，完全用时钟做流量分发。

通知逻辑（useBuddyNotification.tsx:43-77）：

19.7.2 输入彩虹高亮¶

src/buddy/useBuddyNotification.tsx:79-97：

被 PromptInput.tsx:728-739 消费，在用户输入里找 /buddy，把那几个字符染成彩虹。这是个视觉确认：你敲对了命令，Buddy 在等你敲完。

19.7.3 Agent turn 后的气泡¶

src/screens/REPL.tsx:2836-2841（前面引过）。这是 Buddy 唯一主动说话的路径。和 Proactive（见 ch.15 §15.3.1 的状态模块 + §15.4.8 的消费点）不同：

  • Proactive 观察空闲状态（用户久未响应），通过 subscribeToProactiveChanges 让各路消费者（progress bar、prompt suggestion、sub-agent 后台化……）订阅"该不该推"，主动给建议。
  • Buddy observer 在每 agent turn 结束触发，不看用户是否空闲，只写一个 companionReaction 字段。

Proactive 的目标是"该推了就推"，Buddy 的目标是"陪一句就走"。两者共用了 AppState 但走不同的 effect、不同的订阅通道。

19.8 "不打扰"是怎么做到的¶

这是本章承诺要回答的问题，现在集中论证。

19.8.1 默认关闭¶

没 hatch 的用户，整个 UI 渲染在第二行就退出（src/buddy/CompanionSprite.tsx:216-217）：

getCompanion() 读 config.companion，空就返回 undefined。首次装 Claude Code 的人看不到任何 Buddy 元素，直到他主动敲 /buddy。这是第一层不打扰：不主动进入用户视野。

19.8.2 一次性、自限的 teaser¶

teaser 通知只在 4/1-4/7 本地日内出现、15 秒后自动撤、撤了再启动不再出（因为 effect dep 没变）。isBuddyTeaserWindow 在 4/8 起永远返回 false（useBuddyNotification.tsx:15-16）。相当于"你这一周见过了，之后靠自己主动敲"。

对比一下常见的反模式——登录后弹 modal "要不要启用 Foo 功能"，每次都弹直到用户点 "Got it, don't show again"。Buddy 的 teaser 没有"关闭 forever"按钮，因为本来就是时间限定，代码里不需要那个按钮。

19.8.3 一键 mute 和多层短路¶

companionMuted: boolean 是 config 里一个字段（src/utils/config.ts:271）。它在 4 个地方短路：

位置效果
prompt.ts:20不注入 system-reminder（主 agent 不知道 Buddy 存在）
CompanionSprite.tsx:170companionReservedColumns 返回 0（输入框不让位）
CompanionSprite.tsx:217主 sprite 不渲染
CompanionSprite.tsx:344Floating bubble 不渲染

四处每一处都独立生效，不依赖其他三处——任何一处漏加检查，其他三处仍然兜底。这是故意的冗余：mute 是高频用户操作，必须绝对安静。

19.8.4 屏幕列预算显式返回¶

src/buddy/CompanionSprite.tsx:167-175 暴露给 layout 一个精确的数值：

被 PromptInput.tsx:1991 消费：

关键设计：widget 主动上报占用宽度，input 按减法 wrap 文本。layout 不用猜。如果 Buddy 在说话，返回 spriteColWidth + padding + BUBBLE_WIDTH（多让 36 列给气泡）；不说话就只让 sprite 宽度。窄终端（<100 列）直接返回 0，这时 sprite 不渲染到角落，而是折叠成一行放在 footer 区。

这一行代码消除了一整类 bug——如果用户输入的文本宽度计算和 sprite 渲染不自洽，轻则文本 wrap 错位，重则 Ink 重绘抖动。让 widget 自己承诺占多少列是最简单的契约。反过来想：如果让 layout 那边用 measureElement 去测 sprite 实际渲染宽，Ink 在并发模式 + Yoga commit 时序下的 double-draw 会让读到的值晚一帧（Ink 的 layout/commit 时序见 ch.21 §21.5），输入 wrap 就会在每一次 speaking 切换时抖一下。Widget 报账把这个时序问题整个绕过去了。

19.8.5 让位用户操作¶

用户滚屏就清气泡（src/screens/REPL.tsx:1331-1339）：

注释说得很明白：气泡在 fullscreen 是 bottom-right 浮层，会盖住 transcript 内容；用户滚动意味着他在想读底下的东西。这是"显性意图夺回"的典型处理——不等超时，立刻让位。

另外在 fullscreen 下，气泡被拆到 FullscreenLayout 的 bottomFloat slot（REPL.tsx:4619），不占用 bottom 的正常布局高度。FullscreenLayout.tsx:39-43 的注释说明这个 slot 的存在理由：

bottom slot 自己设了 overflowY:hidden，把 absolute 浮层放进去会被裁剪；放到 flexGrow 区才能正确浮出。非 fullscreen 模式气泡只能 inline——因为浮到 Ink 的 Static scrollback 里清不掉。这是工程现实决定的取舍。bottomFloat 这个 slot 本身就是 FullscreenLayout 为 Buddy 专门开的口子（全屏/inline 两套布局的对比见 ch.21 §21.9）。

19.8.6 动画节拍刻意慢¶

前面 §19.4.3 讲过，15-slot idle sequence 里 frame 0 占 12 次、其余 3 次。换算成时间：每 7.5 秒只有 1.5 秒 sprite 在"动"，其余都在 rest frame。frame 之间的变化是单字符级（眼睛变 -、尾巴加 ~），不会在外围视觉里形成强信号。

19.10 设计取舍¶

几个选择值得单独评一下。

为什么 bones 派生、soul 持久化，而不是全派生或全持久化？ 全派生意味着 soul 每次重算——名字和人设会变，失去了"这是我的 Buddy"的持续性。全持久化意味着 users 能改 config 刷 legendary——外部工具 any-buddy 已经证明这个风险是实在的（https://github.com/cpaczek/any-buddy）。分层是折中：soul 能被改但不算作弊（你本来就可以起任何名字），bones 算作弊就用服务器逻辑阻止——因为服务端只认你的 account UUID。

为什么 idle 节拍这么慢（15 槽只 3 次扭动）？ 加快一点会更有生命感，但代价是 draw 频率上升、终端视觉噪声上升。Buddy 设计师选了"低频但可辨"。对比一下游戏里常见的 4-frame loop 常驻动画——那适合 24fps 渲染的平滑性，不适合 Ink 的 terminal 重绘。

为什么 prompt 注入走 user-side system-reminder 而不是 system prompt？ 前面说过，soul 可变 + compaction 可能清掉 + 只注入一次的去重扫描共同决定了这个选择。

这个选择有一个反直觉的副作用值得单独说。

companion_intro 在 src/utils/attachments.ts:824 的 allThreadAttachments 组里——同组注释 821 行原文是 // Thread-safe attachments available in sub-agents——而不是 944-987 行 isMainThread 守卫的 mainThreadAttachments。也就是说，sub-agent 也会收到一份 companion_intro。每个 sub-agent 开一轮对话时，它的 messages 历史是干净的（没有自己注入过的 companion_intro），getCompanionIntroAttachment 扫不到同名就再注入一次。

产品层完全感知不到：sub-agent 里没 sprite、没气泡、没 observer——UI 全挂在主 REPL 上（sub-agent 的 UI 回调被刻意置 undefined，详见 ch.04 §4.6 的"stub 成 no-op"条目）。但每个 sub-agent 每轮都付 ~120 tokens 的 system-reminder 开销。按 Buddy 的"隐形 watcher" 定位，这里更合理的归属本来是 mainThreadAttachments——但源码确实把它放在了共享组里。

隐藏细节（src/utils/attachments.ts:821-870, 944-987）：companion_intro 在 allThreadAttachments 而不是 mainThreadAttachments。每个 sub-agent（含 Task/Explore/Plan 等内置 agent，见 ch.04 §4.7）首轮都会被注入一份 companion_intro system-reminder，约 120 tokens。产品层无感（sub-agent 没 UI），但每个子任务每轮都付这点预算。和 mainThreadAttachments 里 ide_selection/output_style/verify_plan_reminder 的"只给主 agent"归属对照——companion_intro 按 Buddy 的隐形 watcher 定位本该同组，源码没那么归。

为什么 teaser 用本地日不是 UTC？ 注释给了答案：曝光波峰拉平、后端负载柔和。这种"用时钟做 rollout"省了后端的 feature-flag 队列。代价是跨时区的用户可能晚看到几小时，但对于彩蛋功能这不是问题。

为什么不把 /buddy 做成持续性交互（真 Tamagotchi）？ 源码里没有任何"喂食"、"睡眠"、"病了"的状态字段。Buddy 的 stats 只装饰（types.ts:91-97 的 DEBUGGING / PATIENCE / CHAOS / WISDOM / SNARK），既不影响主 agent 也不随时间衰减。社区已经出了 feature request 要求按 token 使用量升级（https://github.com/anthropics/claude-code/issues/41684）。保持无状态的理由我只能推测：开发者工具用户对"后台进程消耗我注意力"的耐受度远低于游戏用户，一旦 Buddy 成了"要照顾的东西"，它就变成了负担。

19.11 可以带走的三个点¶

一，widget 主动报账屏幕预算。任何塞进 CLI 布局的非主流元素，都应该暴露一个 reservedColumns(context) → number 的契约，让上游按减法 wrap。这比"widget 占多少我也不知道，你自己猜"省无数 bug。

二，派生 / 持久化分层。状态里"哪些可编辑、哪些不可"值得用类型系统分开。改名能改、稀有度不能改，分开存就可控；合并时"不能改的后覆盖"保证配置漂移不出问题。

三，时钟做 rollout。时间窗限定的 teaser 用本地日而非 UTC，配合 feature flag 两层开关（编译时 + 用户 muted），可以在不依赖服务端 flag 系统的情况下做"一周热度 + 永久可达"的发布节奏。teaser 期结束不用撤代码、不用发新版——时钟到了自己熄灯。
