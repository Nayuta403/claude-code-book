1. 用户看到什么¶

按下 Shift+Tab 两次，终端状态行从 ⏵⏵ accept edits on 切到 ⏸ plan mode on。Claude 此后读代码、跑 git、查结构，但不会动源文件——它会把思考过程写进一个 plan 文件，最后弹出一个"Exit plan mode?"对话框等你批准；批准后进入实现阶段，并把整份计划连同"你已批准，现在可以开始写代码"的提示一并送回模型。

三条入口等价：

  • 快捷键 Shift+Tab 循环（Windows 上退化为 meta+m，见 src/keybindings/defaultBindings.ts:30）。
  • 斜杠命令 /plan [描述]。带描述时顺手把描述发给模型，src/commands/plan/plan.tsx:83-89。
  • agent 自己调用 EnterPlanMode 工具（src/tools/EnterPlanModeTool/EnterPlanModeTool.ts:77-102）。

还有一条启动期入口：claude --permission-mode plan，由 CLI flag 直接起在 plan 里（官方 CLI 参考：https://code.claude.com/docs/en/cli-reference，访问于 2026-04-19）。

2. 为什么挑这个设计出来讲¶

"先计划后执行"是 agent 领域的公论。值得研究的是 Claude Code 如何把这个约束真正保持住。读完源码后最反直觉的发现是：代码里几乎没有"plan 模式下禁止 FileEdit"这类硬检查。只读约束靠三件事叠加：

  1. 一个会话级的 toolPermissionContext.mode = 'plan' 状态。
  2. 每轮对话前注入的 system-reminder 附件（system-reminder 注入机制详见 ch.03），原话 "you MUST NOT make any edits"。
  3. 一个必须用户点按钮才能退出的 ExitPlanMode 工具。

这三件事单独都不算强，叠起来却把"阶段"这个抽象做实了。下面把每一层拆开看。

隐藏细节（src/utils/permissions/permissions.ts:1268-1281）：整仓没有"plan 模式 && 写工具 → deny"分支——独立 Grep 过 mode === 'plan' 全部出现，没有一处在写工具的拒绝路径上。相反，shouldBypassPermissions 里有一条 mode === 'plan' && isBypassPermissionsModeAvailable 的叠加放行：用 --permission-mode bypassPermissions 启动的会话切到 plan，写工具不仅不 ask，直接 allow。产品层看不到，但会削弱"plan = 只读保证"的心智模型（权限层全貌详见 ch.09）。

4. 关键流程¶

从"按下 Shift+Tab"到"计划被注入执行阶段"，一条主干：

4.1 进入 plan 模式¶

Shift+Tab → handleCycleMode（src/components/PromptInput/PromptInput.tsx:1410）→ cyclePermissionMode（src/utils/permissions/getNextPermissionMode.ts:88-101）。循环次序：

三个入口最后都归并到同一个调用：applyPermissionUpdate(prepareContextForPlanMode(ctx), { type: 'setMode', mode: 'plan', destination: 'session' })。/plan 命令里是这段（src/commands/plan/plan.tsx:74-82）；EnterPlanMode 工具批准弹窗里也是同一段（src/components/permissions/EnterPlanModePermissionRequest/EnterPlanModePermissionRequest.tsx:30-34 的 toolUseConfirm.onAllow({}, [{ type: 'setMode', mode: 'plan', destination: 'session' }])）。

4.2 每轮 prompt 前的 reminder 注入¶

下一轮消息构造时，getPlanModeAttachments 决定是否发送附件：

两层节流：只在 plan 模式；每隔 N 个人类 turn 才重发。第一次总是 'full'，之后多数为 'sparse'，每 N 个附件插一次 'full'。这个节奏是"足够频繁以抵御遗忘，足够稀疏以不烧 token"。

attachment 在消息序列化时渲染成 system-reminder，其中 full 版本的核心一段是：

见 src/utils/messages.ts:3227-3232。之后是 5 阶段（或 interview 变体）的工作流指令 + 当前 plan 文件路径。sparse 版本（messages.ts:3385-3397）只有一句"Plan mode still active ... Read-only except plan file"。

隐藏细节（src/utils/messages.ts:3227-3293）：full 版 plan-mode system-reminder 整段约 4700 字节、约 1K–1.3K tokens；sparse 版不到它的 1/10。PLAN_MODE_ATTACHMENT_CONFIG 配了 TURNS_BETWEEN_ATTACHMENTS: 5 和 FULL_REMINDER_EVERY_N_ATTACHMENTS: 5（attachments.ts:259-261）——也就是每 5 个人类 turn 发一次 attachment，其中每 5 次里只有 1 次发 full。长对话里 full reminder 的 token 开销是"稀释到几乎不计"，但足以把"你在 plan 模式"这件事周期性压回模型注意力窗口。节流窗口之外，attachment 完全不发。

4.3 plan 文件的读写¶

工作流明确告诉模型用 FileWriteTool / FileEditTool 往 plan 文件路径写。普通路径的写请求在 plan 模式下会走到标准的权限"ask"弹框——官方文档把这一条写成 "Permission prompts still apply the same as default mode"（https://code.claude.com/docs/en/permission-modes，访问于 2026-04-19）。对 plan 文件路径的放行是唯一的硬性例外：

checkEditableInternalPath 被所有写工具的 checkPermissions 上游调用（src/utils/permissions/filesystem.ts:1205-1250 的 checkWritePermissionForTool）。plan 文件从而是任何模式下都不需要 ask 的——它不是"plan 模式下的特权"，而是"属于本会话的 agent 内部存储"。

隐藏细节（src/utils/permissions/filesystem.ts:245-255）：isSessionPlanFile 的判定是 startsWith({plansDir}/{planSlug}) + endsWith('.md')。主会话 {slug}.md 和 sub-agent {slug}-agent-{agentId}.md 都天然命中（工具过滤相关详见 ch.08）；但任何以 {slug} 为前缀、.md 为后缀的路径都会放行——比如 {slug}-foo.md、{slug}-notes/dump.md。要利用这个放松，模型得先从 attachment 里读到 slug。没有已知的自发利用路径，但这是可写白名单里的一条"前缀匹配而非精确匹配"的边界。

4.4 ExitPlanMode：唯一的合法出口¶

当模型认为计划完成，它调用 ExitPlanMode 工具。这个工具的两个守卫很关键：

  • 第一重守卫：当前不在 plan 模式时拒绝执行。注释里解释了原因：工具在 deferred list 里，即便 mode ≠ plan 也会被宣告给模型，所以要挡住"compact 之后错误再调用"的情况。
  • 第二重守卫：永远返回 'ask'，触发用户审批对话框。requiresUserInteraction() 对非 teammate 硬编码返回 true（同文件 185-194；teammate 分支走 mailbox 审批，见 ch.04），意味着即使在 bypassPermissions 模式也必须用户点按钮——plan 阶段的终止决不交给模型。

隐藏细节（src/tools/ExitPlanModeTool/ExitPlanModeV2Tool.ts:166, 182-194, 195-220）：ExitPlanMode 自身 isReadOnly() 返回 false——它是一个写工具（落 plan 文件），却是 plan 模式下唯一允许被主动调用的写工具。原因是 shouldDefer: true：它通过 deferred 工具列表宣告给模型（详见 ch.08 的工具过滤），宣告与生效解耦——plan 阶段之外它可见但被 validateInput 一调即拒（errorCode:1）；plan 阶段之内它能过 validateInput 但被自己的 requiresUserInteraction() 锁在用户手里。"可见 ≠ 可调用 ≠ 可执行"这三步是这一个工具维持"阶段闸"语义的全部支点。

用户批准后，call 做三件事（ExitPlanModeV2Tool.ts:243-418）：

  1. 读 plan（优先从 input.plan，否则从磁盘）；如果 CCR Web UI 传回编辑过的版本，立即 writeFile 写回磁盘。
  2. 把 toolPermissionContext.mode 从 'plan' 切回 prePlanMode ?? 'default'；置 setNeedsPlanModeExitAttachment(true)。
  3. 返回结构化 Output，里面带着 plan 原文。

4.5 Plan 注入执行阶段¶

这是最"小"但最关键的一步。mapToolResultToToolResultBlockParam 把整份 plan 拼进 tool_result 的 content 字段：

下一轮模型的输入里，就同时有：

  • 刚才 tool_result 里嵌入的完整 plan 原文（## Approved Plan: ...）。
  • plan_mode_exit attachment（由 getPlanModeExitAttachment 一次性发出，src/utils/attachments.ts:1248-1273）：只有"你已退出 plan 模式"一句，带文件路径。
  • 如果用户在 CCR 中编辑过 plan，标签改成 Approved Plan (edited by user) 提示模型用户动过。

Plan 从此在 context 里显式存在，不依赖模型记住自己刚刚在计划什么。

5. 设计取舍¶

5.1 只读约束为什么不在权限层硬拦¶

你可能预期的实现：hasPermissionsToUseTool 里加一段 "if mode === 'plan' && !tool.isReadOnly() return deny"。源码没有这段。写工具在 plan 模式下的 checkPermissions 与默认模式完全一致——会走到"ask"，然后用户会选"拒绝"。形式上是"提示模型不要做 + 用户兜底"，不是"系统禁止"。

成本：一旦 system-reminder 被挤出 context（超长对话、压缩），模型理论上可能尝试写文件；此时防线只剩用户对话框。

收益：

  • 工具注册表不分叉。plan 模式不必维护一套独立的 tool list。
  • plan 文件的放行天然复用 checkEditableInternalPath 这个路径机制，不需要"plan 模式特权目录"这种额外概念。
  • EnterPlanMode 工具、/plan 命令、Shift+Tab、--permission-mode plan 四条入口共用同一条生效路径——只改 mode 字段。

对"system-reminder 被遗忘"这个风险的对策，就是 §4.2 讲过的周期性 re-attach。每 N 轮一次 full reminder，中间夹 sparse 短句。看起来微不足道，实际是这个方案能成立的支点。

5.2 Plan 为什么落盘¶

两个备选做法：

  • (a) plan 作为 in-context 的 assistant message 存在——这是 ReAct / Plan-and-Execute 常用的做法。
  • (b) plan 作为一个单独的文件。

Claude Code 选 (b)。代价是：多了一份文件系统状态需要和"模型记忆"保持一致；权限层要单独开一个放行口子（isSessionPlanFile）。换到的收益：

  • resume 可恢复。copyPlanForResume（src/utils/plans.ts:164-231）有完整的三级恢复链：文件 → 文件快照 → 从消息历史里扫 ExitPlanMode 的 tool_use input / userMsg.planContent / plan_file_reference attachment。remote CCR 会话里 pod 重启时这个链条尤其重要。
  • sub-agent 各自持有独立 plan。主会话用 {slug}.md，每个 sub-agent 用 {slug}-agent-{agentId}.md，天然隔离（并行 sub-agent 的 worktree 隔离详见 ch.06）。
  • 用户能在会话外编辑。/plan open 会调外部编辑器（src/commands/plan/plan.tsx:104-112）；CCR Web UI 也能编辑并通过 permissionResult.updatedInput.plan 传回。
  • 压缩不吃 plan。压缩走到 plan 时会转为 plan_file_reference attachment（跨章到 ch.07），保原文；compact 之后还会重新 attach plan_mode system-reminder（services/compact/compact.ts:1537-1538），保持"你仍在 plan 模式"这件事不被压没。

5.3 Exit 为什么必须弹窗¶

ExitPlanMode 的 requiresUserInteraction 对非 teammate 硬编码返回 true（ExitPlanModeV2Tool.ts:185-194；teammate 走 mailbox 审批）。这条规则凌驾于 bypassPermissions 之上——"跳过所有权限提示"也跳不过这个弹窗（权限层细节见 ch.09）。

理由：plan 阶段的承诺是"不改你的代码"，而 Exit 意味着解除这个承诺。把解除这个承诺的权力留给模型，等价于把"什么时候可以开始写"也交给模型——这是用户最后一次可以 veto 的时机。所以这个闸必须在用户这一侧。

审批弹框里提供多档选项（官方文档列出的）：批准并回 default / 批准并 auto / 批准并 acceptEdits / 继续规划 / 用 Ultraplan 在浏览器里精修。这把"阶段切换"和"下一阶段的权限模式"合并成一次决策，避免用户分两步做。

5.4 与 ReAct / Plan-and-Execute 的差距¶

ReAct 里没有"计划冻结"概念——模型随时交错思考和行动。Plan-and-Execute 有"计划阶段"，但计划作为 in-context 的一段 assistant 输出，执行器接着展开。Claude Code 介于两者中间：

  • 它有"计划阶段"——靠 mode 字段区分。
  • 它的计划是阶段产物而非阶段中的 scratchpad——落盘、可恢复、可外部编辑。
  • 计划阶段的只读约束靠"prompt + 审批弹框"软实现，而不是硬裁工具集。

这个组合解决的问题是现实里的，不是理论里的：长链路 tool use 中模型会遗忘约束；resume 后 plan 不能蒸发；用户希望在计划和执行之间有一个明确的批准点。

一个值得注意的对比：本章中的 Plan 和 Explore sub-agent（src/tools/AgentTool/built-in/planAgent.ts:77-83）走的是另一条路——disallowedTools 里写死排除 FileEditTool / FileWriteTool / NotebookEditTool（工具过滤机制详见 ch.08），外加 system prompt 里 CAPS 强调 READ-ONLY。sub-agent 生命周期短、上下文独立、硬过滤成本小，所以硬裁；主 agent 要长期存活并最终切回执行，工具集保持稳定更划算。同一个"只读"概念，在不同寿命的 agent 上用了不同实现——这点很值得借鉴。

6. 可迁移的点¶

6.1 阶段切换靠"状态字段 + 周期性 reminder"¶

如果你在做自己的 agent，不要维护"plan agent"和"impl agent"两套 tool registry。维护一个 mode 字段 + 每轮附一段 system-reminder + 少量白名单路径放行——足够了。两套 registry 的成本会在你加第三种模式时爆炸。

6.2 长对话用节流的 re-attach 抵御指令淡化¶

一次性的系统指令在 100 轮 tool use 后会被稀释到背景噪声里。定期 re-attach 是便宜的对策。关键是既不能每轮都发（token 爆）、也不能只发一次（会被忘）。Claude Code 的做法：

  • 数人类 turn，不数 assistant turn（attachments.ts:1288-1310 注释讲清了为什么——单个 user 请求里可能有 100 次 tool call，按 assistant 数会爆 20 倍）。
  • 周期性交替 full / sparse，full 版本包含完整指令，sparse 是一句话提醒。

这是值得直接照抄的模式。

6.3 阶段产物落盘而非仅 in-context¶

Plan 文件等于"阶段间的接口契约"。它比依赖上下文传递稳，原因：

  • 可以外部编辑。
  • 可以被其他 session / sub-agent 引用。
  • 压缩 / resume 时有明确的恢复点。
  • 文件系统上的 diff 就是计划的变更审计——免费获得版本历史（如果目录在 git 里）。

代价是放行口子要开得精准。Claude Code 用"本会话 plan 文件路径"做精准匹配（isSessionPlanFile + slug），而不是开放整个目录。

6.4 阶段终止用工具调用而非文本信号¶

让模型"发一段 [PLAN COMPLETE] 字符串然后解析"是个常见但脆弱的做法。Claude Code 把 ExitPlanMode 做成一个需要权限的工具，顺带取得三样东西：

  • 结构化 payload（input / output schema，见 _sdkInputSchema，ExitPlanModeV2Tool.ts:97-108）。
  • 自然的审批 hook 点（checkPermissions 返回 'ask'）。
  • 工具调用协议的幂等性——validateInput 可以挡住"模式已经不是 plan 了"的错误重入。

把阶段终止嵌进 tool use 协议，比拿文本当信号可靠得多。

7. /ultraplan 不在这章¶

一条脚注。读者看到 /ultraplan 容易以为它是"更强的 plan 模式"。源码里它实际上是一个远端会话启动器：

  • src/commands/ultraplan.tsx:234-292 的 launchUltraplan 调 teleportToRemote({ permissionMode: 'plan', ultraplan: true })，把计划任务外包给 Claude Code on the web 的一个 CCR 会话。
  • 本地 CLI 只做三件事：显状态、轮询远端 ExitPlanMode、在用户选 "teleport back" 时弹 UltraplanChoiceDialog 把计划注入本地。
  • 默认用 Opus（growthbook gate tengu_ultraplan_model，ultraplan.tsx:32-34）。

也就是说 ultraplan = 远端 plan mode + 浏览器评审面板。本章讲的所有机制在 ultraplan 的远端会话里都一样成立——它没有另立一套"增强版 plan"。外包的价值是浏览器 UI 的精细评审能力和一台跑 Opus 的远端机器，不是 plan 机制本身（来源：https://code.claude.com/docs/en/ultraplan，访问于 2026-04-19；远端 CCR 会话的外包机制详见 ch.17）。/ultraplan 仅在 ant 内部构建里启用（ultraplan.tsx:466）。

隐藏细节（src/commands/ultraplan.tsx:275, 292）：触发 /ultraplan 后本地 session 不被阻塞。launchUltraplan 立刻 return buildLaunchMessage(...)，launchDetached 异步在后台 teleportToRemote + startDetachedPoll；launch 消息文案明写 "Terminal stays free while the remote plans"。顶部的 ◇ ultraplan pill 是纯 UI 指示，不拦截输入——用户可以继续在本地跑任何模式的会话。也就是说 Opus 的 token 费用花在浏览器那边，本地不付代价也不排他。

8. 本章回顾¶

Plan Mode 的完整结构是三层：

层实现代码位置
会话状态toolPermissionContext.mode === 'plan' + prePlanModesrc/utils/permissions/permissionSetup.ts:1462-1493
每轮 prompt 约束plan_mode attachment → system-reminder（full/sparse 交替）src/utils/attachments.ts:1186-1242 + src/utils/messages.ts:3207-3297
阶段产物~/.claude/plans/{slug}.md[^plansdir]src/utils/plans.ts:32-144

[^plansdir]: 默认 ~/.claude/plans/，可被 settings.plansDirectory 覆盖（限制在项目根内，见 src/utils/plans.ts:79-111）。

加上两个闸：

  • 入口闸：EnterPlanMode 需要用户点 "Yes"，/plan 和 Shift+Tab 则是用户自己按下的按键——每条入口都过了用户这一关。
  • 出口闸：ExitPlanMode 的 requiresUserInteraction = true 把"从计划走向执行"这个转折点锁给用户。

一句话带走：代码里几乎没有硬的只读拦截；plan 模式的只读性，是"每轮重申的 system-reminder" + "用户审批弹框" + "plan 文件路径白名单"叠出来的。这个观察是本章最反直觉也最值得借鉴的部分。
